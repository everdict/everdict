## Requirements

**Split & roles**
1. A frame's held-out scenario set is partitioned into exactly two roles — `selection` and `confirmation` — never a third bucket and never overlapping; a scenario not held out is `train` by construction (it is `frame.scenarios[i].heldOut === false`, today's meaning, unchanged).
2. A frame written before this change decodes with every `heldOut: true` scenario reading as `confirmation` — the exact single population the gate reads today — with no new value invented for it (schema-split law).
3. `significance.heldOutFamilySize` is checked, and consumed by `campaignSpendOf`/the round-door refusal, **only** against evaluations run over `confirmation`-role scenarios. A selection evaluation never increments family consumption and never counts toward `budget.maxRounds`.
4. `campaignFrameDefects` requires **≥2 `confirmation`-role** scenarios (replacing today's bare "≥2 held-out"), and, when a selection lane is declared (Req. 6), **≥1 `selection`-role** scenario.
5. A round (`POST /campaigns/:id/rounds`) is unchanged in meaning: it is, and only is, a confirmation comparison, judged by the existing significance gate over `confirmation`-role scenarios and consuming the pre-registered family exactly as today.
6. A new comparison kind — a **selection evaluation** — can be reserved, submitted (baseline + candidate arms, same reservation discipline as a round) and logged against `selection`-role scenarios, an arbitrary number of times per campaign, bounded only by a frame-declared, frozen `selectionBudget`, never by `budget.maxRounds` or `heldOutFamilySize`.
7. A selection evaluation's accept/reject decision is a **cheap deterministic rule** (aggregate rate strictly greater on the candidate, no significance correction) — never the confirmation significance gate, and never capable by itself of producing a `CampaignGateAnswer` of `adopt`.
8. `selectionBudget` is declared at frame open and frozen with everything else the verdict depends on; a submission past it is refused the same way a spent round budget is refused today.

**Disclosure tiers (asymmetric, enforced by construction)**
9. `campaignRoundBrief`'s train-split disclosure is extended to carry every non-held-out case's rate/trials/verdict (not just diagnoses+slot for `targets`), partitioned success/failure — a proposer sees full per-case train evidence, as it already does for target diagnoses.
10. The brief carries at most one new field about selection: whether the immediately-preceding selection evaluation was accepted, and its aggregate delta. No selection case id, no selection per-case rate, no selection count, ever appears in the brief.
11. The brief (and every free-text field a driver can write, `learned` included) discloses **nothing** about confirmation beyond what a driver already legitimately learns from calling the round/decision doors itself (Req. 5 is unchanged) — no per-case confirmation score, id or delta reaches the brief, exactly as today's `redactHeldOut` already guarantees for `heldOut === true` scenarios (this now covers `selection` by the same mechanism, satisfying the intent's "existing free-text redaction must cover selection ids too" without new code beyond widening what counts as "held out" for redaction purposes).
12. Nothing built for this change downgrades an existing exclusion: held-out ids never appear structurally, no confirmation/selection score reaches a delegate, no judge free text reaches a delegate.

**Declared edits & the edit verifier**
13. A frame may opt into edit verification by naming exactly one capability slot of the subject's agent spec (`editVerification.capabilitySlot`) whose content is the thing candidates edit. Declared, every round and selection submission for that campaign must carry a declared edit set; undeclared, nothing changes (harness/environment/code campaigns, and agent campaigns not using this discipline, are unaffected).
14. A declared edit set is checked by reproducing the candidate's registered capability content, byte-for-byte, from the frame's frozen baseline capability content plus the edit set, in a pure function with no I/O. A submission whose edit set does not reproduce the candidate's registered digest is refused — never silently accepted, never partially trusted.
15. The verifier checks WHAT changed, never WHY: an edit's declared rationale/predicted effect is carried as an unverified driver claim, visibly labelled as such wherever it is stored or rendered.
16. A frame may declare `protectedRegions` (patterns within the edited capability's content) that an ordinary step edit (`add`/`delete`/`replace`) may not target. A distinguishable edit kind (`consolidate`) is the only kind the verifier permits to touch a protected region, so a driver's slow/meta update is mechanically distinguishable from a local fix rather than trusted by comment.
17. A protected region is never rewritten in place by the platform: the content it lives in is edited only by registering a new immutable capability version, exactly like every other candidate (L4 — no rewrite-in-place path is introduced).

**Everything else**
18. No existing round, decision, settle, adopt or merge door changes its refusal semantics for a campaign that never uses the selection lane or edit verification — every requirement above is additive and opt-in at frame-open time.
19. A new lifecycle transition (a selection logged) emits its own platform fact, non-triggerable, classified on the existing activity axis map, exactly as `campaign.round_logged` does today.
20. Every new Zod-validated field follows the creation/decode split already established for the frame (`CampaignFrameSchema` vs `StoredCampaignFrameSchema`) — a rule enforced at creation is never silently enforced at decode.

## Design

**Packages touched, one-way per the layer spine:** `contracts` (schema) → `domain` (pure gate/verifier logic) → `application-control` (`CampaignService`, reservation/round/selection doors) → `db` (new rows) → `apps/api` (transport). No package below `domain` is touched; `agent-runtime`/`apps/agent` are untouched because the driver-side loop (minibatch partition, reflection, edit merge/rank, `L_t` schedule, rejected-edit buffer, meta prompt) is explicitly **not** platform surface (per the intent and `docs/architecture/evolution-research-directions.md`).

**1. `contracts/records/evolution-campaign.ts`**
- `CampaignFrameShape.scenarios[i]` gains an optional `role: z.enum(["selection","confirmation"])`, meaningful only when `heldOut: true`. `StoredCampaignFrameSchema` normalizes an absent role on a held-out scenario to `"confirmation"` on read (a derivation, not a second boolean — the schema-split law's preferred repair, since `role` restates nothing new for legacy rows: it *is* what `heldOut: true` always meant).
- `campaignFrameDefects` (shared by creation and every decision path, unchanged pattern) requires ≥2 `confirmation` scenarios; when `selectionBudget` or `editVerification` is present, ≥1 `selection` scenario.
- `CampaignFrameShape` gains `selectionBudget: z.object({ maxEvaluations: z.number().int().min(1).max(10000) }).optional()` and `editVerification: z.object({ capabilitySlot: z.string().min(1), protectedRegions: z.array(z.string().min(1).max(300)).max(50).default([]) }).optional()`. Both frozen with the rest of the frame; both absent = today's campaign exactly.
- `CampaignEvaluationRequestSchema`/`CampaignEvaluationSchema` gain `tier: z.enum(["selection","confirmation"]).default("confirmation")` — the **same** reservation ledger and arm-state machinery (`CampaignArmState`, `AttemptStanding`) serves both, distinguished by tier, so nothing about the reservation door, the ragged-upload refusal, or the ingest-trials check is duplicated.
- New `CandidateEditSchema`: `{ op: z.enum(["add","delete","replace","consolidate"]), target: z.string().min(1).max(500), before: z.string().optional(), after: z.string().optional(), rationale: z.string().max(2000).optional() }` — `rationale` is explicitly the unverified driver claim (Req. 15).
- `CampaignRoundInputSchema` and a new `CampaignSelectionInputSchema` both gain `editSet: z.array(CandidateEditSchema).max(200).optional()`, required by the write (not by the schema — same pattern as `delegationRunId`'s frame-conditional requirement) when `frame.editVerification` is declared.
- New `CampaignSelectionRecordSchema`, deliberately thin next to `CampaignRoundSchema`: `seq`, `candidateVersion`, `baselineScorecardId`, `candidateScorecardId`, `editSet?`, `verdict: { comparable: boolean, accepted: boolean, delta?: number, detail?: string }`, `at`, `by`. No `learned`/`hypothesis` requirement — a selection is cheap and frequent by design; a driver that wants to record why still can, in `editSet[].rationale`, but nothing on the platform reads it as evidence (same posture as `learned`).
- New `PLATFORM_EVENT_KINDS` entry `campaign.selection_logged`, classified in `ACTIVITY_AXIS_BY_KIND` (`evaluation` axis), **not** added to `TRIGGERABLE_EVENT_KINDS` — a feed fact, exactly like `campaign.round_logged` (skill `evolve`'s "the campaign's own facts... are feed facts and are NOT triggerable").

**2. `domain/evolution/`**
- `campaign-gate.ts`: `winning()` is untouched — it already only ever sees `CampaignRound`, and a round is, and stays, a confirmation-only object. `campaignSpendOf`/`experimentFamilyLimit` (in `campaign-attempts.ts`) gain a `tier` filter: only `tier: "confirmation"` attempts feed `consumed`/`outstanding` against `heldOutFamilySize`; `selectionBudget.maxEvaluations` is checked by a **parallel**, structurally identical `selectionSpendOf` reading `tier: "selection"` attempts plus logged `CampaignSelectionRecord`s — same shape (`{consumed, outstanding}`), same unknown/live/lost fold, no new vocabulary invented (Req. 3, protocol L3 — one predicate, not two divergent ones).
- New `selectionAccepted(baselineArm, candidateArm): { comparable: boolean; accepted: boolean; delta?: number }` — the cheap rule (Req. 7): aggregate candidate rate strictly greater than aggregate baseline rate over the `selection`-role scenarios of the pair actually run; `comparable: false` on the same conditions a round already checks (policy mismatch, unresolvable stamp, wrong scenario set) reusing the existing comparability predicate rather than a second one.
- New `verifyCandidateEdits(baselineContent: string, editSet: CandidateEdit[], candidateDigest: string): boolean` (or a richer result if intermediate diagnostics are wanted) — pure, no I/O, applies each op in order to `baselineContent` and digests the result against `candidateDigest`. A `protectedRegions` variant, `editsRespectProtection(editSet, protectedRegions): string[]` (violating targets, empty = clean), consumed by the same door — never inferred from op names alone, so a `"consolidate"` targeting outside a protected region is legal too (the restriction is one-directional: protected regions may only be touched by `consolidate`, not that `consolidate` may only touch protected regions).
- `round-brief.ts`: `campaignRoundBrief` gains a `lastSelection?: { accepted: boolean; delta?: number }` input, rendered as one line in `context` when present, and its train-evidence section is generalized from "targets only" to "every non-held-out case in the last round's evidence" — `RoundEvidenceCase.heldOut === false` is already the exact predicate needed; `heldOutIds(frame)` (used by `redactHeldOut`) is extended to union `selection` and `confirmation` roles, which is definitionally already true since both are `heldOut: true` scenarios — no code change to the redaction call sites, only to what feeds them if role filtering is added elsewhere.

**3. `application-control/evolution/campaign-service.ts`**
- `open()` validates the new frame fields through the extended `campaignFrameDefects`/`CampaignFrameSchema` — no new method.
- The reservation path (`POST /scorecards` → `campaignEvaluation`) reads `tier` and stamps it on the `CampaignEvaluation` row; a `tier: "selection"` reservation is checked against `selectionSpendOf` instead of the round-budget refusal.
- New `logSelection(campaignId, input)` — mirrors `logRound`'s shape (reads the reserved evaluation, computes `selectionAccepted`, runs the edit verifier when `editVerification` is declared, appends the record, emits `campaign.selection_logged`) but never touches `campaignAdoption`/`campaignStoppedAt` and is refused, 409, once `selectionBudget` is exhausted — same shape as today's round-budget refusal, new detail string.
- `logRound` (confirmation, unchanged path) gains the edit-verifier check ahead of the append, refusing 400 with the existing "cannot be stored as sent" family of messages when `editVerification` is declared and the edit set does not reproduce the candidate.
- `campaignRoundBrief`'s caller resolves the campaign's most recent `CampaignSelectionRecord` (if any) and passes `lastSelection`.

**4. `db`**
- A `evolution_campaign_selections` table (append-only, sequence-per-campaign, same contiguity discipline as `evolution_campaign_rounds`) and a `tier` column on the existing evaluation-reservation table. No new object-storage mechanism for edit sets — they ride inline on the round/selection row (bounded, ≤200 ops) the same way `verdict.detail` does; if an edit set grows large enough to need staging-by-digest, that's the existing `evidence: {key, digest}` pattern already used for `RoundEvidence`, reused rather than reinvented.

**5. `apps/api`**
- `POST /campaigns/:id/selections` (MCP `log_campaign_selection`), BFF↔MCP parity required by rule `api-layer`.
- `POST /campaigns` frame body accepts `scenarios[].role`, `selectionBudget`, `editVerification`.
- `POST /scorecards` / `run_scorecard` / `POST /scorecards/ingest` accept `tier` on the `campaignEvaluation` block.
- `GET /campaigns/:id/brief` unchanged path, extended payload only.
- `GET /campaigns/:id` (or a new `GET /campaigns/:id/selections`) lists selection records the same way it lists rounds — this is the answer to the intent's "is a rejected-edit buffer a platform record at all" question: no, it is a **read** over the append-only selection ledger the platform already owns, not a new schema (see Areas of concern).

## Areas of concern

- **The "confirmation discloses nothing, not the fact that it ran" constraint, read literally, conflicts with the existing campaign protocol.** `campaign_decision` already tells the driver `roundsLeft`/`consecutiveRejected`, and today's `campaignRoundBrief` literally states "Round N of campaign X, N-1 round(s) have run" — both are counts of confirmation comparisons, visible to the same driver that is supposedly told nothing about confirmation. I have resolved this by reading the constraint as "confirmation discloses nothing about **outcome** (scores, deltas, ids) beyond what the terminal `adopt`/`halt` state already reveals" — round *counting* stays visible exactly as it is today, because a driver that calls the round door inherently knows it called the door. If the maintainer intends the stricter reading (a driver must not know how many confirmation attempts a campaign has spent), that is a materially different, larger change (it would have to hide `roundsLeft` and renumber rounds out of the brief) and should be confirmed before planning.
- **The platform/driver boundary is a design call I made, not a settled fact — exactly as the intent says.** I put the split, the two disclosure tiers, the edit verifier, and the protected-region check on the platform, and left minibatch partition/reflection/edit merge/rank/`L_t`/rejected-edit buffer/meta prompt entirely to the driver. The intent's own test — "whether a second driver could be written against it" — is not something this spec can verify; it should be the plan stage's first checkpoint, ideally by sketching the second driver's call sequence before writing platform code.
- **Whether a selection evaluation needs the platform at all, versus being purely driver-side, is assumed rather than proven.** I assumed selection must run through Everdict's dispatch (so the platform can enforce the disclosure asymmetry — if the driver held the per-case selection results itself, "the platform hides them" would be theater). This is the right call given the constraint's wording, but it means every selection evaluation still pays Everdict's dispatch/scorecard overhead, which the intent's own cost argument (2,200 vs 30,000 case executions) assumes is cheap relative to a confirmation trial — true for the trial *count* (n=3 vs n=75) but not argued for dispatch/scheduling overhead per evaluation. Twenty selection evaluations a round, run through the full scorecard pipeline, may have a fixed-cost tax the arithmetic in the intent did not price.
- **`selectionBudget.maxEvaluations` is a count, and the intent explicitly says this may be the wrong shape** ("a driver that evaluates cheaply and often is the behaviour this is trying to enable"). I chose a count because it mirrors `budget.maxRounds` and is the only shape the rest of the frame's "frozen and declared" discipline already knows how to enforce (a reservation-door refusal). A rate- or cost-bounded alternative would need a different enforcement primitive (a sliding window, a $ meter) that does not exist anywhere else in this frame today, and building one is a larger, separate change. Flagged rather than resolved, per the intent's own framing.
- **The small-campaign power question is not enforced anywhere in this design.** A 14-scenario campaign can still declare `selectionBudget` and a `selection` role that leaves too few `confirmation` scenarios to be meaningful; `campaignFrameDefects` only enforces the ≥2 / ≥1 floors, which do not know about total scenario count or expected effect size. This mirrors today's un-enforced `minDelta`/N-trials guidance in `frame-design.md` — a documented risk, not a gate — and I have not invented a new gate for it because the intent says "nothing here knows where that line is," which reads as a statement that the floor is not yet known, not that this change should guess one.
- **`editVerification`/`protectedRegions` are scoped to exactly one capability slot per frame**, matching "no skill campaign subject yet... candidates differ in one capability pin." If a future campaign edits more than one artifact per candidate (a skill *and* an MCP tool spec, say), this schema does not extend to it without a second design pass — flagged because the intent's constraint list treats "one lever" as a *driver* discipline (`round-brief.ts`'s existing "ONE lever" constraint text) but this spec turns it into a *platform* structural limit for the specific case of edit verification, which is a narrower and stronger claim than the intent stated.
- **The `consolidate` op kind is my invention to make the protected-region boundary mechanically checkable**, since the intent says a protected region exists "so a longitudinal consolidation is not overwritten by the next local fix" but does not say how the platform is meant to tell a consolidation from a local fix. Without some machine-checkable marker, `protectedRegions` degrades to prose the driver polices itself — which is exactly the annotation failure rule `protocol` exists to name. This is a guess at the cheapest fix that closes that gap; an alternative (a separate door for consolidation writes, never taking an edit set at all) is also legitimate and simpler, and should be weighed at plan time.

## Open questions carried forward

- **How much of the loop is the platform's?** Restated, not answered: my Design section is one concrete answer (split + disclosure + verifier + protected region = platform), offered for the plan stage to pressure-test against a second driver, not offered as settled.
- **Does the selection split steal power the confirmation set cannot spare?** Unanswered. This spec adds the mechanism and the floors (`campaignFrameDefects`) that were already there; it does not add a floor tied to total scenario count, because the intent says nobody yet knows where that floor belongs.
- **What bounds selection spend?** Answered provisionally (a count, `selectionBudget.maxEvaluations`) with the intent's own doubt about that answer carried into Areas of concern above, unresolved.
- **Is a rejected-edit buffer a platform record at all?** Answered: no new schema. The append-only selection ledger this spec adds *is* the read a driver needs — `GET /campaigns/:id` (or a selections-listing door) over `CampaignSelectionRecord`s already carries every rejected candidate's edit set and outcome, exactly as the intent's G5 question hoped.
- **The `L_t` schedule constants were not recovered.** Still true; out of scope for this spec by design (it is driver state, and this design deliberately keeps driver scheduling off the platform).
