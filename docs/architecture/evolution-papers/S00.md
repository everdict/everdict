# S00 — WikiSkill: persistent knowledge for skill evolution

WikiSkill improves a frozen agent by turning execution experience into two different products: a durable knowledge base for the agent proposing changes, and a compact set of instructions for the agent doing the work. Its central contribution is preserving and organizing what an unsuccessful change teaches, even when that change is rolled back. This is a study of **skill evolution across tasks**, rather than model training or adaptation inside one long task.[^1]

## Research question and background

A tool-using language model can repeatedly make the same procedural mistake: search too broadly, misunderstand spreadsheet formula behavior, or enter an action loop. A skill supplies reusable instructions that address such mistakes without changing model weights. The optimization problem is to discover useful instructions from experience, test them on other tasks, and retain improvements.

Earlier systems already analyze traces and propose skills. EvoSkill preserves proposal feedback; Trace2Skill merges diagnoses from individual trajectories; SkillOpt aggregates reflections and remembers rejected edits. WikiSkill argues that these mechanisms leave room for a separately maintained, queryable representation of accumulated knowledge. The distinction is therefore **how experience is represented and used**, not whether earlier methods have any memory at all. Its three-layer design draws on the LLM Wiki idea of compiling raw sources into linked knowledge.[^1]

## Principles and system state

The state is an active skill set S and a wiki W. An execution trajectory is the sequence of observations, actions, tool results, and final answer produced while solving a task. Three stores give those records different roles:

| Layer | Contents | Update behavior | Consumer |
|---|---|---|---|
| Raw experience | Complete training execution traces | Immutable after collection | Maintainer and proposer |
| Wiki | Failure patterns, successful strategies, index, evolution history, skill impact records | Incremental patches; retained across rejected proposals | Maintainer and proposer |
| Skills | Procedural instructions and a purpose file linking them to motivating patterns | Candidate edits can be accepted or rolled back | Executor receives skill instructions |

The wiki is a development aid. In the default experiment, the executor does not read it during training rollouts. All active skill contents are injected directly into the executor's system prompt. Consequently, the experiment removes skill discovery and triggering failures from the measurement; it does not show that a large searchable skill catalogue will work equally well.[^1]

## Algorithm, step by step

1. Start with empty skills and an empty wiki. Measure the no-skill validation score.
2. Run the current executor and skills on the training tasks, preserving trajectories.
3. Give the maintainer up to eight trajectories: at most five failures and three successes, each truncated to 15,000 characters. It updates pattern pages, their index, and an evolution log. Successes help preserve behavior already working.
4. Give a ReAct-style proposer the wiki index, prior skill impact records, and training outcome summaries, including predictions and training answers. It can read selected patterns and raw traces through tools instead of receiving the entire history in one prompt.
5. Propose one atomic change to one skill: create it or patch an existing skill. Apply the change to form a candidate skill set.
6. Evaluate that candidate on the validation split. Accept only if its mean score is **strictly greater** than the best score so far. Otherwise restore the previous skills.
7. Preserve the wiki in either case. The outer harness records the proposal, diff, validation score, and acceptance outcome in the skill impact history. Stop early if validation reaches 100%.[^1]

In compact notation, S(next) is the candidate when R(validation, candidate) > R(best), and otherwise remains S(current). W(next) always retains the iteration's accumulated knowledge. The score inequality is a search rule; it is not a statistical guarantee of improvement on the deployment distribution.

## A worked example

The paper's ALFWorld example follows Qwen-3.6-27B. An initial trajectory reveals repetitive take/examine/move behavior. A broad goal-directed skill fails validation and is rejected, but its diff and rejection remain visible. The next proposal uses that history to create a more specific rule preventing an item from being returned to its origin, and this change is accepted. Later traces expose a different repeated-operation loop, prompting a further restriction on repeating an operation for the same item.[^2]

The example explains the intended causal chain: an observed failure becomes a named pattern, a pattern motivates a targeted edit, and the edit's measured outcome changes future proposals. It is an illustrative case, not an isolated randomized test of each sentence in the skill. The figure also simplifies the underlying files for presentation.

## Experimental design

The main comparison uses five executor models: Qwen-3.5-4B, Qwen-3.5-9B, Qwen-3.6-27B, Gemma-4-31B, and Gemini-3.5-Flash. Open models are served with vLLM. Every method starts with no skills; the controls are no skill, Trace2Skill, EvoSkill, and SkillOpt. Results average three independent runs of the complete evolution process, with up to eight evolution iterations.[^3]

| Benchmark | Train / validation / test | What the executor does |
|---|---|---|
| LiveMath | 35 / 18 / 124 | Answer mathematics questions without tools |
| SealQA | 16 / 10 / 85 | Search the web and inspect retrieved material; July 2026 release |
| SpreadsheetBench | 80 / 40 / 280 | Manipulate spreadsheets using shell/Python execution |
| OfficeQA | 50 / 24 / 172 | Reason over Treasury documents with local search tools |
| ALFWorld | 39 / 18 / 134 | Execute household actions in an interactive simulator |

These are the subsets and conditions used by WikiSkill, not the complete sizes of the original benchmarks. OfficeQA additionally supplies pre-parsed oracle reference pages as initial evidence. Its scores therefore should not be equated with an end-to-end OfficeQA setup in which the agent must discover all relevant documents unaided. Small validation sets make individual acceptance decisions noisy.[^3]

## Main results and transfer

The following table extracts the five-benchmark averages from Table 1. A percentage-point change is the subtraction of two percentages, not a relative percentage increase.[^3]

| Executor | No skill | Best other method's average | WikiSkill | Change from no skill |
|---|---:|---:|---:|---:|
| Qwen-3.5-4B | 26.2 | 35.2, SkillOpt | 38.5 | +12.3 points |
| Qwen-3.5-9B | 29.9 | 42.3, EvoSkill | 47.4 | +17.5 points |
| Qwen-3.6-27B | 39.4 | 53.3, EvoSkill | 63.3 | +23.9 points |
| Gemma-4-31B | 41.3 | 49.1, SkillOpt | 54.9 | +13.6 points |
| Gemini-3.5-Flash | 49.5 | 56.1, EvoSkill | 68.1 | +18.6 points |

An average gain does not mean every cell improves. Qwen-3.5-4B OfficeQA falls from 30.2 without skills to 28.5 with WikiSkill. Gemini's ALFWorld score stays at 85.9 because the source model already reaches perfect validation and does not evolve a skill. The paper uses paired bootstrap resampling with 1,000 iterations and groups methods statistically indistinguishable from the best into ties; a numerically larger cell is not automatically a significant win.[^3]

Cross-model transfer is informative but uneven. On LiveMath, Gemma obtains 56.7 using its own evolved skills and 73.7 using Qwen-3.6-27B's skills. On spreadsheets, Gemini obtains only 18.1 using skills evolved with Qwen-3.5-4B, below its 50.5 no-skill baseline. A transferable procedure can help another executor, while a workaround tailored to one model can interfere with another. A skill's source model is therefore not a sufficient predictor of its usefulness to a receiver.[^3]

## Ablations and mechanism evidence

Table 3 uses **Gemini and four benchmarks**, excluding ALFWorld. With executor wiki access disabled, removing proposer access and the maintainer yields 48.7 average; the default with proposer access yields 63.7, a gain of 15.0 points. Enabling executor access as well gives 60.9, 2.8 points below the default. The no-skill average for these four tasks is 40.4, different from the five-task average above.[^2]

The first comparison changes both the maintainer and proposer access. It does not isolate a wiki against equally large, equally curated flat history. The second supports restricting executor access **under this skill-development protocol**. The authors hypothesize that the executor can bypass skills using wiki knowledge, making its traces less useful for improving skills. They do not demonstrate leakage as the cause, or establish that runtime memory is generally harmful.

The descriptive analysis shows continued accepted edits beyond the first two iterations: for SealQA, 33% of accepted edits occur in iterations 2–4 and 28% in iterations 5–7. These are shares of accepted updates, not success rates for attempted edits. The optimizer-call analysis treats a full training batch as one batch; fewer optimizer calls do not remove the cost of executing every training task or the token cost of long traces.[^2][^3]

## Related research and limits

EvoSkill is the closest basic discovery loop; Trace2Skill offers finer per-trajectory diagnosis; SkillOpt supplies explicit edit budgets and multi-timescale feedback. GEPA and archive-based program search suggest ways to preserve complementary or neutral candidates that strict acceptance discards. SkillRet, SkillRouter, and skill-retrieval augmentation address the deployment stage deliberately excluded here. Harness evolution changes tools and control flow in addition to instructions, while WikiSkill holds that broader harness fixed.[^1]

The paper explicitly leaves automatic wiki pruning, neutral stepping stones, large-library retrieval, and tasks spanning hundreds of actions or hours unresolved. Repeated use of a small validation set can overfit selection. Three complete search runs and test-set bootstrap analysis improve reporting but do not turn every accepted edit into an independently confirmed improvement. The results also leave open whether the same knowledge benefit survives an equal total token-and-rollout budget comparison against a carefully curated flat-memory baseline.

## Implications and a concrete Everdict experiment

The useful change is a **curated projection over durable experience**. Everdict's first-loop proposal already assigns curation to the driver and proposes recording the digest of the advice consumed by a proposal. That design can preserve raw round evidence while allowing a derived knowledge view to reorganize, resolve contradictions, and supersede advice. This is an Everdict design inference, not a feature evaluated in WikiSkill.[^4]

Compare three proposer conditions with the same executor, initial skills, development cases, and total search budget: current round history; a size-matched flat digest; and source-linked curated patterns plus proposal outcomes. Hold retrieval access and context allowance comparable. Record advice bytes, cited source rounds, proposed edits, repeated failed ideas, accepted candidates, and end-to-end search cost. Measure final task performance on a separate confirmation set after selecting the final candidate. A useful curator should improve confirmed utility per budget, rather than merely create more pages or more accepted edits.

Run executor memory as a separate candidate feature if it is a desired product behavior. Similarly, preserving a neutral proposal in a development archive need not mean adopting it for production. Those distinctions let Everdict investigate WikiSkill's open questions while retaining independent evidence for deployment decisions.
