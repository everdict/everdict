# R15 — SkillsBench: paired evaluation of whether a skill actually helps

SkillsBench measures the change caused by giving an agent a reusable skill package. It pairs the same task, environment, model, and harness with and without curated skills. The v4 snapshot contains 87 tasks in eight domains and 18 model–harness configurations, with 9,396 selected public result files for its main two-condition aggregate. This explanation follows arXiv 2602.12670v4; the earlier 86-task, seven-configuration results cited by R11 are a different snapshot.[^1]

## Research question and related work

A benchmark score for an agent combines foundation-model ability, tool interface, controller behavior, and additional knowledge. It does not tell a developer whether adding a particular skill helps. SkillsBench makes the augmentation itself the paired experimental variable. A skill is a filesystem package with `SKILL.md` and optional scripts, examples, templates, or references that guide a class of tasks.

This sits alongside Terminal-Bench, SWE-bench, web/desktop benchmarks, and broader agent evaluations. Procedural-memory systems such as Voyager and reasoning/action methods explain how reusable guidance might help, while DSPy and other optimization frameworks concern improving programs or prompts. SkillsBench supplies an evaluation design for the utility of the resulting artifact. It does not itself implement a multi-generation skill-evolution algorithm.[^2]

## Construction: useful expertise without an answer key

The release derives from 400 candidate task submissions by 142 contributors. A task bundles a human-owned instruction, Docker environment and data, an oracle reference solution, and a deterministic script verifier. Curated skills should pre-exist the specific benchmark instance and apply to a task class. The instruction must not tell the solver which skill to use; discovery occurs through the harness's normal loading mechanism.[^3]

Automated checks cover structure, oracle execution, instruction provenance screening, and possible leakage of task-specific paths, constants, commands, or expected outputs. Human review examines realistic data, task validity, oracle quality, reusable skill quality, and shortcuts. Passing an oracle check shows that at least one solution satisfies the verifier; it does not establish that the verifier accepts every legitimate solution. AI-text detection is a screening heuristic, not proof of human authorship.

The inventory has six tasks estimated to take a human specialist under an hour, 53 at one to four hours, and 28 above four hours. Those are contributor estimates, not measured human baselines. Tasks with little separation between skill conditions are filtered as low-signal, and high-quality skills are selected. This enriches the collection for informative augmentation examples; the mean gain is not an unbiased estimate for arbitrary tasks and marketplace skills.

## Ecosystem study and its sampling boundaries

The construction snapshot counts 2,014,000 source-partitioned skill entries: 234,896 direct/source records, 1,773,213 marketplace records, and 5,891 partner records. Deduplication occurs within partitions before summing. The count therefore should not be called two million globally unique, independently verified skills.[^4]

Structural analyses use the reachable clone sample of roughly 767,430 bundles. Median instruction size is 4.8 KB and median total bundle size 7.2 KB; approximate token counts divide bytes by four. About 59.9% contain a single file, while 86.4% have five or fewer. The collection is dominated by text but has a long tail of large executable/resource bundles. Repository last-push timestamps are not reliable skill creation dates.

The rubric rates completeness, clarity, specificity, and examples. Benchmark skills are selected from the high-quality part of the distribution; their mean rubric score is reported as 10.1/12 versus 6.2/12 for the ecosystem analysis. A well-written package is not automatically effective, and this quality selection makes the benchmark an optimistic use case rather than a random ecosystem sample.

## Paired protocol and the meaning of the reported score

Four terminal harness families are used: OpenHands, Claude Code, Codex CLI, and Gemini CLI. Each main condition targets three selected trials per task/configuration, giving 87 × 3 = 261 slots per condition and 18 × 87 × 2 × 3 = 9,396 overall. Fresh containers isolate trial state. The task data, limits, and verifier are matched; only access to the task's skill bundle changes. Harness-bundled skills remain part of the harness baseline.[^5]

The primary aggregation first averages verifier reward over each task's three slots, then macro-averages over the 87 tasks. The paper calls this pass rate and often describes binary checks, but its formal definition allows fractional reward in [0,1], and the diagnostic appendix separates fully solved from partial outcomes. Consequently, the headline 33.9→50.5 aggregate should not silently be equated with the appendix's fully-solved rates of 31.3→47.7. Exact reproduction requires preserving the released reward semantics.

Normalized gain is (skill score − baseline score)/(1 − baseline score), the fraction of remaining headroom closed. The mean normalized gain averages configurations individually, so it need not equal the result recomputed from the rounded grand means. This is different from relative percentage improvement over the baseline.

Run selection favors healthy, verifier-scored public results and reruns stale, rate-limited, or unscored trajectories; timeouts enter as failure backfill where replacements are unavailable. Some diagnostic tables nevertheless include runtime errors as zero reward. The manuscript's healthy-only descriptions and diagnostic accounting are not fully uniform, so retain the exact selected-file manifest and distinguish operational failures from task failures when reproducing it.

## Main model–harness results

The reported mean rises from 33.9 to 50.5, an absolute gain of 16.6 percentage points and mean normalized gain of 25.5%. Every configuration has a positive aggregate delta, ranging from 4.1 to 25.7 points. This does not imply every task benefits.[^6]

| Configuration | No skills | Curated skills | Absolute gain |
|---|---:|---:|---:|
| OpenHands + GPT-5.5 | 51.5 | 67.3 | 15.8 points |
| Codex + GPT-5.5 | 46.8 | 66.5 | 19.7 points |
| Claude Code + Opus 4.7 | 43.0 | 61.2 | 18.2 points |
| Gemini CLI + Gemini 3.1 Pro | 36.0 | 60.8 | 24.8 points |
| OpenHands + GLM 5.1 | 32.7 | 58.4 | 25.7 points |
| OpenHands + Gemini 3.1 Flash Lite | 16.0 | 20.1 | 4.1 points |

The strongest absolute score and largest gain occur in different configurations. Harness choice also matters within a model family: Gemini 3.1 Pro reaches 60.8 in Gemini CLI versus 52.8 in OpenHands; Opus 4.7 reaches 61.2 in Claude Code versus 53.1 in OpenHands. Those differences combine loading, prompting, tools, and execution behavior rather than isolating one harness feature.

## Domain, task, and design-factor analyses

All eight domain aggregates improve. Natural Science gains 28.8 points, Media/Content 24.1, Cybersecurity 18.9, Industrial/Physical Systems 15.7, Finance/Economics 14.2, Office 12.6, Software Engineering 11.6, and Mathematics/Operations Research 9.7. Specialized procedures may fill gaps in model knowledge, but pretraining coverage is not experimentally isolated from task design and skill authoring quality.[^6]

Thirteen of 87 tasks have negative deltas. Audited failures involve an unnecessarily heavy pipeline, replacing a stronger native strategy, or mandating a solver the agent cannot debug. Examples include control/optimization tasks, sequencing, and security-rule workflows. Positive case studies show concrete missing knowledge: spreadsheet pivot APIs, hydrological data processing, filing formats, scheduling constraints, and required artifact structure. These explain plausible mechanisms rather than supplying independent effect estimates for each instruction.

Tasks with one skill gain 18.0 points, two or three gain 19.0, and four or more gain 10.1. Length buckets show gains of 19.0 for compact, 21.5 for standard, 14.5 for detailed, and 0.7 for comprehensive documentation. The paper calls these design ablations, but the tables group different tasks by existing skill count/length. They are not controlled edits shortening the same skill on the same tasks. The comprehensive group has only five tasks. The defensible conclusion is an association deserving a matched follow-up experiment, not a universal maximum document length.[^7]

## Discovery versus successful use

Invocation analysis counts reads or calls to the task-provided skills, excluding harness-bundled skills. Rates range from 46.4% to 99.2% across configurations. Codex + GPT-5.5 reads/invokes a task skill in 259/261 trials, yet its aggregate resolution score is 66.5. Merely accessing a package therefore does not establish correct application.[^8]

Conditional success among invoked trials is also not a causal estimate of invoking a skill: easier tasks, clearer metadata, or more capable trajectories can influence both invocation and success. The relevant evaluation should separate discovery, reading, resource execution, applicability, and final verified outcome. This is directly useful for diagnosing an evolved library that looks better in retrieval metrics but fails downstream.

## Self-generated skills: protocol and negative results

A separate diagnostic condition asks the same model to create skill packs using an official skill-authoring guide, then gives those packs to a fresh solver session. It is evaluated only on the three dedicated CLI configurations. Claude Code generates packs within each trial and shares sandbox state between creator and solver scenes; Codex and Gemini CLI generate once per task/configuration and reuse the packs. Claude's creator condition uses max effort while its baseline uses high, so the comparison is not perfectly matched.[^9]

| Configuration | No skills | Self-generated | Curated |
|---|---:|---:|---:|
| Claude Code + Opus 4.7 | 43.0 | 34.9 | 61.2 |
| Codex + GPT-5.5 | 46.8 | 35.5 | 66.5 |
| Gemini CLI + Gemini 3.1 Pro | 36.0 | 24.5 | 60.8 |

Public scored coverage is 258, 258, and 253 of 261 slots respectively; a skipped task and missing records matter to interpretation. The negative deltas of −8.1, −11.3, and −11.5 points describe this creation/loading protocol, not every form of iterative skill evolution.

A targeted audit of twelve solver trajectories finds several mechanisms. Generated packs can go undiscovered; creator work can consume the task's opportunity to finish; an incorrect unit assumption can become an unquestioned script; and creator access to the graded sandbox can leak instance-specific fixes. The strongest cited positive case is interpreted as such leakage rather than reusable expertise. One unit-related verifier was later patched, further limiting that case's causal interpretation. Missing creator logs and omitted tool outputs constrain the audit. These details prevent using the result as proof that self-generated content alone is necessarily worse.

## Cost, runtime, uncertainty, and remaining limitations

Token usage is available for all 18 configurations and priced runtime cost for ten. Skills increase tokens for some configurations and decrease them for others. OpenHands + Opus 4.7 changes from about 1.77M to 1.09M recorded tokens per trial and $10.99 to $6.37, while Claude Code + Opus 4.7 changes from about 4.33M to 6.43M and $5.21 to $6.74. These are historical harness-reported totals, including repeated/cached context where recorded, not single prompt lengths or current price quotations.[^10]

Agent runtime is broadly similar at fleet level; an example is OpenHands + Opus 4.7 decreasing from 10.0 to 6.5 minutes per task. The timing excludes other lifecycle work such as human skill authoring. Lower runtime does not automatically imply lower total evolution cost.

The plotted confidence intervals use binomial Wald intervals based on selected result counts. With repeated trials clustered by task and possible fractional rewards, these intervals are not a full paired, task-cluster uncertainty analysis of each delta. Stronger length-matched controls, randomized irrelevant context, and component-level experiments remain future work. Containerization and temperature zero also do not eliminate all nondeterminism or pretraining contamination. Terminal tasks do not directly establish GUI or very-long-horizon performance.

## Implications and a proposed Everdict experiment

Adopt the paired artifact comparison, while making the scoring and missing-run policies explicit. Freeze candidate bytes, executor, harness, task inputs, verifier revision, and train/select/confirm split. Evaluate baseline and candidate on the same confirmation tasks; aggregate fully solved, partial, and operational errors separately before applying a declared utility. Estimate uncertainty by resampling paired tasks when that matches the intended inference.

To test evolution, compare a curated seed, one-shot generated skills, and iteratively evolved skills with equal discovery support and total creation/evaluation budgets. Use a clean solver environment that receives only declared candidate files. This removes the creator-state and visibility confounds highlighted by the self-generation audit. Include no-skill cases and applicability boundaries so a candidate can improve by declining an unnecessary heavy procedure.

A separate matched experiment can shorten the same skill, remove its script, or remove its examples while holding task and budget fixed. That tests which element causes utility instead of inferring causality from length buckets. In Everdict's first loop, these can be driver-proposed candidate edits; confirmed evidence and adoption remain platform-owned. The paper's strongest lesson is to measure actual changes in behavior and outcomes, not reward the mere existence, size, or polished appearance of a skill package.
