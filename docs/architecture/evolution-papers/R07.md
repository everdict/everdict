# R07 — Gemma 4 technical report: the executor beneath the skills

The Gemma 4 report describes a family of open-weight multimodal models, including the 31B executor used in WikiSkill. It explains model architecture, training, memory/compute optimizations, and evaluations. It is background for understanding the agent's capabilities and cost; it does not propose an experience-to-skill evolution algorithm. This note follows arXiv 2607.02770v2.[^1]

## Problem and research lineage

Useful local or self-hosted agents need enough reasoning ability to follow procedures, enough context for observations, and an affordable memory footprint. Increasing model size can improve capability but reduces concurrency and increases serving cost. Gemma 4 combines changes to the model, multimodal inputs, attention, quantization, and decoding rather than treating parameter count as the only scaling dimension.

Its background includes decoder-only Transformers, Gemma 3/3n, mixture-of-experts models, rotary position encoding, speculative decoding, quantization-aware training, vision Transformers, and Conformer-based audio encoders. These are different mechanisms: fewer bits reduce storage, a drafter reduces serial generation work, and attention/cache changes reduce the state carried through long sequences. Their effects should not be collapsed into one generic “smaller model” claim.[^1]

## Model family and architectural principles

The family includes E2B and E4B with approximately 2.3B and 4.5B effective parameters, dense 12B and 31B models, and a 26B mixture-of-experts model with about 3.8B activated parameters. The small models' per-layer embeddings mean effective and total parameter counts differ: E2B and E4B have roughly 5B and 8B total parameters. For an MoE, activated parameters characterize per-token computation more closely than the total weight storage requirement.[^2]

The decoder uses RMS normalization and query/key normalization. Most attention layers use local windows, with a global layer periodically allowing distant information to interact. The local/global ratio is 4:1 for E2B and 5:1 for the others. Selected models reuse keys as values in global layers and use partial rotary encoding; the report attributes up to 37.5% lower global KV-cache footprint to these optimizations. E2B/E4B instead also share caches across layers. The exact benefit depends on model architecture and sequence length.

For an agent processing a long tool trace, model weights occupy persistent memory while cached keys/values grow with the sequence. Quantizing weights may fit the model onto a device, but long histories and concurrent tasks still consume cache memory. This is why a serving configuration must be evaluated at the intended context length and concurrency, not just by whether the checkpoint loads.

## Vision, audio, and the encoder-free variant

E2B/E4B use a 150M vision encoder and a 305M audio encoder; larger vision-enabled models generally use a 550M vision encoder. Vision processing preserves aspect ratio and supports different token budgets, up to 1,120 vision tokens. Audio processing uses 40-millisecond chunks and continuous representations, rather than a vector-quantized token interface.[^2]

The 12B variant removes separate modality encoders. A lightweight projection maps image patches into the language model's embedding space, while 40-millisecond raw audio chunks are projected similarly. The model must learn more of the modality processing in the shared backbone. The report's comparison shows competitive audio/text behavior, but the family-wide benchmark table does not isolate this architecture from differences in size and training.

## Training and inference efficiency

Pretraining uses web documents, code, images, and audio where supported, with a stated January 2025 data cutoff. Filtering addresses benchmark contamination and unwanted content. Instruction tuning adds a thinking mode and examples encouraging attribution, hedging, and appropriate refusal. Training uses TPU infrastructure, JAX/Pathways, sharded optimizer state, and infrastructure techniques that tolerate localized failures.[^2]

Quantization-aware training adapts the model to low-precision weights and activations rather than merely rounding a finished checkpoint. Mobile formats mix low-bit weights and int8 activations; larger models also use Q4_0. For the 150M vision encoder, the report gives a forward-pass memory reduction from 400 MB to 200 MB and a 44% latency reduction relative to Gemma 3n on newer hardware. Hardware changes limit attribution of that latency comparison to quantization alone.

A separate multi-token prediction drafter uses the main model's activations and cached state to propose future tokens for speculative decoding. A small model can cheaply propose several tokens, which the main model checks. The throughput benefit depends on acceptance rate and serving implementation. This does not create cross-task learning or a persistent skill memory.[^2]

## Evaluation design

The evaluation has five major families: blind human preference comparisons, text/reasoning/coding and tool-use benchmarks, vision tasks, audio transcription/translation, and long-context tasks. Most Table 5 Gemma 4 scores use thinking mode; the Gemma 3 27B comparison is explicitly non-thinking. Table 9's long-context comparison is instead **without thinking**. These mode differences are essential to interpretation.[^3]

| Representative result | Gemma 3 27B | Gemma 4 31B | What the metric means |
|---|---:|---:|---|
| MMLU Pro | 67.6 | 85.2 | Broad academic knowledge/reasoning |
| AIME 2026, no tools | 20.8 | 89.2 | Competition mathematics |
| LiveCodeBench v6 | 29.1 | 80.0 | Code-generation evaluation |
| Terminal Bench Hard | 4.0 | 36.0 | Agentic terminal tasks under this report's setting |
| RULER, 128k, no thinking | 66.0 | 96.4 | Synthetic long-context capability |

The final-model comparison changes architecture, training, and reasoning mode together. It demonstrates the resulting system's reported capability, not the isolated contribution of each architectural change. “Terminal Bench Hard” is also not automatically the same task version or protocol as Terminal-Bench 2.0/2.1 results elsewhere.

## Further results and controlled comparisons

The June 19, 2026 Arena snapshot gives Gemma 4 31B Elo 1451 ± 8 and the 26B-A4B model 1438 ± 8. These are preference estimates against the sampled comparison pool, not percentages of tasks solved or current leaderboard positions. In Table 5, adding search to Gemma 4 31B's HLE setting raises 19.5 to 26.5; this is a change in tool access as well as inference behavior.[^3]

Vision token budget provides a more specific within-model comparison. Gemma 4 31B scores 82.8 on InfographicVQA at 280 vision tokens and 92.0 at 1,120. Its MMMU Pro values change much less, 75.8 to 76.9. Input resolution can therefore matter differently by task, especially where small text or details carry the answer. Saving vision tokens can change the evidence available to the agent, not merely the execution price.

Audio evaluation uses CoVoST translation and FLEURS transcription; lower word/character error is better, while higher BLEU is better. E2B's average reported transcription error changes from Gemma 3n's 0.108 to 0.090; E4B changes from 0.085 to 0.075. Long-context evaluation additionally covers LOFT retrieval, GraphWalks, and translation from a supplied grammar book, showing that a context-size limit and effective use of that context are different properties.[^3]

## Safety evaluation and reporting limits

The report describes data filtering, automated and human evaluation, and checks of text/image content behavior without additional safety filters. It reports improvements over previous Gemma models while aiming to keep unnecessary refusals low. These are developer-reported model evaluations; a deployed agent's tools, permissions, and workflow introduce additional behavior not settled by the model report.[^4]

The training recipe and family tables do not supply a complete factorial ablation of every change. Exact training mixtures, serving details, and evaluation modes constrain reproducibility. Human preference, coding accuracy, retrieval recall, and transcription error answer different questions. Combining them into a single ranking would obscure the tradeoffs relevant to a particular agent workload.

## Implications and an Everdict experiment

Pin executor checkpoint, tokenizer/template, quantization, thinking mode, serving version, input resolution, and context limit alongside the evolved skill. Otherwise a changed executor can be mistaken for a better skill. Preserve that identity on every trajectory used to derive future proposals.

A useful experiment fixes a skill library and varies executor/serving conditions, then fixes the executor and compares evolved libraries. Measure task success, tool-format errors, instruction compliance, latency, memory, and total cost per confirmed improvement. For multimodal tasks, vary resolution explicitly; for long tasks, test useful evidence retention rather than advertised context length alone. This uses the report to design transfer and cost controls, not as evidence that Everdict should train a new foundation model.
