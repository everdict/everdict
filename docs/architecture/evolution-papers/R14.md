# R14 — Meta-Harness: a coding agent searches over executable harnesses

Meta-Harness asks a coding agent to improve the program that constructs context, retrieves examples, updates memory, and orchestrates a frozen language model. The proposer can inspect a filesystem of prior programs, scores, and detailed traces. It decides what to read and how to revise the implementation. The principal evidence comes from text classification, retrieval-augmented mathematics, and TerminalBench-2, with different generalization protocols in each domain. This note follows arXiv 2603.28052v1.[^1]

## Problem and relationship to other optimizers

An agent's output depends on more than its instruction text. Retrieval can select the wrong examples, memory can retain unhelpful details, and a controller can hide important observations until too late. A local prompt rewrite may not fix a structural defect in that program. The paper therefore optimizes the executable harness H around a fixed model M, seeking higher expected task reward over rollouts.

Related work includes GEPA/TextGrad/OPRO-style textual optimization, evolutionary program search, ADAS-style agent design, workflow search, and external-memory/context engineering. Meta-Harness differs in the breadth of its editable implementation and the proposer's adaptive inspection of history. The paper's characterization of earlier methods should not be read as a universal impossibility result: GEPA can inspect traces and optimize multi-component systems, and program-search frameworks admit different configurations. The experiments compare particular instantiated interfaces and budgets.[^2]

## Outer-loop mechanism

Initialize a population of valid harness programs and evaluate the seeds. Store each candidate's source, scores, and execution traces in its own directory. At each iteration, a coding-agent proposer searches those files, diagnoses failures, and emits one or more new programs. An interface validation step rejects malformed programs before expensive evaluation. An external evaluator runs valid candidates and appends the results. The search retains evaluated candidates and a Pareto frontier where multiple objectives matter.[^3]

There is no compulsory parent-selection rule. The proposer can use any earlier candidate, combine ideas, or rewrite substantially. History may exceed its context window; terminal reads and searches make access selective. This is not equivalent to placing the whole archive into one prompt, nor does storing the archive guarantee that every relevant record will be read.

The reported proposer is Claude Code with Opus-4.6; candidate harnesses are single Python files, typically hundreds of lines. A domain instruction defines allowed files, interfaces, and outputs. The base executor stays frozen. Generic remarks about a typical 20-iteration, roughly 60-harness run are not the exact budget for every experiment: classification uses 40 new candidates, math 109, and the described terminal trace spans ten iterations.

## Why detailed traces may help credit assignment

A scalar score says that a candidate failed. A trace can reveal whether retrieval omitted a necessary example, a prompt confused two labels, or an early environment assumption caused later errors. Comparing several candidates can expose confounded edits: if both changed the prompt and controller, their regressions do not identify which change was harmful.

The qualitative terminal trace shows the proposer recognizing such a confound, separating structural edits from a prompt rewrite, and eventually choosing a smaller additive change. The file-access study reports a median of 82 reads per iteration, with approximately 41% directed to harness source and 40% to execution traces. This establishes substantial use of the feedback channel, not formal proof that each diagnosis was causally correct or that reading more files always helps.[^4]

## Experiment 1: online text classification

A GPT-OSS-120B classifier receives labeled examples sequentially, updates harness-managed memory, and is later tested on held-out examples. Search uses LawBench criminal-charge classification with 215 classes, Symptom2Disease with 22, and USPTO-50k with 180 precursor-reactant classes. Seeds include zero-shot, few-shot, ACE, and MCE. The search runs 20 iterations with two candidates each. Candidate selection uses the search set, and the proposer does not see the final test scores.[^5]

The selected harness reaches mean test accuracy 48.6%, compared with ACE 40.9% and MCE 40.0%. It uses 11.4k additional input tokens versus 50.8k and 28.5k respectively. Thus the 7.7-point gain over ACE accompanies lower reported context volume. It is not a 7.7% relative gain, nor a complete total-cost comparison including search and every model call.

The per-dataset values matter: Meta-Harness scores 14.0 on USPTO, 86.8 on S2D, and 45.0 on LawBench. It does not beat ACE's USPTO 16.0. Aggregate improvement does not imply every domain improved.

## Discovered classification procedures

The low-context draft-verification variant first retrieves five similar examples and predicts a label. It then retrieves five examples supporting that label and five similar examples with other labels, asking the model to keep or revise its answer. With fewer than five stored examples it falls back to a simpler few-shot call. The second retrieval is conditioned on the first prediction, making the challenge specific to the current hypothesis.[^6]

The higher-accuracy label-primed variant uses one larger call. It lists valid labels, supplies a query-relevant example for each available label, and adds locally similar examples with contrasting labels. TF-IDF retrieval and query-anchored pairing expose both global label coverage and nearby decision boundaries. This is a concrete algorithm discovered in the search, rather than the instruction “reason more carefully.”

The appendix reports other frontier variants such as error annotation, chain-of-thought replay, cluster coverage, cascaded retrieval, and reciprocal-rank-fusion/contrastive combinations. Their existence illustrates multiple accuracy/context tradeoffs, not a factorial ablation proving every named component helps independently. Table 9 measures context in thousands of **characters**, whereas Table 2 measures thousands of **tokens**. The 45.5 versus 11.4 values must not be treated as contradictory token counts.

## Search controls, information ablation, and transfer

Program-search comparisons use the same Opus proposer configuration and the same number of full harness evaluations. Search-set best accuracy is 40.2 for GEPA, 44.2 for independent Best-of-N, 43.3 for OpenEvolve, 45.6 for the text-selection component of TTT-Discover, and 56.7 for Meta-Harness. The claim of ten times fewer evaluations concerns reaching the compared methods' performance on this classification search, not a universal wall-clock or dollar speedup.[^5]

| Proposer information | Median candidate accuracy | Best candidate accuracy |
|---|---:|---:|
| Source code and scores | 34.6 | 41.3 |
| Source code, scores, and generated summaries | 34.9 | 38.7 |
| Full interface including raw traces | 50.0 | 56.7 |

These are search-interface ablations. They support retaining diagnostic trace access in this setting; they do not prove that all summaries or curated wikis are harmful. A summary-only replacement and a curated index that preserves access to raw records are different interventions.

On nine datasets unseen during harness search, the selected classifier reaches 73.1% average accuracy versus ACE 70.2%. The datasets cover citation intent, financial entities, reviews, financial sentiment, emotions, banking intents, news, entailment, and hate-speech classification. It wins on six of nine, while ACE remains stronger on FiNER and Financial PhraseBank. This tests transfer of the context-management procedure across datasets, with task-specific labeled memory still supplied in the target setting.

## Experiment 2: mathematical retrieval

Search uses GPT-OSS-20B on a stated 250-problem set from OlympiadBench and hard Omni-MATH, with 40 iterations producing 109 candidate retrieval harnesses. The retrieval corpus has 535,356 solved problems from eight sources. Filtering removes selected benchmark families, exact-prefix matches, and fuzzy Jaccard matches at threshold 0.8; top retrieved examples are also manually inspected. These precautions reduce known overlap but do not prove semantic decontamination.[^7]

The final code routes each query by lexical features into combinatorics, geometry, number theory, or a default route. Combinatorics retrieves 20 BM25 candidates, deduplicates to eight, reranks, and keeps three. Geometry combines one fixed hard reference with two raw BM25 neighbors. Number theory retrieves twelve and favors useful difficulty/early technique descriptions. The default retrieves ten and chooses an adaptive example count. A math-aware tokenizer preserves useful LaTeX features. The proposer combined successful geometry and combinatorics lineages.

The 200-question held-out set contains 100 IMO-AnswerBench, 60 IMO-ProofBench, 17 December ArXivMath, and 23 January ArXivMath problems. Accuracy is pass@1 averaged over three samples per problem. The same harness is evaluated with the search executor and four additional unseen model configurations. The paper sometimes calls all five models held-out, but GPT-OSS-20B was used during search; the problem set is held out for all five, while model transfer applies to four.

Mean accuracy rises from 34.1 without retrieval to 38.8 with the discovered harness, compared with BM25 37.5 and dense retrieval with five examples 38.1. All five improve over no retrieval. However, Gemini-3-Flash scores 46.3 with Meta-Harness versus 46.6 with fixed BM25, and dense top-five retrieval reaches 47.2. The discovered policy has the strongest average, not every individual cell.

## Experiment 3: terminal harness discovery

TerminalBench-2 search starts from Terminus 2 and Terminus-KIRA. **Search and final evaluation use the same 89 tasks.** The paper explicitly treats this as public-benchmark discovery, with regex/manual inspection for task-specific strings. Such audits can catch literal hardcoding but cannot establish held-out generalization.[^8]

The selected harness reports 76.4% with Opus-4.6 versus Terminus-KIRA's 74.7%, and 37.6% with Haiku-4.5 versus 33.7%. Other comparison values are drawn from the contemporary leaderboard and can include different systems or conditions. The paper's rank claims are historical. Its inability to reproduce another entry from public code alone does not itself establish that entry is invalid.

The discovered change adds an environment snapshot before the first model turn: current directory, a bounded file listing, available languages/versions, package managers, and memory. It inherits native tool calling, a 30-KB output cap, and the completion checklist from Terminus-KIRA. The new bootstrap is approximately 80 lines with a 15-second timeout and a nonfatal failure path. The authors identify gains on seven tasks involving non-obvious tooling and interpret reduced early probing as the mechanism. This is narrower than inventing an entirely new coding architecture.

## Reporting limits and implementation lessons

The practical appendix recommends navigable logs, cheap interface smoke checks, a small informative search set, and evaluation outside the proposer. It labels these as engineering lessons, not controlled scientific findings. It also mentions an 88-problem math search example, unlike the main experiment's 250; use the main section for the reported experiment and retain the appendix discrepancy rather than silently merging budgets.[^9]

The study mainly uses one strong proposer system. Equal evaluation count does not equal equal proposer tokens, navigation time, or total cost. Classification and math provide held-out evidence; terminal results do not. Hypotheses derived from readable code remain hypotheses until tested, and visible absence of task strings is weaker than absence of overfitting. Co-evolving model weights is proposed future work, not a result of this paper.

## Implications and an Everdict experiment

The strongest actionable idea is selective access to preserved diagnostic evidence. A driver should be able to compare earlier candidate bytes, scores, and traces, including failed and non-leading candidates. It can propose a causal explanation and a targeted edit, while the platform checks the declared artifact and controls evaluation/adoption authority.

Compare three driver interfaces under the same train/select/confirm protocol: scores and source only; a bounded summary; and a curated view with drill-down into raw traces. Measure confirmed gains, total cost, repeated failed ideas, and whether proposed explanations survive targeted component tests. This reconciles Meta-Harness's trace-access result with WikiSkill's curated knowledge: the experiment tests curation while preserving the underlying evidence channel.

For an initial executable change, the environment-snapshot idea is small enough to evaluate separately. Freeze the task environment, compare equivalent observation access with and without early summarization, and charge the snapshot's calls/tokens/time. Keep its implementation within declared candidate files; it must not modify the evaluator or acquire hidden confirmation information. Everdict's first-loop proposal can support this test without copying Meta-Harness's entire search implementation.
