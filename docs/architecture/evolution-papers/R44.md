# R44 — CoEvoSkills: co-evolving executable skills and surrogate tests

CoEvoSkills v3 builds a multi-file skill for a particular task, repairs it using independently generated tests, and escalates those tests when a hidden oracle rejects a fresh execution. The main Opus experiment improves full task success from 30.6% without skills to 71.1%. The useful idea is a coupled solver–test-development loop. The essential qualification is that evolution **does use hidden-oracle feedback**, and the reported transfer primarily changes models on the adapted tasks, rather than testing unseen task families.[^1]

## Background: the tool–skill distinction and prior evolution systems

A tool exposes an operation. A skill combines a procedure, executable helpers, and references that coordinate several operations. Generating a folder in one pass can leave inconsistencies between its instructions, function names, actual implementation, and required outputs. Iterative execution provides evidence that a syntactically plausible bundle is insufficient.

SkillsBench establishes that useful human-authored skills can improve agents but do not help uniformly. SkillRL trains policies with a skill bank; EvoSkill uses task evaluation to search reusable skill folders. CoEvoSkills emphasizes executable multi-file bundles and a separate surrogate verifier that supplies detailed repair guidance when oracle diagnostics are hidden.[^2]

The paper's broad statements that prior systems cannot generate multi-file skills are stronger than this comparison supports: EvoSkill already searches skill folders. The substantive distinction is the particular feedback architecture and task-conditioned evolution protocol, not exclusive ownership of structured skill generation.

## Three components and what each is allowed to see

The generator sees the task instruction, observable inputs, background documents, a skill-creation meta-skill, and its accumulated conversation. It writes a procedure and callable utilities, executes them, and receives surrogate diagnostics. Skills persist across evolution iterations **for the current task**, as the full system prompt explicitly states.[^3]

The surrogate verifier runs in a separate session of the same backbone. It sees instructions, input data and background, current output artifacts, and its previous test script. It does not receive the generator's reasoning, skill source, or hidden oracle tests. Separate sessions reduce direct imitation of the generator's rationale, but do not make the models statistically independent or remove shared pretrained biases.

The oracle runs a fresh agent with the skill in a clean environment and evaluates its regenerated outputs. Its hidden test content and detailed failures are withheld from the generator and surrogate. Only a success/failure status is exposed to the generative loop. However, the host algorithm reads a numeric oracle reward to retain the best snapshot. Host-visible score and agent-visible feedback are distinct information channels.

This is restricted oracle supervision, not an oracle-free real-world procedure. A binary result still contains information, and repeated querying can adapt to hidden criteria without seeing their implementation. Fresh execution tests whether the bundle carries the solution procedure; it does not make the task itself unseen.

## Alternating skill repair and test escalation

The verifier first generates deterministic assertions from the task and visible artifacts. Their mean pass fraction is the surrogate reward. When any assertion fails, the test suite remains fixed while the generator receives failed checks, proposed causes, and revision suggestions. The generator repairs the skill and reruns it.[^3]

When the surrogate fully passes, the host invokes the oracle on a fresh execution. Perfect oracle success ends evolution. Otherwise the host saves a better-scoring snapshot if appropriate, exposes failure status, and asks the verifier to strengthen its tests. The new verifier can inspect its previous tests and visible artifacts, but receives no hidden diagnostic explaining the oracle's rejection.

The default limits are five oracle rounds, fifteen surrogate repair retries, and a stop above 70% context usage. The pseudocode's repair counter is cumulative; it is not reset to fifteen after each oracle round. A verifier escalation need not immediately rewrite the skill: the existing candidate can first be tested under the new suite.

The formal POMDP describes incomplete observations and hidden reward criteria. The optimization equations specify desired objectives; LLM sampling approximates them. There is no convergence theorem showing that independently strengthened surrogate tests must approach the oracle's true criteria.

## Why the exported artifact can differ from a successful local run

The system prompt requires outputs to be produced by importing the skill's functions. Runtime fixes must be written back into those functions and their documentation, rather than left in a one-off runner or manually patched output. This makes the clean-environment oracle meaningful: a fresh executor gets the bundle, not the generator's entire workspace history.[^4]

The prompt also requires environment and tool discovery, reading reference documents, self-reflection, execution, and a final evolution summary. A progress checklist can block oracle access even after surrogate success. This additional control is visible in the case study but not represented as a separate gate in the simplified algorithm.

These constraints are stronger than generic skill drafting, yet are not automatic evidence of portability. The background-document provenance and exact contents need to be pinned. Import conventions, dependencies, paths, and the executor's skill-discovery hint also affect behavior. A checked box reports a claimed phase completion; it should not replace evidence that the phase actually ran.

## Experimental setup, scope, and baseline differences

The sole suite is an eighty-five-task SkillsBench subset using eleven domain labels. Two tasks are excluded for unavailable infrastructure: authenticated calendar/email state and a CUDA training requirement. The main metric is binary full success, requiring reward exactly 1.0. Partial oracle scores can influence host snapshot selection but are not counted as final task success.[^5]

Opus 4.6 and GPT-5.2 perform separate evolution runs, with same-backbone surrogate sessions. Oracle and final execution use Claude Code for Opus and Codex for GPT-5.2. Evolution allows an effective 3,000 seconds per task with four workers; final evaluation allows 7,200 seconds with ten workers. Context and timeout stops can end search before the nominal retry caps.

The main comparison uses five runs; model transfer uses three. The paper reports mean and standard deviation, but does not provide a full total token/API-cost ledger or equal-compute accounting across all baselines. Fresh task executions and extra evolution work are significant resources.

Baselines include no skill, one-pass self-generation, a structured CoT self-generation prompt, an autonomous adaptation of Anthropic's skill creator, and the benchmark's human skill bundles. The skill-creator baseline uses separate creation and execution sessions and at least three refinement iterations, but its prompt forbids solving the target task or writing target outputs. CoEvoSkills explicitly executes the target during evolution. This difference, along with background context and oracle access, prevents attributing the entire gain solely to verifier independence.

## Main quality comparison

| Opus 4.6 + Claude Code condition | Full success % |
|---|---:|
| No skill | 30.6 |
| One-pass self-generated skills | 32.0 |
| CoT-guided self-generation | 30.7 |
| Autonomous skill creator | 34.1 |
| Human-curated skills | 53.5 |
| CoEvoSkills | 71.1 |

The gain is 40.5 percentage points over no skill and 17.6 over human bundles. The two one-pass variants provide little average benefit, with reported standard deviations 3.1 and 5.2 points respectively. This supports the practical value of the full iterative procedure relative to these implementations.[^6]

It does not prove that agents intrinsically write better skills than humans, that every one-pass strategy is insufficient, or that human–machine cognitive mismatch is the causal explanation. The conditions differ in feedback, task exposure, executable code, and search effort. Human bundles can be broader reusable guides while the evolved package is optimized for the present task.

## Cross-model transfer: broad executor portability on adapted tasks

| Receiving model | No skill % | Opus-evolved skill % | Gain in percentage points |
|---|---:|---:|---:|
| GPT-5.2 | 29.6 | 65.0 | 35.4 |
| Claude Sonnet 4.5 | 20.0 | 63.1 | 43.1 |
| Claude Haiku 4.5 | 10.4 | 54.5 | 44.1 |
| Qwen3 Coder | 8.4 | 50.8 | 42.4 |
| DeepSeek V3 | 13.0 | 48.8 | 35.8 |
| Mistral Large 3 | 4.9 | 43.1 | 38.2 |

GPT-5.2's own evolved skills reach 69.8%, 4.8 points above its Opus-transferred result. Sonnet uses Claude Code; Haiku, Qwen, DeepSeek, and Mistral use Terminus-2. The comparisons within each receiving model preserve its harness, while cross-model absolute rankings include harness differences.[^7]

The consistent gains show that a task-conditioned bundle can be useful to other executors. They do not establish transfer to new input distributions or new task families. Executable functions can carry much of the adapted solution, making this a meaningful portability test but a different question from learning a generally better agent.

## Domain analysis and uncertainty in the plotted counts

The authors report evolved skills exceeding human bundles in nine of eleven domains. Finance and cybersecurity show reported margins of 56.9 and 23.2 points. Natural science's human bundle slightly reduces performance, while the evolved condition improves substantially. Energy is approximately tied and robotics slightly favors human skills in the figure.[^8]

Domain sample sizes are uneven: finance eight tasks, natural science eleven, cybersecurity seven, office thirteen, healthcare one, media twelve, manufacturing three, software thirteen, research nine, energy three, and robotics five. A 100% healthcare result therefore does not establish broad medical capability.

There is also a reporting ambiguity: the single-task healthcare baseline is plotted around 62%, which cannot be a five-run mean of strictly binary success on one task. The domain figure's exact aggregation or run population is not reconciled with the main protocol. Its directional pattern can be discussed, but these bars should not be treated as fully reproducible per-domain estimates without the underlying records.

## Ablations: useful evidence with several mechanisms removed together

Without the surrogate verifier, the generator still receives up to five oracle outcomes but no synthesized detailed diagnostics; success is 41.1%. Background context without evolution yields 42.4%, versus the 30.6% no-skill condition. Full CoEvoSkills reaches 71.1%.[^9]

These results suggest that background knowledge helps and that detailed iterative feedback adds substantial value. However, the ablation rows are single runs while the full result is the reported multi-run mean. Removing the surrogate also removes many repair opportunities and associated compute; removing evolution removes multiple components at once.

There is no matched frozen-surrogate-versus-evolving-surrogate ablation, same-session-versus-isolated-verifier ablation, or prose-versus-code control. Consequently, the data do not isolate co-evolution, informational separation, and executable packaging as three individually proven causes. A genuine no-oracle variant is also not established by these experiments.

## Evolution dynamics: several different result populations

Figure 2 shows approximately 32, 32, 44, 63, 72, and 75% success over rounds zero through five. Its 75% endpoint and 32% baseline differ from the main five-run results, 71.1% and 30.6%. The trajectory should be described as its own illustrated run/aggregation, whose exact relationship to the main mean is not fully specified.[^10]

Appendix B reports averages of 4.1 verification cycles and 2.4 oracle rounds, with over 60% of tasks requiring at most two oracle rounds. Roughly 41% of cycles therefore avoid oracle execution, but this ratio is not a measured 41% saving in total cost: surrogate tests and generator repairs can themselves be expensive.

The distribution figure labels seventy-six passed and ten failed tasks, totaling eighty-six, while its caption and protocol say eighty-five. Its iteration counts must not be silently used to reconstruct the main 85-task success rate. A finite curve leveling by the five-round budget is evidence of diminishing observed gains, not a general convergence guarantee or a complete cost analysis.

## Exoplanet case: the solver and verifier can both be wrong

The detailed case estimates a transit period from TESS lightcurve inputs and exports a value to five decimal places. A lightcurve records brightness over time; transits create repeated dips amid stellar variability. Box Least Squares (BLS) searches a box-shaped dip model, while Transit Least Squares (TLS) uses a more realistic transit shape. Detrending removes slower variation but can also damage the signal if applied poorly.[^11]

The initial BLS/biweight-detrending bundle fails all fifteen surrogate checks. A revised version passes the surrogate, but a missing progress-checklist step delays oracle use. Later BLS versions reach only three of four oracle checks. The final skill combines TLS, Savitzky–Golay detrending, broad then narrow period search, and checks of half/double-period aliases; its oracle execution passes all four.

The surrogate initially accepts a 1% period tolerance despite the task's stated five-decimal requirement. This is an observable specification gap as well as a hidden-grader alignment issue; five-decimal formatting and exact numerical agreement must be distinguished. Later, its own BLS estimate differs from the candidate's TLS estimate by 0.00002 days, and it rejects the candidate that the oracle ultimately accepts. An independent verifier can therefore be both too permissive and too strict.

The case table says one intermediate version fixed precision but failed aliasing, whereas adjacent version prose says precision still failed. It also describes repeated 75% feedback, while the main protocol restricts agent-visible oracle feedback to a bit. These should be interpreted as author/host analysis unless exact logs establish what the generator saw. They are unresolved reporting differences, not grounds to invent hidden diagnostic access.

Trying several BLS configurations unsuccessfully does not prove a universal five-decimal precision limit for BLS. Several algorithmic and preprocessing choices change simultaneously in the successful version. The case demonstrates a useful strategy change under feedback, not an isolated scientific comparison of the algorithms.

## What the final skill contains and what its success means

The case compares five human skill documents totaling 1,096 lines with one evolved bundle containing sixty-four instruction lines and 142 Python lines in nine functions. The evolved bundle implements period refinement, alias checks, and a fixed processing sequence rather than leaving those as general suggestions. It passes five fresh Opus executions on this task.[^11]

This is strong evidence that useful work moved into a portable artifact and survived a session reset. It is not five unseen astronomy tasks. Line count also mixes documentation and executable logic; fewer lines do not alone explain accuracy. A relevant transfer test would change lightcurve families, noise, sampling, period ranges, and required output precision while preserving the intended task class.

## Everdict proposal: co-evolve diagnostics while freezing settlement

Everdict can let a driver propose both a candidate skill and diagnostic tests, with separate versioned artifacts for each. Diagnostic results should identify their test version, input evidence, expected behavior, and uncertainty. The evaluator that settles the campaign should remain frozen and independent of those evolving tests.

A first experiment should compare fixed diagnostics, independently regenerated diagnostics, and diagnostics strengthened after limited selection feedback. Equalize total generator and verifier compute. Include false-positive and false-negative test cases, not only easy structural checks, and measure confirmed task success alongside diagnostic precision and coverage.

A second experiment should distinguish clean-session replay on the adapted task, cross-model replay, and new-task-family generalization. All three are useful but answer different questions. Count binary selection queries in the search budget and reserve confirmation evidence that never drives test escalation.

The strongest directly reusable engineering rule is to write every runtime fix back into the exported candidate and rebuild it in a clean environment. The risky rule is to equate surrogate agreement with correctness. These are Everdict proposals, not implemented behavior; the paper's own transit example shows why both the generator and its independently written tests need external evidence.

## Sources and reproduction boundary

The review covers the complete v3 text and prompts, five result figures, ablations, iteration analysis, and the full case study. No model runs or astronomy experiments were independently reproduced. Reported gains support task-conditioned artifact evolution with restricted oracle feedback, while new-task generalization, fully oracle-free operation, and several causal explanations remain untested.
