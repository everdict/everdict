# R17 — Agentic Harness Engineering: predictions, component edits, and regression blindness

Agentic Harness Engineering (AHE) evolves a coding agent's external harness while keeping the foundation-model identity fixed. It combines editable component files, layered trajectory analysis, and a manifest predicting which tasks an edit will fix or endanger. Its most useful result for Everdict is both positive and cautionary: structural edits improve outcomes, but the evolving agent predicts regressions poorly and beneficial components do not add linearly. This note follows arXiv 2604.25850v4.[^1]

## Problem and relation to other evolution methods

A coding agent can fail because its prompt is vague, a shell command times out, a useful warning is buried, or an output is deleted after successful validation. These are different mechanisms. Improving only the prompt leaves many of them unchanged; allowing arbitrary edits without a clear boundary can instead change the evaluator or resource budget and invalidate the comparison.

AHE connects harness engineering and agent-computer interfaces with reflective optimization, ACE-style playbooks, training-free feedback methods, and executable agent/program search. Its contribution is an explicit action space plus observability of both execution and edit decisions. Compared with Meta-Harness's flexible inspection of a history filesystem, AHE supplies an overview, per-task analyses, and trace drill-down, then checks predictions recorded before the next evaluation. These are different feedback interfaces, not mutually exclusive principles.[^2]

## Seven editable surfaces and protected infrastructure

The NexAU substrate exposes system prompts, tool descriptions, tool implementations, middleware, skills, subagent configurations, and long-term memory as file-level components. The seed has a shell tool and no middleware, skills, or subagents. Each logical edit is committed separately for inspection and rollback.[^3]

The evolver may edit the harness workspace; run records, tracer, verifier, and model configuration are read-only, and the seed system prompt cannot be deleted. Those restrictions preserve the intended experimental variable. They do not mean that file separation makes behavioral effects independent: a tool change can alter which prompt instructions are meaningful, and a middleware warning can compete with memory for attention.

An illustrative Everdict mapping is to separate a changed procedure from its completion checker. The candidate may improve how it produces an artifact, while the checker determines whether the result meets the frozen requirement. Letting the same candidate rewrite that requirement would test a different objective.

## Layered evidence and the iteration

Each task receives multiple rollouts. Agent Debugger groups traces for the same task, explores message-level files, and writes a report identifying failures or successful patterns. A benchmark overview links those reports. Both raw and lightly cleaned traces remain available to verify the summaries. This preserves diagnostic detail while providing a manageable entry point.[^3]

The outer iteration runs the current harness, cleans traces, attributes the previous edit manifest against observed task deltas, rolls back rejected changes, distills the evidence, proposes new edits, and commits the new manifest. Predictions include supporting evidence, a root-cause hypothesis, the target component, expected fixes, and tasks at risk of regression. An initial exploration process seeds reusable skills from framework code and public references; later rounds may remove them.

A manifest makes predictions falsifiable, but agreement with next-round deltas is not by itself causal attribution. Several edits may ship together and stochastic outcomes may change. A component ablation or targeted matched test supplies stronger evidence about one edit's effect. The distinction matters when deciding whether a remembered explanation should guide later generations.

## Operating point and experimental identity

The reference campaign runs ten iterations over all 89 Terminal-Bench 2 tasks, with two rollouts per task, a one-hour task timeout, and 96 concurrent rollouts. Harbor dispatches/verifies tasks in fresh E2B sandboxes. The code agent uses GPT-5.4 high, temperature 0.7, top-p 0.95, a 200k context limit, and up to 300 model turns. The campaign takes roughly 32 hours.[^4]

The main setup says the role agents share GPT-5.4 at high reasoning, but Appendix A's configuration table gives the Evolve and Explore agents xhigh. The fixed model family therefore does not imply identical reasoning settings across roles. Use the configuration snapshot for reproduction and retain the inconsistency rather than assuming all calls had the same budget.

Pass@1 averages binary outcomes across rollouts; it is not best-of-two success. Infrastructure exceptions and timeouts count as failures. Token means exclude aborted trials to avoid truncated usage, so numerator and cost denominator cover different outcome populations. A reported successes-per-million-tokens ratio consequently needs this exclusion policy alongside it; it is not complete campaign cost.

## Main results on the optimization benchmark

The selected best harness reaches 77.0% from the seed's 69.7%, a gain of 7.3 percentage points. The comparison panel reports Codex 71.9%, Training-Free GRPO 72.3%, and ACE 68.9%. The automated baselines start from the same seed, but the methods have different editable surfaces; the comparison tests the full methods rather than isolating observability alone.[^5]

The difficulty breakdown is informative. AHE reaches 100% on four Easy tasks, 88.2% on 55 Medium tasks, and 53.3% on 30 Hard tasks. Codex's Hard result is 56.7%. Most of the benchmark is Medium, so optimizing the macro score can prefer changes that help Medium even if they sacrifice some Hard performance.

Search and the reported best Terminal-Bench result use the same 89 tasks. This is improvement on the optimization benchmark, not held-out confirmation within Terminal-Bench. The separate transfer experiments provide broader evidence, but only one ten-iteration campaign is reported; the full search's run-to-run variability is not established.

## Transfer to a new benchmark and different executors

The frozen harness transfers to SWE-bench Verified without further evolution. Its reported aggregate is 75.6% versus seed 75.2%, with mean completed-trial tokens 461k versus 526k, about 12% lower. ACE and TF-GRPO report 74.6%/74.2% and 679k/582k. The success gain over the seed is only 0.4 points; this is stronger evidence for the reported token reduction than for a large accuracy improvement.[^6]

Some repositories improve or tie while others regress. The table lists 500 tasks overall, but its seven displayed repository counts sum to 460, leaving 40 tasks unexplained in that breakdown. Do not reconstruct the overall average from those rows as though coverage were complete. The text's suggestion that small-repository regressions reflect variance is an interpretation, not a demonstrated significance result.

On the same Terminal-Bench tasks with other executors, DeepSeek V4 Flash changes from 51.7 to 61.8, Qwen 3.6 Plus from 56.2 to 62.5, and Gemini 3.1 Flash Lite from 36.5 to 41.6. GPT-5.4 medium and xhigh each gain 2.3 points. These establish transfer across the tested model/settings, while retaining the already optimized task set. The non-monotone gains across reasoning effort also reflect a timeout/step budget tuned for high; more reasoning can consume the fixed wall-clock allowance.

## Component ablations and non-additive interactions

The paper inserts one evolved component at a time into the seed while leaving the other layers unchanged.[^7]

| Variant | Overall pass@1 | Hard-task pass@1 |
|---|---:|---:|
| Seed | 69.7% | 51.7% |
| Evolved memory only | 75.3% | 63.3% |
| Evolved tool only | 73.0% | 46.7% |
| Evolved middleware only | 71.9% | 50.0% |
| Evolved system prompt only | 67.4% | 46.7% |
| Complete evolved harness | 77.0% | 53.3% |

The memory contains twelve boundary-case lessons. The tool becomes a large shell implementation that surfaces contract hints and protects validated outputs. Middleware adds completion checks and risk reminders. The prompt's general rules depend partly on those supporting mechanisms, explaining why transplanting the prompt alone can fail to reproduce the full system.

The three positive individual gains sum to 11.1 points, exceeding the full system's 7.3-point gain. This is evidence of non-additivity, not a license to sum success rates as independent effects. In particular, repeated closure checks can consume time, and memory alone performs better on Hard tasks than the full harness. A full interaction study would require more combinations than these single-component insertions.

## What the discovered edits actually do

The qualitative cases trace four useful edit families. Early edits add contract extraction/validation guidance and expose a shell timeout parameter, reducing truncation of long setup commands. Later edits mark output files and roots protected after a successful final check, so cleanup does not destroy the deliverable. The initial override can still permit a reset, requiring renewed validation.[^8]

Subsequent changes protect generator entrypoints and add middleware that notices shallow checks, repeated failing retries, budget-consuming commands, or use of an unofficial interface where the task names a required one. Finally, the tool makes selected destructive post-success operations non-overridable, and warnings move into the next model turn so they are less easily missed.

The case studies cover database WAL recovery, path tracing, MCMC sampling, and a Git webserver. They illustrate how an agent can reach a valid state and then invalidate it, or verify a proxy that misses the actual requirement. They do not prove that a heuristic shell guard catches every equivalent command or that all inferred task contracts are correct. Such mechanisms need their own behavioral testing before use as platform invariants.

## Prediction quality: fixes are easier to anticipate than regressions

Across nine next-round checks, mean fix precision is 33.7% and recall 51.4%, compared with random baselines 6.5% and 10.6%. Prediction is informative but far from perfect: many named fixes do not materialize, and nearly half of actual fixes are not anticipated.[^9]

Regression precision is 11.8% and recall 11.1%, versus random baselines 5.6% and 5.4%. The appendix's cumulative accounting reports 43 regression predictions, five correct, and 40 unpredicted regressions. Its cumulative precision 11.6% differs slightly from the mean-round 11.8% because aggregation differs. The important result is that most regressions remain unforeseen.

This directly challenges adopting a candidate because its explanation sounds well targeted. A proposer can articulate benefits while missing collateral damage. Predicted at-risk tasks are useful for selecting additional tests, but they cannot define the entire regression set; otherwise the system tests only risks it already understands.

## Pseudocode and other reporting limitations

Algorithm 1 evaluates H(t−1), then creates H(t), yet the best-candidate assignment appears to attach the previous rollout score to H(t). Read literally, that is an indexing mismatch. This note does not establish that the released implementation has the same bug; it flags that the pseudocode alone is insufficient to verify evaluated-artifact identity. Everdict should bind every score to the exact bytes that actually ran.[^3]

The study covers two coding/terminal task surfaces, one main evolution operating point, and selected alternate executors. It does not isolate every evidence-layer contribution with a full factorial study or demonstrate safe unrestricted self-modification. File-level rollback can also interact with later dependent edits. The paper describes the framework as a controlled research prototype, with long-term cleanup and stronger misuse prevention still incomplete.[^10]

## Implications and a proposed Everdict experiment

Use a change manifest as a driver-produced hypothesis record: evidence identifiers, changed component, predicted benefits, and possible regressions. Preserve it before evaluation, then compare predictions with observed outcomes. Keep that assessment as evidence rather than giving the driver's narrative authority to adopt a candidate or rewrite the evaluator.

Compare a driver with and without explicit prediction/feedback under equal total budgets and the same train/select/confirm split. Measure confirmed gain, calibration of predicted fixes/risks, unanticipated regressions, and time spent on redundant checks. Add component and selected pairwise ablations when edits interact. A candidate's aggregate gain should be accompanied by task-family regressions relevant to the campaign's declared requirements.

For Everdict's first loop, bind manifest, advice digest, candidate bytes, model settings, and evaluation artifacts. Roll back or reconstruct an immutable candidate from declared edits rather than attaching an old score to the post-edit workspace. The paper's strongest evolution lesson is to make an edit's expectations inspectable while accepting that those expectations are incomplete; independent confirmation remains necessary.
