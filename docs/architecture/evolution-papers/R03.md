# R03 — Anthropic's complete guide to building skills

This entry is an **authoring guide**, not a research paper or an experimental optimizer comparison. The substantive source is Anthropic's linked PDF, rather than only the short announcement. It explains how to package procedural knowledge, make a skill activate appropriately, test its behavior, and revise it from failures. Its numerical examples are suggested targets or illustrations, not measured benchmark results.[^1]

## Purpose and conceptual background

A skill packages instructions for a repeatable workflow so the agent does not need the same domain procedure explained in every conversation. The guide distinguishes three common purposes: creating documents or assets, automating multi-step workflows, and improving the use of an MCP integration. The shared question is what the user should accomplish consistently.

MCP provides access to a service and its operations; a skill describes how to combine those operations for an outcome. Connecting a project tracker does not by itself teach good sprint planning. The skill can explain which information to collect, how to reason about dependencies, and what to validate before writing the result. It remains dependent on the environment, available tools, and permissions.[^1]

## Packaging and progressive disclosure

The basic bundle has a required Markdown instruction file with YAML metadata and optional scripts, references, and assets. Metadata describes identity and when the skill is useful. The main body contains operational instructions; linked resources provide deeper detail when needed. This three-level disclosure limits initial context consumption while keeping specialized material available.[^2]

The consequence for evolution is that **activation text, procedural content, and executable resources are separate editable surfaces**. Improving the body cannot help if the skill is never loaded. Expanding a description indiscriminately may increase false activation. Moving detail into a reference can reduce context cost while making that detail less likely to be read. Each change therefore needs a behavioral measurement appropriate to the layer it affects.

The guide recommends explicit compatibility and dependency information, clear parameterized scripts for mechanical operations, and bundles that coexist with other skills. Its naming and upload conventions describe the guide's publication setting; they should be checked against current runtime documentation before being treated as today's installation procedure. This note is an analysis of the guide, not a current API migration manual.

## Designing a skill from a concrete workflow

Begin with two or three concrete use cases: the user's request, required operations, relevant domain knowledge, and expected result. Write a description that combines what the skill does with recognizable conditions for using it. In the body, specify steps, dependencies, expected outputs, and recovery behavior. Link to the exact reference material needed at the relevant step.[^2]

For an explanatory example, a report-generation skill could require collecting a fixed input schema, validating units and missing values, generating a draft, checking required sections, and repairing only the failing portions. A helper can validate the schema deterministically; the model can handle interpretation and prose. The distinction avoids treating a fluent final report as proof that every data precondition was satisfied. This example illustrates the guide's method rather than a reported trial.

## Five workflow patterns

| Pattern | Principle | Failure that needs testing |
|---|---|---|
| Sequential orchestration | Preserve step ordering and pass identifiers between stages | Later writes use missing or wrong earlier outputs |
| Multi-service coordination | Make handoffs and intermediate artifacts explicit | Each service works individually but the combined workflow fails |
| Iterative refinement | Check quality and repeat targeted repairs with a stopping condition | Endless revision or polishing that leaves factual errors |
| Context-sensitive tool choice | Choose a route using stated task conditions and fallbacks | Routing by superficial keywords selects the wrong capability |
| Domain-specific procedure | Encode specialized checks before consequential operations | A generic workflow bypasses a necessary domain constraint |

These are observed authoring patterns, not five algorithms compared in a controlled experiment. The failure column is this review's interpretation of what each pattern implies for evaluation.[^3]

## Testing, evidence, and iteration

The guide separates **triggering**, **functional behavior**, and **performance versus a baseline**. Trigger tests include obvious requests, paraphrases, and unrelated requests that should not activate the skill. Functional tests check final output, tool behavior, recovery, and edge cases. Baseline comparisons use the same task with and without the skill, recording consumption and user corrections as well as completion.[^4]

Suggested checks include 10–20 activation queries and repeated runs of a request. A 90% trigger target is explicitly aspirational. The example contrasting 12,000 tokens without a skill with 6,000 with one is illustrative, not an empirical estimate of expected savings. The guide also says its skill-creator assistant does not itself execute automated suites or produce quantitative evaluation results. Generating a proposed test case must not be recorded as passing it.

Iteration should target the observed failure layer. Under-triggering suggests missing applicability information; over-triggering suggests overly broad descriptions or missing exclusions. A loaded skill that produces wrong outputs needs instruction, dependency, or error-handling changes. A disconnected MCP service requires an infrastructure repair rather than a stronger sentence in the skill. Excessive context suggests selective loading and moving detail to linked resources.[^3][^4]

## Related research and evidential limits

The earlier Anthropic Agent Skills engineering article supplies the packaging rationale. SkillsBench tests whether curated skills help; SkillRouter and SkillRet examine discovery; EvoSkill, Trace2Skill, SkillGrad, and SkillOpt automate the revision loop. WikiSkill organizes the accumulated experience used to propose those revisions. The guide makes the artifact and authoring workflow understandable but cannot establish the relative effectiveness of these optimizers.

There is no experimental dataset, trained model, randomized control, ablation table, or significance analysis in this resource. Its practical advice derives from product experience and examples. File-format portability also does not guarantee behavioral portability when tools, model capabilities, or execution dependencies differ. A well-written skill can still be unnecessary, incorrectly activated, or harmful in combination with another skill.

## Everdict changes and a concrete authoring baseline

Use the guide to define an interpretable baseline candidate: a narrow activation description, explicit workflow, linked references, and executable checks where appropriate. Pin the whole bundle and required capabilities. Keep tests of discovery, execution, and task utility distinct so an optimizer can identify which layer needs repair.

For a first comparison, hold the body fixed while evolving the description, then hold the description fixed while evolving the procedure. Add unrelated requests, paraphrases, missing dependencies, and realistic exceptional inputs. Finally evaluate the combined candidate under the same total context and execution budget. A useful result is improved task utility with acceptable false activation and cost, not merely compliance with a file template. This is a proposed Everdict evaluation derived from the guide.
