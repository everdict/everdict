# R05 — HarnessX: compositional harness and model evolution

HarnessX makes an agent harness a structured object whose components can be replaced and evaluated. Its AEGIS procedure evolves that harness from traces; a further experiment combines harness changes with model reinforcement learning. The most important qualification is that **all reported gains are measured on the same tasks used for evolution**. Its peak scores demonstrate adaptation-set optimization, not confirmed generalization to unseen tasks.[^1]

## Problem, background, and the evolving object

An agent's behavior depends on more than the model prompt. Context assembly, memory, tools, recovery, budgets, and execution environment can determine whether it succeeds. If those behaviors are tangled in application code, a proposer must rewrite a large system to make a small change. HarnessX supplies a compositional representation so changes can target an identifiable component.

The harness separates model-role configuration from behavioral configuration. Behavior consists of ordered processors attached to lifecycle hooks, plus shared resources such as the tool registry, workspace, sandbox, and tracer. The paper organizes the design space into nine dimensions: model selection, context assembly, memory, tools, environment, evaluation/reward, control, observability, and training bridge. This taxonomy describes possible responsibilities; it is not evidence that every dimension can safely be mutated under the same evaluation authority.[^2]

## Processor algebra and its limits

A processor consumes an event and can pass it through, transform it, split it, intercept it, or interrupt execution. Eight hooks cover task start/end, step start/end, and before/after model and tool calls. Hook contracts restrict which fields may change. For example, task start can affect the system prompt, tool hooks can transform tool inputs or results, and task/step end are read-only. Singleton groups and ordering metadata constrain composition.[^2]

The key idea is to make an edit like “insert a context-cleaning processor before the next model call” representable without replacing the whole harness. Equal input/output event types preserve pipeline compatibility. They do **not** prove that a new processor preserves the meaning of the task: validly typed context removal can discard essential evidence, and a well-formed tool wrapper can still change results incorrectly.

## AEGIS: from trace to candidate

The four stages use the same meta-model and share the trace store. The **Digester** compresses task executions into outcomes, failure categories, implicated components, and evidence excerpts linked across rounds. The **Planner** maps unresolved failure groups and prior edits into possible incremental or structural interventions. The **Evolver** produces typed edits and a change manifest. The **Critic** compares claimed effects with traces and can request one revision before recommending an ordering of candidates.[^3]

The manifest records candidate identity, edit type, changed files, capability evidence, predicted affected tasks, and an attribution signature: an observable trace feature that should appear if the mechanism actually runs. New processor code needs a smoke test. A deterministic gate then checks manifest completeness, normalized configuration, build/smoke results, and regression on previously passing tasks. Upstream stages can stop early when no useful change is available.

For an explanatory example, repeated failures after large search results might motivate summarization at the model-input hook. The manifest would predict fewer context-related failures and identify the processor invocation in the next trace. A passing syntax check would show the processor runs; paired task results would still be needed to show that it preserved the evidence required for correct answers. A trace signature confirms intervention delivery, not the intervention's causal benefit by itself.

## Global search versus variant isolation

The default evolves a single harness across all tasks. A variant-isolation alternative maintains several harnesses and routes a task toward the variant with the best prior success on its cluster. An edit that helps one group but hurts another can create a new variant rather than overwrite the shared harness. Regression checking is then scoped to the tasks assigned to the edited variant.[^3]

This resembles preserving specialized evolutionary niches: a useful behavior need not win on every task. But routing itself becomes part of the system. Success on repeatedly observed task clusters does not establish routing quality on unseen requests, and variant-specific tests do not prove safety when routing or shared resources change. The evaluator must eventually assess the complete routed candidate.

## How harness-model co-evolution works

The co-evolution extension stores scored trajectories in a bounded, recent replay buffer, tagged with the model and harness versions that produced them. AEGIS uses those traces for symbolic edits. GRPO uses them for weight updates, grouping trajectories by **task identity across harness versions**. Within a group, the normalized advantage is the trajectory reward minus the group mean, divided by group standard deviation plus a small stabilizer.[^4]

Different harness versions create strategic diversity beyond random sampling of one policy. During training, each trajectory's token probabilities are computed in the prompt/tool context of its generating harness. Cached behavior probabilities support importance ratios and clipping for older trajectories. This reuses rollouts already collected for harness adaptation, but forward passes and gradient updates still cost compute. A recent FIFO buffer and clipping limit drift heuristically; they are not a proof of unbiased off-policy learning.

## Experimental design

The main task models are Claude Sonnet 4.6, GPT-5.4, and Qwen3.5-9B; the meta-agent is Opus 4.6. The static baseline is already a manually composed, benchmark-specific harness. Runs use up to fifteen rounds, early stopping after three rounds without a shipped edit, and a meta-agent token budget of 100–175 million depending on benchmark. Appendix hyperparameters list four proposals per round and three seeds per cell.[^5]

| Benchmark | Evaluated subset | Outcome |
|---|---|---|
| GAIA | 103 tasks across three difficulty levels | Exact answer match |
| ALFWorld | 134 valid-unseen tasks | Goal completion |
| WebShop | 100 fixed sampled tasks | Attribute match |
| τ3-Bench | Retail, airline, telecom | Rule-compliant completion |
| SWE-bench Verified | 55 sampled tasks | Patch resolution |

The main metric is pass@2: a task counts as solved if either of two attempts succeeds. The full fixed task set is re-evaluated each round. “Valid-unseen” is the ALFWorld split's name relative to the original benchmark training; because HarnessX adapts on those same tasks, it is not a held-out set for this optimizer. Peak selection and repeated exposure both matter.[^5]

## Main results and the peak-versus-final distinction

Table 4 reports initial-to-**peak** changes. Across its fifteen model/benchmark cells, the mean gain is about 14.5 percentage points. Representative cells are:[^5]

| Condition | Initial | Peak | Change |
|---|---:|---:|---:|
| ALFWorld, Qwen3.5-9B | 53.0 | 97.0 | +44.0 points |
| WebShop, Sonnet 4.6 | 60.0 | 76.0 | +16.0 points |
| GAIA, GPT-5.4, global | 73.8 | 73.8 | 0.0 points |
| SWE-bench subset, Sonnet 4.6 | 76.4 | 87.3 | +10.9 points |
| τ3 domain average, Qwen3.5-9B | 93.5 | 94.6 | +1.1 points |

The global GAIA/GPT run peaks at 73.8 but ends at **49.5**. Its regression gate therefore does not prevent all long-run degradation. Binary pass@2 outcomes and a noise threshold can hide small probability changes that accumulate across edits. This observed failure is more informative than treating the gate's intended “no regression” property as a universal guarantee.

## Component comparisons and failure analyses

On the same GAIA/GPT setting, variant isolation reaches both peak and final 87.4, using 107.8 million tokens versus 143.7 million for global search. The result supports specialization under the tested routing and repeated task exposure. It does not establish monotonically improving population performance on new tasks.[^5]

With variant isolation fixed, the four-stage AEGIS and a single-session Claude Code SDK evolver use the same Opus model and infrastructure. Final scores are 87.4 versus 86.4, a gap the authors regard as within sampling uncertainty. Tokens are 107.8 million versus 123.1 million. The evidence supports an efficiency benefit from the staged design more clearly than an accuracy benefit. The paper attributes this to compressing roughly ten million raw trace tokens into roughly ten thousand summary tokens; compression's causal contribution would benefit from a dedicated ablation.

Co-evolution uses Qwen3.5-9B on GAIA and WebShop with a four-round replay window, learning rate 10^-6, clip 0.2, five training steps per round, and **zero KL coefficient** in the experiment despite the general objective including a KL term. Peak GAIA rises from 37.4 with harness-only evolution to 41.7 with co-evolution; WebShop rises from 49.0 to 54.0. Final values also improve, 36.4→39.8 and 46.0→50.0 respectively. These comparisons do not fully isolate a matched model-RL-only baseline.[^4][^5]

Qualitative failure analyses examine reward exploitation, loss of previously successful behavior, and under-exploration of structural changes. The paper's “operational mirror” to reinforcement learning is a conceptual mapping of symbolic edits, traces, and feedback; it does not inherit all theoretical guarantees of a formal learning algorithm.

## Related research and limits

Prompt search such as GEPA changes instructions; Meta-Harness and Agentic Harness Engineering broaden the editable code; archive-based systems preserve alternative candidates. HarnessX contributes an explicit component representation and explores routing plus a shared training buffer. WikiSkill's curated knowledge can be a complementary proposal aid, but was not part of the demonstrated HarnessX combination.

The authors explicitly acknowledge no held-out generalization experiment, peak-selection bias, discrete text actions only, dependence on a capable closed meta-agent, limited SWE/domain subsets, and the operational burden of controlling both model training and harness changes. Large adaptation gains should be read with those constraints, rather than as expected production improvements.

## Everdict experiment and architectural implications

Everdict should first test structural edits under a fixed model: context assembly, recovery, and tool wrappers are plausible candidate components. Record changed components and expected trace signatures before execution. Preserve adoption authority, budget accounting, and confirmation evidence outside the mutable candidate, even if an external framework's taxonomy includes evaluation among harness dimensions.

Compare one global harness with a bounded archive and a frozen router. Use separate development, selection, and confirmation tasks, and report initial, selected, final, and confirmed scores rather than peak alone. Measure whole-run cost and regression probabilities over repeated attempts. Only after this works should a separate experiment add model training with explicit model/harness/trajectory provenance and a model-only control. This proposed sequence tests whether HarnessX's adaptation mechanisms produce transferable improvement in Everdict.
