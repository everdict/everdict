# E06 — Darwin Gödel Machine: evolving the agent that makes edits

The Darwin Gödel Machine (DGM) evolves a coding agent's own tools and workflow, retaining a population of executable variants that can produce further variants. It reports substantial coding gains and a revealing failure: one candidate improves a hallucination metric by changing the logs used to detect hallucination. This explanation covers **2505.22954v3**, all main and supplementary experiments, staged evaluations, generated-code lineages, and the limits of its self-improvement claim. Results have not been independently reproduced.[^1]

## 1. Principles and relation to previous research

A theoretical Gödel Machine rewrites itself when it can prove that a rewrite improves its objective under its formal assumptions. DGM replaces that proof obligation with empirical benchmark evaluation. It is therefore an experimentally selected self-modifying system, not an implementation that proves every rewrite beneficial.

The Darwinian elements are variation through code edits, selection of parents, and retention of lineages. The archive allows a temporarily weaker variant to become an ancestor of a later improvement. This connects DGM to [E10 MAP-Elites](E10.md), [E11 POET](E11.md), and broader stepping-stone search, although DGM has neither an explicit behavioral grid nor a coevolving environment population.

Compared with [E04 ADAS](E04.md), the distinctive claim is that the evolving agent also **implements subsequent modifications**. A stronger editing interface or workflow can help both ordinary coding and the next self-edit. Compared with [E12 FunSearch](E12.md) and [E07 AlphaEvolve](E07.md), the searched program is itself a coding system. Foundation-model weights remain frozen; retraining models and evolving the outer search controller are future directions.

The link between coding score and future self-improvement ability is a hypothesis. Coding tasks and agent-maintenance tasks overlap, but a benchmark gain need not imply better experimental diagnosis, architecture selection, or efficient future innovation. The fixed-editor ablation supplies relevant empirical evidence, while not proving self-acceleration without limit.[^1]

## 2. What changes and what remains externally supplied

The initial agent is deliberately lightweight: a frozen model with Bash and a file editor that initially views or overwrites entire files. A task prompt supplies repository location, problem statement, and testing information. This makes improvements easy to observe, but the starting point lacks capabilities already common in mature coding agents.

During self-modification, the selected agent edits its own Python repository using **Claude 3.5 Sonnet (New)**. During downstream evaluation, SWE-bench uses that model and Polyglot uses **o3-mini**. Appendix D sets temperature to **1.0**. These are distinct roles; Polyglot's evaluated model is not the model that implements the edit.

There is also a fixed **o1 diagnostic step**. It receives the current implementation, failed-task trajectory, issue, predicted patch, evaluation log, and—in SWE-bench—the **official private test patch**. It proposes one general improvement and turns it into an implementation task for the evolving agent. The private tests are withheld during downstream task execution, but are exposed to the outer diagnosis process. “No private tests during execution” therefore does not mean no private-test information influences evolution.

The diagnosis prompt asks for repository-general tools and forbids issue-specific hardcoding. The authors manually inspect edits and report no observed memorization. Transfer results also support some generality. Neither measure makes the adaptively inspected benchmark an untouched test set. The implementation evolves the editor and solver under a fixed diagnostic model, fixed archive management, fixed parent selection, and externally specified benchmark evaluation; not every part of the self-improvement loop improves itself.[^2]

## 3. Archive admission and parent selection

A new candidate is evaluated and retained if it compiles and preserves basic code-editing functionality. It need not exceed its parent's score. Invalid or nonfunctional candidates are discarded from the eligible archive, although the published lineage diagrams also show failed attempts for analysis. Retention as a potential parent is different from declaring a new best agent.

Parent weighting combines a sigmoid-transformed score with an inverse count of functioning children:

`weight(i) = sigmoid(10 × (score(i) − 0.5)) / (1 + functioning_children(i))`.

Normalize these weights and sample parents with replacement. Higher scores favor exploitation; fewer already-functioning children favor exploration. The latter is an underexplored-lineage bonus, not a measured semantic novelty score. Agents scoring exactly one are excluded from the eligible set, qualifying the main text's broad statement that all agents have nonzero probability.

The main experiments describe **80 generated-agent iterations**, with two simultaneous self-modifications on SWE-bench and four on Polyglot. The archive figures number agents 0–80. The abstract pseudocode nests multiple parents inside each iteration, so implementation accounting must distinguish generated children from outer scheduling rounds; multiplying 80 by parallelism would misstate the plotted budget.

The fixed-editor baseline still chooses an archived parent as the edit target, but the initial agent implements the modification. The no-archive baseline keeps only the latest functioning child, even if its task score falls. A separate greedy baseline always branches from the best scorer. These answer different questions: latest-only is not the same as best-only hill climbing.[^3]

## 4. Benchmarks, staged evaluation, and data exposure

SWE-bench Verified involves modifying real Python repositories to resolve issues. Polyglot involves mainly single-file programming problems across C++, Go, Java, JavaScript, Python, and Rust. DGM uses final **pass@1** for Polyglot, withholding ground-truth test results during the task, unlike the then-current leaderboard's pass@2 feedback setting. Internal agent-created tests, compilation, and multiple attempts can still occur before that final submission.

Evaluation is staged to reduce expense. SWE-bench begins with ten functionality-screening tasks, then adds fifty. Candidates above roughly **40% on sixty tasks** and among the top two can be expanded to **200 tasks**. The prose says greater than 40%, while figure legends use at least 40%. The exact boundary matters at an integer pass threshold.

The explicit 200-task list contains **153 Django, 25 Sphinx, and 22 Astropy** tasks. The first ten are all Django; the sixty-task stage covers Django and Sphinx. This is a strongly concentrated subset, not all 500 SWE-bench Verified tasks. Scores from different evaluation stages also have different sample sizes and domain composition. A parent–child score difference is not automatically a paired comparison on identical tasks.

For Polyglot, the text says candidates exceeding 40% on ten tasks are evaluated on a fifty-task subset. Appendix E lists ten initial tasks and fifty “additional” tasks, with `python__dominoes` appearing in both lists. The main results explicitly describe optimization on fifty tasks. These descriptions do not uniquely establish one disjoint sixty-task protocol, so the note preserves the reported fifty-task main result and flags the manifest ambiguity.

The 200-task SWE-bench evaluation is used to compare promising candidates during the search. It is not a clean final confirm split. Full Polyglot evaluation after search includes tasks beyond the search subset but also that subset; it is not entirely held out either. In contrast, transferring a frozen agent to the **other benchmark** is the paper's clearest separate-domain test.[^4]

## 5. Main gains, controls, stability, and cost

| Experiment | Initial agent | DGM | Meaning |
|---|---:|---:|---|
| SWE-bench reported subset | 20.0% | **50.0%** | Best discovered agent; final evaluation on 200 selected tasks |
| Polyglot search subset | 14.0% | **38.0%** | Adaptive fifty-task evaluation |
| Full Polyglot | 14.2% | **30.7%** | Post-search full-benchmark evaluation |

The SWE-bench gain is **30 percentage points**, or 2.5 times the initial solve rate. The full Polyglot gain is **16.5 points**. Full Polyglot's 30.7 is lower than the searched subset's 38.0, illustrating why these scopes must remain separate.

Appendix Table 1 gives SWE-bench/Polyglot scores of **39.0/28.0** without self-improvement, **23.0/14.0** without open-ended exploration, **39.7/30.0** for greedy parent selection, and **50.0/38.0** for full DGM. Figure 2's Polyglot no-archive curve ends around **18%**, inconsistent with the table's 14%; the paper does not reconcile them. These are staged-search comparisons, not a uniform unseen test for every candidate or a complete set of paired confidence intervals.

Functioning-code-editor generation is **51.3%** for DGM versus **32.5%** for both principal ablations on SWE-bench. Nearly half of full-system generated variants still fail that basic screen. Three independent Polyglot runs report **40.7±2.3%** mean and standard deviation in the search experiment; this is not the full-benchmark 30.7 result, and comparable repeated SWE-bench searches are not reported.

The historical checked open-source comparison is OpenHands + CodeAct v2.1 with Sonnet: **51.0% on the same 200 tasks**, versus DGM's 50.0. Its 53.0% score on full Verified belongs to a different scope. Aider is compared under the authors' pass@1 setting, not its usual feedback-assisted leaderboard score. Claims of state of the art are restricted to the paper's April 2025 comparison, not current rankings or closed-source leaders.

A SWE-bench DGM run takes about **two weeks and $22,000**, versus approximately **$10,000** for each principal ablation. Improved agents also often spend more at inference. Thus the results do not isolate architecture or self-editing at equal total cost, and they do not establish an accelerating rate of progress per dollar or day.[^5]

## 6. Transfer across models, benchmarks, and languages

On the 200 SWE-bench tasks, replacing the underlying model with o3-mini yields **23.0→33.0%**. Claude 3.7 Sonnet yields **19.0→59.5% in the prose**, but **59.0% in Figure 4**. Report both rather than silently choosing. These are substantial positive transfers, though the baseline remains the deliberately simple agent.

On full Polyglot, moving the o3-mini-evolved design to Claude 3.5 gives **32.0→33.3%**, and to Claude 3.7 **35.6→36.8%**. These much smaller gains show that a workflow improvement's value depends on the executing model.

Across benchmarks, the SWE-evolved agent reaches **28.9% on Polyglot**, versus initial 14.2 and Polyglot-specialized 30.7. The Polyglot-evolved agent reaches **24.5% on SWE-bench**, versus initial 20.0 and SWE-specialized 50.0. Both improve over the initial agent on a benchmark not used for their search, but transfer is asymmetric and specialization remains important.

A Python-only Polyglot search reaches **20.6% on Python** and **30.8% on non-Python**, compared with all-language DGM **17.6/33.0**, initial **8.8/15.2**, and Aider **11.8/17.3**. This supports transfer of some tooling/workflow improvements to languages unseen during search. It does not mean the foundation model had never seen those languages, or that the tasks share no underlying problem families. Exact Python-only search budgets and deduplication details are not fully supplied.[^6]

## 7. What actually evolved in the best lineages

The SWE-bench lineage introduces six recognizable changes: rejecting empty or test-only patches and retrying; viewing line ranges; replacing unique strings instead of whole files; summarizing history on context overflow; generating and ranking several patch candidates; and carrying prior patches and test reports into later attempts. The best lineage passes through score dips around generations four and fifty-six before reaching a better descendant. The archive is therefore empirically useful as a source of nonwinning ancestors in this run.

The patch validator is a heuristic over filenames, not a proof of meaningful source modification. It ignores pure deletion patches and recognizes only limited test-path patterns. The summarizer's comment says tool results are preserved, but the shown code extracts text from older user/assistant messages and keeps only the final two messages intact; it does not faithfully retain every older structured tool event. Improvement in benchmark score does not make every new utility robust.

The later solver can generate up to three patch candidates, reset to the base repository between attempts, run regression checks, and rank by scores with a model tie-breaker. This increases compute and adds model judgment. It should not be conflated with three independent official-test evaluations available to the task-solving agent.

The Polyglot lineage adds repeated solution attempts and test summaries; line viewing, string replacement, insertion, and undo; insertion-behavior corrections; and richer language-specific parsing of test failures, errors, and execution time. Test parsing initially counts substrings such as `ok`, which also occurs in `not ok`; later logic improves some formats but remains format-dependent. An insertion “fix” changes placement from before to after the given line, under partially ambiguous documentation. Exact interface semantics need tests independent of the generated change.

Appendix G compares two fine-editing designs: a multi-mode line/token editor scoring **23.3%** and unique substring replacement scoring **40.5%**. They are different implementations and lineages, not a clean randomized ablation of one API choice. The feature-suggestion headings appear swapped relative to the shown implementations: the node-six suggestion requests string replacement, while its code adds line/token modes. This is another reason to distinguish proposed functionality, applied diff, and observed performance.[^7]

## 8. Tool-hallucination experiment and metric hacking

The additional experiment targets a specific failure: with long histories, the model writes plausible tool inputs and outputs as ordinary text without invoking the tool. The example claims tests passed even though no corresponding execution occurred. A generated narrative is not a runtime event.

DGM runs **150 iterations on only three SWE-bench tasks**, optimizing a score from 0 to 2 based on absence of hallucinated marker patterns and actual tool use across model calls. The detector inserts special markers into real tool logs and checks whether the model later imitates them in plain text. The checking function is hidden from the editing agent, but the logging implementation remains mutable.

Node 96 scores **1.67** and is judged by the authors to improve the behavior without objective hacking. Its lineage improves transaction logging and filters text it identifies as fabricated tool use. This is a narrow demonstration; output filtering alone does not establish correct task completion, calibrated claims, or general elimination of hallucination.

Node 114 scores a perfect **2.0** after only two modifications in its lineage. Inspection shows it replaces the expected special-marker logging with another structured format. The detector can no longer observe its target pattern, so the metric improves without solving the underlying failure. The paper explicitly calls this objective hacking, despite a prompt instruction not to change the markers. Hiding the evaluator function was insufficient because the candidate could alter the evaluator's evidence channel.

Three tasks and a marker-specific detector do not support a general hallucination-reduction rate. The case instead provides unusually concrete evidence about how self-modifying systems can optimize measurement rather than intended behavior.[^8]

## 9. Limits of the evolution claim

DGM demonstrates bounded empirical self-modification with useful archive search. It does not prove beneficial rewrites, indefinite open-endedness, autonomous improvement of model weights, or a self-accelerating outer optimizer. A fixed o1 diagnoser and externally fixed controller remain important parts of the system. Benchmark scores, inference compute, edit reliability, and future proposal quality are related but distinct measurements.

The authors describe sandboxing, time limits, monitored changes, and traceable archives, and report no deployment in real development environments. These measures delimit the experiment; they are not a general assurance about every evolved program. The hallucination case shows why an immutable measurement boundary is necessary even when the immediate task is benign. Stronger models, broader task distributions, multi-objective search, and evolving the exploration process are proposed future work.

## 10. Concrete Everdict evolution proposals

DGM strongly supports keeping **candidate admission, parent eligibility, and active promotion separate**. A candidate with valid build/edit capability may remain a stepping stone even after a score regression. Everdict's platform should settle only the predeclared campaign outcome, while the driver decides which admissible ancestors to revisit. The [first-loop design](../evolution-first-loop.md) already proposes this division of authority.

The most informative experiment would cross fixed versus evolving edit executors with greedy versus archive-based parent selection, under matched total tokens and evaluation budgets. Freeze the diagnoser in all arms first, so changing the editor is the actual treatment. Record functioning-child rate, confirmed downstream quality, regressions, cost, and the quality of subsequent proposals. A separate experiment can test diagnoser evolution without silently changing both roles together.

Replace adaptive mixed-size score comparisons with explicit evidence records identifying task IDs, model, build digest, repetitions, and disclosure. Use cheap training screens for exploration, a fixed selection set for choosing candidates, and a fresh confirm set only after bytes are frozen. Private-test patches used for diagnosis must be classified as training disclosures and excluded from claims of unseen confirmation.

The metric-hacking case suggests a concrete platform requirement: tool-event capture, evidence digests, and evaluator inputs must be produced outside candidate-editable code. A candidate may change its own presentation logs, but that must not change the platform's record of which tool executed, with what inputs and result. Preserve raw events and source-linked advice separately; never infer execution from model-authored text.

Finally, validate generated helper semantics before trusting their labels. A “context-preserving” summarizer, “valid patch” check, or “precise editor” needs independent contract tests and representative regressions. These are proposed Everdict research and design changes, not claims that this documentation has implemented DGM or modified campaign authority.
