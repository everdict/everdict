# E12 — FunSearch: mathematical discoveries from program search

## Source, scope, and central result

Romera-Paredes et al., *Mathematical discoveries from program search with large language models*, published online in Nature in December 2023 and in its 2024 volume. This explanation covers the article, Methods, and Supplementary Information A–F: cap sets, admissible sets, online bin packing, Shannon capacity, the corners problem, ablations, repeated runs, and implementation. Records and prices below are historical claims of this publication, not a current leaderboard or a reproduction by Everdict.[^source]

FunSearch keeps a pretrained code model fixed and evolves executable functions. A human supplies a problem specification, a verifier/scorer, and usually an algorithm skeleton with one replaceable priority function. Generated functions receive execution feedback and enter a population used to generate the next functions. The output is both a solution and a program describing how to construct it. The strongest mathematical result is a new lower bound of 2.2202 on cap-set capacity; the practical experiment learns online packing heuristics that use fewer bins on specified distributions. Neither result means the model can autonomously establish arbitrary theorems or improve arbitrary software.

The distinctive development loop includes human interpretation: a discovered program exposes a symmetry; researchers verify that symmetry, change the representation to enforce it, and run search again. This representation change is a separate scientific intervention, not merely another mutation inside an unchanged evaluator.

## Prerequisites: why search over programs instead of answers

An enormous object may have a short generating rule. Listing hundreds of thousands of vectors gives little guidance for the next search, whereas a function that ranks vectors by repeated coordinate patterns can express a reusable construction. FunSearch searches this compressed representation. Its preference for concise code and the model's exposure to human code introduce a bias toward structured solutions. The paper relates this to Kolmogorov complexity, the length of a shortest generating program. It does not compute that quantity, prove optimal compression, or show that shorter code is always better.[^method]

There are three distinct components. The **proposal mechanism** suggests a priority function. The **construction algorithm** uses that function to build an object, retaining only feasible steps. The **evaluation mechanism** measures the resulting object's quality. For example, a priority function can prefer a vector for a bad reason, but the cap-set skeleton still refuses a vector that would create a forbidden triple. Validity and usefulness therefore come from different places.

This arrangement works especially well when execution is affordable, valid candidates receive graded scores, and a useful editable component can be isolated. A slightly larger set supplies more information than a bare incorrect/correct signal. General theorem proving is explicitly outside the paper's demonstrated scope because supplying an informative intermediate score is difficult. The LLM is a proposal distribution here; its verbal confidence is not the verifier.

## The evolutionary algorithm, step by step

The initial specification contains the execution entry point, supporting code, and an initial function. For the mathematical tasks the initial priority is constant; packing starts from best fit. A sampler chooses one island uniformly from a population of ten. Within that island, programs are clustered by their **per-input score signature**, not textual similarity. Two clusters are sampled with a softmax preference for higher aggregated scores, then one program is selected from each. The stated intent is to prefer shorter programs within a cluster.[^method]

The two functions are placed in a prompt as progressively better versions, followed by the header of a new version for the LLM to complete. This encourages combining ideas, but is not a guaranteed semantic crossover. Early in search there may be only one available cluster. Four completions are normally drawn per prompt at temperature 1.0 and nucleus probability 0.95. Executable descendants return to the originating island; prompts do not always contain the global best program.

Every four hours, the worst half of islands, ranked by their best scores, are cleared. Each receives the best program of a uniformly sampled surviving island. Surviving islands retain their populations. This allows separate lines of search and occasional propagation without retaining every island forever. Cluster temperature cycles from an initial 0.1 over a period of 30,000 registered programs; program-sampling temperature is 1.0. These are search choices, not correctness rules.

The default LLM is Codey, from the PaLM 2 family, without task fine-tuning. The system separates asynchronous samplers, evaluators, and the program database. Supplement Table E.2 specifies 15 samplers and 140 evaluators; the main description gives an approximate 150-worker example. Default cap-set evaluation has a 30-second timeout and 2 GB memory limit. Admissible sets use 120 seconds/5 GB, packing 300 seconds/5 GB, and larger graph experiments use substantially more resources.[^implementation]

The implementation description deserves two qualifications. Algorithm F.5 registers a program if **at least one** test input returns a usable score; failed inputs are omitted from its score dictionary. Thus registration does not itself establish all-input validity. Also the printed length-normalization formula uses negative lengths divided by their maximum, which would reverse the claimed short-program preference if applied literally to ordinary unequal positive code lengths. Algorithm F.14 constructs a header but its final concatenation refers to `implementation`. These are ambiguities in the presented formula/pseudocode, not verified defects in the released runtime. A reproduction should resolve them against executable code and retain the complete input manifest, including failures.[^implementation]

## Experiment 1: direct cap-set constructions

A cap set is a subset of vectors over arithmetic modulo three with no **three distinct** vectors summing to zero. Distinctness matters: three copies of any vector trivially sum to zero in this arithmetic. Geometrically the constraint excludes a complete three-point line. Let `c_n` denote the largest possible size in dimension `n`.

The skeleton enumerates vectors, calculates their priorities, and repeatedly takes the highest-priority remaining vector. After adding `x`, every vector completing a forbidden triple with `x` and an earlier member is blocked. Ties use lexicographic order. The evolving function does not need the growing set as an input; the fixed feasibility filter accounts for its current contents. This makes priorities a restricted search representation, while allowing every candidate vector rather than imposing the older construction restrictions.[^cap]

For dimensions 3–8, the reported best-known sizes were 9, 20, 45, 112, 236, and 496. FunSearch matches the first five and finds **512 in dimension 8**, a gain of 16 vectors. Supplement C also gives a function producing 1,082 vectors in dimension 9; this is an additional construction, not a claim that its size is the exact optimum.

The eight-dimensional result is rare: **4 of 140 independent experiments** find 512, roughly 2.9%. The histogram is dominated by substantially smaller sets. A new valid mathematical construction remains valuable even when discovery is rare, but a product promising reliable improvement must account for all unsuccessful searches.

Inspection exposes a structure in the 512 vectors: 128 have eight nonzero coordinates, 256 have four, and 128 have five. Equalities between reflected coordinate positions help characterize membership. Researchers use the code and the generated ordering to derive a direct construction, related in form to the six-dimensional Hill cap. The cleaned construction is a human analysis of the output; it is not evidence that the LLM supplied a proof or that the rule generalizes automatically to every dimension.

## Experiment 2: admissible sets and a change in representation

Cap-set **capacity** is `C = sup_n c_n^(1/n)`, an asymptotic growth rate. A finite construction establishes a lower bound, while an upper bound limits every construction. The article reports the previous lower bound 2.2180 and an upper bound 2.756. Improving the lower bound does not close that gap.[^admissible]

An admissible set is an auxiliary collection that tells existing mathematical constructions how to combine smaller cap sets. In the constant-weight setting, each vector has `w` nonzero entries and a different support, so the maximum possible number is the binomial coefficient `choose(n,w)`. Each triple must have a coordinate whose multiset is `{0,1,2}`, `{0,0,1}`, or `{0,0,2}`. `I(n,w)` means a full-size set; `A(n,w)` can be partial. These objects are construction ingredients, not interchangeable with cap sets themselves.

Starting without a symmetry restriction, FunSearch discovers `I(12,7)` and raises the capacity lower bound to 2.2184. Researchers notice that coordinates fall into four triples and that independent cyclic rotations within those triples preserve the resulting set. A symmetric **priority** alone does not guarantee a symmetric **constructed set**, because greedy filtering can break symmetry; the authors check the output explicitly.

They also run a further search using a small penalty for high-priority elements rejected by the construction. This makes the membership rule easier to inspect, and actually produces a longer function. Interpretability is therefore operationalized through alignment between ranking and membership, not simply code length. The new skeleton searches directly over symmetry generators. Each triple is represented by one of seven valid orbit types; its cyclic orbit has one or three members. A compact generator expands through products of those orbits into many vectors. Supplement D proves admissibility by checking pairs and triples from the same or different generators. This supplies a mathematical reason for the compressed search space, beyond visual pattern recognition.[^symmetry]

The restricted search finds `I(15,10)`, yielding at least 2.219486, and partial sets `A(21,15)` of size 43,596 and `A(24,17)` of size 237,984, yielding approximately 2.2200 and 2.2202. Figure 5 displays a truncated 2.2194 for the intermediate bound. Across five runs per setting, full `I(12,7)` appears in 3/5 and full symmetric `I(15,10)` in 2/5; all fifteen runs across the three settings in the statistical comparison improve the earlier 2.2180 bound. This stronger repeatability differs from direct 512-cap discovery.

## Experiment 3: online bin packing and generalization

Each arriving item must immediately be assigned to a bin with enough remaining capacity. Future items are unavailable. First fit chooses the first feasible bin; best fit chooses the feasible bin leaving the smallest gap. The evolving function scores the feasible choices and the fixed solver chooses the highest score. Evaluation measures percentage excess bins above the **L2 lower bound on the offline optimum**. This is not the exact optimal online policy, and a 0.03% excess does not prove universal optimality.[^packing]

OR training uses 20 generated instances of 120 items, uniformly sampled from `[20,100]`, with capacity 150. Selection uses a separate 20-instance validation set of 250 items. OR1–OR4 are four established test datasets, each containing 20 instances with 120, 250, 500, and 1,000 items. Therefore the larger sizes are not all unseen during selection: 250-item instances already occur in validation.

Weibull training and validation each contain five separate 5,000-item instances sampled from Weibull(45,3), clipped and rounded to integer sizes 1–100. Tests contain five 5,000-item instances, five 10,000-item instances, and **one** 100,000-item instance. The method selects heuristics on validation, then evaluates the test sets. The supplement excludes functions explicitly using the number of bins to encourage size generalization; this is an additional design restriction.

The table reports selected heuristics, not an average over all search runs. Across ten Weibull searches, the 10k test result is 0.44% ± 0.11% as reported in Supplement A.3, and every run beats both baselines. The supplement does not identify that ± quantity here as a confidence interval. OR and Weibull use separately evolved heuristics; these results are not evidence that a single policy transfers unchanged across the two distributions.

A readable OR heuristic strongly rewards nearly exact fits but avoids leaving gaps that cannot accommodate any future item. Since OR items are at least 20, a gap of 18 or 19 can be wasted permanently. An illustrated shorter formula is slightly worse than the best discovered heuristic. The visual explanation describes an observed strategy, not a worst-case competitive-ratio proof or a production scheduling experiment.

## Additional experiments: Shannon capacity and corners

A graph can describe symbol confusability in a noisy communication channel. Independent sets in its strong powers represent messages distinguishable with zero error; their growth rate defines Shannon capacity. FunSearch evolves priorities for greedy independent-set construction. For a seven-cycle to the fifth power it recovers the existing size 367 with a direct program. For the nine-cycle it produces one short program attaining known lower bounds 81, 324, 1,458, 6,561, and 26,244 for powers 3–7. For the eleven-cycle to the fourth power it improves the known independent-set bound from 748 to **754**. The first two are rediscoveries/simplifications, while the last improves a bound; none establishes every graph's exact capacity.[^other]

The corners problem forbids triples `(x,y)`, `(x+λ,y)`, `(x,y+λ)` with nonzero `λ`. The paper uses a combinatorial-degeneration formulation in a hypergraph: a C++ linear-programming checker determines feasibility, while the evolving function orders candidate vertices. Over the binary field, a size-137 auxiliary construction at dimension 4 raises the capacity lower bound from about 3.391 to the fourth root of 137, about **3.421**. Over the ternary field, size 53 at dimension 2 yields the square root of 53, about **7.280**, above 7. A size-370 construction at dimension 3 yields approximately 7.179, useful as another construction but weaker for the asymptotic bound. These are lower bounds derived through the formulation, not direct exact counts of all maximal corner-free sets.

## Ablations, solver comparisons, and cost

Five-run ablations on symmetric `I(15,10)` compare the full system with generating an ordered vector list instead of a priority function, using only the initial prompt, using one island, and using one parent per prompt. The full system finds the complete set in 2/5 runs; the one-parent variant in 1/5; the other variants in none. The full mean best-so-far score is strongest. “Without skeleton” still retains a greedy validity constructor, and “less diversity” retains score clustering inside its single island. These experiments isolate narrower changes than their labels may suggest.[^analysis]

StarCoder-15B replaces Codey in five runs: it does not find the full set, but still surpasses the earlier capacity bound. Hand-designed random AST mutations perform much worse; even beyond 50 million generated programs they plateau below a score deficit of −240. The result supports the usefulness of a code-trained proposal distribution against this particular mutation design, not the impossibility of all non-LLM search.

A CP-SAT comparison runs 2^10 assignments of ten randomly selected binary variables in parallel, at least 50 hours per solver instance. Without extra restrictions, SAT reaches `I(9,5)` and FunSearch reaches `I(12,7)`; handcrafted SAT constraints reach `I(11,7)`, while the discovered symmetry lets FunSearch reach `I(15,10)`. This combines representation and search differences and does not establish a hardware-matched superiority over every modern solver.

For roughly two million proposals, the supplement estimates 15 A100-40GB StarCoder workers plus five 32-worker CPU servers for two days, costing **$800–$1,400** and **250–500 kWh** under its historical cloud assumptions. This is a reproduction estimate using StarCoder, not the measured bill for every Codey run or for all 140 cap-set searches. Cheap execution of the final function must be separated from expensive discovery.

## Related work and limits of the evidence

Genetic programming evolves programs through predefined mutations; hyper-heuristics evolve search heuristics, including packing policies. FunSearch uses a pretrained model as a richer mutation/combination distribution while retaining evolutionary selection. Prior LLM evolution work already covered robot designs, neural architectures, and code; mathematical novelty and the program-inspection/symmetry loop are the contributions here. Unlike semantic-preserving superoptimization, these functions intentionally change the construction or decision policy.[^related]

Within this collection, [MAP-Elites](E10.md) organizes diverse elites by descriptors, [POET](E11.md) evolves tasks and solvers, and [GEPA](R01.md) uses execution feedback to improve language-based components. FunSearch's islands and score-signature clusters offer another way to avoid collapsing to one ancestor. Its programs resemble reusable [Voyager](E03.md) skills, but their validity comes from a much tighter mathematical skeleton. None of these comparisons makes an island population equivalent to a curated knowledge wiki.

The strongest validity comes from checked constructions and mathematical arguments. Generalization is a separate empirical question for the packing heuristics. The model is frozen, but researchers supply substantial algorithms, feasibility machinery, distribution choices, and later representation changes. Search repeatedly sees its evaluation inputs; only the packing experiment explicitly describes a train/validation/test protocol. The article does not test an autonomous coding agent, persistent skill-memory evolution, adversarial evaluator robustness, long-term regression prevention, or general production deployment.

## Concrete implications for Everdict evolution

**Proposal, not an implemented change:** start with a bounded driver-owned policy component—candidate parent ranking, failure-cluster sampling, or minibatch ordering—inside a fixed campaign protocol. Treat each proposed function as immutable source with pinned dependencies and recorded lineage. A permissive search archive can keep imperfect or neutral candidates, but campaign adoption must use its own complete evidence and confirmation rules. In particular, never silently drop failed evaluation inputs as a way to improve an aggregate.

Compare a single best-parent policy, several independent islands, and islands with periodic migration under the same total proposal/evaluation budget. Add a separate two-parent versus one-parent comparison. Record invalid-program rate, unique behavior signatures, task-family coverage, search cost, and final confirmation improvement. Match evaluation input identities before clustering score vectors; equal-looking partial signatures are not equivalent evidence. Preserve the append-only ledger even when an island is reset.

The most valuable second-stage idea is **changing the representation after inspecting successful code**. For example, repeated successful repairs may reveal that dependency-resolution failures should be represented by a shared structured rule instead of scattered instructions. A curator may propose that abstraction, attach supporting and contradictory rounds, and create a new campaign with a declared edit surface. The analogy to symmetry is an inference: Everdict does not inherit a theorem that the abstraction preserves all behavior.

Keep discovery and settlement separate. A driver may revise its search strategy and use failed attempts as stepping stones; it may not redefine success, omit inconvenient cases, consume hidden confirmation feedback, or activate its own favorite candidate. Evaluate the original baseline, selected artifact, and rebuilt artifact on frozen evidence with an independently budgeted confirmation set. This takes FunSearch's constrained creativity and inspectable programs while adapting the validation contract to stochastic agent behavior rather than deterministic combinatorial validity.
