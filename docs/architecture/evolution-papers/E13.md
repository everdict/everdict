# E13 — DSPy: compiling declarative LM calls into improving pipelines

## Source, scope, and central claim

Khattab et al., *DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines*, arXiv **2310.03714v1**, October 2023. This note covers the original version's programming model, compiler, both experimental case studies, and Appendices A–F. It is a historical paper explanation, not a tutorial for the current DSPy API. Paper results have not been independently reproduced here.[^source]

DSPy separates a language-model program's intended transformations from the prompts or model weights used to implement them. Developers compose modules in Python; an optimizer generates and selects demonstrations, can repeat that process with an improved teacher, and can optionally fine-tune a smaller model. The main experiments concern **GSM8K math** and **HotPotQA retrieval-based question answering**. They demonstrate that a small declarative program plus data-driven compilation can outperform the paper's uncompiled or manually demonstrated baselines.

“Self-improving” mainly means **offline compilation using examples and a metric**. It does not mean a deployed agent continuously rewrites its own architecture or judges its own promotion. Most experiments keep language-model weights fixed, but the T5 experiment explicitly changes them. The contribution is an abstraction and optimization process for multi-stage systems, not one universal evolutionary algorithm.

## Prerequisites: signatures, modules, and trainable parameters

A **signature** names inputs and outputs: for example, `question -> answer` or `context, question -> search_query`. Field names provide natural-language clues about the desired transformation. Optional instructions, descriptions, and formatting prefixes add specificity. In this version, fields default to free-form strings; stronger data types are work in progress. A signature is therefore an interface and behavioral hint, not a static type proof or a guarantee that an answer is correct.[^model]

A **module** implements that signature. `Predict` stores the signature, model configuration, and demonstrations. At execution it formats a prompt, invokes the model, and parses output fields. During compilation it records the module's inputs and outputs. `ChainOfThought` adds a rationale output before the answer. This is not necessarily two separate model calls: the simplified implementation uses one `Predict` to generate both fields. `MultiChainComparison` takes several attempts and asks for a new answer informed by them. `ReAct` alternates reasoning and tool use.

A **program** composes these modules with ordinary control flow, including loops and branches. Declaring nested modules makes their parameters discoverable to the compiler. A retrieval pipeline might fetch passages and then answer; a two-hop pipeline might generate a query, retrieve, generate another query from the accumulated context, retrieve again, and answer. Changing the architecture changes which demonstrations each stage needs.

The parameters being optimized can include demonstrations, instructions, field descriptions, model choice, or fine-tuned weights. The original study focuses on **generating and selecting demonstrations**. “Compilation” is therefore empirical optimization, not a conventional compiler's promise to preserve the behavior of a fully specified source program. A natural-language specification leaves considerable behavior to be learned.

## How the compiler learns intermediate examples

A **teleprompter**, the original name for an optimizer, takes a program, training inputs, a metric, and optionally a teacher program. Intermediate labels need not be supplied. The teacher runs on a training input while the system records all module-level input/output pairs. If the final prediction passes the metric, these pairs become candidate demonstrations for the corresponding student modules. Rejected runs do not contribute demonstrations in the simplest implementation.[^compiler]

Consider a question requiring the birth year of a documentary's author. A successful run might first retrieve the documentary, then generate an author-specific query, then produce the year. With only the final answer labeled, the compiler obtains examples for query generation and answer generation. It learns how intermediate information should flow through this particular pipeline without a human labeling every hop.

This is **outcome-filtered weak supervision**. A correct final answer does not prove every intermediate claim was true, every retrieval necessary, or the rationale causally faithful. The model might know the answer already or recover from an earlier error. Likewise, checking that an answer occurs in a retrieved passage is weaker than checking that the passage supports the answer to the question. The paper allows custom metrics and demonstrates combining answer exact match with passage inclusion; those checks are not equivalent to a formal grounding proof.

Typical compilation has three stages. First, discover candidate parameter values through accepted traces. Second, choose combinations using random search, Bayesian-style optimization, or fine-tuning. Third, optionally change the program at a higher level, such as constructing an ensemble. The third stage's demonstrated operation is ensembling; broader dynamic bootstrapping and backtracking are future possibilities, not separately validated features in this paper.

The optimizer can be composed with an earlier compiled program as its teacher. This supports a second bootstrap when the initial model has too few successes, or distillation from an expensive ensemble into a cheaper program. Teacher/student predictor correspondence must be compatible; arbitrary unrelated programs cannot automatically exchange every internal trace.

## The optimizer variants and implementation limits

`LabeledFewShot` randomly chooses eight labeled examples in these experiments. It can fill fields shared with the training data, such as question and answer, but does not invent missing rationales. Reported random-demonstration results average 3–5 runs depending on the setting.[^optimizers]

`BootstrapFewShot` executes the teacher and collects successful module traces until enough examples are available. `BootstrapFewShotWithRandomSearch` varies training order and demonstration counts, evaluates whole candidate programs, and returns the best. The simplified appendix defaults to sixteen trials. A second bootstrap uses a previously compiled program as teacher. `BootstrapFewShotWithOptuna` first forms a demonstration pool and searches demonstration choices per predictor; its illustrative code selects one demonstration per predictor. **Optuna is explained but has no separate result row in the two main tables.**

An ensemble uses the seven highest-ranked candidate programs from a bootstrap run and majority voting. This changes inference compute as well as quality. A reflection program already samples five reasoning attempts and runs a comparison stage; ensembling several such programs is materially more expensive than one direct answer. A fair deployment comparison needs actual tokens, latency, and calls, not source-code line count.

The appendix is explicitly simplified pseudocode. Its no-validation-set fallback assigns `valset = trainset`; that alone does not implement out-of-fold validation. The paper calls the HotPotQA procedure cross-validation over training, but the displayed code does not specify fold construction or per-example exclusion. There are also naming shortcuts such as a locally updated signature versus a `self.signature` reference. These should be resolved from a pinned executable implementation, not copied as a complete reproducibility specification or treated as confirmed runtime bugs.

## Experiment 1: GSM8K design and full comparison

The authors sample **200 training** and **300 development** question–answer pairs from GSM8K's official training partition, then evaluate selected representative configurations on the approximately **1,300-example official test set**. Main training examples omit human reasoning chains. A separate human-CoT comparison adds those chains. The metric extracts the final numerical value in the output. The two execution models are GPT-3.5 and Llama2-13b-chat.[^math]

The programs are direct `vanilla`, one rationale-and-answer `CoT`, and `reflection`, which generates five attempts and synthesizes another answer through multi-chain comparison. The table below retains development and test separately. A dash means the paper does not report that evaluation, not zero performance.

| Vanilla, bootstrap | 44.0 | — | 28.0 | — |
| Vanilla, bootstrap twice | 64.7 | 61.7 | 37.3 | 36.5 |
| Previous row + ensemble | 62.7 | 61.9 | 39.0 | 34.6 |
| CoT, none | 50.0 | — | 26.7 | — |
| CoT, random few-shot | 63.0 | — | 27.3 | — |
| CoT, human reasoning | 78.6 | 72.4 | 34.3 | 33.7 |
| CoT, bootstrap | 80.3 | 72.9 | 43.3 | — |
| Previous row + ensemble | 88.3 | 81.6 | 43.7 | — |

All values are percentage accuracy. Several findings matter more than the headline. Bootstrap improves every studied program relative to its simple few-shot version on development data, but ensembling is not uniformly better: vanilla Llama test falls from **36.5 to 34.6**, and vanilla GPT development falls from 64.7 to 62.7. Reflection is strong without compilation, so comparing the weakest direct answer with the strongest ensemble combines architecture, demonstrations, and compute changes.

For a closer comparison, GPT CoT with generated demonstrations scores **72.9 test versus 72.4 with human reasoning**, only +0.5 percentage points; its ensemble reaches 81.6 with more computation. Llama's reported best reflection ensemble reaches 46.9 versus 9.4 for uncompiled direct answers, but those are different pipelines. The introduction's approximate “33 to 82” for GPT mixes the **33.1 development** few-shot baseline with the **81.6 test** ensemble result. It is not a paired gain on the same examples. The table's broad “4–20 to 49–88” framing also emphasizes development endpoints rather than one uniform test comparison.

Development selection helps avoid tuning directly on test, but evaluating only promising representatives leaves some comparisons unavailable. The paper does not provide confidence intervals or a full repeated-search distribution for every optimized row. A small numerical difference should not be presented as statistically established superiority.

## What the generated math prompts reveal

After two bootstraps, the apparently direct-answer program learns to put reasoning **inside the answer field**. The numerical extractor accepts that behavior. Therefore “vanilla” describes the declared interface, not a guarantee that the final model answers without reasoning. The optimizer discovers a permissible use of an underspecified output field.[^examples]

The displayed generated shopping example computes a 10% discount on a total of 130 and correctly ends at 117, but its prose briefly describes 13 as what the shoppers will pay before subtracting it as the discount. That local wording inconsistency survives because the final number is correct. It illustrates why successful demonstrations are not necessarily reliable explanatory knowledge. Other examples show sensible arithmetic and context-conditioned queries; they are selected illustrations, not a quantified reasoning-faithfulness audit.

For Everdict, a score-compatible output change must still satisfy the user's contract. If a field is required to contain only a number, accepting a rationale followed by a number would be a contract change even if the benchmark extractor tolerates it. Conversely, if explanation is permitted, placing useful reasoning there is legitimate. The verifier and field contract decide which interpretation applies.

## Experiment 2: HotPotQA retrieval and answer generation

The task is open-domain, full-Wikipedia multi-hop QA using HotPotQA's **2017 Wikipedia abstracts** and a **ColBERTv2** index. Because the official test labels are hidden, the authors reserve 1,000 examples from the official validation set as their test. They divide official training 70/30, retain hard questions to match the evaluation distribution, and sample 200 training and 300 development examples. This is the paper's evaluation subset, not the hidden official leaderboard test.[^qa]

Answer EM measures exact answer agreement. Passage accuracy measures retrieval of the supporting passage pair; it is a separate diagnostic, not sentence-level evidence F1 or a complete grounded-answer metric. `CoT_RAG` retrieves directly from the original question, so changing its answer demonstrations cannot improve its fixed retrieval stage. `ReAct` has a one-passage retrieval tool and at most five iterations. `multihop` generates two successive queries, retrieving three passages per hop and accumulating context before answering.

| Program and compilation | GPT dev answer | GPT test answer | Llama dev answer | Llama test answer |
| --- | ---: | ---: | ---: | ---: |
| Vanilla, few-shot | 34.3 | 31.5 | 27.5 | 21.8 |
| CoT_RAG, few-shot | 36.4 | 29.8 | 34.5 | 28.0 |
| CoT_RAG, bootstrap | 42.3 | — | 38.3 | 32.9 |
| ReAct, none | 20.3 | — | 20.0 | — |
| ReAct, human reasoning | 33.0 | — | 28.3 | — |
| ReAct, bootstrap | 31.0 | — | 24.7 | — |
| ReAct, bootstrap twice | 39.0 | — | 40.0 | — |
| Multihop, few-shot | 36.9 | 31.2 | 34.7 | 31.3 |
| Multihop, bootstrap | 48.7 | 39.6 | 42.0 | 36.4 |
| Previous row + ensemble | 54.7 | 45.6* | 50.0 | 41.0 |

The starred GPT ensemble is tested on **only 500 questions**, half the usual test subset, due to cost. Its 45.6 cannot be treated as a fully matched comparison with the 31.5 baseline over all 1,000 questions. Llama's 21.8→41.0 comparison uses the reported full subset but still combines architecture, compilation, and ensemble compute.

The cleaner multihop bootstrap comparison raises GPT test answer EM from **31.2 to 39.6** (+8.4 points) and Llama from **31.3 to 36.4** (+5.1). Test pair retrieval rises from **40.8 to 43.8** and **30.8 to 43.5**, respectively. Development pair retrieval rises 38.3→47.0 for GPT and 32.0→48.3 for Llama. CoT_RAG remains at 36.0 development and 34.4 test passage accuracy, consistent with its unchanged retrieval policy.

One bootstrap does **not** beat human ReAct demonstrations: 31.0 versus 33.0 for GPT, 24.7 versus 28.3 for Llama. The second bootstrap reaches 39.0 and 40.0. There are no ReAct test results in Table 2, so these remain development findings. The method benefits from iteration, but the paper does not establish indefinite monotonic improvement with additional bootstraps.

## Experiment 3: distilling the pipeline into T5

The fine-tuning demonstration uses **T5-Large, 770M parameters**, with 200 labeled inputs and 800 unlabeled questions. Its teacher is an ensemble/union of two compiled Llama2-13b-chat multihop programs. The teacher generates stage-specific supervision, and `BootstrapFinetune` updates the smaller model used by the resulting multihop system.[^finetune]

The reported outcome is **39.3% answer EM and 46.0% passage accuracy on development data**. No corresponding test result or measured serving-cost table is supplied. This is a real weight-changing experiment, distinct from the frozen-model prompt studies. Section 3's illustrative Flan-T5-large example is not the same as Section 7's reported T5-Large target.

The authors argue the smaller local model could make inference orders of magnitude cheaper than a proprietary model. That is an efficiency expectation based on model size and deployment, not a measured end-to-end cost ratio including retrieval, teacher generation, fine-tuning, and serving. The result shows a path from expensive successful traces to a smaller compiled system; it does not prove lossless compression or general transfer to unrelated tasks.

## Related work, framework comparison, and missing experiments

The programming model borrows the separation of layers, parameters, and optimizers from neural-network frameworks. It extends in-context learning, chain-of-thought, self-consistency, retrieval augmentation, and the earlier Demonstrate–Search–Predict framework. [ReAct](R39.md) supplies a reasoning/tool-use pattern; [Reflexion](E01.md) and [Self-Refine](E02.md) improve behavior through feedback, while DSPy here mainly selects successful traces as demonstrations. [TextGrad](R41.md) and [GEPA](R01.md), published later, optimize with textual feedback in related modular settings. Their mechanisms and results should not be retroactively attributed to DSPy v1.[^related]

Appendices B–C compare the programming approach with contemporary LangChain and LlamaIndex. A September 2023 informal source survey finds 50 LangChain strings longer than 1,000 characters and none in DSPy, alongside numerous prompt files. Example prompts range from 101 to 992 words. This is evidence about where hand-authored prompt content lived in those snapshots, **not** a controlled developer-productivity study, current feature comparison, or proof that DSPy's compiled runtime prompts are shorter. Automatically generated demonstrations can still produce long prompts. One PAL example's character count differs between the prose and the summary table, reinforcing that the counts are illustrative rather than a rigorous complexity metric.

The paper tests two task families with two primary execution models and one fine-tuned student. It supplies no controlled information-extraction or synthetic-data benchmark, although those uses are mentioned as future reporting. It does not test long-term memory maintenance, agent code self-modification, online regression control, or a fixed-budget optimizer leaderboard. Compilation is described as minutes to tens of minutes, often involving a few thousand executions, such as 10–20 trials over 150–300 validation examples. This is not a complete per-row token/cost manifest. Historical cross-paper comparisons use different model versions, tools, and samples and are explicitly informal.

## Concrete implications for Everdict evolution

**Proposed change:** make a candidate's adjustable stages explicit before deciding how to optimize them. A driver could distinguish failure classification, evidence selection, repair proposal, and verification-plan generation, with named inputs/outputs and immutable implementation references. This would make it possible to change demonstrations for one stage without accidentally changing every instruction in a monolithic harness. The paper supports this modularity argument; it does not require replacing Everdict with DSPy or adding a new campaign subject type.

Start with a three-arm driver experiment: fixed authored demonstrations, randomly selected successful traces, and metric-filtered generated demonstrations selected using held-out selection data. Keep the execution model, architecture, demonstration token budget, proposal count, and campaign confirmation protocol equal. Test a second bootstrap only as a separate treatment. Test ensembles separately too, since their gain may come from increased inference compute.

Store a selected example with the exact candidate, module path, input, output, tool results, metric version, and supporting round IDs. A successful final task should permit consideration of intermediate material, not automatically certify every intermediate statement. A curator should retain contradictory rounds and label causal explanations as hypotheses until supported. Keep raw failed traces in the append-only ledger even when the demonstration pool omits them.

For compilation, use train data to generate examples, selection data to rank programs, and an independently budgeted confirmation set to settle adoption. The driver must not use the simplified appendix's training-as-validation fallback as if it were independent confirmation. Build and record the complete compiled artifact, including demonstration ordering, formatting logic, retrieval configuration, model version, and any changed weights. An unchanged high-level Python program can produce different behavior after compilation, so source text alone is insufficient provenance.

A later experiment can distill an expensive successful candidate into a smaller execution model, with teacher cost and additional failure modes accounted for separately. Acceptance must evaluate the distilled artifact itself. This follows DSPy's most useful lesson for Everdict: **evolution can change how a stable module is realized, while the platform retains control of what counts as verified improvement.**
