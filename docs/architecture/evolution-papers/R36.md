# R36 — MetaClaw: fast skill adaptation, delayed policy training, and data versions

MetaClaw v1 proposes a deployed agent that changes external skill instructions quickly and updates model weights more slowly during presumed idle periods. Its most relevant contribution to Everdict is recognizing that a trajectory's meaning depends on the skill version that generated it. The paper also contains important mismatches between its buffer descriptions, tables, and figures; those limits matter when translating the design into an evidence-preserving evolution system.[^1]

## The two-timescale problem

A user's tasks change over time. Some repeated mistakes can be addressed with a short rule, while more difficult behavior may require training the policy. MetaClaw represents the adaptable system as a pair: model parameters θ and skill library S. A task retrieves relevant skills through embeddings, then the model acts with those skills in its prompt.

The fast loop uses failures to generate new instructions without changing θ. The slow loop performs cloud LoRA reinforcement learning on later trajectories. LoRA changes a relatively small trainable parameterization rather than requiring local full-model training. “No local GPU” means computation is delegated to a cloud service; it does not mean training is free or needs no accelerator.

The paper connects this arrangement to meta-learning: support experience changes the skill context, and query experience evaluates behavior after that change. This is a useful adaptation structure, but the presented update does not differentiate through the discrete skill evolver as MAML differentiates through an inner optimization step. A two-phase learning curve alone does not demonstrate a learned general adaptation algorithm.

## Fast adaptation: what enters a skill

Failure trajectories are passed to an LLM skill evolver. The library update is additive: retain existing skills and union newly generated ones. Each library change advances a generation counter. Later tasks immediately retrieve from the new generation.[^2]

The appendix's evolver sees up to six failures, including the last 600 characters of conversation context and first 500 characters of the response, plus existing skill titles. It generates one or more new skills with a slug, description, category, and six to fifteen Markdown lines containing steps, an example, and an anti-pattern. This is a practical compact synthesis prompt; it does not expose every full execution trace or independently verify the inferred failure cause.

Retrieved content is appended to the system message. Examples require backups before edits or timestamps with a particular timezone offset. Those are benchmark or workspace conventions, not universal requirements for all users. Duplicate prevention is prompted using titles; the paper does not fully define semantic deduplication, contradiction resolution, replacement, retirement, or bounded growth.

Prompt injection takes effect without a weight hot-swap, explaining the intended fast deployment. Nevertheless, generated text can still cause regressions. Immediate deployment is part of MetaClaw's proposal, not evidence that each new instruction has passed a separate adoption test.

## Support/query versioning and an unresolved buffer policy

A failure used to create a new skill is support data for that adaptation. A later trajectory collected after the new skill takes effect is query data. Training as though the earlier failure occurred with the new context would misattribute behavior. Recording the generating context and its version is therefore essential.[^2]

The paper gives two different buffer descriptions. Section 3.3 says the RL buffer can accumulate query trajectories from multiple post-adaptation generations, each trained with its original generation. Section 3.4 and Algorithm 1 instead flush all samples at or below the old generation whenever a new generation is created. Under that rule, previously valid queries are also discarded, leaving only the newest generation after recollection. These policies have different data efficiency and reproducibility requirements and cannot both be assumed without clarification.

The pseudocode also routes failures to support and only non-failures to the RL buffer. The broader definition of post-adaptation query data does not inherently require success. If rewards were purely binary, a successes-only group would have no relative reward variation for GRPO; a varying process reward could avoid that problem. The exact filtering, grouping, and reward implementation needs to be specified to reproduce the method.

An older reward is not universally invalid just because the context changed. It remains evidence about the original context and can be useful in explicitly off-policy analysis or replay. The error is treating it as evidence from a different version without an appropriate method. MetaClaw proposes a conservative separation rule; it does not prove that all version-aware reuse is mathematically wrong.

## Slow policy optimization and idle scheduling

Once sufficient eligible data exists, MetaClaw performs GRPO-based cloud LoRA updates using a process reward model, then swaps the model weights. The full Kimi-K2.5 condition uses a five-day training run. The paper does not disclose enough PRM calibration, LoRA rank, learning-rate, group-size, token-budget, or total-cost detail to reproduce the full training recipe from text alone.[^2]

The Opportunistic Meta-Learning Scheduler monitors three signals: configured sleep hours, operating-system input inactivity with a default thirty-minute threshold, and calendar events indicating that the user may be occupied. It can pause and resume training using checkpoints across fragmented windows. The intended policy opens a window on absence and closes it when user activity returns.

Sleep schedules and meetings are predictions of availability, not guarantees. A calendar meeting does not prove inference is idle. The paper acknowledges dependence on configuration, and does not report a controlled scheduler ablation, interruption-latency distribution, or measured production availability. Thus zero downtime is an architectural goal and a prompt-update property, not a fully quantified service-level result for the complete system.

## MetaClaw-Bench: an authored sequential task stream

The benchmark contains 934 questions across forty-four simulated workdays, not forty-four days of observed customer usage.[^3]

Part I has 346 questions across thirty days, about ten to fifteen per day. Workspace state persists across rounds within each day, and a question includes the prior round's evaluation feedback. Tasks combine file operations checked by programs with multiple-choice procedural questions. Difficulty is deliberately increased by day, so later-day performance confounds accumulated experience with harder tasks.

Part II has 588 questions across fourteen days: 434 multiple-choice and 154 file-check tasks, forty-two questions per day. It emphasizes recurring conventions. Five initially implicit preferences become active progressively: timezone-qualified timestamps from day one, date-prefixed filenames from day four, required metadata from day six, backups from day eight, and completion-log entries from day ten. These are learned from feedback rather than stated completely in the initial system prompt.[^4]

A first failure on an undisclosed preference does not necessarily show poor general reasoning. This setting tests adaptation to an authored convention stream. It is valuable, but different from solving independently sampled tasks under fully specified requirements.

The overall “accuracy” is mean question score. The multiple-choice template gives max(0, 1 − (false positives + false negatives)/number of options), allowing partial credit. For a four-option question with two correct choices, choosing none would receive 0.5 under that formula. File completion separately requires passing all checker assertions. Overall accuracy therefore must not be described as the fraction of perfectly solved tasks.

## Main results and the role of each component

Table 1 gives all five model/condition pairs.[^5]

| Model and condition | Part I mean score | Part I file completion | Part II mean score | Part II file completion |
|---|---:|---:|---:|---:|
| GPT-5.2 baseline | 41.1 | 14.7 | 44.9 | 58.4 |
| GPT-5.2 skills | 44.0 | 17.1 | 49.1 | 67.5 |
| Kimi-K2.5 baseline | 21.4 | 2.0 | 21.1 | 18.2 |
| Kimi-K2.5 skills | 28.3 | 2.0 | 26.9 | 33.8 |
| Kimi-K2.5 full | 40.6 | 16.5 | 39.6 | 51.9 |

Skills increase the displayed overall scores in both models and parts. The largest relative skills-only mean-score gain is Kimi Part I's 32.2%, corresponding to +6.9 percentage points. Kimi's full system adds 12.3 points over skills on Part I mean score and 12.7 on Part II.

The 8.25-fold Part I completion improvement is from 2.0% to 16.5%, or +14.5 points. Part II full completion improves from 18.2% to 51.9%, or +33.7 points and approximately 185% relative. Large ratios from a small baseline should be presented alongside the endpoints.

The prose says skills leave Part I completion unchanged for both models, but Table 1 shows GPT-5.2 improving from 14.7% to 17.1%. Skills also raise Part II completion substantially. Therefore, the stronger conclusion that weight training is necessary for end-to-end completion is not supported universally by the table.

There is no RL-only arm without skills, so the study does not isolate a unique interaction between the two mechanisms. Full adaptation is tested only on Kimi because it requires a configured training endpoint. No repeated-run uncertainty is given for the headline table. All results here are source reports, not independently reproduced measurements.

## Day-level curves, figures, and selected recoveries

The thirty-day plot uses a three-day rolling average. Full Kimi has its strongest visible period around days nineteen and twenty, before all systems struggle with later tasks. Its peak near 0.8 is an absolute accuracy level, not an eighty-point advantage over every baseline. Day difficulty changes alongside experience, and chronological averages cannot isolate learning from task composition.[^6]

The original figure labels the OpenAI model GPT-5.1, while Table 1 and the main text call it GPT-5.2. The task-type bar chart also labels GPT-5.1 and shows equal file-check bars, unlike Table 1's GPT-5.2 endpoints. The figure and table should be treated as an unresolved configuration discrepancy rather than silently combined into one experiment.

The Part II narrative describes Kimi full file completion rising around day eight and reaching 100% on days twelve and fourteen. Each day has only eleven file-check tasks; a perfect day is not broad reliability. New preference rules and changing tasks also make this an observational learning trajectory, not a randomized test of the proposed timescales.

Two cases illustrate the intended mechanisms. A backup instruction learned earlier prevents a later overwrite-related checker failure without weight changes. Another example needs all deployment-log fields, a timezone-qualified timestamp, and a backup; the full model succeeds where the skills-only model omits a field. These are selected recoveries, not proof that RL was the only possible repair for that task.

## AutoResearchClaw: transfer of the method to a research pipeline

The second evaluation applies skills-only adaptation to a twenty-three-stage research workflow. Failures and warnings from a run become skills for subsequent runs, injected into eighteen LLM-driven stages. Nineteen stages are scored for completion. These three stage counts describe different roles.[^7]

The reported A/B comparison holds topic, backbone, and pipeline configuration fixed. Retry rate falls from 10.5% to 7.9%, refinement cycles from 2.0 to 1.2 per stage, scored completion rises from 18/19 to 19/19, and a composite robustness score rises from 0.714 to 0.845. The last change is 18.3% relative. The completion change is approximately +5.3 percentage points, but about +5.6% relative; the table labels its 5.3% as relative.

The composite weights completion at 40%, retry reduction at 30%, and refinement efficiency at 30%, but the text does not fully specify every normalization needed to independently reconstruct the score. Trial counts, dispersion, topic diversity, and run-order effects are insufficiently detailed.

This is transfer of the adaptation mechanism to a new domain where it learns new pipeline-specific skills. It is not evidence that the same CLI-generated skill library transfers unchanged to research. Finishing pipeline stages is also not independent validation of a paper's scientific correctness, novelty, or publication quality.

## Related work and limits on the evolution claim

Reflexion, Voyager, ExpeL, and other memory systems already accumulate or revise knowledge, so describing all prior libraries as static overstates the distinction. SkillRL also combines library changes with policy training. MetaClaw's sharper contribution is coordinating serving-time adaptation, training eligibility, and scheduling through an explicit version model.[^1]

The study does not separately ablate version flushing, scheduling, skill retrieval, or PRM quality. It does not establish long-term forgetting resistance, stable growth, or safety of arbitrary generated instructions. The appendix also permits compressing the native system prompt below 2,000 tokens after the first session. Whether and how that transformation was applied consistently needs to be part of a reproduction manifest; a request to preserve all rules is not a proof of semantic equivalence.

## Everdict changes: preserve provenance before adding background training

Everdict can use the strongest idea immediately: bind every trajectory to the exact model, skill bundle, harness, environment, and evaluator versions that produced it. Mark which evidence generated a candidate and which evaluated it afterward. Preserve old records in the raw ledger even if a trainer excludes them from its active buffer.

A driver can compare two explicit policies: newest-generation-only training and version-aware replay with the original context. Measure data discarded, adaptation delay, performance, regressions, and cost. Neither policy should silently relabel an earlier result as evidence about a new candidate. Support/query separation also does not replace train/select/confirm separation: newly collected query data can still become development data when used for training.

For the first evolution loop, test fast text changes with a frozen executor before introducing background weight training. Candidate production and adoption remain distinct. Generated skills cannot rewrite platform rules, and a idle-time scheduler cannot grant itself new authority. If weight updates are later included, the frozen candidate must identify both checkpoint and skill digests, and adoption must use the permitted independent confirmation evidence. These are proposals grounded in MetaClaw's useful versioning insight, not functionality added by these notes.[^8]
