# R13 — PagedAttention and vLLM: making more evaluation requests fit

This 2023 systems paper introduces PagedAttention and the original vLLM serving engine. Its goal is higher inference throughput through efficient key/value-cache memory management. It does not evolve prompts, skills, or model weights. For Everdict, it explains an infrastructure constraint that can determine how many candidate evaluations fit within a time or GPU budget. This note follows arXiv 2309.06180v1, corresponding to the SOSP paper, rather than assuming that current vLLM behaves exactly like this initial implementation.[^1]

## Background: why decoding consumes memory

An autoregressive language model generates the next token conditioned on the prefix. Attention uses each new token's query vector to weight the keys and values of earlier tokens. Recomputing all previous keys and values at every step would be wasteful, so the serving engine retains them in a KV cache.

Prefill processes the known prompt with efficient parallel matrix operations. Decoding then adds tokens sequentially; each step depends on the previous generated token. At small batch sizes, repeatedly moving model weights and reading caches can limit GPU utilization. Batching several requests amortizes work, but all active requests' caches must fit alongside the weights and temporary tensors.[^2]

The paper's OPT-13B example uses about 800 KB of KV state per token: two vectors, hidden width 5,120, 40 layers, and two-byte values. A 2,048-token request can therefore require about 1.6 GB. This is an architecture-specific example, not a formula to apply unchanged to models with grouped-query attention, different precision, or shared caches.

## The memory problem and neighboring techniques

A contiguous allocation sized for a request's possible maximum length wastes space in three ways. Some slots are reserved for future tokens; some remain unused when generation ends early; allocator gaps create external fragmentation. The paper observes that effective use can be as low as 20.4% in its earlier-system comparisons. Even excellent per-token kernels cannot batch requests whose caches do not fit.[^2]

Orca's iteration-level scheduling already allows completed sequences to leave a batch and new requests to join between decoding steps. PagedAttention complements that scheduling by increasing the number of working sets that fit. FlashAttention reduces attention I/O through kernel tiling; it addresses a different dimension and can be used during prefill. FlexGen studies inference with offloading under limited memory, with a different emphasis from online request latency. The key distinction is scheduling work, executing attention efficiently, and managing persistent token state.

## Principle: logical order without contiguous physical storage

PagedAttention divides a sequence's KV cache into fixed-size token blocks. A block table maps the sequence's logical blocks to physical GPU blocks. Attention follows those mappings while preserving the sequence's logical order and the normal attention normalization across relevant tokens. Paging changes where state lives, not which past tokens the mathematical attention operation should consider.[^3]

For an illustrative block size of four, a seven-token prompt needs two blocks. One slot remains for the next token. Once that block is full, the engine allocates another physical block wherever space is available and appends its mapping. It does not reserve enough memory for every possible future token. Only the unfinished final block creates this kind of per-sequence slack.

The OS virtual-memory analogy is useful but limited. This is application-managed token-state storage, not simply enabling the GPU's ordinary virtual-memory facility. The engine knows that decoding needs a sequence's entire relevant cache, that generated tokens can be recomputed in a prefill-like pass, and that some prefixes are shared. It exploits those semantics explicitly.

## Sharing, reference counts, and copy on write

Several outputs sampled from one prompt can share the prompt's cache. Beam search can share additional generated prefixes because surviving hypotheses may descend from common earlier sequences. The manager tracks reference counts so a shared physical block remains alive until every user releases it.

When two sequences diverge inside their last shared block, a writer gets a private copy before appending new state. Already completed shared blocks remain shared. This copy-on-write design limits copying to affected blocks, instead of repeatedly duplicating an entire prefix. Shared system instructions can similarly use precomputed prefix blocks in the paper's predefined-prefix setting.[^3]

Identical text alone is insufficient for arbitrary cache reuse: a token's keys/values depend on its preceding context, position, model, and execution conditions. For an evolution campaign, changing an early instruction can invalidate the cached states after it even if a later paragraph is unchanged. Cache identity must respect the actual computation, not just a matching substring.

## Scheduling, preemption, and implementation

The original scheduler uses first-come-first-served priority and preempts later arrivals first. Related sequences belonging to one request are scheduled together. If GPU space is exhausted, it evicts all cache blocks of a selected sequence/group rather than retaining arbitrary pieces that cannot support the next decoding step.[^3]

Recovery can swap cache blocks through CPU memory or recompute them from the retained tokens. Recomputation can process the already known sequence in parallel, so it need not repeat the original slow token-by-token generation. Which option is cheaper depends on transfer bandwidth, compute, and block size.

The implementation combines a Python scheduler/block manager with C++/CUDA kernels for block writes, attention reads, and batched block copies. Tensor-parallel GPU workers share the logical block mapping while each stores its own attention-head shard. The centralized scheduler sends mappings and token inputs; workers still synchronize model computations through collective communication. These are the paper's engineering choices, not a current installation guide.

## Experimental design and baselines

The study uses OPT-13B/66B/175B and LLaMA-13B on Google Cloud A100 configurations. OPT-13B uses one 40-GB GPU; 66B uses four; 175B uses eight 80-GB GPUs. Workloads reproduce prompt/output length distributions from ShareGPT and Alpaca, with synthetic Poisson arrival times because the source datasets lack timestamps. Most traces last one hour; the 175B experiments use fifteen minutes because of cost.[^4]

The primary metric is normalized latency: each request's end-to-end latency divided by its output length, averaged over requests. Sweeping the arrival rate reveals the point at which queues grow rapidly. A throughput multiplier here means supporting more incoming requests at comparable latency, not generating every individual token that many times faster.

FasterTransformer receives a custom dynamic-batching scheduler. Because Orca was unavailable, the authors implement an approximation with three output-reservation policies: exact future lengths as an unattainable oracle, power-of-two reservation, and reservation up to the model maximum. The oracle is a strong information advantage, but the reconstruction still limits claims about the original proprietary Orca implementation.

## Main experiment families and results

| Experiment family | Reported result | What changes |
|---|---|---|
| Basic sampling, ShareGPT | 1.7–2.7× supported request rate versus Orca Oracle; 2.7–8× versus Orca Max | Memory utilization enables larger active batches |
| Parallel sampling, Alpaca | 6.1–9.8% block-memory savings from sharing | Multiple outputs share prompt state |
| Beam search, Alpaca | 37.6–55.2% block-memory savings | Hypotheses also share generated prefixes |
| Shared-prefix translation | 1.67× throughput with one example; 3.58× with five, versus Orca Oracle | Longer common prefixes save repeated state/work |
| Chatbot workload | About 2× supported request rate versus Orca variants | Long prompts benefit from less reservation waste |

The basic-sampling comparison reaches up to 22× over the tested FasterTransformer setup, which lacks the same fine-grained scheduling. That maximum is not an isolated paging effect. For OPT-175B on short Alpaca sequences, the advantage over stronger Orca variants is smaller because enough cache memory is available and compute becomes the bottleneck.[^4]

For ShareGPT, sharing saves 16.2–30.5% in parallel sampling and 44.3–66.3% in beam search. The translation experiment uses WMT16 English-to-German with LLaMA-13B and common prefixes of 80 or 341 tokens. The chatbot experiment truncates prompts to the last 1,024 tokens, generates at most 1,024, and does not retain caches between conversation turns. It therefore does not measure unlimited conversational memory or a persistent cross-turn cache policy.

## Ablations: why a slower kernel can yield a faster service

PagedAttention's attention kernel is 20–26% slower than the optimized FasterTransformer kernel in the microbenchmark because block indirection, branches, and variable lengths add work. End-to-end throughput still improves because more requests fit and execute together. This is a useful systems lesson: a component's latency can worsen while total service capacity improves.[^5]

Block size trades parallel GPU access against fragmentation and sharing granularity. ShareGPT performs well at sizes 16–128; shorter Alpaca sequences favor 16 or 32 and suffer with larger blocks. The original implementation chooses 16 as a practical default. It is an empirical choice for those workloads, not a timeless optimum.

The recovery study compares swapping and recomputation. Small blocks create many small transfers and hurt effective PCIe bandwidth, favoring recomputation. Larger blocks make swapping more competitive; sizes 16–64 have similar end-to-end behavior in the tested setting. The manuscript's wording about one relative recomputation-latency bound is awkward, so this note retains the supported qualitative tradeoff rather than manufacturing a precise universal ratio.

## Limits and Everdict implications

The evaluation is about serving throughput, not improved task reasoning. Workloads use selected model architectures, length distributions, and synthetic arrival processes from 2023. Modern models, accelerators, serving engines, long contexts, and tool-heavy agent workloads can shift the bottleneck. A fully compute-bound workload may gain little and even pay extra indirection overhead.[^5]

For Everdict, preserve serving identity and resource settings when comparing candidates. More efficient batching can allow more experiments within a wall-clock budget, but if one strategy receives more attempts, its gain mixes search quality and allocated computation. Record both completed evaluations and total GPU/time/token cost. Keep task quality and infrastructure capacity as separate outcomes.

A useful experiment replays a frozen candidate-evaluation workload under controlled concurrency, context lengths, and shared-prefix conditions. Measure throughput, tail latency, peak memory, preemptions, failed requests, and verified task success. Then compare evolution strategies at equal evaluation count and, separately, equal elapsed cost. This identifies whether a better serving engine accelerates the same research or changes which search strategy is feasible. The paper motivates that infrastructure control; it does not justify changing Everdict's adoption semantics.
