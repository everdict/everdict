# R41 — TextGrad: routing textual feedback through a computation graph

TextGrad turns a compound AI system into a graph of editable variables and operations, then uses LLM criticism to suggest improvements upstream. Its central contribution is a reusable optimization interface spanning prompts, individual answers, code, molecules, and numerical-planner settings. The word gradient is explicitly a metaphor: there is no numerical derivative, chain-rule guarantee, or general convergence proof. This note analyzes the original arXiv v1 experiments; it does not silently merge results from the later Nature publication.[^1]

## Background and relationship to earlier optimization methods

Traditional automatic differentiation works because each operation supplies a mathematical derivative. An API call to a language model, a code interpreter, or a simulator generally cannot provide the derivative of answer quality with respect to an instruction string. TextGrad instead asks a capable model to explain how an upstream variable should change given its downstream consequences.

ProTeGi already introduced textual gradients for prompt optimization. DSPy treated LLM pipelines as programs whose instructions and demonstrations could be optimized. Reflexion and Self-Refine used feedback to revise solutions. TextGrad generalizes these ideas into graph abstractions and especially emphasizes **instance optimization**: directly improving one solution, molecule, or plan, as well as learning reusable prompts.[^2]

This distinction matters for Everdict. Repairing one answer at test time is not persistent evolution. Learning an instruction that transfers across future questions is. The same framework supports both, but their evidence requirements and generalization claims differ.

## Forward pass, backward feedback, and textual updates

A variable contains its value, a role description, predecessor references, accumulated feedback, and a flag indicating whether it should be optimized. Roles distinguish, for example, a reusable system prompt from a final numeric answer. Fixed task inputs can be marked non-editable.[^3]

In a simple graph, `prompt + question → model answer → evaluation`, the evaluator first critiques the answer. A backward operation then sees the actual prompt, question, answer, and downstream criticism and explains how changing the prompt might help. When one variable contributes to several outputs, feedback from those uses is accumulated. The optimizer receives the current value and this feedback, then emits a replacement variable.

The backward model supplies criticism; the update model supplies the revised text. Keeping these roles separate makes attribution inspectable, but does not make it causally correct. An error may originate in retrieval, reasoning, an evaluator, or an unlucky generation even when the prompt is editable. A persuasive critique can blame the wrong component.

Every custom operation needs forward and backward behavior; registering a node does not magically reveal its semantics. The paper describes at most one extra backward-model call per graph edge, in addition to forward evaluation and variable-update calls. Larger graphs and repeated candidates therefore incur substantial overhead beyond the original task call.

## Batch feedback, momentum, and constraints

Minibatch optimization concatenates feedback from several examples. The `sum` abstraction organizes text rather than performing a calibrated numerical sum of causal effects. Contradictory suggestions can remain in the accumulated feedback and must be resolved by the optimizer.[^4]

Momentum supplies past variable versions as additional context. It is not a weighted numerical velocity with a demonstrated stability property. Natural-language constraints ask the optimizer to preserve formats or requirements. The paper acknowledges that many simultaneous constraints reduce reliability; a prompt instruction is not a hard feasibility check.

The same general backward and update prompts are reused across applications, but objectives, variable roles, domain tools, initialization, and example contexts are application-specific. “General framework” therefore does not mean zero task engineering. One printed backward example even critiques answer-checking runtime for an already correct counting answer, illustrating why the intended objective must remain explicit throughout the graph.

## Code experiment: local repair versus hidden completion tests

The code study re-extracts thirty-nine LeetCode Hard problems. Its dataset likely differs from the earlier Reflexion paper's extraction. Local examples guide repair, while final completion requires passing the platform's hidden tests. The historical GPT-4 figures are consequently background, not a clean matched comparison.[^5]

GPT-4o supplies generation and feedback. TextGrad uses no in-context demonstration and allows five repair iterations; Reflexion uses one demonstration and five iterations. Experiments repeat over five seeds. Each TextGrad repair uses three calls: evaluate the current code and local tests, compute feedback, and rewrite the code.

Table 1 reports completion rates of 26% for zero-shot, 31% ± 1.2 percentage points for Reflexion, and 36% ± 1.8 for TextGrad. The nearby prose instead states 23% for zero-shot. Using the table consistently, the TextGrad improvement is ten points over zero-shot and five over Reflexion, approximately 16.1% relative to Reflexion. The introductory “20%” improvement should not be substituted for this calculation.

The implementation describes submitting candidates that pass local tests to the hidden platform during the iterative procedure. This should not be relabeled as first-sample pass@1 or evidence of a reusable code-generation skill. A reproduction should record candidate submissions, stopping rules, what feedback is visible, and whether success means any submitted candidate or a selected final one.

The experiment supports feedback-assisted repair on this small set. It does not establish equal total model calls with Reflexion, stronger performance on all coding tasks, or that local-test success guarantees hidden-test success.

## Scientific question answering: more test-time computation

The solution-optimization experiment directly edits a response to each multiple-choice question. The evaluator receives the question and current solution but no ground-truth answer. It is asked to investigate errors and consider alternatives. Model weights remain fixed, despite the analogy to test-time training.[^6]

Evaluation uses GPQA Diamond's 198 questions, MMLU Machine Learning's 112, and MMLU College Physics's 92. The GPT-4o baseline uses a zero-shot reasoning prompt at temperature zero; the historical release result uses temperature 0.5. TextGrad performs three update iterations and votes across the trajectory's solutions, introducing both refinement and aggregation.

| Dataset | Matched CoT baseline % | TextGrad % | Gain in percentage points |
|---|---:|---:|---:|
| GPQA Diamond | 51.0 | 55.0 | 4.0 |
| MMLU Machine Learning | 85.7 | 88.4 | 2.7 |
| MMLU College Physics | 91.2 | 95.1 | 3.9 |

Each update costs three GPT-4o calls, so three rounds add up to nine calls beyond initial generation. There is no matched independent-sampling-and-voting control establishing that feedback, rather than extra computation plus aggregation, explains the entire gain. The paper's best-known-result language is historical to v1, not a current leaderboard claim.

Feedback without labels can improve an answer, but can also talk a correct answer into a wrong one. The aggregate score does not supply an error-calibrated stopping rule or a guarantee that the last revision is best.

## Reusable prompt optimization: genuine cross-query learning

Here the editable variable is a single instruction for `gpt-3.5-turbo-0125`, with GPT-4o providing backward feedback and updates. Training uses batches of three for twelve iterations, giving thirty-six sampled training slots with replacement, not necessarily thirty-six distinct examples. A validation gate accepts a prompt only when it improves validation performance.[^7]

Object Counting and Word Sorting each use 50/100/100 train/validation/test examples. GSM8k uses 200/300/1,319. Object Counting and GSM8k use numeric exact-match extraction; Word Sorting uses a GPT-4o judge against the reference list. Dataset metrics therefore have different judge dependencies.

| Task | Initial CoT % | DSPy BFSR % | TextGrad % |
|---|---:|---:|---:|
| Object Counting | 77.8 | 84.9 | 91.9 |
| Word Sorting | 76.7 | 79.8 | 79.8 |
| GSM8k | 72.9 | 81.1 | 81.1 |

DSPy's BootstrappedFewShotRandomSearch searches ten candidate programs with up to eight demonstrations. TextGrad exports only the learned instruction. It wins one task and ties two, rather than universally outperforming DSPy. Combining DSPy demonstrations with the learned GSM8k instruction reaches 82.1%, suggesting complementarity.

The learned instruction emphasizes restating the problem, decomposing calculations, verifying intermediate steps, and retaining the output format. These are reusable behaviors rather than benchmark answer strings. However, the result also incorporates strong-teacher feedback and repeated validation. It does not isolate a benefit from graph-based credit assignment over every simpler prompt-rewriting method, nor demonstrate that adaptive validation cannot overfit.

## Molecule experiment: optimizing two computational proxies

Molecules are represented by SMILES strings. RDKit checks structural validity and computes quantitative estimate of druglikeness (QED), a 0–1 composite of physicochemical descriptors. DOCKSTRING standardizes structure preparation and AutoDock Vina docking. More negative Vina scores are better under that scoring model; they are not directly measured binding affinities or clinical efficacy.[^8]

The objectives conflict: docking can favor larger structures with more interactions, whereas QED favors a balance of properties. GPT-4o receives the molecule, target name, and two scores and proposes structural revisions. Invalid structures return an error message. The model does not receive the full binding-pocket geometry through the text loss.

The prompt says docking matters ten times as much as QED. Post-selection uses `Vina + (1 − QED)`, where lower is better. The approximate relative emphasis comes from the metrics' natural scales, not an explicit factor-ten coefficient in that equation. Changing score units would change the tradeoff.

The study runs fifty-eight protein targets, three initial fragments—acetamide, pentane, benzene—and ten iterations. Twenty-nine targets have 118 suitable approved DrugBank comparators. Those comparators are rescored through the same computational pipeline. The best candidate per target and initial fragment is selected by the overall score; reported selected distributions are not distributions of every generated intermediate molecule.

The selected molecules show docking scores comparable to approved drugs and generally higher QED, with substantial improvement over the tiny starting fragments. A PPARA trajectory illustrates docking/QED moving from approximately −4.2/0.44 to −7.5/0.79 early in optimization. Later points trade off the two objectives; they are not uniformly monotonic.

This is a computational proof of concept without a matched state-of-the-art molecular-generation search baseline or laboratory binding measurements. Starting from a simple fragment is useful evidence of construction, but opaque GPT-4o pretraining still supplies chemical knowledge; “no prior training set” means no task-specific training dataset for this optimization run.

## Molecule controls: initialization, novelty, and predicted toxicity

The initialization control finds overlapping optimized score distributions from all three fragments. This supports robustness across those starts, not independence from arbitrary initial structures. Selecting the best of ten also means the optimizer's exploration budget contributes to the reported result.[^9]

Novelty is defined using ChEMBL's roughly 2.4 million compounds: no database molecule may exceed Tanimoto similarity 0.8. By iteration six, about 95% of generated molecules meet that threshold. For the eighty-seven selected candidates on approved-drug targets, comparison with DrugBank gives median Tversky similarity 0.42 and a broad 0.14–0.90 range.

These fingerprint comparisons argue against merely copying many complete known molecules. They do not prove absence of training-data influence, chemical patent novelty, synthesizability, or experimental function. The Tversky discussion also alternates which molecule contains the other's substructure; its direction and parameters must be fixed for reproduction rather than inferred from loose prose.

An ADMET-AI predictor estimates mutagenicity and clinical toxicity for the selected candidates and approved-drug comparators. Distributions are broadly overlapping, with generally low predicted clinical toxicity. This is a learned-model proxy on selected molecules, not toxicology experiments or proof that TextGrad automatically avoids harmful compounds. The mutagenicity plot does not show every generated candidate as uniformly safer than every approved drug.

## Radiotherapy: an outer optimizer around a numerical planner

The radiotherapy study tunes importance weights for the planning target volume (PTV), bladder, rectum, femoral heads, and body. The inner matRad optimizer uses a dose-influence matrix to turn nonnegative beam intensities into a dose distribution while balancing target coverage and organ penalties. TextGrad changes the outer weights, not the physical dose model.[^10]

An LLM compares dose-volume histograms and statistics with supplied clinical protocols. It proposes which organ or target weights should change; matRad then produces a new plan. Three clinician-optimized example plans and their parameters guide updates, and past iterations provide momentum-like context. The relationship between these three examples and the five evaluated patients is not fully described as an independent split.

All weights start at 100. The fixed objective doses are 70.20 Gy for the PTV, zero for bladder and rectum, and 30 Gy for femoral heads and body. These are optimizer targets in this experiment, not standalone treatment prescriptions. Stop when the LLM says protocols are satisfied or after ten iterations.

The phrase projected gradient descent describes guidance by examples, a soft analogy rather than a mathematical projection into a verified feasible set. The inner formulation explicitly enforces PTV D95 at the prescribed dose; exact D95 matching therefore cannot be credited entirely to an emergent LLM capability. The printed organ-penalty equation is linear in excess dose while its explanation calls it squared, another implementation detail to verify against matRad configuration.

## Radiotherapy results and what they do not demonstrate

Five previously treated prostate-cancer patients supply images, contours, and Eclipse clinical plans. The comparison is retrospective and computational. D95 denotes the dose received by at least 95% of the structure; dose-volume metrics describe the planned distribution, not observed tumor control or adverse effects.[^11]

| Metric | Clinical plan | TextGrad plan |
|---|---:|---:|
| PTV mean-dose deviation from 70.20 Gy | +1.97 Gy | +0.51 Gy |
| PTV D95 deviation | −0.10 Gy | 0.00 Gy |
| Rectum mean dose | 23.88 Gy | 17.18 Gy |
| Bladder mean dose | 22.39 Gy | 20.92 Gy |

The appendix additionally reports PTV minimum deviation −8.88→−8.48 Gy and maximum deviation +4.66→+3.63 Gy. Rectum D5/D50 decrease 64.26/20.04→58.82/9.54 Gy, and bladder D5/D50 decrease 67.81/14.78→65.96/14.11 Gy. Standard deviations across five plans are reported, without a clinical outcome trial.

The main prose calls the target mean dose higher, but the table shows a **lower overshoot and closer match** to the prescription. Figure 3's example also briefly crosses the plotted bladder threshold at iteration one, so the claim that exposure stays below the maximum should apply to the accepted endpoint, not every intermediate candidate.

Better reported dose summaries do not establish overall clinical superiority, delivery robustness, or patient benefit. The comparison changes planning software and workflow and does not isolate every clinical constraint. The authors explicitly place experimental and clinical validation outside this study's scope.

## Everdict proposal: route evidence without changing authority

The useful abstraction is a graph connecting an editable artifact to the observations and evaluated outputs it influenced. For a candidate driver change, Everdict could preserve the exact prompt or code version, its role, upstream inputs, actual execution, evaluator result, and proposed correction. This would make a critique's target and supporting evidence reviewable.

A first experiment could compare direct whole-artifact reflection, graph-routed feedback, and graph-routed feedback with short history, under the same total call and token budget. Separate instance repair from reusable candidate improvement. Evaluate both on fresh task families, and track false diagnoses, unrelated edits, regression rates, and verified improvement per search cost.

Only declared candidate variables should be editable. Task contracts, hidden answers, evaluator definitions, budget accounting, and confirmation evidence remain outside the optimizer's writable graph. Natural-language constraints are useful reminders; structural validation and independent execution must enforce the actual boundary.

A second test should deliberately include misleading local feedback and conflicting examples. The question is whether attribution helps preserve valid behavior while fixing a defect, not whether the optimizer can produce an articulate explanation. These are Everdict proposals, not tests conducted in TextGrad or existing shipped mechanisms.
