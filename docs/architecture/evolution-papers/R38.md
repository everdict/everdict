# R38 — SkillOpt: bounded edits, rejected proposals, and slow optimizer memory

SkillOpt v2 trains one reusable text skill while freezing the task-execution model. An optimizer reads scored trajectories, proposes a limited number of edits, tests them on a selection split, remembers rejected proposals, and periodically extracts longer-term lessons. Its 52-cell evaluation and extensive controls make it especially relevant to Everdict. However, a selection gate is not an independent confirmation guarantee, and several narrative claims are stronger than the paper's tables and learning curves support.[^1]

## The optimization object and comparison with related work

For model M, harness h, task x, and skill s, execution returns a trajectory and a score between zero and one. Training tasks supply candidate ideas, selection tasks choose among candidates, and test tasks measure the exported artifact. The deployed output is `best_skill.md`, not new model weights or an expanding public skill library.[^1]

TextGrad supplies textual feedback as an optimization signal. GEPA supplies reflective search with task-level evidence and diverse candidates. Trace2Skill supplies trajectory distillation, and EvoSkill supplies skill-folder evolution. SkillOpt emphasizes one persistent compact document and explicit controls over evidence batches, edit counts, rejection history, and slow updates. These are distinctions in implementation and search policy, not proof that prior prompt optimizers cannot export persistent text.

The optimizer is separate from the target. A strong GPT-5.5 optimizer can write a skill for a smaller model and disappear at deployment. That is still transfer of information from a teacher through text, even though student weights remain unchanged. Target-matched optimizer experiments test whether a stronger teacher is necessary for all gains.

## Forward evidence, reflection, and edit aggregation

Each step runs the current skill on a training rollout batch. Evidence can include messages, tool calls, observations, command output, final answers, verifier feedback, and task-specific context such as workbook previews or document references. Accumulation allows several batches to contribute to one update.[^2]

Failures and successes are separated into reflection minibatches. Failure analysis proposes corrective rules; success analysis reinforces reusable behavior not already covered. Both can return no edit. Failure proposals and success proposals are first merged separately, then combined with priority for failure corrections unless they conflict with well-supported successful behavior.

The prompts ask for common mechanisms rather than hardcoded task values. Merges retain source type and estimated support counts, remove duplicate or contradictory proposals, and rank systematic, complementary, general, actionable changes. Support counts are LLM estimates from the supplied proposals, not independent causal-effect measurements. Frequent patterns may also crowd out rare but important cases.

This differs from keeping only failures: a successful trace can explain what should survive a repair. It also differs from SkillGrad's default paired recovery evidence: SkillOpt's ordinary minibatches group current successes and failures separately, while its later slow update performs same-task comparisons across versions.

## A textual learning rate limits operations, not semantic distance

The learning-rate analogue Lₜ caps the number of selected edits. Patch mode supports append, insert-after, replace, and delete. A separate rewrite mode uses selected suggestions to condition a full rewrite. Constant, linear, cosine, and autonomous schedules are supported.[^2]

The cap makes update intent inspectable, but one replacement can still change many tokens or a central rule. It is not a bound on semantic distance, behavioral risk, or context growth. Rewrite mode weakens the interpretation of a small edit count further. Everdict should preserve the actual diff and content digest alongside an operation count.

The appendix requires edits to respect a protected slow-update region. A per-edit application report records whether each requested operation was accepted or skipped. This separates the proposal from the text actually evaluated. A useful optimizer cannot assume that a requested patch was applied merely because a model emitted valid JSON.

## Selection gating, score caching, and rejected-edit memory

Every candidate is scored on the same selection split. It becomes current only if its score is strictly higher; ties are rejected. The best accepted version is exported. Identical skill hashes reuse cached selection scores. This prevents silent textual drift on ties and avoids repeating an identical evaluation within the run.[^2]

The epoch-local rejected buffer records failed proposals, associated score changes, and unresolved patterns. Later reflection receives this evidence so that it can avoid repeating an unsuccessful idea. The buffer resets each epoch; it is not the full permanent history of the campaign.

Strict score improvement does not mean statistically reliable improvement. A small finite selection set and stochastic executions can favor lucky candidates, and caching preserves the first sampled score unless repeats are explicitly part of the evaluator. Repeated adaptive use of selection feedback can overfit that split even without exposing its answer text directly. The candidate set itself depends on earlier gate outcomes.

The paper discusses gate strictness but supplies no matched no-gate or tie-accepting ablation. Its effectiveness as a generalization mechanism should not be inferred solely from the number of rejected edits. A strict gate can also exclude neutral intermediate candidates that would support useful descendants, a tradeoff relevant to Everdict's driver search.

## Slow target guidance and optimizer-only memory are different

At epoch boundaries from epoch two onward, the method runs the same sampled training tasks under previous and current epoch skills. It groups outcomes as improvements, regressions, persistent failures, and stable successes.[^3]

One process writes longitudinal guidance into the protected region of the **target's skill**. This guidance is deployed and must itself pass the selection gate. Another writes a **meta skill for the optimizer**, summarizing which edit styles helped, failed, or caused regressions. That memory conditions future analysis, merging, and ranking, and is not shipped to the executor.

This separation is central: advice about solving tasks and advice about improving the solver are different artifacts. A same-task comparison is informative, but differences can still reflect stochastic execution or multiple simultaneous edits. A slow update is a hypothesis generated from that comparison, not a proven causal explanation.

## Benchmarks, models, harnesses, and exact experimental scope

The main suite covers SearchQA, SpreadsheetBench, OfficeQA, DocVQA, LiveMathematicianBench, and ALFWorld. Seven direct-mode targets are GPT-5.5, GPT-5.4, GPT-5.4-mini, GPT-5.4-nano, GPT-5.2, Qwen3.5-4B, and Qwen3.6-35B-A3B. GPT-5.5 additionally runs five benchmarks under each of Codex and Claude Code. ALFWorld is omitted from those two harnesses because their adapters do not represent its persistent interaction. Thus 42 + 5 + 5 gives 52 model/benchmark/harness cells.[^4]

The label direct chat does not mean every task is one tool-free answer. The protocol includes OfficeQA loops of up to twenty-four tool calls, spreadsheet code execution of up to thirty turns, and ALFWorld episodes of up to fifty steps. Native task adapters matter. OfficeQA's learned rule explicitly refers to oracle parsed pages, so its scores should not be represented as unrestricted full-corpus retrieval performance.

The default split is train/selection/test = 2:1:7 with seed 42 unless overridden. ALFWorld uses thirty-nine training tasks, 140 selection environments, and 134 test environments. LiveMath uses thirty-five training items per epoch and a rollout batch cap of 200. The appendix does not fully specify every dataset's exact membership and scoring normalization; its native-hard/EM wording should not erase differences between document QA, workbook output checking, and interactive success.

Defaults are four epochs, rollout batch forty, reflection minibatch eight, sixteen analyst workers, merge batch eight, up to three reflection refinements, edit budget four with cosine decay to two, and twenty tasks for slow updates. Teacher and student reasoning effort default to medium. The main matrix uses matched target, test split, and scorer for each baseline comparison, but does not establish equal total optimizer computation or full repeated-seed confidence intervals.

## Main matrix: broad measured gains, with a precise denominator

SkillOpt is best or tied best in all 52 measured cells, and every cell improves over its own no-skill baseline. This means 52 settings, not 52 independent replications or wins over every baseline under every harness: the direct and CLI blocks contain different comparison methods.[^5]

| Direct target | No-skill mean over six benchmarks | SkillOpt mean | Absolute gain |
|---|---:|---:|---:|
| GPT-5.5 | 58.77 | 82.28 | 23.52 |
| GPT-5.4 | 59.68 | 72.43 | 12.75 |
| GPT-5.4-mini | 48.88 | 64.33 | 15.45 |
| GPT-5.4-nano | 30.65 | 57.35 | 26.70 |
| GPT-5.2 | 51.27 | 67.88 | 16.62 |
| Qwen3.5-4B | 38.63 | 57.85 | 19.22 |
| Qwen3.6-35B-A3B | 55.88 | 65.00 | 9.12 |

These means are calculated from the printed Table 1 cells; their overall average gain is about 17.62 points. GPT-5.5's skill scores across SearchQA, spreadsheets, OfficeQA, DocVQA, LiveMath, and ALFWorld are 87.3, 80.7, 72.1, 91.2, 66.9, and 95.5. Its largest direct-mode gains are spreadsheets +38.9 and OfficeQA +39.0. The best competing method chosen separately for each benchmark averages 76.9, about 5.4 below SkillOpt.

GPT-5.5's five-benchmark mean gain is 24.8 points under Codex and 19.1 under Claude Code. Spreadsheet scores reach 85.0 and 80.4, respectively; LiveMath reaches 78.4 and 56.5. This variation demonstrates that the execution environment remains part of the result.

Not all baselines benefit from adding text. Examples include GPT-5.4's one-shot OfficeQA skill falling 50.0→20.4 and Qwen3.6's TextGrad LiveMath falling 31.2→7.2. SkillOpt avoids such negative headline cells in this matrix, but the evidence is finite and not independently reproduced here. The prose also exaggerates one ratio: GPT-5.4-nano ALFWorld 34.3→69.4 is about doubling, not tripling.

## Ablations: evidence quantity, edit budgets, and memory

The main ablation reference is 87.1/77.5/61.3 on SearchQA/SpreadsheetBench/LiveMath, distinct from the headline GPT-5.5 row. The following controls should be read against their matched reference.[^6]

Training-size analysis improves spreadsheets from 47.5 with one example to 78.0 with all training examples, and LiveMath from 59.1 to 70.5. SearchQA peaks earlier. However, Table 2 explicitly fixes a 4:1:5 split for this sweep, while Appendix C says 2:1:7. That unresolved discrepancy affects exact comparison and replication.

Reflection minibatches range from one to thirty-two and rollout batches from eight to a full epoch. SearchQA and spreadsheets are fairly stable, but LiveMath is more sensitive: reflection size two gives 54.8 versus 64.5 at four; full-epoch rollouts give 53.2 versus 62.9 at twenty-four. Larger batches change both evidence per update and update frequency.

Edit budgets of one, two, four, eight, and sixteen are tested. LiveMath's highest value in that sweep is 66.9 at eight, while spreadsheets reach 78.2 at four and sixteen. Constant/cosine/linear schedules give spreadsheet scores 80.7/77.5/72.9. This does not identify one universally best schedule, and the headline row does not equal every stated default ablation.

Removing the edit budget gives 84.6/75.7/57.3; an autonomous budget gives 85.8/71.8/54.0. Removing rejected-edit memory gives 85.5/72.9/58.9, losses of 1.6/4.6/2.4 points from the reference. Removing optimizer meta memory alone gives 85.1/75.7/58.1; removing both meta memory and slow target guidance gives 86.3/55.0/59.7. The latter is especially harmful on spreadsheets, but removing more components is not monotonically worse on the other two benchmarks.

Slow-update samples of five, ten, twenty, and forty are also compared. The prose says alternatives stay within 2.7 points, but LiveMath at forty is 54.8 versus the twenty-sample reference 61.3, a 6.5-point difference. This is a meaningful exception to broad robustness wording.

## Epoch curves show why selection is not confirmation

Figure 3 plots training, selection-best, and test performance across extended epoch checkpoints. Spreadsheet test performance rises while selection plateaus. SearchQA test performance peaks around epoch four and then slightly declines despite a flat best-selection score.[^7]

LiveMath is more concerning: test performance peaks near 0.62 at epoch four, then falls to roughly 0.57 at later checkpoints, while best-selection rises from roughly 0.77 to 0.82 by epoch sixteen. These are approximate readings of the plotted curves. They directly qualify the narrative that selection checkpoints consistently track test generalization.

The plot supplies a reason to retain independent confirmation, not a proof that the gate prevents overfitting. Repeatedly inspecting test checkpoints also means later hyperparameter choices informed by that plot need fresh confirmation evidence. The paper does not report uncertainty bands sufficient to separate all stochastic variation from systematic degradation.

## Transfer and optimizer-strength experiments

All eleven actual transfer rows are positive relative to the receiving baseline: four across models, four across harnesses, and three across math benchmarks.[^8]

GPT-5.4 spreadsheet skills improve mini by 9.4 points but nano by only 3.0, versus directly optimized gains of 11.4 and 19.0. LiveMath transfer gives mini +4.5 and nano +5.6; the nano transfer score 28.8 exceeds its direct score 27.2. Transfer can preserve much or little of the source benefit.

Codex→Claude Code spreadsheet transfer reaches 81.8 versus receiver baseline 22.1 and directly optimized 80.4. The reverse reaches 71.1 versus 27.5 and direct 85.0. LiveMath cross-harness gains are much smaller, +1.6 and +12.8. OlympiadBench→Omni-MATH gains are +3.7, +1.8, and +1.3 for GPT-5.4, mini, and nano. These support portability in tested directions without proving arbitrary cross-domain transfer.

Four optimizer-strength cells compare GPT-5.5 with a target-matched optimizer under the same loop. The matched optimizer retains approximately 56–74% of the stronger optimizer's gains. For nano spreadsheets, scores are baseline 23.5, matched 35.4, and strong 42.5. For mini SearchQA they are 75.9, 78.3, and 80.2. A stronger teacher helps these four cases, but a strict selection gate cannot mathematically guarantee that stronger teachers always generalize better or are more cost-effective.

## Artifact size, accepted updates, and cost inconsistencies

Table 6's final skills range from 379 to 1,995 tokens, with a median near 921. It records one to four **accepted bounded updates**, not necessarily one to four atomic operations. The text sometimes calls them individual edits; the caption's update unit matters because one update can contain several edits.[^9]

| Benchmark | Final tokens | Accepted updates | Training tokens | Reported million tokens per test point |
|---|---:|---:|---:|---:|
| SearchQA | 857 | 4 | 213.8M | 37.9 |
| SpreadsheetBench | 1,995 | 4 | 21.4M | 0.6 |
| OfficeQA | 883 | 1 | 20.8M | 1.1 |
| DocVQA | 959 | 3 | 188.2M | 46.4 |
| LiveMath | 379 | 1 | 23.2M | 3.6 |
| ALFWorld | 1,321 | 2 | 59.3M | 15.9 |

Most reported cost-per-point values do not equal training tokens divided by the headline Table 1 improvement. For example, OfficeQA's 20.8M divided by 39.0 points is about 0.53M, not 1.1M; LiveMath's 23.2M divided by 29.3 is about 0.79M, not 3.6M. The denominator or run identity needs clarification. Do not use that column for an Everdict cost forecast without resolving it.

The qualitative runs also have different endpoints: nano ALFWorld 49.3→74.6 and GPT-5.5 spreadsheets 40.4→78.9, rather than their main-table values. They illustrate learned rules but should not be presented as the same baseline/candidate measurements.

Rules include maintaining a search frontier, matching exact object identity, binding an answer to the correct visual row, tracking table dates and units, and choosing the strongest justified theorem statement. Spreadsheet rules favor computed literal values when the grader reads values. That can be useful in this evaluation but must not override a user's explicit requirement for live formulas. Compact wording and absence of copied entity names do not by themselves prove absence of benchmark-specific optimization.

## Everdict design implications

The strongest immediate experiment compares the existing raw-ledger driver, a static compact summary, and a maintained optimizer memory with rejected proposals and superseded advice. Keep execution budgets, edit surfaces, and disclosure identical. Test bounded operation counts separately from bounds on actual diff size so their effects are distinguishable.

Keep target-facing procedural guidance separate from optimizer-facing advice. Both need source links and versioned content, but only the target-facing artifact belongs in the deployed candidate. Preserve raw failed proposals even if an epoch-local working buffer resets. Record requested edits, applied edits, and the exact candidate evaluated.

SkillOpt's strict selection rule is a driver strategy to compare, not a universal platform adoption rule. Everdict can permit neutral or temporarily worse search parents while preserving an immutable accepted baseline. The platform must still enforce train/select/confirm boundaries, declared edits, reproducible bytes, and independent adoption evidence. The paper motivates concrete curation experiments; it does not establish that adding a gate or a meta-memory field alone makes evolution reliable.[^10]
