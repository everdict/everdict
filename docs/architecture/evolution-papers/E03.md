# E03 — Voyager: curriculum, executable skills, and feedback

Voyager connects an adaptive task curriculum, a persistent library of executable programs, and iterative execution feedback. Its frozen LLMs accumulate capabilities outside their weights while exploring Minecraft. This explanation covers **2305.16291v2**, including the implementation prompts, exploration, transfer, ablations, and demonstrations. The important result is a working combination of these components under a particular symbolic interface; it is not unrestricted autonomous learning from pixels. Results have not been independently reproduced.[^1]

## 1. Problem, prerequisites, and related work

An agent given only a distant objective can spend its entire budget attempting actions whose prerequisites it lacks. A fixed curriculum solves some ordering problems but cannot easily adapt to an unexpected world. Repeatedly regenerating low-level action sequences also wastes discoveries. Voyager addresses all three: propose an achievable new goal, solve it with feedback, and save the successful procedure for later composition.

In hierarchical reinforcement learning, an *option* is a temporally extended action with initiation and termination conditions. A Voyager skill plays a similar practical role: a JavaScript function can collect materials, craft prerequisites, and perform a larger task. However, its conditions are described or implemented in generated code, rather than learned and formally verified as an option model. Retrieval supplies procedures that an LLM can compose; it does not guarantee that their assumptions hold in a new state.

Compared with [R39 ReAct](R39.md), Voyager adds durable executable memory and autonomous goal selection. Compared with [E01 Reflexion](E01.md), it preserves working programs in addition to using critique. Compared with classical Minecraft RL and imitation learning, it exploits substantial pretrained language knowledge, a structured state interface, and expert-written control primitives. These differences explain both its efficiency and the limits of direct comparisons. [S00 WikiSkill](S00.md) later generalizes the idea of an evolving external resource toward maintained knowledge, while Voyager emphasizes procedural code.[^1]

## 2. Environment and the actual learning boundary

The implementation combines MineDojo with Mineflayer. The agent receives inventory, equipment, nearby blocks and entities, coordinates, biome, and other symbolic observations. Nearby searches generally cover 32 blocks. It does not infer these facts from camera images or learn motor control from scratch. Supplied helpers cover mining, crafting, smelting, placement, combat, exploration, pathfinding, and chest interactions.

The models are GPT-4-0314 and GPT-3.5-turbo-0301. GPT-4 handles curriculum, code generation, and success criticism; GPT-3.5 helps with intermediate planning or questions and skill descriptions. Descriptions are embedded with text-embedding-ada-002. No weights are updated. Temperatures are zero except the curriculum's 0.1. An optional Minecraft knowledge base can assist question answering, so “learning” combines pretrained domain knowledge with newly acquired procedures and observations.

Several environment accommodations matter. Death preserves inventory and respawns the agent near suitable ground. Crafting tables and furnaces are recycled after programs. The autonomous curriculum explicitly excludes building, planting, trading, and shelter construction because the symbolic interface cannot reliably verify them. The studied open-endedness is therefore exploration within a constrained task vocabulary, not arbitrary Minecraft behavior.[^2]

## 3. Adaptive curriculum and warm-up

The curriculum prompt requests one specific task that is feasible given the current state, sufficiently novel, and useful for progress. It sees completed and failed tasks, so it can avoid redundant goals or return to prerequisites after failure. Additional GPT-3.5 questions decompose what knowledge a useful next task requires; the prompt asks for several self-contained questions and can consult the knowledge base.

Observation complexity grows through a hand-designed warm-up schedule. Core inventory, equipment, nearby blocks, and position are available immediately. Nearby entities appear after five completed tasks, full inventory after seven, biome and recent blocks after ten, and health, hunger, time, and extra question answering after fifteen. This schedule is prior engineering knowledge, not a curriculum policy learned entirely from experience.

Curriculum quality is coupled to the evaluation objective. A manual sequence aimed at obtaining one diamond may be sensible for that goal while collecting fewer distinct items than a novelty-driven curriculum. Randomly selecting a difficult item without its prerequisites is a particularly weak alternative. Accordingly, the curriculum ablation measures these implemented alternatives, not the superiority of machine curricula over every human curriculum.[^2]

## 4. Skill retrieval, code repair, and admission

A skill is an asynchronous function taking the Mineflayer bot. GPT-3.5 writes a concise functional description, which becomes the embedding key; the stored value is executable code. The retrieval query includes the task plan and environment feedback, allowing prerequisite skills to be retrieved even when their names differ from the final goal. Up to five skills are supplied and retrieval is repeated during refinement.

Code generation receives the goal, relevant state, existing helper APIs, retrieved skills, prior code, execution errors, environment messages, and the critic's advice. It explains failure, plans a correction, and emits code. The prompt discourages unbounded loops, recursion, and event listeners, and reminds the model that unsaved functions from earlier rounds are unavailable. Instructions are constraints on generation, not an execution proof that every emitted function obeys them.

There are three feedback channels. **Environment feedback** includes program-written messages about missing materials or failed operations. **Execution errors** expose invalid APIs or JavaScript failures. **Self-verification** asks GPT-4 whether the resulting state satisfies the task and requests a critique if not. Each task allows an initial program and three repairs, at most four code generations. After exhaustion the curriculum selects another task. Importantly, the world continues changing between repairs; this is not four independent executions from the same initial state.

The library admits code after the critic accepts the task. It does not separately demonstrate correctness across a fresh-state precondition matrix. A function that succeeds because materials were collected by an earlier failed program can therefore be less reusable than the successful episode suggests. The printed `craftWoodenPlanks` example also saves an inventory lookup before collecting a missing log and then uses the stale value. This is a static observation about the appendix example, not a reproduced failure of the current project. It illustrates why successful episode memory and independently reusable code are different artifacts.[^3]

## 5. Exploration experiments and measurement

The principal experiments use three runs and **160 code-generation prompting iterations**. This is not 160 total LLM calls: curriculum generation, criticism, descriptions, and auxiliary questions add calls. The paper does not establish equal total tokens, money, or wall time across all methods.

The authors adapt ReAct, Reflexion, and AutoGPT to the same environment. ReAct and Reflexion receive broad exploration objectives and iterative feedback; Reflexion uses the Voyager-style critic. AutoGPT decomposes exploration into subgoals, treats execution without error as subgoal completion, retries failures, and replans after repeated lack of new items. Its completion test is weaker than Voyager's semantic critic. These are documented ports, so the comparison is against these configurations rather than every possible implementation of the named frameworks.

Voyager obtains about **63 distinct items**, approximately **3.3 times AutoGPT**, and reports **2.3 times greater travel distance**. Unique items reward discovery, not reliability, usefulness, or repeated competence. Recorded coordinates and map snapshots demonstrate broader exploration, but enclosing map circles are not proof that every enclosed block was visited.

| Method | Wooden tool | Stone tool | Iron tool | Diamond tool |
|---|---:|---:|---:|---:|
| ReAct / Reflexion | 0/3 | 0/3 | 0/3 | 0/3 |
| AutoGPT | 92±72; 3/3 | 94±72; 3/3 | 135±103; 3/3 | 0/3 |
| Voyager without library | 7±2; 3/3 | 9±4; 3/3 | 29±11; 3/3 | 0/3 |
| Voyager | 6±2; 3/3 | 11±2; 3/3 | 21±7; 3/3 | 102; **1/3** |

Numbers preceding success fractions are reported prompting iterations. The 15.3×, 8.5×, and 6.4× speed claims follow from the wood, stone, and iron means relative to AutoGPT; they are not measured wall-time ratios. The library does not improve every cell: the no-library variant reaches stone tools sooner. Diamond discovery during exploration succeeds in only one of three full-system runs.

There is a reporting inconsistency: the appendix's first AutoGPT item list contains none of the tool categories whose Table 1 rows report 3/3 success. The scope of these listed runs is insufficiently explained to reconcile them. The unusually wide reported ± values also lack enough detail here for independent uncertainty reconstruction. Preserve the table as reported rather than silently repairing it.[^4]

## 6. Fresh-world transfer and portability

The transfer experiment resets the world and inventory and asks for four previously unseen target tasks. It permits **up to 50 prompting iterations**, including decomposition and repair. “Zero-shot” means no additional task-specific training examples or weight training; it does not mean one attempt or zero adaptation during execution.

| Method | Diamond pickaxe | Golden sword | Lava bucket | Compass |
|---|---:|---:|---:|---:|
| Voyager | 19±3; 3/3 | 18±7; 3/3 | 21±5; 3/3 | 18±2; 3/3 |
| Voyager without library | 36; 2/3 | 30±9; 3/3 | 27±9; 3/3 | 26±3; 3/3 |
| AutoGPT with Voyager library | 39; 1/3 | 30; 1/3 | 0/3 | 30; 2/3 |
| ReAct / Reflexion / AutoGPT | 0/3 | 0/3 | 0/3 | 0/3 |

The no-library Voyager remains strong, solving eleven of twelve attempts. This shows that planning and repair already explain much of the downstream capability; the bank mainly improves efficiency and the hardest task's reliability in these small samples. Supplying Voyager's bank to AutoGPT produces four successes out of twelve versus zero without it, supporting some cross-harness portability, with a substantial remaining gap. Rows with failures do not fully specify how unsuccessful attempts enter timing averages; do not interpret a successful run's iteration count as expected cost per arbitrary task.[^5]

## 7. Ablations, retrieval, and human demonstrations

The study removes or changes the curriculum, skill library, environment feedback, execution errors, critic, and code generator. Random curriculum reduces discovered items by a reported **93%**. Removing the critic reduces them by **73%**. However, the no-critic version spends a fixed four generations per task, while a successful full-system task may stop earlier. The effect mixes feedback quality with how the exploration budget is distributed.

Replacing the code generator with GPT-3.5 produces **5.7 times fewer items** than the full version. GPT-4 still supplies curriculum and criticism in this ablation; it is not an all-GPT-3.5 system comparison. Removing the library causes later stagnation, consistent with compositional reuse becoming more useful as procedures grow. Removing environment messages or interpreter errors also hurts, but these interventions do not establish that every natural-language explanation is causally accurate.

On **309 retrieval samples**, reported top-1 to top-5 accuracy is **80.2, 89.3, 93.2, 95.2, and 96.5%**. This supports returning several candidates, while leaving questions about labeling, all-prerequisite coverage, and whether retrieved code is correctly used. Additional GPT-4 version comparisons indicate broadly similar exploration curves for the tested versions; they do not establish robustness to arbitrary models.

House and Nether-portal demonstrations replace the automatic critic with **human visual feedback** and use human task decomposition. They show that the architecture can incorporate such assistance, not that the autonomous symbolic system independently learned unrestricted construction. The human intervention is especially relevant because autonomous curriculum prompts otherwise forbid building-related tasks.[^6]

## 8. Failure modes and evidence limits

The model can invent nonexistent items, recipes, fuels, or APIs. A critic can reject a successful task because an expected item name differs, or accept an action based on a weak final-state proxy. Appendix examples infer killing a zombie from rotten flesh, eating from full hunger, and planting from nearby wheat. Without comparing initial state and action provenance, preexisting items or conditions can satisfy these proxies. Program-written chat is also not independent evidence of what occurred.

Persistent storage prevents literal deletion of earlier functions, but does not prove freedom from behavioral forgetting: retrieval can miss them, assumptions can become invalid, and composition can misuse them. Unbounded-loop patterns appear in example code despite prompt prohibitions. Three-run experiments, incomplete total-cost accounting, pretrained Minecraft knowledge, specialized helpers, and narrow transfer tasks limit generalization. The contribution remains substantial: executable memory plus adaptive goals and repair work together, while reusable correctness needs stronger admission evidence.

## 9. Concrete Everdict evolution proposals

Voyager suggests separating **what to try next**, **how to repair it**, and **what deserves retention**. In Everdict's proposed first loop, the driver could prioritize authorized training probes using unresolved failure families and missing prerequisites. The platform would continue fixing the campaign objective, budget, disclosure, and confirm split. A curriculum must not redefine success or turn confirm outcomes into new training instructions.

A first experiment should compare a fixed task order with adaptive selection while holding candidate representation, eligible training pool, and total evaluation budget constant. Measure independently confirmed capability gains and family coverage, not only the number of attempted tasks or saved records. A second experiment can compare plain retrieved guidance with composable executable helpers, charging the latter for building, validation, and maintenance. A third can isolate structured runtime evidence, interpreter errors, and generated critique under matched call budgets.

For code retention, require an immutable candidate with source/build digests, declared preconditions, fresh-state replay, and relevant regression cases. Preserve the successful continuous episode separately: it explains discovery but is weaker evidence than restarting with the declared prerequisites. Store a critic's diagnosis as a hypothesis linked to observations, not as a platform verdict. Record retrieval misses, invalid assumptions, and composition failures as distinct failure types.

These are research proposals, not shipped Everdict behavior or authorization to add a new campaign subject. They fit the existing separation between driver search and platform settlement: a useful library entry can remain a candidate or stepping stone without being promoted to an active capability. See the [first-loop design](../evolution-first-loop.md) for the proposed authority boundary.
