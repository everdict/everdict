# R04 — SkillCraft: learning reusable tool compositions

SkillCraft asks whether an agent can recognize a recurring sequence of tool calls, turn it into a parameterized program, and reuse it efficiently. It contributes both a benchmark and a small skill-library protocol. A useful skill here is executable composition: intermediate data can stay in program variables instead of repeatedly passing through language-model context. The inspected paper is arXiv 2603.00718v2.[^1]

## Research problem and surrounding ideas

Ordinary tool benchmarks often reward solving one task with a fixed tool set. If only two calls are needed, inventing a reusable abstraction has little value. SkillCraft deliberately creates longer tasks with repeated structure, where solving each entity from scratch is inefficient. This makes success, acquisition cost, and reuse observable together.

The background is procedural learning and the idea that intelligence includes acquiring reusable skills with limited resources. Existing environments such as Toolathlon, WebArena, and M3ToolEval provide tool-use tasks; executable libraries such as Voyager show how code can preserve a learned behavior. SkillCraft concentrates on whether composition reduces actual work, rather than whether a model can produce a document named as a skill.[^1]

## Benchmark construction

The authors first explore more than 60 tasks from existing benchmarks, then create 21 seed task families: five adapted tasks, twelve handcrafted web-API tasks, and four local processing tasks. Scaling the number of entities and the complexity of operations produces 126 tasks, distributed as 63 easy, 42 medium, and 21 hard cases. APIs include GitLab, weather, public reference data, and local DNA processing.[^1]

For an illustrative workflow, an agent might retrieve metadata, obtain related records, and produce a structured summary for each of several entities. A single function taking an entity identifier can perform that chain repeatedly. The model still chooses the goal and handles exceptional cases, but need not re-read every intermediate record after each atomic API call. This example explains the benchmark's repeated structure; it is not an additional reported result.

## Protocol and verification

The skill library exposes four operations: save, retrieve, list, and execute. A stored entry contains executable code, parameter names, a description, and execution statistics. The agent first checks for reusable skills. If none fits or execution fails, it uses atomic tools, abstracts the successful sequence into a parameterized program, tests it, and stores it for reuse.[^2]

The coding verifier has three distinct checks. Syntax validation rejects malformed code with location information. Runtime failures return exception and input details to support repair. A post-execution heuristic detects suspiciously empty outputs, such as more than half of fields being unknown, null, or zero. These checks establish increasingly useful operational properties, but the last rule can reject legitimate zero-valued results and does not prove semantic correctness. Final task scoring remains separate.

The implementation describes a maximum of 150 conversation turns, a 60-minute task timeout, token limits, and temperature 0.0. Skills execute through a unified tool-call interface. Even at zero temperature, reproducibility also depends on provider behavior and external API state; freezing the sampling parameter alone is not a complete deterministic environment.[^2]

## Experimental design and metrics

Eight models are compared with and without the skill mechanism: Kimi-K2-Thinking, DeepSeek-V3.2-EXP, DeepSeek-R1, GLM-4.7, MiniMax-M2.1, GPT-5.2, Gemini 3 Pro, and Claude 4.5 Sonnet. Human-authored task rules score outputs; a task succeeds at a score of at least 90%. Partial credit can cover output existence, valid structure, completeness, and field accuracy.[^3]

The study reports overall task success, successful skill executions, reuse count, tokens, API cost, turns, and tool calls. Crucially, **efficiency is averaged only over tasks where both compared modes succeed**. That paired-success restriction makes the consumption comparison more interpretable, but it excludes failures and therefore does not give the total cost of completing the whole benchmark.

## Main results

| Model | Successful tasks, baseline → skill | Token change on mutually successful tasks | Interpretation |
|---|---|---:|---|
| GPT-5.2 | 109/126 → 114/126 | −79% | Large reduction in context traffic with a modest success gain |
| Claude 4.5 Sonnet | 119/126 → 121/126 | −71% | Near-ceiling success; most value is efficiency |
| GLM-4.7 | 91/126 → 108/126 | −39% | A substantial task-success gain as well as savings |
| DeepSeek-V3.2-EXP | 76/126 → 87/126 | −49% | Useful composition despite imperfect skill execution |
| Kimi-K2-Thinking | 55/126 → 56/126 | −42% | Almost unchanged success; turns increase by 24% |

These Table 2 results explain why “up to about 80% fewer tokens” must be tied to a specific model and the paired-success subset. Savings in tokens do not imply fewer model turns for every executor. Execution rates range widely; a saved skill can still fail on a later invocation. API dollar figures are historical measurements, not current price estimates.[^3]

## All additional experiment families

**Hierarchical composition.** Nesting skills inside skills increases abstraction but also propagates exceptions and incomplete fields. DeepSeek improves from 87 to 92 successful tasks when moving from flat to hierarchical skills; GPT-5.2 drops from 114 to 100, and Claude remains at 121. Hierarchical GPT skill execution is 95%, yet end-task success falls to 79%. Local execution success is therefore insufficient to establish overall utility.[^4]

**Cross-task transfer.** Easy-to-hard, hard-to-easy, and hard-to-same-hard reuse are evaluated for Claude and Gemini. Gemini's easy-to-hard task success rises from 16/21 to 19/21 while tokens fall 41%; Claude's rises from 20/21 to 21/21 with 19% fewer tokens. Reusing a skill on the same hard task can establish amortization but is not evidence of generalization to a new task distribution.[^4]

**Cross-model static reuse.** Four creators and four executors yield sixteen combinations on eight hard tasks. Agents may execute supplied skills but cannot create new ones. Claude-created skills achieve success on all eight tasks for all four receivers, with reported token savings of 54–81%. MiniMax-created skills range from increased token consumption to modest savings. The small sample supports sensitivity to skill quality; it does not establish universal transfer.[^4]

**Direct execution and trajectory analysis.** On a 48-task subset, directly running existing skills can reduce tokens further but loses success in some settings: GPT's baseline succeeds on 45 tasks, skill mode on 43, and direct execution on 41. Qualitative traces identify omitted output fields, syntax failures, incorrect tool chaining, and expensive repairs. The paper also breaks down results by difficulty. These experiments show that deciding when to abstract and when to recover manually is part of the capability being measured.[^4]

## Limits and connections to evolution

The benchmark is constructed to make repetition common, so its efficiency gains may be smaller in one-off or rapidly changing workflows. Live APIs introduce environmental variability. A shallow validation heuristic can miss wrong but well-formed results. Hierarchies also need versioned dependencies: changing a low-level helper can change every skill that calls it.

Unlike WikiSkill's instruction optimization, SkillCraft emphasizes executing reusable code and keeping data out of model context. Unlike retrieval-only benchmarks, it measures actual task completion and usage. Its protocol can supply a mutation target for an evolution system, but the benchmark itself does not establish that a long-running optimizer continually improves a library.

## Everdict experiment and proposed changes

Represent executable skill bundles with pinned helper dependencies and record invocation, input/output schema, exception, fallback, and final task outcome separately. Compare atomic tools, flat executable skills, and nested skills on repeated artifact-processing workflows. Hold the underlying tools and verification logic fixed, and vary entity count to test where abstraction pays for its construction cost.

Report whole-campaign cost including skill synthesis, verification, failures, repairs, and repeated execution, alongside the paper-style paired-success metric. Evaluate reuse on new entities, new task families, and another executor as distinct transfer axes. A candidate should be valuable when verified task utility improves per total budget; successfully storing or executing a function is only an intermediate event. These are proposed Everdict changes inferred from the study.
