# R21 — SpreadsheetBench: testing a reusable transformation across workbooks

SpreadsheetBench evaluates whether a model can produce a spreadsheet transformation that works on several input workbooks for the same instruction. Its main contribution is a realistic artifact benchmark and an online-judge-style evaluation, not an evolution optimizer. For Everdict, it explains why a candidate should be tested against input variation and why executable code, plausible output, and robust task completion are different outcomes. This note follows arXiv 2406.14991v2; model results are historical results from that paper.[^1]

## Problem and neighboring benchmarks

A spreadsheet is not necessarily a clean relational table. A sheet can contain several tables, missing or nested headers, explanatory text, colors that encode meaning, and outputs placed in a specific range. A workbook can contain several sheets whose names or roles are selected by cell values. Flattening this into a short CSV-like preview can remove information needed to solve the task.

The paper distinguishes manipulation from TableQA, table-to-text, and text-to-SQL. Here the answer is a modified workbook, produced by code or another procedure; it is not merely a textual value extracted from a table. SheetCopilotBench and SheetRM largely use synthetic instructions and simpler workbooks. InstructExcel includes more complex files but shorter annotated instructions and one test case per instruction. SpreadsheetBench adds forum-derived problem context and several tests of the same proposed transformation.[^2]

This connects naturally to program synthesis and code evaluation. A script that happens to write the right values for one example may be overfit. Reapplying the same script after changing input data tests whether it learned a transformation rather than copied a result. Three cases still cover only a tiny part of the possible input space; the benchmark improves evidence rather than proving universal correctness.

## Dataset construction and what was excluded

The authors source material from ExcelForum, MrExcel, ExcelGuru, and Chandoo. They retain solved, spreadsheet-focused, feasible, and representative questions, using solved tags or GPT-4-assisted identification, keyword filtering, and human review. Posts without attachments, ambiguous or excessively long discussions, and software-interface questions involving buttons/forms are excluded. This favors tasks that can be formalized and checked, not every difficult need encountered by spreadsheet users.[^3]

GPT-4 condenses information spread across a thread into a self-contained instruction; annotators check completeness against the original discussion and attachments. They obtain the reference workbook either from an accepted answer or by applying the forum's formula/VBA procedure. The instruction specifies the target cells or sheet range so that equivalent placements do not become accidental grading disagreements.

Twenty experienced Excel annotators construct the data, with two validators and two authors performing successive quality checks. For each suitable instruction, annotators create two additional input variants and derive their outputs using the same reference procedure. Modifications should preserve the instruction's meaning and exercise plausible edge cases, such as blank cells rather than zero-valued cells. A reference procedure can itself be incomplete, so inherited forum acceptance is useful provenance but not a formal oracle proof.

Instructions are rewritten, input values changed, and some table/answer positions moved to reduce exact memorization from public forum material. These perturbations mitigate straightforward leakage; they do not establish that a pretrained model has never seen the underlying problem or solution strategy. Dataset versions and original source lineage still matter.

## Scale, structure, and software independence

The release contains 912 instructions and 2,729 input-output test cases, averaging approximately three cases per instruction. It covers ten broad operations: finding, extracting, summing, highlighting, removing, modifying, counting, deleting, calculating, and displaying. Instruction length averages 85.7 words; the table compares this with 27.9 for SheetCopilotBench and 9.8 for InstructExcel.[^2]

About 35.7% of spreadsheets contain multiple tables and 42.7% contain nonstandard relational tables. Most are small, but the long tail exceeds 100 columns and 20,000 rows. The workbook/file statistics include 2,019 single-sheet and 710 multi-sheet files, totaling 3,917 sheets. Later analysis groups tasks rather than files, so its multiple-table and nonstandard percentages differ; those are different denominators, not interchangeable corpus statistics.

The benchmark uses XLSX and focuses on operations intended to be portable across spreadsheet applications. It permits Python manipulation rather than requiring one product's API. This is a practical attempt at software independence, not a guarantee that every spreadsheet engine interprets formulas, styles, and cached values identically. A reproduction should pin the calculation engine and grading implementation as well as the files.

## Evaluation: soft and hard restrictions

For a given instruction, the agent sees an input workbook and produces one code solution. The solution is then applied to the associated test workbooks. Each output is compared with the reference at the designated answer location. Different implementations are allowed; the dataset does not require reproducing the reference formula or VBA text.[^4]

The soft score first computes the fraction of accepted cases for each instruction, then averages those fractions across instructions. The hard score counts an instruction only if all its cases pass. For an illustrative three-case instruction with two correct outputs, the contribution is two-thirds to the soft score and zero to the hard score. This is partial credit across test cases, not necessarily partial credit for individual correct cells inside a failed case.

The same generated procedure must handle all cases. Independently regenerating a tailored script for each workbook would be a different protocol and could conceal brittle transformations. Conversely, a lower hard score can reflect a single corner-case failure even when most examples work. Report both scores and the failed variants rather than treating one number as a complete diagnosis.

The checker observes designated answer regions and its implemented semantics. It does not automatically certify every untouched workbook property or every possible functional equivalence of formulas. Preservation requirements and recalculation behavior should be explicit if an Everdict campaign needs them.

## Main experimental protocol

The paper evaluates TableQA systems, open code models, open general models, proprietary LLMs, and spreadsheet products. Ordinary code-generating models receive the instruction, workbook path, a small row preview, manipulation type, answer range, and output path. The single-round condition generates one solution. The multi-round condition allows up to five turns of content-inspection code or final-solution code, returning execution output and tracebacks when execution fails.[^5]

This feedback is not equivalent to revealing the hidden answer workbook. A script can run without exception and still implement the wrong rule. The protocol's stopping behavior therefore matters: once the final workbook is produced successfully, a semantic mistake may receive no repair opportunity.

TableQA systems instead generate textual answers separately for each test case, an interface difference that limits direct interpretation as a code-generation comparison. Spreadsheet products are manually evaluated on only fifty instructions and one case each, approximately five percent of the dataset; their soft numbers do not measure the full three-case robustness requirement. Human experts are evaluated on fifty instructions with three cases each, providing formula/VBA solutions rather than directly filling known answers.

The reported sampling parameters are temperature 1 and top-p 1. Open models run on an Ubuntu 22.04 machine with eight A100 80GB GPUs. Product evaluations use their actual application interfaces. The main table should not be interpreted as a current leaderboard or a uniformly repeated, equal-cost comparison.

|---|---:|---:|
| CodeQwen 7B | 0.51% / 0.33% | 3.66% / 2.97% |
| DeepSeekCoder 33B | 2.60% / 2.20% | 5.31% / 3.85% |
| Mixtral 8×7B | 3.11% / 2.42% | 3.88% / 2.85% |
| Llama 3 70B | 1.32% / 1.10% | 3.74% / 3.18% |
| GPT-3.5 | 2.34% / 1.64% | 7.09% / 5.37% |
| GPT-4o | 18.35% / 15.02% | 16.96% / 13.27% |

Binder has soft 1.17% and hard 0%; TaPEx/TaPas score zero in this task interface. On their restricted sample, SheetCopilot scores 14% and Copilot in Excel 20%, with no hard score. Human experts score 71.33% soft and 62% hard on their fifty-instruction sample. The human/product subsets and different case counts prevent treating all rows as measurements on an identical population.[^6]

The main GPT-4o result is a counterexample to assuming more interactive turns always help. The authors initially attribute the decline partly to redundant reading of already provided rows. Most weaker code models improve with execution feedback, although their final performance remains low. The gap between soft and hard scores also shows that successful visible examples do not ensure robustness to changed values.

## Additional experiments revise the multi-round story

Appendix D runs four repetitions on a 200-instruction sample and aligns the prompts more closely, including removal of a single-round-only instruction to answer carefully. It compares four settings: preview only; preview plus execution-error repair; ReAct inspection plus repair without the preview; and ReAct plus repair plus preview.[^7]

For GPT-4o, mean soft/hard scores are respectively 12.79/10.63, 16.08/13.50, 13.54/10.88, and 14.67/11.75. For GPT-3.5 they are 5.38/4.00, 6.58/4.50, 5.50/4.38, and 6.04/4.25. Standard deviations are reported for these repeats. In this experiment, all multi-round means exceed the single-round mean, while execution-error repair without ReAct inspection is strongest.

This does not simply “correct” the main table by averaging more runs: the subset and prompt also change. It provides evidence that the interaction design, sampling variation, and information-acquisition behavior affect the result. The experiment does not show that ReAct is universally harmful; it shows that this implementation often rereads known rows or fails to choose useful new regions.

A further fifty-instruction analysis varies preview rows among 1, 2, 5, and 10 and varies turn limits. Performance tends to improve up to five rows, but ten rows hurts in two settings. More turns show an overall upward trend in the repeated appendix experiment, unlike the earlier main plot. These are small, historical sensitivity studies, not a universal five-row optimum.

## Structural analysis, qualitative failures, and metric audit

GPT-4o's soft score is 20.63% for tasks with at most fifty rows versus 11.50% for larger ones; 22.50% with at most ten columns versus 10.51% for more; 21.12% for single-table tasks versus 13.71% for multiple tables; and 19.50% for relational tables versus 16.95% for nonstandard tables. These are observational task groups, not controlled edits to the same workbook, so complexity and task type may be confounded.[^6]

The case studies isolate two failure families. One model understands a task but uses the wrong column index/object when writing code. Another writes executable code after misaligning a lookup table or reading only its first ten rows, leaving relevant entries unprocessed. A blank-versus-zero example shows why value perturbations matter. A sheet-selection example changes the controlling cell from one sheet name to another, exposing hardcoded source-sheet assumptions.

The metric audit samples fifty instructions and 150 cases with GPT-4o outputs. It observes no false discoveries among accepted cases, while 3.8% of rejected cases are judged correct by humans. At instruction level, 4% contain at least one correct prediction rejected by the metric. Extra output content is one cause. The appendix's prose briefly reverses the error-direction wording; the defined rates clearly indicate observed false rejections, not proof of zero error in every direction.[^8]

A small audit finding zero false positives does not establish an infallible checker. Its useful lesson is to audit both accepted and rejected outputs, and to distinguish strict contract violations from semantically acceptable alternative formatting.

## Everdict evolution proposal and limits

For an artifact-manipulation campaign, make the candidate a reusable transformation procedure and group related input variants under one task family. Keep those variants together when splitting train, selection, and confirmation; otherwise near-identical workbooks can leak across the evaluation boundary. Freeze the exact code or declared candidate behavior before running hidden variants, and preserve output hashes, checker version, and calculation-engine identity.

Candidate improvements could target workbook inspection, range discovery, type/blank handling, or post-write verification. Compare a seed with a structured-inspection helper and with a budget-matched generic retry baseline. Evaluate all-case success, partial case success, preservation of required structure, cost, and failure categories. A repair that eliminates Python exceptions should still face the independent semantic checker.

The benchmark's source selection excludes some messy real workflows, its approximately three cases are not exhaustive, and public-source perturbation is not a contamination proof. WikiSkill uses its own 80/40/280 subset split, so its results cannot be directly compared with this paper's full 912-instruction experiment. These are proposed Everdict evaluation practices; no new runtime campaign has been implemented by this note.
