# E04 — ADAS: searching for agent architectures in code

*Automated Design of Agentic Systems* introduces ADAS as a research formulation and **Meta Agent Search** as one implementation. A frozen foundation model writes agent programs, evaluates them, and uses an archive of previous designs to propose further designs. This explanation covers **2408.08435v2**, all five main domains, cross-domain and cross-model transfer, initialization experiments, and the printed framework and agents. Results have not been independently reproduced.[^1]

## 1. The problem and three-part formulation

A reasoning agent is more than a prompt. It can generate several solutions, assign roles, critique candidates, execute tools, retain intermediate information, and decide when to stop. Optimizing only an instruction string leaves these structural choices fixed. ADAS asks whether the architecture itself can be discovered automatically.

The formulation separates a **search space**, a **search algorithm**, and an **evaluation function**. The search space determines what programs are expressible; the algorithm determines which are tried; the evaluator determines what counts as progress. These are independent design choices. A rich representation cannot compensate for a misleading evaluator, and an expressive language does not imply that finite search will find every useful program.

Python is used because the proposing model already has code-writing knowledge and can represent branches, loops, prompts, tool calls, and communication patterns together. The paper invokes Turing completeness to motivate expressiveness. In practice, the experiments search a `forward` function inside a small, supplied framework with fixed APIs and models. They do not demonstrate unrestricted discovery of every possible agent, new foundation-model training, or autonomous modification of the outer search algorithm.[^1]

## 2. Relation to neighboring methods

Chain-of-thought, self-consistency, [E02 Self-Refine](E02.md), debate, role assignment, and decomposition are human-designed building blocks. ADAS can combine and modify their implementations. Prompt optimizers such as OPRO change narrower components, while graph-based workflow methods search predefined nodes or edges. [E13 DSPy](E13.md) compiles structured language-model programs, and [E05 AFlow](E05.md) later supplies a more explicit workflow-search strategy.

The archive connects Meta Agent Search to quality-diversity and open-ended evolution: an intermediate design can contribute an idea without immediately being the best scorer. This resembles the stepping-stone motivation of [E10 MAP-Elites](E10.md) and [E11 POET](E11.md), but ADAS does not implement their behavioral grid or environment–policy coevolution. Its novelty pressure is a language-model judgment requested in a prompt, not a measured diversity objective.

[E12 FunSearch](E12.md) also uses language models to write code under external evaluation. ADAS changes the object of search from a mathematical or optimization program to an agent that itself calls language models. Higher-order self-improvement of the meta-agent is proposed as future work, rather than tested in this paper.[^2]

## 3. Framework and search loop

The supplied framework has fewer than 100 lines excluding comments. An `Info` record carries a name, author, content, and iteration index. An `FM_Module` constructs prompts by combining such records, adds a role and requested output fields, calls a model, and returns structured responses. The candidate implements `forward(taskInfo)` and returns the final answer.

A search iteration has four stages. First, the meta-agent reads the domain description, framework, output contract, and archive of prior programs and scores. It proposes a rationale, name, and complete function. Second, two self-reflection calls review novelty, implementation mistakes, and possible improvements. Third, the candidate runs on validation tasks; runtime errors can trigger up to five debugging attempts and re-evaluations. Fourth, the refined program and its performance enter the archive. Search continues for a fixed number of iterations.

The archive is normally seeded with hand-designed baselines. There is no requirement that a new program beat the incumbent before its design becomes available as inspiration. That preserves potentially useful ideas. However, only numerical performance and runtime errors are central to the described outer feedback; systematic analysis of full success/failure trajectories is explicitly future work. A rationale that says a design is novel or useful is not an independent causal explanation of its score.

The meta-model is **gpt-4o-2024-05-13**, called GPT-4 in the main text; default execution uses **gpt-3.5-turbo-0125**. Default framework sampling temperature is 0.5, and candidates can set other temperatures. Thus the result involves a stronger model designing workflows for a cheaper model. It is not the weaker model alone discovering its own improvement.[^3]

## 4. ARC experiment: learning a transformation program

ARC tasks show input/output grids and require the output for a new input. Here grids are strings of two-dimensional integer arrays, not visual model inputs. Agents write transformation code. Supplied tools test that code against the task's visible demonstration pairs and apply it to the hidden-output input. Matching visible examples is legitimate within-task feedback; the final grid is scored by exact match.

The experiment selects **20 validation and 60 test questions**, limited to grids at most **5×5** from ARC's public easy training collection. Each agent is assessed five times on each split. Search runs **25 iterations**. This is a small, filtered ARC setting, not the full ARC benchmark or a claim of general intelligence.

On GPT-3.5, the strongest listed baseline is self-consistency at **8.0±3.2%**, versus **13.7±3.9%** for the best listed discovered architecture. Figure 3's staircase shows progressively better observed test scores, ending around 13.7%. All discovered agents are evaluated on test, and the cross-model experiment explicitly chooses the three agents with the **best test accuracy**. Therefore test has also served an analyst selection role for that transfer procedure; it should not be described as a final untouched confirmation set for selecting those architectures.

The design story is compositional: early candidates add multiple initial solutions, later candidates add memory for refinement, and subsequent ones combine human-like critique with efficiency, readability, and simplicity roles. These are plausible stepping stones visible in the archive. The paper does not remove individual ancestors or replay alternative histories to prove that each was necessary.[^4]

## 5. What the discovered ARC program actually does

The printed best agent generates five candidate programs at temperature 0.8 and retains those passing at least one demonstration. Each surviving candidate receives a human-like critique and three expert critiques. It then undergoes up to three refinement rounds with execution feedback. The three candidates with the largest visible-example pass counts are presented to a final model that generates a new program for the test input.

This mechanism has two distinct sources of guidance: executable example checks and model-authored critiques. The latter are not human feedback simply because their prompt says “human-like.” A role named “Efficiency Expert” is still a prompted instance of the same model, without independent expertise or a runtime efficiency benchmark.

Static inspection also exposes important limitations in the appendix listing. Its feedback “deduplication” splits the text into words, makes a set, and rejoins it, destroying sentence order rather than merging redundant propositions. A revision replaces a previous solution whenever it passes at least one example, even if its pass count is lower. The final decision stage generates fresh code without a visible final demonstration check in that listing. Moreover, it calls an existing `refinement_module` instance as though constructing a new `FM_Module`, passing a `temperature` keyword that the printed `__call__` signature does not accept.

These are observations about the published example, not proof that the evaluated repository had the identical errors: the appendix says some names were edited for presentation. They make exact source snapshots and replay essential before reusing the code. The architecture diagram and descriptive names alone are insufficient implementation evidence.[^4]

## 6. Four reasoning domains and principal results

Separate searches run for **30 iterations** on DROP, MGSM, MMLU, and GPQA. GPQA Diamond is divided into **32 validation and 166 test** questions and evaluated five times. The other domains use **128 validation and 800 test** examples with one evaluation each. DROP uses a one-shot question format; the others use zero-shot formats. Repeated inference on the same questions is not multiple independent search runs.

| Measure | Best hand-designed baseline | OPRO prompt optimization | Meta Agent Search |
|---|---:|---:|---:|
| DROP F1, 0–100 | 65.8±0.9 | 69.1±0.9 | **79.4±0.8** |
| MGSM accuracy | 39.0±3.4 | 30.6±3.2 | **53.4±3.5** |
| MMLU accuracy | 65.9±3.2 | 67.6±3.2 | **69.6±3.2** |
| GPQA accuracy | 31.6±3.2 | 32.9±3.2 | **34.6±3.2** |

The headline gains of **13.6 F1 points** and **14.4 percentage points** compare DROP and MGSM against their strongest hand-designed baselines. MMLU and GPQA gains are smaller, with overlapping reported 95% bootstrap intervals. The paper bolds results whose median lies inside the best treatment's interval; this convention is not a pairwise significance test proving equivalence or superiority.

The authors hypothesize that reading and arithmetic errors can be reduced by workflow changes, whereas missing scientific knowledge limits GPQA improvements. This is an interpretation, not a controlled knowledge intervention. The study also lacks a per-question inference-cost-matched comparison: a discovered agent may make substantially more model calls than a baseline. Its quality gain is a system-level result, not an isolated benefit of architecture at fixed compute.[^5]

## 7. Transfer across domains and models

Three MGSM agents transfer to other math datasets without a new target-domain search. The strongest result per column is **69.5% GSM8K**, **31.2% GSM-Hard**, **82.6% SVAMP**, and **91.8% ASDiv**, compared with best hand-designed values **43.6, 18.0, 78.5, and 89.2%**. The strongest design differs by dataset. The large GSM8K and GSM-Hard gaps are 25.9 and 13.2 points; related math benchmarks should not automatically be treated as unrelated task families without source-problem deduplication evidence.

Beyond math, these agents reach up to **71.9 DROP F1** and **67.0 MMLU accuracy**, versus baseline best 65.8 and 65.9. But the best MGSM agent drops to **62.4 on MMLU** and **28.6 on GPQA**. Across all three transferred agents, GPQA is only **28.6–29.9**, below the best baseline's 31.6. Overlapping uncertainty can support cautious comparability, not the claim that every transfer improves performance.

ARC transfer tests Claude 3 Haiku, GPT-4o, and Claude 3.5 Sonnet. The Dynamic Memory and Refinement agent reaches **9.7, 37.0, and 48.3%**, versus each model's best hand-designed **6.3, 23.0, and 39.3%**. Yet the architecture that was best on GPT-3.5 scores only **5.0 on Haiku** and **38.7 on Sonnet**, below those baseline bests. Model–architecture compatibility matters, and choosing the best of three separately for each target is different from deploying one fixed winner everywhere.[^6]

## 8. Initialization, example designs, and costs

Removing baseline seeds produces **73.9 DROP, 67.5 MGSM, 68.5 MMLU, and 32.7 GPQA**, compared with seeded **79.4, 53.4, 69.6, and 34.6**. Empty initialization is substantially better on math by **14.1 points**. This challenges a universal “more good examples always help” claim and motivates exploring seed-induced search bias. It does not isolate the cause without replicated search seeds and diversity analysis.

Other appendix designs illustrate cross-review among four role-based solvers, decomposition followed by round-robin expert assignment, and generation–verification–use of a purported visual representation. The “Verified Multimodal Agent” passes representations through the same text/JSON interface; its name is not evidence of rendered-image perception or externally verified diagrams. The appendix also labels GPQA “Reading Comprehension,” a naming error inconsistent with the domain definitions.

Reported historical API expense is approximately **$500 per ARC search-and-evaluation run** and **$300 per reasoning-domain run**, mostly executor evaluation calls. These are 2024 experiment estimates, not current prices or per-task deployment costs. The paper optimizes performance alone. Multi-objective cost/latency optimization, richer trace feedback, continual deployment adaptation, and meta-agent self-modification are future directions. Experiments remain single-question tasks, even when their internal workflows have many steps.[^7]

## 9. Concrete Everdict evolution proposals

ADAS supports broadening the **declared candidate edit space** from prose to selected agent-code components, provided the campaign evaluator and authority remain fixed. In the proposed first loop, every candidate would still require exact source and build bytes, a bounded execution interface, and its own evidence. A readable program is easier to inspect than an opaque label, but readability is not correctness or authority to execute arbitrary operations.

The strongest immediate experiment is an archive comparison: retain only the best candidate, retain all scored candidates, or retain a diverse curated projection while keeping the raw append-only ledger. Keep proposer model, training/selection pools, total evaluation budget, and allowed edits identical. Measure later confirmed improvements, lineage reuse, cost, and regressions. A low-scoring ancestor can remain available as a search ingredient without becoming an active capability.

A second experiment should compare prompt-only and prompt-plus-workflow edits under matched execution budgets. Count model calls, retries, tool work, and search costs separately; otherwise an apparent architecture improvement may be extra sampling. Use validation for adaptive selection and reserve a fresh confirm set after the winner and build digest are fixed. Test transfer by freezing the source winner before viewing target outcomes, then report every target, including losses.

Finally, store a proposed design rationale separately from measured behavior. Claims such as “diverse experts helped” or “structured feedback reduced redundancy” need ablations and actual code inspection. ADAS's printed-code discrepancies are a concrete reason to make rebuild-and-replay evidence part of Everdict's platform contract. These are proposals aligned with the [first-loop design](../evolution-first-loop.md), not implemented changes.
