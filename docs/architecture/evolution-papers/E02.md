# E02 — Self-Refine: iterative feedback and revision

Self-Refine uses the **same frozen LLM** to draft an output, critique it, and revise it. Its distinctive proposal is specific, actionable, sometimes multi-dimensional feedback without training a separate critic or refiner. The strongest reported gains concern preferences and explicit generation constraints; math correctness barely improves without an external correctness signal. This explanation covers **2303.17651v2**, all seven task families, supplementary experiments, and Appendices A–S. Results have not been independently reproduced.[^1]

## 1. Problem, principles, and neighboring research

Producing a first answer and identifying weaknesses in an existing answer are different conditional generation problems. A model that overlooks a requirement while drafting may notice it when explicitly asked to inspect that requirement. A third prompt can then focus on implementing the proposed fix. This decomposition is the central hypothesis; it does not require an assumption that the critic is always smarter than the generator.

Feedback is **specific** when it identifies the problematic phrase, operation, or omission, and **actionable** when it says what to change. “Make this faster” is generic. “Replace repeated work inside this loop with a precomputed value” identifies a target and a direction. Multi-aspect feedback can separately address relevance, informativeness, readability, or pronunciation instead of compressing all preferences into one unexplained score.

Unlike a trained corrector, Self-Refine supplies the task through instructions and demonstrations. Unlike parameter-based RL, it changes the current output and prompt history, not model weights. Compared with [E01 Reflexion](E01.md), the emphasis is a structured critique–revision process for an output, including open-ended text, rather than memory across long environment episodes. The concurrent papers' broad novelty claims should be interpreted within their historical comparisons. [R41 TextGrad](R41.md) later propagates feedback through several variables, and [E08 ACE](E08.md) turns accumulated feedback into a maintained context resource. Self-Refine itself does not demonstrate a lasting library that improves future unrelated tasks.[^1]

## 2. Algorithm, stopping, and actual supervision

For input `x`, generate `y0 = M(generation prompt, x)`. Then produce feedback `ft = M(feedback prompt, x, yt)` and revise with `M(refinement prompt, x, y0, f0, …, yt, ft)`. Keeping earlier outputs and critiques can prevent repeated mistakes, while also increasing prompt length and carrying forward incorrect assumptions.

The algorithm stops at a fixed iteration limit or when a task-specific indicator in the feedback says improvement is unnecessary. The main setup says up to four iterations and returns the **last** output. Some appendices instead select the highest self-scored output; dialogue excludes the initial output from that selection, and readability runs five iterations. These are distinct task implementations, not one universal last-output procedure.

No model is newly trained, but the method is not devoid of human supervision. Appendix S describes author-written feedback and improved demonstrations: two failed math examples receive manually corrected solutions, acronym examples receive rubric scores, sentiment examples receive conversion descriptions, and constrained-generation examples are deliberately corrupted to illustrate missing concepts or incoherence. These prompts are part of the method and should be versioned.

The main models are text-davinci-003, gpt-3.5-turbo, and GPT-4, with Codex in code experiments. The main text's phrase “greedy decoding with a temperature of 0.7” is technically inconsistent: positive-temperature sampling and greedy decoding are different. Readability gives separate explicit temperatures for critic and editor. Exact decoding and selection settings must therefore be recovered per experiment rather than inferred from that single sentence.[^2]

## 3. Seven tasks and their measurement contracts

| Task | Data described in Appendix A | What the reported measure asks |
|---|---|---|
| Sentiment reversal | 1,000 review passages | Which rewrite better matches the target tone? |
| Dialogue response | 372 conversations | Which response is preferred in context? |
| Code optimization | 1,000 PIE programs | What fraction are successfully optimized? |
| Code readability | 300 CodeNet programs | What fraction of variable names are judged meaningful? |
| Math reasoning | 1,319 GSM8K questions | Does the executed Python solution give the right answer? |
| Acronym generation | 250 curated title/acronym items | Which acronym better balances the rubric? |
| Constrained generation | 200 CommonGen-Hard items | How well are required concepts covered? |

These percentages are **not commensurate accuracies**. A dialogue preference win rate is not factual correctness; naming quality is not semantic preservation; concept coverage is not complete commonsense validity. The headline average improvement across heterogeneous tasks should not become a universal expected accuracy gain.

Preference evaluation uses GPT-4 comparisons, supplemented with blinded human A/B judgments by the authors. The paper reports correspondence with human preferences of 82% for sentiment, 68% for acronyms, and 71% for dialogue, calling these correlations without a fully specified correlation estimator. Appendix C reports 150 examples per dataset, with Self-Refine/direct/tie preferences of 75.00/21.43/3.57% for sentiment, 44.59/12.16/43.24% for acronyms, and 47.58/19.66/32.76% for dialogue. These are separate human results, not the main table values.

The evaluation prompts allow both/neither. Ties matter: main sentiment and acronym rates need not sum to 100%, while dialogue's main pair does. Appendix P also describes assigning wins to either side when both win, and the dialogue appendix names text-davinci-003 as an evaluator where the main text specifies GPT-4. These reporting differences limit reconstruction of a single unified evaluation protocol.[^3]

## 4. Main results and what is actually improved

Each cell below is **base → Self-Refine**, using the main Table 1's own task metric.

| Task | GPT-3.5 / text-davinci-003 | ChatGPT / gpt-3.5-turbo | GPT-4 |
|---|---:|---:|---:|
| Sentiment reversal | 8.8→30.4 | 11.4→43.2 | 3.8→36.2 |
| Dialogue preference | 36.4→63.6 | 40.1→59.9 | 25.4→74.6 |
| Code optimized | 14.8→23.0 | 23.9→27.5 | 27.3→36.0 |
| Meaningful variable naming | 37.4→51.3 | 27.7→63.1 | 27.4→56.2 |
| Math solve rate | **64.1→64.1** | **74.8→75.0** | **92.9→93.1** |
| Acronym preference | 41.6→56.4 | 27.2→37.2 | 30.4→56.0 |
| Concept coverage | 28.0→37.0 | 44.0→67.0 | 15.0→45.0 |

GPT-4's dialogue gap is 49.2 percentage points between the two sides of a preference comparison. It is not a 49.2-point rise in independently measured task correctness. Conversely, its code-optimization gain is **8.7 points** in the fraction optimized, and math gains only **0.2 points**. The same broad claim of improvement hides substantially different evidence strength and practical meaning.

Appendix J supplies Wilson intervals and asterisks, marking six of seven GPT-4 gains, four ChatGPT gains, and three GPT-3.5 gains as significant. Math is unmarked throughout. The caption says 95% confidence but the following paragraph says 99%; the reported interval construction and paired comparison are not sufficiently consistent to reproduce a definitive significance claim. Report the authors' markings with this qualification rather than silently choosing a confidence level.[^4]

## 5. Task-specific procedures and supplementary experiments

**Code optimization** critiques a functionally correct program for algorithmic inefficiency, then rewrites it. One example replaces combinatorial nested loops with dynamic programming. Appendix F compares against PIE and best-of-16/32 sampling: GPT-4 Self-Refine reaches 36.0% optimized, while PIE few-shot best-of-32 is 38.3%. It therefore does not exceed every listed baseline. Counting four candidate samples also omits feedback calls and growing prompt costs. Appendix N reports a separate setting: direct 9.7% optimized, feedback-free iterations 10.1/10.4%, full iterations 15.3/15.6%. Its speedup columns have insufficient aggregation detail to combine with the main table; the first full iteration improves optimization incidence while its displayed speedup falls from 3.09 to 2.90, before reaching 3.74.

**Readability** starts directly from input code, with no initial generation. The appendix uses text-davinci-003 critics at temperatures 0 or 0.7, a greedy editor, and five rounds on 300 programs. Meaningful-name ratio, comments per line, and function-unit counts generally increase. On a 60-program human-rewrite subset, human / sampled-critic Self-Refine values are 0.653/0.700 for names, 0.24/0.25 for comments, and 0.70/1.33 for function units. More functions or comments are proxies, not proof of maintainability or preserved behavior. The shown dense-code example becomes several named intermediate operations; no comprehensive semantic-equivalence evaluation is reported for this task.

**Dialogue** scores ten aspects: relevance, informativeness, interest, consistency, helpfulness, engagement, specificity, safety, user understanding, and fluency. Explanations accompany scores. Its appendix describes three refinement rounds and choosing the highest total score among revised outputs. It also reports 342 test instances, versus the 372-conversation inventory, and 100 human-evaluated instances, versus Appendix C's 150. Table 15's ChatGPT preference column sums to **116%** (48+18+50), an unresolved reporting error. The valid-looking GPT-4 column is 54/16/30%; do not repair the other column by guessing.

**Sentiment** changes long review passages rather than isolated sentences, for at most four rounds. A coarse Vader classifier already judges positive-target outputs 100% successful for both base and refined systems; negative-target rates are 92 versus 93.6%. The larger preference gains therefore concern intensity or expression beyond coarse polarity. An additional pinpoint-feedback experiment reports sentiment preference dropping from 85 to 73% and dramatic-style preference from 80.09 to 58.92% when feedback is vague. Those conditions are not the main table's 43.2% metric.

**Acronyms** trade off pronunciation, spelling, title relation, positive connotation, and familiarity. The curated dataset contains 250 items. The main generator prompt is described as 15 examples, and author-scored demonstrations guide critique/refinement. A displayed four-step example has scores 11→17→12→17, showing non-monotonic quality. The table labels total out of 25 while showing four component columns, and the appendix claims maximum-score selection at an algorithm line that actually performs revision. The intended task-specific selection is clear enough conceptually, but the exact score bookkeeping should not be assumed verified. Familiar known acronyms such as Seq2Seq may also reward prior knowledge, not invention of a novel useful name.

**Constrained generation** expands CommonGen from 3–5 concepts to 20–30. Feedback separately identifies missing concepts and implausible sentences. An additional GPT-3.5 preference figure reports refined/direct wins of 35/3% on concepts, 10/5% on commonsense, and 32/0% overall, distinct from coverage. Missing-word checks can help, but a sentence listing all words is not automatically a sensible one. Some prompt examples mark the concept “animal” as satisfied even without that literal word; this reinforces the need to specify lexical versus semantic coverage.

**Math** uses Python solutions in the PaL style. Without oracle feedback, ChatGPT says the solution looks good on **94% of instances**, including many errors, explaining the weak net gains. Appendix H's oracle condition proceeds with refinement only when the current answer is wrong: GPT-3.5 rises 64.06→68.9%, ChatGPT 74.8→76.2%, GPT-4 92.9→93.8%. This supplies ground-truth correctness information and must remain separate from intrinsic self-feedback. Appendix O explicitly uses correct labels and plots 71.34→76.19% across rounds; Appendix F gives still other math values such as GPT-4 94.5%. These are not evidence that the main no-oracle GPT-4 run reached 94.5%.[^5]

## 6. What the ablations establish

Specific versus generic versus no explicit feedback scores **27.5/26.0/24.8** on code optimization, **43.2/31.2/0** on sentiment, and **56.4/54.0/48.0** on acronyms. No-feedback still permits iterative revision. Specific feedback helps in these tested recipes, but the particularly low sentiment result should not be generalized to every direct rewriting prompt.

Iteration averages show diminishing gains: code optimization 22.0→27.0→27.9→28.8 and constrained generation 29.0→40.3→46.7→49.7. These average curves do not imply every item improves monotonically. They also use their own aggregation; sentiment's initial 33.9% in this analysis is not the average of the main table's direct preference rates.

A human comparison against **four independently generated ChatGPT outputs** asks whether one refined output beats all four. Figure 9 gives Self-Refine/multiple-sample/tie rates of **33.3/15.5/51.1%** for sentiment and **40.05/6.1/53.82%** for acronyms. Refinement wins more often than it loses, but a majority are ties; this is not majority preference over all alternatives. Four raw outputs do not match the full feedback/refinement token budget or compare an equally strong automatic selector.

Vicuna-13B struggles to follow the same feedback and revision prompts, sometimes repeating outputs or hallucinating a conversation. Keeping prompts fixed tests portability, not the best attainable performance with Vicuna-specific tuning. A mixed system using Vicuna for initialization and ChatGPT for feedback plus revision raises math performance **24.18→40.5%**; this is cross-model assistance, not successful same-model self-refinement.

A manual sample of 70 code/math cases, balanced between 35 successes and 35 failures, attributes failed improvement to wrong error localization in 33%, an unsuitable proposed fix in 61%, and poor implementation of good feedback in 6%. Among successes, 61% follow accurate useful advice and 33% succeed despite partly wrong feedback. This selected diagnostic sample is not a population failure distribution. A separate dialogue audit finds incorrect/generic/misscored feedback and refiners that ignore advice or introduce new problems; its listed percentages overlap and should not be forced into one normalized confusion matrix.[^6]

## 7. Qualitative demonstrations, limitations, and interpretation

Two website examples revise an ice-cream page and a photosynthesis page, changing typography, spacing, imagery, and content. They demonstrate an editing workflow without controlled user testing, accessibility evaluation, or measured business value. The provided feedback even contains malformed color notation; the screenshots should not be treated as validation that every proposed instruction was technically correct.

Several demonstrations themselves contain imperfect feedback: the acronym refinement changes the input title, and a math critique omits division by the number of cups although the final refined code restores it. The final output can improve while the critique remains flawed. This is precisely why critique quality and artifact correctness need separate measurements.

The core limitations are correlated generator/critic errors, self-score inflation, prompt dependence, English-only evaluation, cost from extra calls and long histories, and the absence of durable cross-task learning. The study supports testing critique–revision as an inference procedure; it does not justify turning every self-critique into a permanent rule or automatically treating later revisions as better.

## 8. Everdict evolution proposal

Use Self-Refine as a **candidate-generation operator**: given one immutable candidate and authorized failure evidence, ask for a localized critique and an explicit proposed change. Attach the critique to its source observations, preserve the parent, and rebuild the child from declared edits. Keep platform success criteria fixed; changing the rubric to match the new output would invalidate the experiment.

Compare direct proposal generation, generic critique, and specific critique under equal total calls, tokens, execution time, and feedback access. Track whether the critique correctly locates the defect, whether the edit implements it, whether the original defect disappears, and whether unrelated behavior regresses. Include a separate independent-sampling-plus-selection baseline. Limit rounds using selection evidence and cost, not a model's claim of perfection.

For multi-objective changes, score correctness, latency, readability, and maintenance separately. Retain the original as an eligible candidate; the dialogue appendix's exclusion of the initial response would be a poor default for software evolution. Human or LLM preference can guide a proposal, while confirmed executable outcomes decide whether an operational claim is supported.

This fits the [first-loop architecture proposal](../evolution-first-loop.md) at the driver layer. Durable memory curation is a subsequent experiment: only promote a lesson after it transfers beyond the task that produced it. A useful first result would be fewer recurring failures at equal cost on held-out families, not simply longer explanations or higher self-assigned scores.
