# R11 — SoK: Agentic Skills: a lifecycle and architecture vocabulary

This systematization organizes reusable agent procedures across their lifecycle, representation, execution, and governance. It does not introduce a new optimizer or run a fresh controlled comparison of evolution methods. Its value for Everdict is a vocabulary for identifying exactly what changes, how it is invoked, and what evidence would establish that it improved. This note follows Jiang et al., arXiv 2602.20867v1.[^1]

## Research question and conceptual lineage

An atomic tool call, a one-time plan, a remembered episode, and a reusable procedure are related but distinct objects. Calling all of them “skills” makes comparisons difficult: a system may improve routing without improving the procedure, or store more episodes without acquiring an executable capability. The authors propose a skill-centered abstraction to make these distinctions explicit.

The conceptual lineage includes ACT-R and Soar procedural memory, reinforcement-learning options, hierarchical planning, tool-use agents, and agent memory. An RL option provides an initiation condition, an internal policy, and a termination rule for an action that spans several steps. This paper adapts that intuition to language, code, learned policies, and hybrid artifacts, adding an explicit callable interface. The formalization is a proposed analytic schema, not a universally adopted file format or a proof that every named system satisfies it.[^2]

## Four components of a skill

The proposed tuple is S = (C, π, T, R). C decides whether the current observations and goal make the skill applicable. π maps observations/history into primitive actions or other skill invocations. T determines when execution has ended relative to the goal, successfully or otherwise. R specifies the reusable name, parameters, and return interface. Applicability and termination can be implemented by an external orchestrator rather than stored inside the artifact.

Consider an illustrative spreadsheet repair procedure. C checks that the task concerns formulas in a supported workbook; π inspects formulas and makes the repair; T checks completion or records an unresolved failure; R defines workbook and sheet inputs plus an output artifact and status. A paragraph describing spreadsheets may help reasoning but lacks this complete operational contract. Conversely, a real deployment can distribute the contract across metadata, executable code, and platform checks.

The distinction highlights failure modes. An excellent procedure selected for the wrong workbook is an applicability failure. A correct edit followed by a false success claim is a termination/evidence failure. A changed parameter convention is an interface failure. These need different evolution targets.

## Survey methodology and coverage

The authors report searches in Google Scholar, Semantic Scholar, DBLP, ACM Digital Library, IEEE Xplore, and arXiv, plus forward/backward citation tracing. Approximately 180 candidates yielded 65 retained papers, with 24 systems described as analyzed in depth. Inclusion requires reusable procedural capabilities, a relevant lifecycle stage, or a benchmark that measures such behavior. Single-turn tool calling without composition and tuning without explicit skill representation are excluded.[^3]

The stated main search window is January 2020–February 2025, with SkillsBench from February 2026 identified as an exception. The text also discusses later production systems and security sources. That mixed temporal scope should be retained rather than treating the survey as an exhaustive, uniformly sampled view of September 2026 research. Feature matrices and three rounds of refinement produced the taxonomy; no external expert validation or formal inter-rater agreement is reported.

## The lifecycle and its feedback loops

Seven stages connect discovery, practice/refinement, distillation, storage, retrieval/composition, execution, and evaluation/update. Discovery identifies recurring subproblems. Practice tests possible behavior. Distillation turns a particular trace into a general procedure. Storage preserves it with metadata and versions. Retrieval/composition selects and combines it. Execution applies it, and evaluation can trigger revision, replacement, or retirement.[^4]

These stages are not one linear pipeline. Failure to retrieve a relevant procedure can require metadata revision without changing its body. A failed execution can reveal a new skill boundary. Environment drift can retire a once-useful version. Distillation changes representation, whereas practice changes reliability; fine-tuning traces into weights is a different form of distillation from writing a reusable script.

The surveyed examples show these differences: Voyager stores tested code from exploration, Reflexion uses verbal feedback across attempts, AgentTuning distills trajectories into model weights, and memory systems manage stored context. The paper explicitly notes boundary cases: transient reflection is not automatically a persistent library update, and simulated social memories need not satisfy the strict skill definition.

## Seven system patterns and two descriptive axes

The patterns are non-exclusive architectural choices. A production system can combine several, so the list is not a ranking or seven mutually exclusive algorithms.[^5]

| Pattern | Mechanism | Main design question |
|---|---|---|
| Metadata disclosure | Load descriptions before full instructions | Does the summary preserve applicability? |
| Code as skill | Invoke reusable executable programs | Are inputs, dependencies, and side effects controlled? |
| Workflow enforcement | Controller constrains execution stages | Is a rule enforced outside the interpreted text? |
| Self-evolving library | Execution feedback updates stored procedures | Which evidence admits or retires an artifact? |
| Natural-language/code hybrid | Prose guides executable components | What resolves disagreement between prose and code? |
| Meta-skill | A callable process creates or edits skills | Can errors propagate across generations? |
| Marketplace distribution | Package and share versioned artifacts | Which exact dependency closure is consumed? |

The separate representation axis includes natural language, code, tool macros, learned policies, and hybrids. The scope axis includes single-tool procedures, multi-tool orchestration, web, desktop/OS, software engineering, and physical robotics. The same representation can serve different scopes, and distribution can package any representation.

Some qualitative table claims need qualification. Code is testable but can depend on randomness, external APIs, and mutable state; it is not automatically deterministic. A workflow written in prose is not a hard gate merely because it uses mandatory wording. The controller must enforce the relevant transition. These qualifications matter directly to Everdict's division between editable advice and platform-owned decisions.

## Acquisition, composition, and recovery

Acquisition can use expert authorship, demonstrations, self-practice, curricula, or generators that create other procedures. A trajectory must be generalized beyond its original instance, and an external outcome signal helps distinguish successful behavior from a persuasive explanation. The survey contrasts constrained environments with reliable feedback against open-ended generation where incorrect heuristics can accumulate.[^4]

Composition adds interfaces and state. Embedding retrieval can shortlist candidates; model reasoning can check applicability. Hierarchies invoke subskills, but conflicts require a policy when several candidates appear relevant. Failure recovery can itself be a procedure that retries, backtracks, or changes strategy. Its permission scope must be deliberate; recovering from a failure does not inherently authorize stronger actions.

For evolution, a component's local score is therefore insufficient. A skill may work alone but return a value its caller misinterprets. Retrieval, interface compatibility, and recovery behavior require evaluation alongside the edited body.

## Security analysis and the case study

The paper analyzes poisoned metadata/retrieval, malicious payloads, cross-tenant leakage, environmental drift, misuse of a legitimate privileged skill through untrusted observations, and manipulated applicability conditions. Its four proposed trust tiers range from metadata access through instruction access, constrained execution, and autonomous execution. A crucial caveat in the paper is that merely loading instructions is not isolated if those instructions can induce the agent's ordinary tool loop.[^6]

The marketplace case study describes malicious skill distribution, deceptive setup instructions, credential theft, and subsequent scanning responses. This is a synthesis of external incident reports, not a controlled security experiment performed by the survey authors. The text is internally inconsistent about a 36.8% figure: it first refers to skills with a security flaw and later labels it a malicious-skill rate. Those are different populations and definitions; this note does not treat that figure as a verified prevalence estimate.

The proposed defenses cover provenance, pinned versions, dependencies, runtime isolation, and monitoring. Signing establishes origin/integrity, not benign behavior. Scanning supplies evidence within its detection scope, not a universal clearance. The paper also cites small evaluations of auditing tools; they are external tool reports rather than a new comparative evaluation in this SoK.

## Evaluation evidence, component tests, and limits

The evaluation framework separates correctness, robustness, efficiency, generalization, and safety. Environment-state checks can be more repeatable than judging prose, but a deterministic checker can still encode an incomplete goal. Different benchmarks cover different dimensions, so one scalar does not settle every concern.[^7]

The quantitative anchor is an earlier SkillsBench snapshot: 86 tasks, 11 domains, seven agent/model configurations, and 7,308 trajectories. The SoK reports curated-skill gains of 16.2 percentage points and self-generated-skill change of −1.3 points. It further summarizes variation by domain, number/length of skill modules, model size, and tasks where skills hurt. These are borrowed benchmark analyses, not the survey's own ablations. Its rounded endpoints 24.3% and 40.6% do not subtract exactly to the quoted 16.2; retain the reporting distinction.

Later SkillsBench v4, covered separately in R15, changes the task/configuration scope and reports different aggregates. Mixing those versions would produce a fictitious combined experiment. The SoK itself warns that its central utility evidence relies heavily on one preprint. Claims that scarce pretraining coverage explains domain gains are hypotheses, with task difficulty, authoring quality, and verifier strictness as alternatives.

The taxonomy may age, omit unpublished/non-English systems, and classify borderline cases subjectively. Unoccupied cells in its design matrix suggest questions; they do not establish that those combinations are useful. Open problems include validated autonomous generation, discovery without supplied curricula, verification across representations, environmental drift, and distribution incentives.

## Implications and a proposed Everdict experiment

Use the tuple to specify the candidate's editable surface and the platform's invariant surface. For a skill-body change, freeze applicability, interface, executor, dependencies, and completion checks where possible. If one of those changes too, declare it as part of the candidate rather than attributing everything to better prose. Preserve the exact evaluated artifact and evidence lineage.

A useful experiment distinguishes retrieval-only edits, procedure-only edits, and combined edits on the same train/select/confirm split. Measure selection precision, end-to-end success, interface failures, cost, and regressions under a pinned environment update. Include tasks on which no skill should activate. This directly tests the survey's distinction between availability and utility.

Everdict's first-loop proposal already reserves adoption and evidence-integrity mechanisms for the platform while allowing drivers to curate advice. The survey supports asking these boundary questions; it does not require implementing all seven patterns, a marketplace, or a new trust-tier product before running the initial evolution experiment.
