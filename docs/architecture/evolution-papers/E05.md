# E05 — AFlow: workflow search with local change history

AFlow searches executable LLM workflows using reusable operators, a tree of parent–child modifications, and measured execution feedback. Its most useful evolution idea is to attach the outcome of a change to the specific parent on which it was tried. This explanation covers **2410.10762v4**, all six reasoning benchmarks, transfer and cost comparisons, operator ablation, implementation examples, and the two open-ended case studies. Results have not been independently reproduced.[^1]

## 1. Problem, representation, and neighboring research

A workflow determines which model calls occur, what each receives, how outputs are combined, and when code execution or revision happens. Optimizing one prompt leaves much of this structure fixed. AFlow represents a workflow in Python so branches, loops, data dependencies, and calls can change together.

Its general formulation describes an LLM node by model, prompt, temperature, and output format, with edges specifying execution relationships. The actual search **fixes model, temperature, and output format**, concentrating on prompts and code connections. An MCTS tree node is a **complete candidate workflow**; it is not one of the LLM-call nodes inside that workflow. Distinguishing these two levels is necessary to understand the algorithm.

[E04 ADAS](E04.md) also searches agent code, but presents prior full programs in an archive. AFlow supplies parent-specific modification histories and reusable operator APIs. [E13 DSPy](E13.md) and [R41 TextGrad](R41.md) optimize structured model programs or their components through different compilation/feedback procedures. Self-consistency and [E02 Self-Refine](E02.md) are ingredients that AFlow can incorporate, rather than equivalent outer search algorithms.

The representation is expressive, but practical search remains shaped by the operator implementations, fixed model configuration, optimizer prompt, and a requested graph complexity limit of ten. Claims of a virtually unlimited code space describe representation, not exhaustive exploration or freedom from human design.[^1]

## 2. Operators and the boundary of execution feedback

Operators package familiar patterns: generation, formatting, review and revision, ensembling, testing, program execution, and a basic Custom call. The supplied Ensemble asks an LLM to select a labeled candidate; it is not necessarily deterministic majority voting. Programmer generates Python and retries execution up to three times. Test runs available tests and can request repairs for up to three loops.

The Test operator uses publicly available task tests. For MBPP, the paper designates the **first test case of each problem as public feedback**. This is a deliberate within-task disclosure setting, which must accompany the reported code scores. The paper does not fully specify in the appendix whether that same assertion is excluded from final scoring. It should not be described as coding with no reference-derived feedback, nor should unspecified overlap automatically be labeled a proven hidden-test leak.

Generated tests have a different status. An MBPP case creates extra assertions and appends them to the textual problem. The printed Test implementation calls `exec_code(solution, entry_point)` without passing that augmented problem. Consequently, the listing does not establish that the generated assertions are actually executed; they may only influence a repair prompt. Trace inspection is needed before attributing improvements to additional executable test coverage.

Similarly, code execution confirms what a program did under a particular environment, not that its mathematical interpretation was correct. Figure 5's workflow selects Programmer output by truthiness: a zero value and a nonempty error string can be treated differently from what a semantic success flag would require. The appendix's thread-based timeout also does not demonstrate forcible cancellation of running Python: cancelling a running future cannot by itself stop its thread. These are static limits of the printed examples, not reproduced defects in a pinned repository.[^2]

## 3. Search loop and implementation discrepancies

The dataset is split **20% validation / 80% test with seed 42**. Before search, the initial template runs five times on validation. High-variance questions are selected as the final search validation subset. Its exact threshold and resulting per-dataset sizes are not fully reported. This focuses search on unstable cases and changes the distribution on which candidate selection operates.

At each round, choose a parent, load its local successes and failures, ask the optimizer for one modification, execute the child five times, and record the mean and standard deviation. The optimizer sees both predicted and expected training/validation outputs in execution logs. Such label-bearing feedback belongs to search data, not a future independent confirm set. Parent experience stores the modification and whether the child's average improved over that parent; global records support candidate selection.

The main selection rule mixes uniform probability with a softmax of scores:

`P(i) = λ/n + (1−λ) × exp(α(si−smax)) / Σj exp(α(sj−smax))`.

Subtracting the maximum stabilizes exponentiation without changing the distribution. The main text specifies **α=0.4, λ=0.2** and chooses among the top workflows plus the initial template. Appendix A.6 instead sets **λ=0.4, α=0.2**, and its selection pseudocode takes only the top three, without explicitly reinserting the initial template. It also accumulates per-run records but does not clearly show aggregation into distinct workflows before parent selection. These details must be resolved from exact implementation bytes for reproduction.

Search allows **20 rounds**, with top-three stagnation for **five rounds** as early stopping. The main text describes unchanged top-k average score, while the detailed algorithm describes an unchanged top-k set. These stopping rules can differ. One-step modification is a prompt instruction; appendix descriptions sometimes combine adding a node and changing an ensemble, so it is not a mechanically enforced one-edit constraint.

The authors call this an MCTS variant. Unlike standard UCT, the described rule does not use a visit-count exploration bonus or conventional rollout-return backup through every ancestor. It is best understood concretely as probabilistic workflow selection plus LLM expansion and parent-linked experience. Its merits should be assessed from that implementation rather than imported guarantees from another MCTS algorithm.[^3]

## 4. Main experimental protocol and results

Claude 3.5 Sonnet is the optimizer. Main execution uses **GPT-4o-mini-0718**, with other experiments using DeepSeek-V2.5, GPT-4o-0513, and Claude-3.5-sonnet-0620. DeepSeek temperature is 1; the other executors use 0. ADAS is re-run with the same optimizer and GPT-4o-mini for 30 rounds, while AFlow gets 20. Equal round counts would still not equalize model calls or evaluation costs, and these different round counts do not establish total search-budget equality.

The paper uses the available GSM8K, HumanEval, and MBPP datasets, samples **1,000 HotpotQA and 1,000 DROP** questions, and selects **617 level-five MATH** questions from four categories: combinatorics/probability, number theory, pre-algebra, and pre-calculus. The 20/80 split is applied before validation filtering. Main test scores average **three executions**, not three independently replicated searches.

|---|---:|---:|---:|---:|---:|---:|---:|
| Direct model | 68.1 | 68.3 | 87.0 | 71.8 | 92.7 | 48.6 | 72.8 |
| CoT | 67.9 | 78.5 | 88.6 | 71.8 | 92.4 | 48.8 | 74.7 |
| CoT self-consistency | 68.9 | 78.8 | 91.6 | 73.6 | 92.7 | 50.4 | 76.0 |
| MedPrompt | 68.3 | 78.0 | 91.6 | 73.6 | 90.0 | 50.0 | 75.3 |
| MultiPersona | 69.2 | 74.4 | 89.3 | 73.6 | 92.8 | 50.8 | 75.1 |
| Self-Refine | 60.8 | 70.2 | 87.8 | 69.8 | 89.6 | 46.1 | 70.7 |
| ADAS | 64.5 | 76.6 | 82.4 | 53.4 | 90.8 | 35.4 | 67.2 |
| **AFlow** | **73.5** | **80.6** | **94.7** | **83.4** | **93.5** | **56.2** | **80.3** |

The headline **5.7%** is approximately the relative increase from average 76.0 to 80.3, a **4.3-point** increase. **19.5%** is relative to ADAS's 67.2, a **13.1-point** gap. The claimed roughly 57% improvements on MATH and MBPP are likewise relative, not percentage-point gains. Averaging F1 and solve/pass rates gives a descriptive benchmark macro-average, not one unified probability of success.

Code pass@1 means one final submitted solution per workflow execution, after that workflow may generate, select, test, and repair several internal candidates. It is not one model call. The absence of full uncertainty intervals and replicated searches limits claims about small gains, especially GSM8K's 0.7 points above the strongest manual baseline.[^4]

## 5. Cross-model transfer and the cost frontier

HumanEval workflows are searched with either GPT-4o-mini or DeepSeek-V2.5, then executed on four models. The mini-searched workflow scores **94.7, 93.9, 96.2, and 95.4%** on mini, DeepSeek, GPT-4o, and Sonnet, respectively. The DeepSeek-searched workflow scores **90.8, 94.7, 95.4, and 94.7%**. Transfer is often useful, but DeepSeek's workflow on mini is worse than mini's own 94.7 and the 91.6 self-consistency/MedPrompt baseline. Workflow compatibility is model-dependent.

The cost plot compares historical token-priced **execution on the divided HumanEval test set**, excluding amortized search and operator-development expense. Appendix D reports DeepSeek running the mini-searched workflow at **93.90% and $0.0291**, versus direct GPT-4o **93.89% and $0.6371**. That is near parity at about **4.55% of the reported execution cost**, not a large accuracy improvement at 4.55% of total project cost.

DeepSeek's own workflow is **94.66% at $0.0377**, and mini's own is **94.70% at $0.0513**, approximately 5.92% and 8.05% of that GPT-4o direct cost. On GPT-4o itself, the mini-searched workflow rises to **96.2% but $1.0111**, so improved quality can cost more on a fixed model. The table labels scores as percentages while displaying fractions such as 0.947; conversions here make the units explicit. These are paper-era estimates, not current API prices or an all-domain deployment guarantee.[^5]

## 6. Operator ablation and change-history examples

Removing predefined operators on GSM8K leaves the Custom interface. The paper reports **93.1%** without operators, versus 93.5% in the main full-system table. Figure 5's plotted endpoints are approximately 92.9 and 93.6, a small reporting difference; do not manufacture exact agreement. Its no-operator test curve improves faster initially, while the operator-assisted curve eventually overtakes it. Thus “more efficient” depends on the stage and target quality, not every early round.

The no-operator search creates three differently prompted solutions and an LLM comparison step. This shows it can implement an ensemble without the packaged API. However, the optimizer prompt explicitly suggests ensemble and describes multi-answer selection. It is rediscovery in code with prior guidance, not invention without knowledge of the pattern. The experiment isolates operator availability, not all human contribution.

The GSM8K lineage adds an ensemble, a Programmer check, output formatting, and more explicit reasoning. A review that directly rewrites an answer can reduce accuracy; overemphasizing discounts can overfit a particular topic. MATH combines executed computation with several textual solutions and selection. HotpotQA benefits partly from returning concise answer spans, which directly affects F1. MBPP combines multiple programs, selection, public tests, and a final repair.

Appendix C's MATH history preserves failed edits and zero-score candidates. Similar “add ensemble” descriptions appear under different parents with gains, ties, or losses. This is strong motivation to retain parent context. But the prose attributes one loss to removing Programmer although the stored modification describes adding an ensemble; the parent record itself describes Programmer being introduced only later. The history supports observed differences, not the certainty of that causal narrative. No separate ablation isolates tree memory, mixed selection, detailed execution feedback, or one-step editing at matched total compute.[^6]

## 7. Open-ended writing and research-idea experiments

Appendix F replaces the exact evaluator with GPT-4o judging four dimensions from 1 to 5: relevance, quality, coherence, and comparison with expected/reference quality. The optimizer prompt is adjusted for open-ended work. Human scores are also reported, but rater recruitment, independence, and repeated-search uncertainty are insufficiently specified for a broad quality claim.

**Novel generation** uses one prompt requesting **exactly 20,000 words**, with Sonnet both optimizing and executing. After eight rounds, the workflow builds an outline and character profiles, then writes ten chapters. The authors report **27,000 words**, while GPT-4o gives **20/20** and humans average **19.3/20**, versus initial 12/20 and 2/20. The exact length requirement is therefore violated by the reported output despite the perfect model score. The chapter prompt requests approximately 10,000 words per chapter, and the code neither counts total words nor supplies earlier chapter text to later chapters. This is a concrete evaluator–contract mismatch, not evidence of exact-length compliance. The final listed cost is $0.863 versus $0.005 initially, so higher quality here is not lower absolute generation cost.

**Research ideas** use ten questions, mini execution, Sonnet optimization, and GPT-4o judgment. The selected round-six workflow generates three ideas, selects and prioritizes one, elaborates, critiques, and refines it. Reported model/human means rise from **18.4/15.6 to 19.7/19.1** out of 20, with listed cost $0.004→$0.235. The table includes eight rounds and shows later declines, despite describing the best workflow after six. This supports selection under the rubric on these questions; it does not establish verified scientific novelty, implemented feasibility, or held-out research productivity.[^7]

## 8. Theoretical and empirical limits

Appendix G claims finite-iteration optimality from bounded scores, valid workflows, and nonzero probability of improvement. Those conditions alone are insufficient. A positive probability is not a guarantee of sampling an optimum within a finite budget; a bounded objective may only have an unattained supremum in an unbounded space. Top-k restriction, early stopping, and unknown LLM proposal support further weaken completeness claims. The paper supplies useful algorithmic intuition, not a formal finite-time optimality proof.

Other limits are adaptive validation overfitting, uncertain high-variance filtering, fixed operator priors, incomplete cost matching, and metric-driven formatting improvements. A valid output format is often a legitimate task requirement, but improving a parser score should be distinguished from improving underlying reasoning. The novel case demonstrates why independently checkable requirements should not be delegated entirely to a generic LLM rubric.

## 9. Concrete Everdict evolution proposals

AFlow's most direct contribution is a **parent-linked change record**: exact parent digest, proposed and applied edit, child digest, execution evidence, and measured delta. Driver curation can summarize this graph while the original ledger remains append-only. A rejected change should remain scoped to its parent, task distribution, and budget; “ensemble failed” is too broad when the same change works elsewhere.

Test three driver conditions under an identical campaign contract: flat candidate summaries, parent-linked modification histories, and those histories plus selected execution traces. Freeze proposer, candidate edit scope, validation pool, and total evaluation budget. Measure independently confirmed quality, regressions by task family, reattempted failures, search cost, and later reuse of nonwinning ancestors. Keep authority for promotion and confirm disclosure in the platform, as proposed in the [first-loop design](../evolution-first-loop.md).

If adaptive high-variance sampling is explored, restrict it to training data and compare against a fixed representative selection set. Log inclusion rules and sample identities so gains on unstable examples are not confused with population gains. Mechanically validate declared edits and output contracts instead of trusting “single modification” text or a perfect judge score. For subjective objectives, combine explicit deterministic checks with separately recorded rubric judgments.

Finally, evaluate a cost–quality frontier using total search plus deployment cost at stated reuse volumes. A cheaper deployed workflow may justify an expensive search only after sufficient reuse. These are research proposals for Everdict evolution; this documentation does not change runtime or implement AFlow's search policy.
