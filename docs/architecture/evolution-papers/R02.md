# R02 — EvoSkill: automated skill discovery

EvoSkill uses three roles—executor, proposer, and skill builder—to turn recurring task failures into reusable skill folders. It keeps the underlying model fixed and searches over instructions plus optional helper code. The practical attraction is a portable, inspectable artifact: a discovered capability can be applied to a different task without retraining. The evidence in arXiv 2603.02766v1 is promising but includes single-run experiments and several internal reporting inconsistencies that matter for reproduction.[^1]

## Problem and research context

A general coding agent has tools but may lack the domain procedures needed to use them well. Correctly reading a Treasury table, for example, requires checking the row, column, unit, and period before computing an answer. More reasoning on top of the wrong extracted number will not repair the mistake.

Handwritten skills encode such procedures in a directory with a description, instructions, scripts, and references. EvoSkill automates their discovery. It builds on textual-feedback optimization and evolutionary search, moving the editable unit from a final answer or isolated prompt to a reusable capability bundle. The format itself is not the optimizer: learning requires execution feedback, a proposal process, selection, and persistent history.[^1]

## Components and information flow

The executor solves tasks with the current program and skills. The proposer reads failed trajectories, predictions, training answers, existing skills, and accumulated proposal feedback. It identifies a capability gap and writes a high-level suggestion. A separate builder turns that suggestion into concrete trigger metadata, procedural instructions, and optional Python/TypeScript helpers. All roles can read the base repository, while the builder owns writes to the skills directory.[^1]

The training answers support diagnosis and are not intended to become task-specific answers embedded in the skill. That intended separation should be checked in a reproduction: a convincing-looking generic procedure can still encode dataset-specific facts. The cumulative history records successful and unsuccessful proposals with score changes, allowing later proposals to avoid repetition or refine a partially useful idea.

## Search algorithm and an example

The loop starts with a no-skill program and a bounded candidate frontier. It chooses a parent, runs a category-aware training batch, and collects examples whose score is below a threshold. With no failures, it skips that iteration. Otherwise the proposer diagnoses failures, the builder creates a child, and the child is evaluated on validation tasks. If there is free capacity, the child enters the frontier; once full, it must exceed the weakest member. The final program is the frontier member with the best validation score. Proposal outcomes are remembered whether or not the child survives.[^1]

For example, several wrong Treasury answers may originate in adjacent-cell extraction rather than arithmetic. A useful proposal introduces a verification procedure: identify the metric and time granularity, validate neighboring headers and units, then calculate. The paper presents a discovered extraction-verification skill and a separate quantitative-analysis skill with checkpoints for transformations, aligned dates, and statistical definitions. These illustrate learned procedures; they do not isolate the contribution of each checkpoint experimentally.[^2]

The word “Pareto” in the abstract should be read carefully. Algorithm 1 maintains the top k programs by aggregate score, with round-robin parent selection; it does not define the per-instance non-dominated frontier used by GEPA. Appendix D instead describes choosing the highest-scoring parent and gives default capacity k = 3. It also discusses deleting rejected branches while describing historical snapshots as restorable. A reproduction must specify which parent policy and retention semantics it implements rather than silently treating these descriptions as identical.[^1][^3]

## Data, models, and scoring

All reported main experiments use Claude Code with Opus 4.5. Data are clustered into categories with an LLM and divided into disjoint training, validation, and test partitions. Training drives failure discovery, validation selects candidates, and the remaining test questions are withheld during evolution.[^2]

| Evaluation | Setup | What is measured |
|---|---|---|
| OfficeQA | 246 total questions; training sizes 12, 24, or 36; 17 validation examples; remaining questions for test | Grounded answers over about 89,000 Treasury pages |
| SealQA | seal-0, 111 questions; 10% training; remaining examples divided between validation and test | Search under conflicting or unhelpful evidence |
| BrowseComp transfer | Stratified sample of 128 examples; transferred skill unchanged | Utility on a different search benchmark |

Evolution runs for 1.5 epochs. The OfficeQA study also merges unique skills from independent runs; overlapping names or descriptions keep the version from the highest-performing run. Because training sizes differ, the remaining test partitions need to be checked before treating their scores as paired comparisons on identical cases.[^2]

The scorer extracts numbers, normalizes nearby unit words, and compares relative error. It filters incidental years, checks relevant text for hybrid answers, and requires all values in multi-number answers. Primary evaluation uses exact numerical matching; pure text uses normalized substring matching. During evolution, Appendix C describes a weighted average across tolerances 0, 1%, 2.5%, 5%, and 10%, with weight 1/(1 + 20 × tolerance); a score below 0.8 flags a failure. Table 1 displays a different tolerance grid, including 0.1%. These grids should not be conflated.[^3]

## Results and what they establish

| Condition | Exact-match accuracy | Change from its baseline |
|---|---:|---:|
| OfficeQA baseline | 60.6 | — |
| OfficeQA, 5% training | 63.4 | +2.8 points |
| OfficeQA, 10% training | 65.8 | +5.2 points |
| OfficeQA, 15% training | 64.5 | +3.9 points |
| OfficeQA, merged skills | 67.9 in prose/figure; **68.1 in Table 1** | +7.3 or +7.5 points respectively |
| SealQA baseline → evolved | 26.6 → 38.7 | +12.1 points |
| BrowseComp baseline → transferred | 43.5 → 48.8 | +5.3 points |

The OfficeQA merged result is inconsistent within v1: the abstract, figure caption, and narrative say 67.9, while the table says 68.1. Neither value should be silently “corrected” without the underlying records. The earlier overview follows the headline 67.9; this detailed note preserves both locations explicitly.[^2]

More training data is not monotonically better: the 15% setting underperforms 10%. The merged library's result is consistent with complementary skills, but the study does not separately randomize merge strategy, library size, or execution cost. Each configuration was evaluated in a single run because of Opus cost; the authors leave multi-seed variance analysis to future work.

The SealQA skill broadens query interpretation, checks multiple sources, and discourages premature stopping. Its unchanged transfer to BrowseComp is evidence for one useful cross-benchmark capability. It does not prove all evolved skills transfer, eliminate every form of overfitting, or establish that skill folders transfer better than equally optimized prompts under a matched comparison.[^2]

## Related work and limitations

Voyager supplies an earlier example of reusable executable skills and cross-environment reuse. Self-Refine improves one output through feedback, while EvoSkill aims to preserve improvements across tasks. Feedback Descent contributes the candidate frontier and feedback-history pattern. GEPA searches prompts with complementary instance-wise winners; AlphaEvolve evolves code through automatic evaluators. WikiSkill later makes persistent knowledge curation a separate component around skill generation.[^4]

The main limitations are narrow domain and model coverage, one run per configuration, small validation sets, potential adaptive overfitting, and incomplete isolation of individual design choices. Progressive skill loading also introduces activation behavior: an authored skill is useful only if the executor loads and follows it. More exhaustive search can improve correctness while increasing latency and API cost, which should be measured alongside the headline accuracy.

## Everdict changes and a concrete comparison

EvoSkill is a useful simple driver baseline: diagnose a training failure, declare a single capability edit, build an immutable candidate, evaluate it on selection cases, and preserve the outcome. Everdict can keep the proposal and resulting artifact separately identifiable so that a good diagnosis followed by a faulty build is distinguishable from a bad hypothesis. A candidate should pin the entire skill bundle, including helper code and trigger metadata.

Compare failure-only EvoSkill-style proposals with success-and-failure reflection, then add curated history as a separate arm. Fix the executor, selected training categories, case partitions, and total budget. Log skill activation, actual use, proposal repetition, per-category success, and cost. Test the selected library on unseen tasks and then on a different receiver model. Use a common final confirmation set across arms, and report every attempted candidate rather than only surviving branches. These are proposed Everdict experiments, not outcomes measured by this paper.
