# R35 — SkillRL: co-evolving a trained policy and a hierarchical SkillBank

SkillRL v1 combines external skill evolution with supervised fine-tuning and reinforcement learning of Qwen2.5-7B-Instruct. A stronger teacher distills interaction experience, teaches the student how to use the resulting skills, and adds skills from later failures. This is a joint policy-and-library training system. Its full improvement cannot be assigned to editing external text alone.[^1]

## Why abstraction and policy learning are combined

Raw trajectories mix useful decisions with exploration, repeated observations, and mistakes. Reusing a whole trace can consume context without explaining which action mattered. A distilled skill instead states a reusable principle and its applicability: for example, check the selected product variant's price after changing options, or verify an object's required state before final placement.

The paper distinguishes general skills, which apply across task types within an environment, from category-specific skills. It also argues that a base model may not know how to apply concise advice effectively. Cold-start demonstrations and RL therefore train the executor while the library changes.

ReAct supplies the reasoning/action interaction pattern; Reflexion and ExpeL supply experience-based reflection and memory precedents. GRPO and RLOO optimize policy weights from rewards. MemRL, EvolveR, and memory-plus-GRPO baselines differ in what they store and which parameters they update. The introduction's broad characterization of earlier memory methods as raw-trajectory storage is too coarse: some already distill lessons. The useful comparison concerns the concrete memory representation, retrieval, teacher data, and training procedure implemented here.[^1]

## Stage one: distill successful and failed experience

The base agent first collects interactions. OpenAI o3 is the teacher for skill distillation and supervised-data generation. Successful episodes supply critical decisions and reusable strategies. Failures supply an identified mistake, a proposed better action, and a prevention rule. Both are retained as learning evidence rather than treating every failure as worthless.[^2]

A skill contains an identifier or name, a short principle, and a `when_to_apply` condition. The appendix asks for concise JSON outputs. Initial general-skill prompts request eight to twelve ALFWorld skills or ten to fifteen WebShop skills. These prompts shape the abstraction; the study does not establish that the extracted causal explanations are independently correct for every trajectory.

The examples include systematic exploration, loop escape, action-precondition checks, constraint-rich product search, early rejection of a mismatching product, and checking attributes hidden in a description. Some general rules can conflict unless conditioned: immediate destination placement must yield to cleaning or heating when the goal requires it. A library needs preconditions and precedence, not only memorable slogans.

## Stage two: a hierarchical library and retrieval

SkillBank contains a general set plus category-specific sets. General skills are always included in the agent's context. Specialized skills are selected using embedding similarity to the task description, a threshold, and top-k retrieval; the experiments set k = 6. The policy then receives observations, the task, general skills, and retrieved specialized skills.[^2]

This hierarchy separates common guidance from selective detail. It is not the same hierarchy as metadata/body/resource progressive loading: general principles are injected, and the task-specific entries are short procedural records. The paper does not test searching a large public corpus or dynamically deciding whether to open arbitrary skill files.

The retrieval equation and category-evolution trigger both use the symbol δ. Implementation text associates δ = 0.4 with collecting failures, and the appendix calls it the update threshold. A reproducer should not assume that this unambiguously specifies the embedding cutoff as well. The embedding model and several retrieval details are not fully specified in the paper.

## Stage three: teach skill use and optimize the policy

Before RL, the teacher creates skill-conditioned demonstrations with reasoning and actions. The student is trained by supervised cross-entropy to imitate these sequences. The resulting checkpoint initializes RL and serves as its reference policy.[^3]

For each RL task, the policy samples a group of eight trajectories and receives task rewards. GRPO subtracts the group's mean reward and normalizes by its standard deviation to form relative advantages. A clipped importance-ratio objective limits large policy changes, and a KL penalty discourages excessive deviation from the reference. There is no separately trained value critic. When all rewards in a group are identical, practical normalization needs a zero-variance convention, which the displayed equation does not specify.

The reference penalty encourages continuity; it does not guarantee preservation of every learned skill-use behavior. The methods describe binary terminal rewards, while the appendix also lists an invalid-action penalty of 0.1. That extra shaping must be included when reconstructing the actual objective.

ALFWorld and WebShop execution prompts provide admissible actions and a recent interaction history, and require a reasoning block before the next action. The ALFWorld interface therefore differs from the original BUTLER setting, where generating valid commands is itself a challenge. Scores across those interfaces are not interchangeable.

## Recursive evolution and the role of validation feedback

At validation checkpoints, the system examines category success rates and failed trajectories. The teacher looks for missing coverage and proposes new skills or refinements. The stated sampling scheme groups failures by category and uses round-robin selection to retain diversity. It also mentions severity based on negative rewards, which is not fully reconciled with the binary terminal-reward description.[^2]

The prose says evolution is triggered for categories below a success threshold. The appendix permits analyzing up to ten failures when success is below 0.4 and five when it is above 0.4. This leaves the exact trigger policy ambiguous. It specifies validation every five steps and at most three new skills per evolution event.

Another distinction matters: the main prose allows refining existing skills, but Algorithm 1 updates the bank by set union, and the provided dynamic prompt requests one to three **new** skills given existing titles. A robust replacement, deduplication, contradiction-resolution, or retirement mechanism is not fully described. The reported dynamics primarily demonstrate library growth.

Most importantly, these validation failures generate future training content. This validation stream is adaptive development evidence, not an untouched confirmation set. The paper gives limited detail about final split membership and separation for each environment. Everdict must explicitly track which data changed either the library or the policy.

## Training resources and reproducibility details

The appendix reports 7,500 ALFWorld and 2,400 WebShop supervised examples, three SFT epochs, learning rate 1e-4, and batch size sixteen. RL uses learning rate 1e-6, KL coefficient 0.01, maximum prompt length 6,000, and response length 1,024.[^4]

The main text gives RL batch size sixteen with four gradient-accumulation steps; the appendix lists sixty-four. These may describe microbatch and effective batch, but the paper does not explicitly resolve the terminology. Likewise, the appendix labels 150 as epochs while the growth analysis describes step 150. Exact data traversal should be checked before reproducing the schedule.

The reported infrastructure is eight H100 80GB GPUs. Collection takes about three hours, distillation half an hour, SFT two hours, and RL twenty-four hours: approximately thirty hours per experiment. This is wall-clock context, not proof that all eight GPUs were fully occupied at every stage or a full dollar cost including teacher API calls.

The paper does not provide complete train/validation/test counts, repeat-seed uncertainty, decoding settings, or all search-QA evaluation details in its experimental appendix. Several baseline rows are marked as taken or replicated from earlier work. The tables are useful evidence, but should not be treated as a complete controlled reproduction manifest.

## ALFWorld and WebShop results

Table 1 reports these overall outcomes. WebShop's average score can give partial credit; its success rate is a separate stricter metric.[^5]

| System | ALFWorld success | WebShop score | WebShop success |
|---|---:|---:|---:|
| Qwen2.5-7B baseline | 14.8 | 26.4 | 7.8 |
| GPT-4o | 48.0 | 31.8 | 23.7 |
| Gemini 2.5 Pro | 60.3 | 42.5 | 35.9 |
| Reflexion | 42.7 | 58.1 | 28.8 |
| RLOO | 75.5 | 80.3 | 65.7 |
| GRPO | 77.6 | 79.3 | 66.1 |
| Mem0 + GRPO | 54.7 | 58.1 | 37.5 |
| SimpleMem + GRPO | 62.5 | 67.8 | 46.9 |
| SkillRL | 89.9 | 85.2 | 72.7 |

The difference from GRPO is +12.3 percentage points on ALFWorld and +6.6 on WebShop success. Sharing GRPO as optimizer does not isolate external evolution: teacher demonstrations, cold-start training, library structure, and later updates are also involved. Comparison with proprietary models is a specialized trained-system comparison, not evidence that a 7B model universally exceeds them.

SkillRL's ALFWorld category scores are Pick 97.9, Look 71.4, Clean 90.0, Heat 90.0, Cool 95.5, and Pick2 87.5. Relative to GRPO, Cool improves by 23.0 points, Pick2 by 22.8, and Heat by 15.3. The analysis prose approximately reverses the first two gains. SkillRL is not best in every category: RLOO's Look score is 78.2. The reported All score is not the unweighted average of the six printed category values.

## Search QA and transfer to other datasets

Training uses NQ and HotpotQA; five other QA collections are designated out of domain. Table 2 gives the following scores.[^6]

| Dataset | Training relationship | SkillRL | EvolveR |
|---|---|---:|---:|
| NQ | In domain | 45.9 | 43.5 |
| TriviaQA | Out of domain | 63.3 | 63.4 |
| PopQA | Out of domain | 45.9 | 44.6 |
| HotpotQA | In domain | 43.2 | 38.2 |
| 2Wiki | Out of domain | 40.3 | 42.0 |
| MuSiQue | Out of domain | 20.2 | 15.6 |
| Bamboogle | Out of domain | 73.8 | 54.4 |

The largest displayed advantage over EvolveR is Bamboogle's 19.4 points. Results are mixed elsewhere: TriviaQA and 2Wiki are lower, ZeroSearch is stronger on PopQA at 51.5, and StepSearch is stronger on MuSiQue at 22.6. Transfer is supported, but universal dominance and fully task-agnostic skills are stronger claims than these cells establish.

The reported SkillRL Avg is 47.1; the arithmetic mean of its seven printed scores is approximately 47.51. The paper does not resolve this discrepancy. Preserve both the source aggregate and the underlying cells instead of silently recomputing one as the other. Similarly, the broad headline of more than 15.3% improvement needs an explicit comparator and aggregation before being used in an Everdict decision.

## Ablations: which changes actually account for the gain?

The four ablations provide a more direct decomposition than the headline comparison.[^7]

| Variant | ALFWorld | WebShop success | Loss from full method |
|---|---:|---:|---|
| Full SkillRL | 89.9 | 72.7 | — |
| Task-specific skills only | 76.8 | 61.4 | 13.1 / 11.3 points |
| Raw trajectories instead of skills | 61.7 | 50.2 | 28.2 / 22.5 points |
| No cold-start SFT | 65.2 | 46.5 | 24.7 / 26.2 points |
| No dynamic evolution | 84.4 | 70.3 | 5.5 / 2.4 points |

Removing hierarchy here removes general skills; it is not a content-matched flat-versus-hierarchical comparison. Replacing skills with raw trajectories changes abstraction and context volume. Removing SFT also removes a substantial teacher-demonstration stage. Those interventions support the complete design but do not isolate one abstract principle perfectly.

Dynamic evolution contributes 5.5 and 2.4 points in the reported comparison. It is an additional benefit beyond a strong static-library trained system. There is no separate success-only/failure-only ablation or full test of deletion, conflicting skills, and long-term forgetting. The prose's approximate twenty-point SFT drop and “up to 25” raw-trajectory drop understate some displayed differences; the table above uses the actual endpoints.

## Growth, context efficiency, and qualitative evidence

The illustrated bank grows from fifty-five skills—twelve general and forty-three specialized—to one hundred—twenty general and eighty specialized—by the reported step 150. Growth does not itself measure diversity, correctness, or retention of rare capabilities.[^7]

The method claims ten- to twenty-fold compression of raw experience into individual skill content. The actual full-prompt comparison reports a much smaller reduction, approximately 10.3%, from roughly 1,450 tokens to below 1,300. These are different denominators. Figure 4 shows variable lengths and some overlapping steps; it does not establish universal ten-fold serving savings. No complete latency or cost-per-success experiment is supplied.

The validation learning curve exceeds 80% around step sixty with evolution, while the no-evolution curve reaches a lower peak around ninety. The evolution curve is below the other curve at several early checkpoints, and the plot has no repeated-run uncertainty bands. Because validation failures also inform skill updates, this curve is a development diagnostic rather than independent generalization evidence.

Appendix cases illustrate rejecting a product with the wrong color, rechecking variant pricing, cleaning before placement, heating only after acquiring the object, and pairing an object with a lamp. They explain intended reasoning, but selected successful examples and explicit skill-name mentions do not prove causal use or absence of memorization. Some displayed action sequences are abbreviated, so they should not be copied as fully replayable environment traces.

## An Everdict experiment that separates two kinds of evolution

The useful design is a factorial comparison: frozen versus trained executor, crossed with static versus evolving skills. Give each cell comparable permitted evidence and account separately for teacher calls, model training, runtime retrieval, and confirmation evaluation. This reveals whether a skill edit works with the existing executor or only after policy adaptation.

Keep general procedures concise and specialized rules conditional, but test this against equal-content alternatives before adopting a hierarchy. Record a skill's source trajectories, applicability, current text digest, prior revisions, and observed regressions. Failure-derived counterfactual advice remains a hypothesis until tested; a confident teacher explanation cannot promote itself.

For Everdict's first loop, validation-driven skill generation belongs in driver search. Any feedback used to generate or refine a candidate counts as development evidence. Confirmation must freeze the complete candidate—including model checkpoint and library when both change—and use evidence that did not shape either. The platform protects that lineage and adoption boundary; the driver owns category sampling, curation, and evolution policy. The paper motivates these experiments but does not establish that Everdict must introduce weight training to improve its initial evolution loop.[^8]
