# R33 — SRA-Bench: retrieving, loading, and benefiting from skills

This note covers version 3 of the Skill Retrieval Augmentation paper, including its six research questions and dataset-construction appendix. The paper contributes a benchmark and empirical decomposition of skill use. It does not train a new evolving agent or experimentally validate the lifelong-evolution agenda proposed near its conclusion. Its central lesson for Everdict is that finding a relevant procedure, opening it, and obtaining a better outcome are distinct events.[^1]

## The problem and the three-stage model

A library can contain the right solution procedure while an agent still fails. The retriever might miss it; the agent might ignore it or load a distractor; or the selected procedure might be misapplied. A single final score cannot locate that failure.

The paper represents a skill through its name, short description, main content, and executable payload. Retrieval produces a ranked candidate set from the query and corpus. Incorporation turns candidates into the material used for solving: this may involve selection, rewriting, compression, organization, or an empty selection. Application then solves the task using that material. The experimental baselines implement only some of this broader formulation.[^1]

This resembles retrieval-augmented generation, but the retrieved object contains a procedure or capability rather than only factual evidence. The distinction concerns intended use, not a claim that ordinary RAG can never retrieve instructions. Compared with tool selection, a skill may coordinate several tool calls and encode preconditions and error handling. Compared with SkillsBench, SRA-Bench explicitly labels relevant skills inside a larger distractor corpus. SkillRouter and SkillRet emphasize ranking; SRA-Bench connects ranking, loading behavior, and task outcomes.

## Benchmark construction and what the gold labels mean

The corpus has 26,262 skills: 636 constructed gold skills and 25,626 background skills gathered from public ecosystems including GitHub, Skills.sh, and Hugging Face. Filtering removes malformed, inaccessible, and duplicate entries. This is corpus normalization, not proof that every executable payload is safe or correct.[^2]

| Dataset | Instances | Gold skills | Main capability and scoring |
|---|---:|---:|---|
| TheoremQA | 747 | 320 | Identify and apply a theorem; rule-based answer checking |
| LogicBench | 760 | 19 | Apply an inference pattern; rule-based checking |
| ToolQA | 1,430 | 14 | Execute a tool workflow; rule-based checking |
| MedCalc-Bench | 1,100 | 55 | Select and implement a calculator; rule-based checking |
| CHAMP | 223 | 89 | Combine mathematical concepts; rule-based checking |
| BigCodeBench | 1,140 | 139 | Compose library operations; unit-test pass@1 |

The first four datasets use single-skill annotations; CHAMP and BigCodeBench can require multiple skills. The total is 5,400 instances. Their overall task score is weighted by instance count, so ToolQA and BigCodeBench contribute more than CHAMP. It is not an equal average over six domains.

Construction works backward from tasks and their annotations. An LLM drafts skills using associated questions and answers; source material can also include official solutions, calculator rationales, canonical code, and ToolQA generation templates. Experts then remove copied answer constants and task-specific examples, correct errors, and turn declarative descriptions into reusable procedures. This is task-distribution-informed construction. Expert removal of direct answers improves validity, but it does not make the resulting skills independently learned from a held-out task family.[^2]

The appendix explains different revision problems. TheoremQA needs actionable steps and distinctions between neighboring formulas. LogicBench needs premise extraction, attention to qualifiers, and separation of valid inference from common fallacies. ToolQA needs operational constraints: a top-three document retriever cannot reliably answer an exhaustive aggregation query, which may require a database or Python workflow instead. MedCalc needs branch conditions, units, clamping, and rounding, with calculator checks against examples. CHAMP needs recognition cues and alternative mathematical approaches. BigCodeBench needs precise API behavior, such as regular-expression capture groups and plotting return types. These are concrete kinds of skill evolution, although the paper does not ablate LLM drafts against expert revisions.

The labels identify intended gold skills. An unlabelled background skill might implement an equivalent or useful procedure. Consequently, gold recall is a useful diagnostic, but a non-gold retrieval is not automatically useless.

## Models, controls, and execution protocol

The main experiments use Qwen3-4B, 32B, and 235B-A22B; Llama 3.1-8B and 3.3-70B; and Mistral Small 3.1-24B. The stated context limit is 128K and temperature is 0.7. GLM-5.1 and GPT-5.4 appear in the later loading-behavior studies. The paper does not provide a complete repeated-run, hardware, and total-cost ledger for every condition.[^3]

Five conditions separate different access policies:

1. **Direct:** no skills. This does not always mean no tools: ToolQA still receives its tool definitions and few-shot ReAct setup.
2. **Oracle:** directly provide all annotated gold skills.
3. **Full injection:** in the main comparison, inject the body of BM25's top-one skill.
4. **LLM selection:** expose metadata for BM25's top fifty, require selection of exactly one, and inject its body.
5. **Progressive disclosure:** expose the same fifty metadata entries and allow `LOAD_SKILL` calls over up to ten rounds. The agent can load multiple skills or none.

The top-one versus top-fifty candidate difference means selection gains cannot be attributed solely to a better presentation format. Forced single selection also differs from the multi-skill oracle on CHAMP and BigCodeBench. Oracle is a diagnostic control, not a mathematical upper bound: an annotated skill may be imperfect, and stochastic solving or alternative skills can outperform it.

## RQ1: Do retrieved skills improve final performance?

Table 2 reports the following overall percentages. These are source measurements, not independent reproductions.[^4]

| Executor | Direct | Oracle | Full injection | LLM selection | Progressive |
|---|---:|---:|---:|---:|---:|
| Llama 8B | 29.8 | 44.5 | 32.7 | 37.0 | 36.3 |
| Llama 70B | 47.8 | 64.4 | 52.7 | 59.2 | 48.5 |
| Mistral 24B | 43.4 | 63.2 | 48.5 | 56.6 | 46.7 |
| Qwen 235B | 53.3 | 67.5 | 56.2 | 62.8 | 59.9 |
| Qwen 32B | 50.8 | 67.2 | 54.3 | 62.4 | 55.3 |
| Qwen 4B | 38.8 | 61.6 | 45.5 | 53.3 | 43.2 |

LLM selection is the strongest practical strategy in every aggregate row, while substantial distance from oracle remains. Small models can benefit greatly: Qwen 4B rises from 22.0% to 65.7% on MedCalc with selection, compared with 73.5% using oracle skills.

The result is not uniformly positive. Qwen 4B's LogicBench baseline is 75.0%, versus 70.0% with selection and 65.7% with progressive disclosure. Llama 8B's ToolQA score falls from 16.7% to 13.6% with full injection. Qwen 32B's CHAMP score falls from 65.5% to 58.7% with progressive disclosure. Meanwhile, Qwen 235B reaches 68.1% on TheoremQA with progressive disclosure, exceeding its 65.9% oracle score. These cells matter when deciding whether an evolved library can be adopted globally.

The table marks paired t-test comparisons at p < .05. It does not fully establish repeated-run uncertainty, family-level clustering, or a comprehensive multiple-comparison protocol. Statistical markers should not replace examining task-specific regressions.

## RQ2: Controlled distractors and real retrieval depth

The controlled experiment always includes gold skills, then adds zero, two, four, or eight hard negatives drawn alternately from BM25 and BGE rankings. Candidate order is shuffled. Full injection receives all bodies; progressive disclosure receives metadata and can choose what to load. LLM selection is not part of this comparison.[^5]

All six plotted full-injection curves decline as distractors increase. Progressive disclosure usually declines less, but its clean-candidate starting point is often substantially lower. At eight distractors it overtakes full injection for Llama 8B, Llama 70B, and Qwen 235B, while remaining below it for Qwen 4B, Qwen 32B, and Mistral 24B. Thus robustness and absolute quality are separate properties.

A second experiment uses actual BM25 top-k sets for k = 1, 2, 4, and 8, without guaranteed gold inclusion. Increasing k can improve coverage and simultaneously add interference. Full injection often improves initially and then deteriorates, but Llama 70B declines throughout. Progressive disclosure is more stable and sometimes improves. These smaller pools differ from the top-fifty main experiment; their scores are not interchangeable.

Adding negatives also increases context length, so these plots do not isolate semantic distraction from token-volume effects. A length-matched neutral-text control would help. In addition, an unannotated skill is not necessarily functionally irrelevant.

## RQ3 and RQ4: Better ranking helps, but recall is not utility

The retrieval study compares BM25, TF-IDF, BGE, Contriever, a BM25/BGE interleaving hybrid, and LLM reranking of BM25's top fifty. It measures recall and NDCG at several cutoffs. Recall concerns coverage of annotated relevant skills; NDCG also rewards their ranking position. With multiple gold skills, top-one recall need not equal the probability of retrieving any useful skill.[^6]

BM25 recall@1/@10 ranges from 7.0/55.1 on ToolQA to 57.2/80.7 on TheoremQA. BGE improves those to 32.2/83.4 and 66.8/86.1, but is worse on LogicBench: 4.1/20.5 versus BM25's 12.0/36.1. A retriever's average reputation does not guarantee domain suitability.

Qwen 235B reranking reaches MedCalc recall@1 of 92.3%, versus BM25's 29.3%, and BigCode recall@10 of 80.0%, versus 61.1%. The hybrid starts with BM25, so its identical top-one scores are a consequence of interleaving order, not a surprising learned equivalence. Any reranker remains bounded by what enters its first-stage pool.

RQ4 holds top-one body injection constant and changes the retriever. BM25 plus the executor's own LLM reranker improves aggregate scores for all six models: for example, Llama 8B moves from 32.7% to 39.4%, and Qwen 32B from 54.3% to 61.8%. Nevertheless, Qwen 32B's CHAMP score drops from 70.4% to 65.9%; Qwen 235B's BigCode score drops from 50.4% to 49.4%. Ranking quality and downstream utility remain different measurements. These reranking results also differ from Table 2's forced-selection prompt and should not be silently merged.

## RQ5 and RQ6: Relevance awareness and need awareness

Loading means requesting any valid skill ID, not necessarily a gold skill or one subsequently followed correctly. Overall loading rates range from 11.1% for Llama 70B to 72.1% for Llama 8B; larger models do not monotonically load more or less appropriately.[^7]

RQ5 compares cases where gold appears in the top fifty with cases where it does not. Llama 70B loads in 10.4% versus 14.5% of cases, respectively. GPT-5.4 shows clearer separation, 36.6% versus 3.6%; GLM-5.1 gives 43.5% versus 8.2%. The broad introductory claim of almost no relevance awareness therefore needs this model-specific qualification. These are different task groups, not randomized insertion/removal of gold for the same task.

RQ6 restricts analysis to 4,520 instances whose gold skills are retrieved. It divides tasks by whether the model answered correctly without skills, then measures progressive loading. The mean over eight models is approximately 36.9% for both groups. However, GPT-5.4 loads on 34.4% of natively correct versus 40.2% of natively incorrect tasks, while Llama 8B reverses that direction, 84.5% versus 69.4%.

A single temperature-0.7 baseline outcome is an imperfect label for whether a model intrinsically “needs” help. A skill might reduce cost or variance on an already-correct task, or fail to rescue an incorrect one. A stronger utility test would compare matched with/without-skill outcomes over repeated samples, including cost. The present experiment diagnoses weak alignment with baseline failure; it does not identify the optimal invocation policy.

## Evolution agenda, limitations, and an Everdict experiment

The discussion proposes structured libraries with dependencies and alternatives, offline quality checks and refinement, utility-aware retrieval, and eventual mixtures of external skills with parametric capability. These are research directions, not experimentally established components of SRA-Bench.[^8]

For Everdict, the useful immediate change is better evidence separation. A driver can record candidate skill IDs and digests, retrieved ranks, loaded IDs, execution outcomes, and cost. Loading is observable; genuinely following a procedure needs trace evidence or instrumentation and should not be inferred from a load call alone. Content remains advisory and cannot change campaign authority or evaluation rules.

A concrete study would freeze a corpus and compare full injection, forced selection, and progressive disclosure on identical candidate pools, alongside no-skill and explicitly privileged oracle controls. Run paired tasks and repeated samples, then report per-family outcomes, negative transfers, retrieval coverage, loading, and total cost. Next compare unchanged skills against expert-style procedural revisions while holding routing fixed; only then vary routing. This separates content evolution from retrieval evolution.

Skill construction must use training evidence only, with task-family separation before drafting. Selection can inspect permitted feedback, while confirmation uses a frozen candidate and held-out evidence. The platform should preserve immutable candidate bytes and raw results; the driver may maintain a derived skill or wiki projection. Neither high recall nor frequent loading should independently authorize adoption. The proposed Everdict first loop does not require adding a runtime wiki before these causal questions can be tested.
