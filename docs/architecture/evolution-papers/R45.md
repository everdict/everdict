# R45 — SkillRouter: body-aware skill retrieval

SkillRouter asks how an agent can find a useful skill among roughly 80,000 similar packages. Its central distinction is between what the **router indexes** and what the **executing agent initially sees**: the router benefits from skill bodies even when the agent initially receives only names and descriptions. This is trained retrieval, with frozen downstream agents; it is not a demonstration that automatically rewriting skills makes their procedures better. This explanation covers arXiv **2603.22455v5**, including Appendices A–N and all four figures. Reported results have not been independently reproduced.[^1]

## 1. Problem, prerequisites, and related work

A skill description might say “video processing,” while its body identifies audio transcription, timestamps, or frame extraction. Those capabilities answer different requests. Indexing metadata alone can therefore lose the distinction before an executing agent ever has an opportunity to inspect a skill.

A **bi-encoder** independently maps queries and documents to vectors. Document vectors can be computed offline, making large-catalog retrieval inexpensive. A **cross-encoder** jointly reads a query and each candidate, allowing more detailed interactions at higher cost. SkillRouter uses the first to retrieve 20 candidates and the second to rank them. It adopts established neural information-retrieval architectures; its contribution is the field-access investigation, skill-specific supervision, negative filtering, and ranking recipe.

ToolRet studies heterogeneous tools/API documents; AgentSkillOS emphasizes organization and composition; SkillsBench measures execution when skills are provided. SkillRouter addresses the earlier selection step under long, overlapping natural-language skill bodies. Compared with [R06 SkillRet](R06.md) and [R33 retrieval augmentation](R33.md), its distinctive evidence is the controlled body-versus-metadata study and compact trained pipeline. Unlike [S00 WikiSkill](S00.md), the evolving artifact is principally router weights and its index, not an execution-maintained wiki. Progressive disclosure is compatible with a body-aware index: displaying every body in the agent's context is unnecessary.[^1]

## 2. Benchmark and what each metric measures

The core uses 75 of 87 SkillsBench-derived tasks: 59 clean and 16 mixed tasks with at least one non-generic core skill. Twelve tasks labeled only with generic file skills such as PDF or XLSX are excluded. There are 24 single-skill and 51 multi-skill queries, spanning 55 domains and eight broad categories. The number of labeled skills ranges from one to seven, averaging 2.75. Some multi-skill labels describe substitute or overlapping capabilities, so recovering every annotation is not always identical to satisfying every indispensable task stage.

The Easy pool contains **78,361** natural skills; Hard adds **780 synthetic distractors**, producing 79,141. Distractors deliberately share a domain, technology, or overly broad capability while missing the target function. Unless stated otherwise, headline results average the same 75 queries across both pools. These are two correlated evaluations, not 150 independent user tasks. The pool retains same-name overlaps; only duplicate IDs are removed. Hard is a targeted stress test, not an estimate of real-world distractor prevalence.

| Metric | Meaning | What it does not establish |
|---|---|---|
| Hit@1 | First result is any labeled skill | All necessary skills were found |
| MRR@10 | Reciprocal rank of the first labeled skill, within ten | Quality of the rest of the list |
| Recall@K | Fraction of the query's labeled set in the first K, averaged over queries | Complete coverage on each query |
| FC@10 | All labeled skills occur in the first ten | The agent successfully executes them |

Descriptions are present for 99.88% of the natural pool, but their median length is 21 words versus 704 for bodies. Missing metadata alone therefore cannot explain the body-access effect. The task-difficulty annotations—four easy, 45 medium, 26 hard—are separate from the Easy/Hard **pool** distinction.[^2]

## 3. Body-access experiments and their limits

Removing bodies lowers average Hit@1 from 56.0% to 18.7% for the base 0.6B encoder, 64.0% to 25.3% for the 8B encoder, and 68.0% to 24.0% for the 8B+8B pipeline: losses of **37.3, 38.7, and 44.0 percentage points**.

Three additional controls investigate whether better descriptions could substitute for bodies:

1. **Oracle-ND:** GPT-5.4-mini reads a skill body and writes a query-blind, 40–60-word description. Only ground-truth skills receive replacements; other catalog entries remain untouched. For the compact tuned pipeline, raw metadata / Oracle-ND / all fields score 27.3 / 52.7 / 74.0%. Corresponding values are 26.7 / 56.7 / 64.0% for the small base pipeline and 24.0 / 61.3 / 68.0% for the large base pipeline. This is a privileged diagnostic, not a deployable catalog-wide rewriting baseline or a proof that sufficiently good compression is impossible.
2. **Matched metadata-only training:** using the same 37,979 training pairs and negatives, a metadata-only encoder reaches 51.3%, versus 65.3% with all fields. Applying Oracle-ND to that metadata-trained model instead gives 32.0%; this is a distribution-changing inference intervention, not a third matched training treatment.
3. **Length and attention diagnostics:** body advantages persist across description-length quartiles, including +31.8 points for descriptions longer than 35 words. In attention traces, bodies occupy 96.5% of skill tokens; final-layer attention is 98.1%, exceeding the length baseline in 69/75 cases. Names receive 26.3% at layer 19 despite only 3% of tokens. The measurement averages heads at the final decision position and normalizes within skill fields. It is an association, not a causal explanation of the model's decision.

Appendix D's quartile analysis uses 148 available instances, rather than the main 150 query-pool evaluations; the missing-instance scope is not fully explained. Its aggregate should not silently replace the main result.[^3]

## 4. Training recipe and execution path

GPT-4o-mini generates realistic, approximately 160-word task descriptions from sampled skills across 51 categories, without naming the skill. Benchmark-labeled skills are excluded from positive supervision. The encoder learns from **37,979 query–skill pairs** using InfoNCE: increase the positive pair's similarity relative to alternatives in the batch, with temperature 0.05. The paper combines this with ten mined negatives per query: four semantic neighbors, three lexical confounders, two same-category skills, and one different-category skill. Appendix F clarifies that lexical selection operates within the semantic top-50 candidate set.

A negative may actually be another implementation of the correct capability. Penalizing it would teach the model the wrong boundary. Filtering removes 24,879 same-name pairs, 13,860 high trigram-overlap pairs, and 326 high-embedding-similarity pairs: **39,065**, roughly 10% of mined negatives. Thresholds are Jaccard above 0.6 and cosine similarity above 0.92. These are duplicate heuristics, not an exhaustive semantic-equivalence oracle.

The trained encoder supplies top-20 lists for **32,283 reranker training groups**. Listwise cross-entropy raises a positive's score relative to the other candidates in that list, with temperature 1.0. The pointwise alternative independently classifies each pair, which can fail to learn useful ordering among many broadly relevant candidates.

Both components train for one epoch on a single 96GB Hopper GPU using AdamW, BF16, weight decay 0.01, cosine scheduling, and 5% warmup. Encoder/reranker learning rates are 2e-5/1e-5; batch and accumulation settings are 8×4 versus one list×16. Encoder character caps are query 1,500, description 300, body 2,500, with a 2,048-token cap. Reranker description/body caps are 500/2,000 characters and 4,096 tokens overall. “All-field” therefore means **body access within truncation limits**, not reading an arbitrarily long complete skill.

At deployment, pin the skill inventory, embed it offline, encode the incoming query, retrieve approximately, then rerank 20 pairs. The downstream harness initially exposes chosen skill names and descriptions; body-aware routing does not mean every selected body is automatically placed in the initial prompt.[^4]

## 5. Main results and component experiments

| System | Core average Hit@1 | Relevant comparison |
|---|---:|---|
| BM25 | 31.4% | Sparse lexical baseline |
| BGE-Large-v1.5 / OpenAI embedding API | 60.0 / 62.0% | Stronger generic retrieval alternatives |
| Base Qwen encoder, 0.6B / 8B | 56.0 / 64.0% | Encoder scaling |
| Tuned encoder, 0.6B / 8B | 65.3 / 68.0% | Routing-specific adaptation |
| Base pipeline, 1.2B / 16B | 64.0 / 68.0% | Two-stage generic baselines |
| Tuned pipeline, 1.2B / 16B | **74.0 / 76.0%** | Both stages adapted |

The compact pipeline improves by ten points over the same-size base and six over the 16B base, using about 13.3 times fewer parameters. Its Easy/Hard scores are 76/72%. GPT-4o-mini and GPT-5.4-mini judges reach 67.3/66.0% on the tuned encoder's candidates; they choose a single winner, rather than producing a comparable full scored ranking.

Filtering negatives improves encoder Hit@1 from 61.3 to 65.3%. With that encoder, a base 0.6B reranker gives 70.7%; pointwise fine-tuning falls to 43.3%, while listwise reaches 74.0%. This establishes a large difference between the tested recipes, not that every pointwise ranking method must fail. Across the 150 correlated evaluations, reranking fixes 19 top-one misses but introduces six, leaving a net thirteen improvements.

Choosing K=20 matches or beats K=10 and K=50 on these core comparisons. More candidates do not guarantee a better winner: the tuned reranker at K=50 loses two average points. However, K was selected using the reported core benchmark, so it is a tuned operating point, not an untouched validation result.

The benefit is metric-specific. For multi-skill queries, compact versus large-base Hit@1 is 74.5 versus 68.6%, but Recall@10 is **62.4 versus 63.6%**, and FC@10 **35.3 versus 38.2%**. Even with the same tuned encoder, the base small reranker has higher overall R@10 than the tuned reranker, 72.4 versus 70.4%. Figure 4 overlays Hit@1 stars on Recall@K curves; those quantities should not be treated as identical ceilings. Its K=1 plotted values also resemble Hit@1 despite the fractional multi-label recall definition, so use the explicit metric tables for quantitative conclusions.[^5]

## 6. Supplementary transfer, downstream execution, and cost

**SkillBench-Supp** evaluates the same checkpoints without re-tuning on 256 single-label synthetic queries for 100 skills: 51 OpenClaw, 19 AgentSkillOS, and 30 held-out pool skills. Claude Sonnet 4.6 generates 168 descriptive and 88 indirect requests, using different prompts from training. Name/CLI leakage and length checks regenerate or discard noncompliant queries. Content deduplication plus BM25 top-five/LLM equivalence checks remove overlapping entries; the final pool contains 77,537 skills. This reduces known false negatives but cannot certify that no equivalent alternatives remain.

Compact tuned versus large base Hit@1 is **64.1 versus 63.7%**, approximately one query apart; the scaled tuned pipeline reaches 73.0%. The compact advantage is therefore much smaller than on the core. On indirect queries, compact tuned actually trails the large base, 56.8 versus 59.1%; its encoder also trails the large base encoder, 35.2 versus 39.8%. Using another generator helps test transfer but does not establish human-query validity or rule out every semantic overlap. Oracle-ND still leaves a 5.1–12.1-point pipeline gap to all-field inputs on this supplementary set.

For **execution**, four agents—Kimi-K2.5, glm-5, Sonnet 4.6, Opus 4.6—use Claude Code with a 1,200-second timeout, three trials per task and condition, on the natural pool without synthetic Hard distractors. Average success is 14.89% without skills and 32.67% with gold skills. Base versus compact routing yields 25.78 versus 27.56% at top one, and 25.45 versus 27.78% at top ten: **+1.78 and +2.33 points**. This recovers around 71–73% of the measured no-skill-to-gold uplift, not 71–73% absolute task success. Gold is a useful reference condition, not a mathematical upper bound on every possible package.

Effects vary: glm-5 regresses at top one, and Kimi regresses at top ten. Illustrative cases include a dependency audit improving 0/12 to 12/12, transcription 0/12 to 9/12, and HVAC control regressing 8/12 to 4/12 when important prerequisite skills are missed. Other retrieval cases show a reranker rescuing environment setup and XML-to-TOML conversion from ranks 13 and 11, but failing to infer that invoice-fraud analysis first requires table extraction. These are mechanism examples, not independent statistical tests.

Serving tests time 80 queries: compact/large pipelines have median 495.8/2,900.1ms and p95 871.4/5,676.5ms, with 18,976/22,539MiB GPU memory. The 5.8× median speedup excludes model loading, offline embeddings, index construction, training, and agent execution. Reported GPU-seconds per thousand queries are compute-footprint measurements, not dollar costs. No downstream significance tests or comprehensive equal-total-cost comparison are supplied.[^6]

## 7. Everdict evolution proposal and decision criteria

The strongest transferable idea is **evolving access to existing knowledge independently from evolving that knowledge**. A useful procedure may already exist but remain undiscovered; rewriting it would address the wrong failure.

Propose a driver-side retrieval experiment over frozen, provenance-linked experience and skill snapshots. Compare metadata-only, body-aware generic retrieval, and task-adapted retrieve-and-rerank. Match retrieval limits, executor, prompt budget, and task splits. Pin model weights, index digest, chunking/truncation, skill versions, and candidate order so a result can be replayed. Similarity filters may identify suspect duplicate negatives, but keep the original evidence and log why each pair was excluded.

Measure first-use usefulness, prerequisite coverage, completed-task success, harmful advice retrieval, latency, and total indexing/training cost. Include multi-step tasks with substitute and complementary skills separately. Hold out families for final confirmation and reserve the selection split for K, thresholds, and training choices. Test whether the agent actually loads and uses the routed procedure; Hit@1 alone is insufficient.

This is an experiment proposal within the [first-loop architecture](../evolution-first-loop.md), not an implemented router or a justification for adding 80,000 skills immediately. The platform should continue to own evidence provenance, disclosure boundaries, and confirmation authority. A router or curator can suggest relevant experience; it cannot turn similarity into proof or promote a candidate. Advance this experiment only if end-to-end gains survive equal budgets and new-family confirmation; otherwise, a simpler body-aware index may capture the useful part without training infrastructure.
