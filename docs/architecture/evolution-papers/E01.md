# E01 — Reflexion: learning through verbal experience

Reflexion converts feedback on a failed attempt into a short textual lesson, then conditions another attempt on that lesson. Its important contribution is an explicit **evaluate → explain → remember → retry** loop with fixed model weights. The evidence concerns adaptation over repeated attempts on tasks, not a general proof of lasting transfer to unrelated tasks. This note covers **2303.11366v4**, all experiments and Appendices A–D. Results are author-reported and have not been independently reproduced.[^1]

## 1. Problem and intellectual context

An agent can fail in a long trajectory because an early action was wrong, then repeat the same mistake after a reset. A scalar “failed” signal identifies the outcome but not what to change. Reflexion asks the LLM to derive an actionable explanation from the observed trajectory and feedback, retaining that explanation for the next episode.

This resembles reinforcement learning in that feedback changes the effective policy, but there is no gradient update to model parameters. The paper's “semantic gradient” is a metaphor for a language instruction suggesting a direction of change. It provides neither a derivative nor a formal guarantee that the proposed diagnosis is true or that the next attempt improves.

[R39 ReAct](R39.md) interleaves reasoning and actions within an attempt. Reflexion adds memory **between** attempts. [E02 Self-Refine](E02.md) iteratively critiques and revises a generation; Reflexion additionally studies long action trajectories and environment feedback. CodeT uses generated tests to select code, while debugging approaches use execution feedback to repair it. Reflexion's programming experiment places a verbal diagnosis between test failure and revision. Later work such as [R41 TextGrad](R41.md), [E09 ReasoningBank](E09.md), and [R46 Memento-Skills](R46.md) develops richer feedback propagation or memory units beyond this small sliding window.[^1]

## 2. Method: three roles and two memories

The **Actor** generates text or actions, using CoT or ReAct prompting. The **Evaluator** scores the resulting trajectory through exact-match answers, environment completion, heuristics, LLM classification, or generated tests, depending on the task. The **Self-Reflection** model reads the trajectory, score, and previous lessons and produces a concise explanation of what failed and how to act differently. These are distinct roles; they need not be three independently trained models.

Short-term memory is the current action–observation history. Long-term memory consists of recent reflections, usually only one to three entries because of context limits. A new attempt starts from a reset task environment, with the reflections in its prompt. The method can remember locations already searched, conditions that were overlooked, or a specific coding error without replaying an entire failed trace.

The intended control flow is to stop when the evaluator accepts the result **or** the attempt budget is exhausted. Algorithm 1 prints a loop condition using `not pass OR below max trials`; implemented literally, that would continue after success and could continue beyond the cap on failures. Treat this as a pseudocode inconsistency; a bounded implementation needs both “not yet accepted” and “budget remains.”

Reflection is an inference from observations, not additional external evidence. A useful memory should distinguish “the take action failed” from “I suspect I never possessed the object.” This matters because a fluent explanation can introduce false facts that persist into later attempts.[^2]

## 3. ALFWorld: learning from repeated environment attempts

The decision-making study uses **134 text-based ALFWorld environments across six task types**, such as locating, moving, heating/cooling, and examining objects. The Actor is GPT-3 with ReAct and two domain-specific example trajectories, following the earlier ReAct setup. Memory retains the last three reflections.

Two mechanisms detect unproductive behavior: an LLM classifier and a handwritten heuristic. The heuristic triggers reflection after more than three repeated action/response cycles or more than 30 actions. The baseline also resets and retries when this occurs, but omits reflection. Thus the experiment compares reflection against repeated sampling, not merely one baseline attempt against many enhanced attempts.

The heuristic Reflexion agent solves **130/134 environments, about 97%**, while the ReAct retry curve plateaus near 75%; this is the roughly **22-percentage-point** headline advantage. The LLM-evaluator variant reaches roughly 94%. The curves are **cumulative solved-task proportions**: once a task has succeeded it remains counted. They do not show that every later policy succeeds on 97% in a fresh independent replay. The prose describes 12 consecutive trials, while the success plot shows indices 0–10; the failure plot extends to 11. Preserve this presentation discrepancy when specifying a reproduction budget.

The failure analysis attributes a large share of baseline errors to believing an object was acquired when it was not. Reflection markedly reduces this category; baseline hallucination remains around 22%. The second category is inefficient planning, including searching many containers without retaining useful progress. These classifications support a mechanism hypothesis but are not independently validated causal labels.

The appendix's mug-and-lamp example is instructive. The successful retry stays at the desk where both objects were observed, takes the mug, and uses the lamp. The reflection instead says the agent should find the lamp before the mug. That statement is at best incomplete: the failed trajectory moved away from the observed lamp, and the successful action order still takes the mug before using it. Success therefore does not prove the reflection identified the precise causal error.[^3]

## 4. HotpotQA: retrieval, reasoning, and memory ablation

The QA study uses **100 questions** and three conditions: CoT without supplied evidence, ReAct with Wikipedia retrieval, and CoT with ground-truth supporting context. The last condition isolates reasoning over provided documents rather than search. CoT uses six examples, ReAct two, and reflection two; memory holds three experiences.

Between attempts, the environment uses **exact match against the reference answer** to return correct/incorrect. The reflection is not shown the answer itself, but it receives an answer-dependent oracle signal. This is not fully self-supervised correction. The paper describes stopping after three consecutive failed attempts per question, while aggregate figures span more trial indices; exact per-task scheduling needs care in reproduction. Baseline retries use temperature 0.7.

Figure 4's ReAct curve rises to approximately 54%, versus a baseline around 34%, yielding the roughly 20-point headline. CoT with supplied context rises **61→75%**, a 14-point gain. A separate memory experiment compares supplied-context CoT at about 61%, adding the latest raw trajectory at 66%, and adding reflection at 74%: **eight points beyond episodic memory alone**. The 74 and 75% values belong to different panels, not one exact repeated measurement.

Appendix A tests additional models. Supplied-context CoT improves 60→77% for text-davinci-003, 57→71% for GPT-3.5-turbo, and 68→80% for GPT-4. ReAct improves 30→55%, 26→38%, and 39→51%, respectively. These are additional reported runs; do not overwrite the main plot's values or compare model strength without accounting for prompting and run variation.

Qualitative examples show narrowing an answer to a genuinely shared profession, distinguishing one battle from a campaign, and identifying a particular degree field rather than all possible fields. They also expose unreliable explanations. The Grown-Ups example succeeds by searching Sam Kelly, yet the displayed reflection recommends Gorden Kaye, which led toward the prior wrong answer. Another example states both musicians were in seven bands and nevertheless concludes one was in more. Exact-answer success does not certify a valid reasoning chain or useful reusable lesson.[^4]

## 5. Programming: generated tests and the meaning of pass@1

Programming uses GPT-4 on Python and Rust versions of HumanEval and MBPP, plus **40 hard LeetCode questions** in the introduced LeetcodeHardGym. MultiPL-E supplies translations; the HumanEval Rust experiment uses the 50 hardest translated problems, not the full Python set. The Gym supports 19 languages, but reported experiments focus on Python and Rust. The authors selected LeetCode releases after October 8, 2022, which they describe as the model cutoff; date filtering reduces a contamination concern but cannot independently establish absence of training exposure.

The agent writes tests with natural-language reasoning, filters syntactically invalid tests by attempting AST construction, and samples at most **six internal unit tests**. Syntax filtering does not validate expected answers or test coverage. A failed test supplies evidence for reflection and revision; memory keeps one reflection. The final submitted program is assessed on hidden benchmark tests.

| Benchmark | Base GPT-4 | Reflexion | Absolute change |
|---|---:|---:|---:|
| HumanEval Python | 80.1% | **91.0%** | +10.9 points |
| HumanEval Rust, hardest 50 | 60.0% | 68.0% | +8.0 points |
| MBPP Python | 80.1% | **77.1%** | −3.0 points |
| MBPP Rust | 70.9% | 75.4% | +4.5 points |
| LeetCode Hard Python, 40 | 7.5% | 15.0% | +7.5 points |

The paper calls these **pass@1** because one final program is submitted to hidden tests, and the internal optimization uses self-generated tests rather than hidden-test feedback. This is not one LLM call or one raw sample: the submitted program can result from multiple internal generations, tests, and repairs. Compare it with other systems at a matched total inference budget before interpreting the gain as intrinsic one-shot coding ability. The article does not provide a sufficiently complete programming attempt and cost specification to reconstruct every run from the prose alone.[^5]

## 6. Evaluator quality, component ablations, and negative results

False acceptance is particularly damaging: if an incorrect program passes all internal tests, the loop stops with a bad submission. False rejection can also waste effort or damage correct code, although the model may recognize a bad test and retain the program.

Table 2 labels outcomes TP/FN/FP/TN, but the pairs TP+FP and FN+TN sum to one. The prose defines the false-acceptance quantity as `P(hidden failure | internal tests pass)`, **not** the conventional `P(test accepts | program wrong)` false-positive rate. HumanEval Python's reported false acceptance is about **1.4%**, versus **16.3%** for MBPP Python; this is a plausible explanation for MBPP regression, not a randomized proof that this single factor causes the entire difference. The analysis text also mentions an 82% HumanEval baseline while Table 1 gives 80.1%; use the main table for headline comparisons.

On the 50-problem Rust subset, base accuracy is 60%; reflection without generated tests falls to **52%**; tests without the verbal reflection remain **60%**; the full method reaches **68%**. Without a test signal the system cannot reliably stop when correct and may make harmful revisions. The combination helps in this setting, but the sample does not establish that all debugging without verbal reflection is ineffective.

Two additional failures qualify the general claim. On **100 WebShop environments**, ReAct+Reflexion stalls near 35% versus 34% for ReAct across four trials. The authors attribute this to search requiring diverse exploration; this is a proposed explanation, not proof the entire task class is unsolvable by reflection. On HumanEval Python with **starchat-beta**, both baseline and Reflexion average 26% across eight trials, with reported standard deviations 0.00481 and 0.00305. Stronger-model results therefore do not automatically transfer to a smaller/weaker model.

The paper also notes limited memory, local optima, and difficulties testing nondeterministic or environment-dependent code. It lacks comprehensive equal-cost comparisons, broad cross-task transfer experiments, and repeated uncertainty estimates for most headline results. Appendix C repeats the Actor instruction under the Self-reflection heading and retains reflection text in omission templates, so the appendix alone is not a reliable literal implementation specification.[^6]

## 7. Everdict evolution proposal

Reflexion provides a minimal baseline for the [first-loop design](../evolution-first-loop.md): turn one failed candidate execution into a bounded, provenance-linked lesson before proposing another candidate. Keep the raw trajectory immutable. Store a lesson's observed facts, suspected cause, proposed behavioral change, scope, and evidence links separately enough to avoid promoting an eloquent guess into a verified fact.

Test three driver conditions under the same total model, execution, and evaluation budget: retries without memory, recent raw trajectory memory, and a concise reflection. Distinguish **repair on the same task**, transfer to a new task in the same family, and final confirmation on held-out families. Include failures where the evaluator is wrong and where exploration needs a different strategy, because the paper's MBPP and WebShop results identify different bottlenecks.

Generated tests can screen a candidate and help explain failure, but final confirmation must use the platform's fixed authority and frozen artifacts. Measure false acceptance and false rejection with explicit conditional definitions, harmful revisions to already correct candidates, repeated-failure rate, and new-family success per cost. Preserve the last known valid candidate when uncertain rather than making a retry loop overwrite it.

The first experiment should remain small: a one-to-three-entry reflection baseline before a complicated knowledge store. If it only improves repeated attempts on the same task, report that result accurately and do not call it reusable evolution. More durable skill packaging or curated memory can then be tested against this transparent baseline.
