# R42 — Anthropic Agent Skills: packaging, progressive disclosure, and an evolution interface

This is Anthropic's engineering article introducing Agent Skills, published October 16, 2025, with a December 18 note about an open standard. It is a design resource, not a controlled experimental paper. Its importance to WikiSkill and Everdict is the artifact boundary it popularizes: reusable instructions, references, and executable helpers can travel together as a folder. The detailed evaluation and evolution proposals below are our analysis, not reported experiments.[^1]

## What the source establishes

The article describes a skill directory with a `SKILL.md` entry point. Name and description are loaded first; the agent reads the body when relevant, then follows references to additional resources as needed. Its PDF example separates ordinary guidance from form-specific instructions and includes a script for extracting form fields. The purpose is to specialize a general agent without loading every manual in full.

The article recommends starting from observed capability gaps, testing representative tasks, examining activation and execution, and revising the skill using successful approaches and mistakes. It also discusses reviewing bundled code and external dependencies. These are authoring practices and architectural examples, not measured effect sizes.

The article contains no benchmark split, model-by-task matrix, repeated-trial uncertainty, controlled ablation of progressive disclosure, or quantified study of autonomous skill evolution. Product-support statements describe the article's historical context; this note is not a current compatibility matrix.

## The underlying principle: separate discovery from execution

A useful way to understand the design is to split the decision into stages. First, the agent must recognize that a capability may apply. Second, it must understand the procedure. Third, it must obtain detailed references or invoke code. The description supports the first decision; the main instructions support the second; additional files support the third.

These are distinct failure modes. A perfect procedure is useless if it is never discovered. A broad description can trigger the right folder for many tasks but burden unrelated tasks. A concise main file can still omit the condition that tells the agent when to read a necessary reference. An executable helper can be correct in isolation and still be called with the wrong file or assumptions.

Consequently, activation rate alone is not quality. An evolution method that makes every description broadly applicable may increase loading while reducing success. A method that hides all difficult details in references may reduce initial context while increasing missed prerequisites. The design creates an optimization problem over routing, explanation, and execution together.

## Progressive disclosure changes the cost structure

Consider N installed skills. If each contributes an average m metadata tokens, startup discovery costs approximately `N × m`, plus the host's base context. Loading selected instruction bodies and references adds their actual token lengths. This is a simple accounting model proposed here, not a measurement in the article.

Thus a large filesystem library can exceed the model's context capacity without every file being loaded at once, but discovery metadata, tool calls, and accumulated conversation still have costs. Filesystem storage being large does not imply infinite useful working context. At enough skills, metadata retrieval or routing may itself become necessary.

There is also an information tradeoff. A description that is too short may fail to distinguish two similar procedures. A body that repeats every reference defeats deferred loading. A deeply nested reference structure adds navigation burden. The relevant objective is verified task value per total cost, including failed discovery, not the shortest `SKILL.md` in isolation.

## Why executable helpers are a different kind of memory

An instruction describes an operation; a script implements one. A model can repeatedly generate a sorting procedure, or a tested function can execute it. The latter can reduce repeated generation and produce stable results for fixed inputs. But determinism depends on more than the presence of code: versions, locale, external services, random seeds, concurrency, and filesystem state can all matter.

For an Everdict spreadsheet task, a helper might list sheets and formula cells, while a reference explains how the workbook's required behavior should be preserved. The script's output is evidence about the workbook; the reference is guidance. Neither replaces checking the submitted artifact against the task contract.

Packaging them together makes reuse convenient but creates a versioning obligation. Changing a helper without changing the accompanying explanation can invalidate a previously tested procedure. A candidate must therefore pin the whole dependency closure that affects behavior, rather than only hashing the main Markdown file.

## Relationship to prompts, retrieval, tools, and later research

A system prompt can contain procedural knowledge, but a skill folder makes its resources modular and selectively accessible. Ordinary retrieval often returns factual evidence; a skill can specify a workflow and bundle code. These categories overlap: a retrieved procedure can function as a skill, and a skill can rely on factual retrieval.

A tool or MCP server provides operations and data access through a host-defined interface. A skill can explain when and how to use those operations. Merely installing instructional files does not create credentials, authorize a new external action, or prove that a required tool exists. Portability of files is distinct from portability of runtime behavior.

Later corpus and retrieval papers study which skill to load; skill-evolution papers study how to improve its contents; harness-evolution papers can alter the surrounding execution loop. This source supplies a common packaging idea. It does not settle which retrieval algorithm, update rule, or search archive is best.

For the surrounding reading sequence, [the practical skills guide](./R03.md) expands authoring practices, [SkillsBench](./R15.md) provides empirical task evidence, [skill retrieval augmentation](./R33.md) separates selection and usage, and [WikiSkill](./S00.md) introduces a particular evolution mechanism. Their experiments must retain their own conditions rather than being retroactively attributed to this article.

## What is missing for a persistent evolution system

A complete evolutionary loop needs an initial artifact, evidence collection, proposal generation, candidate construction, evaluation, selection, and durable lineage. The article motivates iterative authoring, but does not define this loop's statistical or authority boundaries.

For example, “capture what worked” leaves several questions unresolved. Did the task succeed because of the proposed procedure or because the model solved it independently? Was the successful trace faithful to the output? Does the advice transfer to another workbook family? Does changing discovery metadata cause unrelated tasks to load the skill? Can the procedure be rebuilt from the same evidence?

Those questions explain why a successful episode should create a **candidate**, not immediate evidence of a generally better skill. A library can grow while its useful coverage shrinks through duplication, contradictory instructions, or overbroad activation. Removal and supersession also need evidence, especially for rare but important capabilities.

## A concrete Everdict artifact proposal

A proposed candidate bundle should include the entry-point metadata, main procedure, referenced resources, executable helpers, dependency declarations, and an immutable manifest of their digests. Its provenance should identify the source tasks, observed failures or recoveries, and the parent artifact. This is an Everdict design proposal, not the article's standard schema.

The manifest should distinguish instructions from evidence and executable code. A reference can support a decision without being authorized to rewrite the user's task. A helper's runtime output should be captured as an observation rather than silently folded into unverified narrative. The driver can suggest updates; platform evaluation and campaign settlement retain their own authority.

The first implementation should reuse Everdict's declared candidate edits and frozen evidence boundaries rather than introduce a new campaign subject merely because the folder is called a skill. Whether runtime skill loading is worthwhile is a separate measurable candidate behavior.

## Evaluation design that separates the mechanisms

A practical experiment can compare no added skill, an always-loaded single document, and a folder with progressive disclosure while keeping substantive knowledge and the executor fixed. Measure verified completion, tokens, tool calls, latency, and omitted prerequisites. Include both relevant and irrelevant tasks so that a broad activation description cannot win by loading everywhere.

A separate test can compare instructions alone with the same instructions plus a deterministic helper. Charge helper construction and validation to evolution cost, then measure reuse over multiple tasks. Record runtime dependencies and test on changed inputs; a successful hardcoded script for one example is not a reusable capability.

Finally, compare a static folder with an evolved folder under equal search budgets and fresh task-family confirmation. Keep metadata-only edits separate from body, reference, and code edits in the analysis. This identifies whether the gain comes from discovery, knowledge, executable behavior, or a larger effective inference budget.

## Limits and the most useful evolution insight

The source's simplicity is an advantage for exchanging artifacts, but its format alone cannot guarantee reliable discovery, grounded advice, compatible dependencies, or generalization. Its strongest contribution to an evolution design is giving improvements a concrete object that can be inspected, versioned, evaluated, and reused.

For Everdict, the next step is to test that object across its full lifecycle: can the agent find it, apply it correctly, produce a verified result, and preserve those properties after revision? The answer must come from controlled evaluations, since this article supplies no quantitative evidence for those questions.
