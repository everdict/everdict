# R12 — LLM Wiki: persistent synthesis as an evolving artifact

Andrej Karpathy's LLM Wiki is an idea document for maintaining a personal knowledge base with an LLM. It proposes immutable raw sources, a model-maintained linked wiki, and a schema describing conventions. Its operations are ingesting sources, answering questions, and checking the wiki for problems. An index organizes content; a chronological log records activity. The document describes an adaptable pattern rather than a fixed implementation, controlled experiment, or benchmarked learning algorithm.[^1]

The remainder of this note develops an analytical reading of that pattern for Everdict. Examples, proposed data structures, evaluation designs, and implementation boundaries below are our interpretation, not additional experiments or mechanisms claimed by the gist.

## The problem: useful synthesis disappears into conversations

Suppose three execution reports reveal the same failure under different names. A later proposal benefits from the connection, not merely from locating one report containing the right keyword. If the connection exists only in a previous chat, the next proposer may have to reconstruct it. Persistent synthesis gives that connection a durable, revisable home.

This changes the artifact being optimized. A transcript is a record of what happened. A wiki page is an interpretation of what the records imply. A skill is a procedure that uses some of those implications. The three can support one another without being interchangeable. In Everdict, the research question is whether a maintained interpretation improves the next candidate enough to justify its maintenance cost and potential errors.

## Principle: separate evidence, interpretation, and maintenance rules

Consider a candidate that fails because a tool response omitted a required field. The raw evidence should retain the actual request, response, tool version, and outcome. A derived page may generalize that this tool version requires an explicit projection parameter. A maintenance rule may require every such generalization to link its supporting traces and record the affected version.

The separation matters when new evidence arrives. If a newer tool version restores the field by default, the correct update is a conditional claim, not erasing the earlier failure or asserting that the original agent was mistaken. Evidence remains historically true while the best current procedure changes. An evolving wiki can express both only if the source-to-claim relationship survives its edits.

A useful mental model is a maintained materialized view over evidence. The view saves repeated interpretation work, but it may be stale or incorrectly computed. Unlike a database query with a precise specification, LLM synthesis is probabilistic and interpretive. It therefore needs traceable support and a way to recover the underlying evidence, not merely a polished final paragraph.

## A concrete ingest example

Imagine an Everdict campaign with two failed candidates and one successful candidate. The first assumes that a filename is stable; the second adds a search step; the third checks the file format before choosing a parser. A useful ingest operation would create or revise a page about discovery and parsing assumptions, link all three candidate records, and explain what changed between them.

It should distinguish at least three statements: the first run failed, the later run succeeded, and format checking caused the improvement. The first two may be directly observed. The third is a causal inference that requires a suitable comparison; other changes or randomness could explain success. A good wiki preserves that difference instead of converting every successful change into a rule.

If the record lacks the actual file or a reproducible outcome, the page should retain the uncertainty. An LLM can propose an explanation for further testing, but the proposal should not quietly become confirmed knowledge. This is especially important when a later generator learns from the wiki and amplifies its phrasing.

## Querying should produce reusable answers with visible dependencies

A query such as “Why do our parsing candidates keep regressing?” may require synthesis across tools, file formats, and previous edits. An answer can identify recurring conditions and point to the relevant evidence. Saving that answer makes future work cheaper only if it remains connected to the conditions that justified it.

A proposed Everdict answer record could include the question, source record identifiers, the candidate/model/environment versions considered, a summary, and unresolved alternatives. This is an experiment-design suggestion, not a requirement to add a new platform entity. Existing records and an external derived file may be enough for the first loop.

The important invariant is that an answer being reused does not become an independent corroborating source. If five wiki pages repeat one unsupported claim, there are still zero independent confirmations. Track shared provenance to avoid counting repetition as evidence strength.

## Maintenance means resolving structure as well as wording

A maintenance pass can detect broken links, orphaned pages, contradictory statements, missing conditions, and claims invalidated by new versions. Some checks are deterministic, such as whether a referenced record exists. Others require interpretation, such as whether two statements actually conflict or apply to different environments.

For example, “always search for the file” and “use the supplied file path” may conflict, or they may apply to tasks with different input guarantees. A curator should first recover those guarantees before deleting one instruction. The useful output may be a branching rule with applicability conditions rather than a universal replacement.

A change log can explain that revision without serving as the knowledge itself. Content navigation answers what the system currently believes; chronological navigation answers how that belief developed. Everdict already has an evidence-history concern, so the experiment should compare a maintained projection against that history rather than replacing the history.

## Relationship to retrieval, memory, and WikiSkill

Query-time retrieval and maintained synthesis solve different parts of the information problem. Retrieval chooses material to inspect now. Synthesis precomputes an interpretation that may connect many records. A system can retrieve over synthesized pages and still inspect raw evidence when needed. It need not choose an absolute opposition between RAG and a wiki.

Episodic memory preserves experiences; procedural memory prescribes behavior. A wiki can contain factual, episodic, and procedural pages, but moving a statement from one category to another needs justification. An observed success is not yet a reusable procedure, and a reusable procedure is not an adoption decision.

WikiSkill makes the connection empirical by studying persistent knowledge used during skill evolution, with explicit executors, benchmarks, and ablations. The gist supplies the conceptual pattern; WikiSkill supplies one particular experimental realization. Evidence from that realization should be cited to S00, with its actual conditions, rather than attributed back to the idea document.[^2]

## What the source does and does not establish

The gist provides an organizing proposal and personal practice observations. It does not report a controlled comparison, confidence intervals, a measured maintenance cost, or a guarantee of factual consistency. There are no ablation results to summarize as if it were a research paper. Statements about convenient scale or low maintenance effort are experiential claims, not a universal operating envelope.[^1]

Several plausible failure modes remain open for experimentation: incorrect compression, lost qualifiers, contradictory updates, retrieval of obsolete pages, and excessive maintenance cost. A wiki may become more coherent in language while becoming less faithful to its sources. Human-readable structure makes inspection easier, but coherence and correctness are separate properties.

## An Everdict experiment that tests the actual hypothesis

Use three proposer conditions on the same campaign tasks and budget: access to the raw round ledger, a bounded static summary of that ledger, and a maintained wiki derived from it. Keep the executor and candidate evaluation unchanged. This isolates whether maintenance adds value beyond merely providing a shorter context.

Charge ingestion, retrieval, querying, and maintenance to the relevant cost accounting. Measure confirmed improvement per total cost, duplicate failed proposals, unsupported claims, contradiction-resolution accuracy, and time spent locating evidence. Blindly audit a sample of derived claims against their source records. Include later environment changes so the experiment tests revision and retirement rather than only initial accumulation.

Freeze train/select/confirm boundaries and disclosure rules before the campaign. A curator can reorganize allowed training/selection evidence, but it should not infer access to hidden confirmation outcomes or acquire adoption authority. Record which derived snapshot informed each candidate. The current first-loop proposal's advice key and digest can provide a minimal identity for that snapshot without turning the whole wiki into a new platform subsystem.

## Practical change priority

Start with one derived knowledge collection for the proposer, a small claim template, and a repeatable comparison against the existing ledger. Preserve exact source references and unresolved contradictions. Add search infrastructure only if navigation measurements show that the simple collection is insufficient. More pages or a richer graph are useful only insofar as they improve proposal quality and evidence recovery.

The evolution insight is that accumulated experience can become an editable intermediate artifact. Its edits need evaluation just as candidate edits do. Treating curation as a testable driver strategy lets Everdict investigate that benefit while keeping confirmed outcomes and adoption decisions independently grounded.
