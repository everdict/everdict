# R46 — Memento-Skills: executable memory and reflective updates

Memento-Skills turns external memory into folders containing instructions, prompts, and executable helpers. A frozen agent retrieves a folder, acts, diagnoses failures, and edits or creates skills for subsequent attempts. Its useful evolution distinction is **repair a particular procedure versus discover a different procedure**. This note covers arXiv **2603.18743v1**, its research and practitioner tracks, figures, and three appendices. It separates the paper's fictional teaching dialogue from experiments; the results have not been independently reproduced.[^1]

## 1. Problem and conceptual foundations

A deployed model with fixed weights cannot permanently learn merely because an old conversation existed. It can nevertheless change behavior if future requests retrieve better external instructions. Memento-Skills makes that memory active: a skill contains a declarative `SKILL.md`, prompts, and code that affects future execution. A trajectory archive remembers what happened; an executable skill encodes what to do.

The system has two adaptation mechanisms. During deployment, it changes external skills and tip memory while keeping the underlying LLM fixed. Separately, it **trains an embedding router**, based on Qwen3-Embedding-0.6B. “No parameter updates” should therefore be read as no updates to the underlying executing LLM during the reflective loop, not no training anywhere in the system.

Memento and Memento 2 provide the case-based memory and decision-process lineage. Text-only reflection methods such as [E01 Reflexion](E01.md) and [E02 Self-Refine](E02.md) improve instructions or answers; Memento-Skills can modify multiple files in a reusable package. [E03 Voyager](E03.md) also stores executable routines. [R45 SkillRouter](R45.md) isolates retrieval training much more extensively; Memento-Skills couples retrieval with a writable library. [R44 CoEvoSkills](R44.md) additionally evolves a surrogate verifier, whereas here a judge supplies feedback and a synthetic test checks proposed mutations.[^1]

## 2. The read–write loop in operational detail

The agent observes a task together with accumulated generic tips, retrieves a skill, and optionally creates one if retrieval misses. It executes the workflow and receives judgment on its answer. Successful executions update utility; failures also add a generic lesson and initiate a skill-level diagnosis.

A failure-attribution selector reads the execution trace and judge rationale to choose the **single skill most responsible**. A rewriter then edits files to add guardrails or alternative strategies while trying to preserve generality. This is a credit-assignment heuristic: selecting one culprit does not establish that only one skill, or any skill rather than the environment, caused failure.

Each skill starts with utility 0.5, later estimated as successes divided by successes plus failures. If utility falls below a threshold **and enough observations exist**, the system escalates from in-place repair to discovery: restructure the folder or synthesize a new skill. The minimum sample condition avoids treating one unlucky run as proof that the whole approach is unsuitable. The paper leaves threshold values and several operational budget settings unspecified in the presented algorithm.

A synthetic test task is generated, executed through the modified skill, and judged. Failed validation triggers rollback; the algorithm and architecture show that this gate can be disabled. This is an automatic proxy test, not necessarily a deterministic assertion suite, an independent held-out benchmark, or a complete regression check. The same current task can then be retried for up to K feedback rounds. Algorithmic judgment explicitly accepts a reference answer, `Judge(task, output, reference)`: benchmark learning is not ground-truth-free.

The implementation drawing separates context management, task planning and ReAct execution, tool dispatch, a skill gateway/store/executor, retrieval, and an evolution engine. Sparse BM25 and dense search can be fused with score-aware reciprocal-rank fusion and optionally reranked. These configurable paths should not all be assumed active in every reported comparison. A virtual Python environment and command policy appear in the architecture, but the paper explicitly leaves systematic execution-isolation evaluation for future work.[^2]

## 3. What the decision-process theory establishes

Let `s` be the environment state, `M` the current skill memory, `c` a retrieved skill, and `μ(c|s,M)` the router. The effective action policy is a mixture:

`π(a|s,M) = sum_c μ(c|s,M) × pLLM(a|s,c)`.

Even when `pLLM` has fixed parameters, changing the memory or retrieval probabilities changes the policy. Augmenting the state to `(s,M)` accounts for memory-dependent transitions. This recovers a Markov formulation **if that augmented state includes the information needed by the transition and write mechanisms**; merely naming a state Markovian does not remove hidden environment history.

The paper imports a Memento 2 theorem that KL-regularized soft policy iteration converges under bounded rewards and discount below one. Regularization discourages abrupt departure from a reference retrieval policy; soft improvement assigns probabilities rather than demanding an immediate deterministic winner. This is a result about the stipulated reflected decision process and policy-iteration procedure. The engineering loop's LLM diagnosis, approximate retrieval, synthetic tests, and arbitrary file edits are not shown to execute exact policy evaluation and improvement. Consequently, a proposed rewrite can regress; the theorem is not a guarantee that every accepted folder edit improves real task success.

A cited value-gap bound has the form `constant × [LLM error at memory coverage radius + retrieval error]`, with constant `2 Rmax / (1−γ)^2`. Intuitively, closer useful examples reduce the generalization demanded of the LLM, while better routing reduces selection mistakes. However, adding more skills can also increase confusable alternatives; declining coverage radius and retrieval error require substantive assumptions. A two-dimensional t-SNE cluster plot does not measure the original-space coverage radius or verify the bound. The paper's interpretation that diminishing gains show theoretical convergence is stronger than the empirical curves alone establish.[^3]

## 4. Router learning and its one-step RL interpretation

The authors collect roughly 8,000 skills and sample about 3,000 as seeds for synthetic routing goals. Collection retains repositories with more than 500 stars. Description whitespace is normalized and SHA-256 hashes remove identical normalized descriptions; the tie-break prefers more stars, newer update time, then lexicographically larger ID. This catches exact normalized duplicates, not arbitrary near-duplicate meanings. Optional name deduplication is a further heuristic, and popularity filtering may omit useful specialist packages.

A query generator sees the skill name and description, while a separate LLM judge can inspect the full file to filter generated pairs. Appendix C also includes a keywords input. Positive goals should call the skill; hard negatives share terminology but would not benefit from that skill. Prompts prohibit naming the skill and request English, concrete, sometimes noisy user phrasing. The supervision represents judged functional fit, rather than measured execution reward for every query–skill pair.

The loss sums positive query mass for each skill under a softmax, divided by all in-batch positive and negative queries. This **multi-positive InfoNCE** objective raises compatible pairs relative to competitors. The paper interprets routing as a one-step decision: state is query, action is skill, reward indicates suitability. At horizon one, ideal Q equals expected immediate reward; a softmax over scores maximizes a reward-minus-KL objective relative to a uniform prior.

That variational interpretation is useful, but a learned similarity score is not automatically a calibrated probability of successful execution. The displayed loss normalizes queries for each skill, while the policy expression normalizes skills for a query; the paper describes their connection as approximate policy fitting via in-batch normalization. It does not present an on-policy exploration experiment or demonstrate equality to long-horizon Q-learning. Training-set sizes beyond the approximate seed count, full hyperparameters, and the complete isolation protocol for the router test are insufficiently specified for exact reproduction.[^4]

## 5. Router experiments: selection improves more than execution

The offline evaluation uses **140 synthetic queries**, counting a hit when a labeled skill appears among the first K. Here Recall@K is an any-hit measure, unlike the fractional multi-label recall in R45.

| Router | Recall@1 | Recall@5 | Recall@10 | Real route hit | Real judge success |
|---|---:|---:|---:|---:|---:|
| BM25 | 32% | 47% | 53% | 29% | 50% |
| Base Qwen3 embedding | 54% | 79% | 86% | 53% | 79% |
| Memento-Qwen | **60%** | **82%** | **90%** | **58%** | **80%** |

The strongest-baseline top-one gain is six percentage points, approximately 11.1% relative using the rounded plotted numbers; the prose calls it 10%. End-to-end judge success improves by only **one point** over the dense baseline. The agent can sometimes solve tasks despite an imperfect route, explaining why task success can exceed route-hit rate. Conversely, a correct route need not solve the task.

The real-trajectory panel does not provide a clear sample count, repeated-run uncertainty, or significance test. Its 80% should not be confused with the GAIA or HLE accuracy reported below. The experiments support the usefulness of the tested routing adaptation, but not a precise general success gain or proof that synthetic functional labels are equivalent to behavioral utility.[^4]

## 6. Self-evolution experiments, transfer, and library growth

The executing LLM is named **Gemini-3.1-Flash** in this version. GAIA uses 165 validation questions, divided into 100 training and 65 test examples. HLE uses a sampled 1,130-question subset of the described 2,500-question benchmark: 788 training and 342 test, spanning eight subjects. These results are not full-benchmark leaderboard evaluations.

The main ablation keeps retrieval, execution, and feedback collection but disables failure attribution, rewriting, and discovery together. Thus it tests a package of changes, not the isolated value of any one component. Both settings are described as read–write loops; “static” here concerns skill-level optimization.

| Evaluation | Read–Write ablation | Full Memento-Skills | Reported difference |
|---|---:|---:|---:|
| GAIA test | 52.3% | 66.0% | +13.7 points |
| HLE test | 17.9% | 38.7% | +20.8 points |

GAIA training rises from 65.1% on the first attempt through 84.3 and 89.2 to 91.6% after three retries. The hardest training level rises from 45.5 to 72.7% on the first retry and then plateaus. Test figures show full-system Level 1/2/3 scores of 68.4/63.0/71.4%, versus 57.1/55.9/30.0%. The reported denominators and exact aggregation do not transparently reconstruct all these decimals from the stated 100/65 split; treat them as reported plotted values, not independently verified integer counts.

HLE training rises from 30.8% at R0 to 54.5% at R3. Final subject values range from Engineering 42.1% to Humanities 66.7%, with Biology 60.7%, Chemistry 62.4%, CS 46.5%, Math 51.2%, Other 57.0%, and Physics 47.4%. Test gains vary sharply: Biology 22.0→57.4%, Humanities 11.4→41.0%, Math 20.0→41.5%, while Engineering remains **21.7→21.7%**. The reported overall 38.7% is not the simple unweighted mean of the plotted subject percentages; weighting details should not be invented.

Starting with five atomic skills, the reported library totals become **41 for GAIA and 235 for HLE**. The paper says many GAIA-trained skills are never triggered on test because tasks differ, whereas HLE's subjects allow more within-domain reuse. This is a plausible transfer explanation, but benchmark difficulty, training-example count, library size, and domain organization all change together; there is no controlled intervention proving taxonomy alignment is the cause. The t-SNE figure visualizes skill embeddings, not observed success on all neighboring questions. Its eight legend counts sum to 271, while the two stated library totals sum to 276; that counting scope is not explained.

The version does not fully specify test-time retry and write permissions, exact baseline budget matching, evaluation-order sensitivity, repeated seeds, judge errors, mutation-gate pass rates, or total token/cost accounting. “Unseen test questions” is evidence of a split, but not enough to infer a fully frozen library and one-shot confirmation protocol. Training retry peaks must remain separate from test generalization.[^5]

## 7. Limitations and numbers that are not experiments

The paper interleaves fictional dialogue among a professor, student, and engineer. The opening 73% performance, later 73→84% in three days, and epilogue **93.5% accuracy / 195ms p99 latency / 8% ablation loss** belong to that narrative. They are not a documented third production benchmark and must not enter an evidence table. Likewise, joking claims that every rewrite is mathematically guaranteed to improve should not override the actual algorithm's approximate components and rollback path.

Further limits follow from the mechanism: single-skill attribution can misdiagnose interacting failures; utility changes with task difficulty and routing exposure; a synthetic judge can reward narrow patches; and expanding memory can produce duplication, contradictions, or stale code. The provided experiments do not quantify long-term retention, cross-domain interference, human oversight burden, or infrastructure safety. These are open questions, not observed failures claimed without evidence.

## 8. Everdict evolution proposal

Adopt the distinction between **repair, restructure, and discover** as driver-side proposal categories. A failure record should name candidate causes, the implicated skill/version, supporting trace locations, and an alternative explanation. Low utility should trigger investigation only after enough comparable exposures; stratify by task family so harder assignments do not automatically condemn a good skill.

Compare three arms at equal total execution and judge budgets: tip-only memory, targeted file repair, and repair plus utility-triggered discovery. Preserve every candidate as immutable bytes with parent and feedback provenance, even if the active skill name remains stable. Synthetic tests can screen a candidate cheaply; select on an authorized selection split, then confirm on separate families under a frozen library. Measure recurrence of the original failure, unrelated regressions, new-family success, actual skill reuse, and maintenance cost.

This fits the [first-loop proposal](../evolution-first-loop.md) if the driver owns diagnosis and proposal generation while the platform owns rebuild identity, evidence disclosure, and confirmation. The paper's in-place mutation should map to a new version in Everdict, not silent editing of already evaluated artifacts. A judge's rationale is advice with a source, not authority to redefine success. Prioritize this experiment after the split and artifact mechanisms exist; router training is a separate optional intervention rather than a prerequisite for testing skill-level reflection.
