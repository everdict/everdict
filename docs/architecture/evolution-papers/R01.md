# R01 — GEPA: reflective prompt evolution

GEPA searches for better prompts by combining language feedback with a population of candidates that succeed on different examples. It treats an execution trace and an evaluator's explanation as more informative than a scalar reward alone. Model weights remain fixed; the evolving object is the set of prompts inside a compound language-model program. The inspected source is arXiv 2507.19457v2, corresponding to the paper cited as a 2026 ICLR publication.[^1]

## Problem and prerequisite ideas

A compound system might retrieve documents, summarize evidence, and answer a question through separate model calls. When the final answer is wrong, changing every prompt indiscriminately wastes trials. GEPA uses the intermediate inputs, outputs, and evaluation feedback to propose an edit to one module. The reflection model performs an approximate, language-based assignment of responsibility; no mathematical derivative is available.

Reinforcement learning such as GRPO updates model parameters from groups of scored rollouts. Prompt optimizers instead update instructions or examples. GEPA asks whether richer diagnostic feedback can make prompt search competitive while consuming fewer executions. Its other prerequisite is Pareto dominance: candidate A dominates B if A is no worse on every measured objective and better on at least one. Here, individual task instances supply the objectives, preserving different ways of succeeding.[^1]

## State and optimization loop

GEPA maintains candidate programs, parent relationships, and a vector of per-instance scores for each candidate. Development data are separated into a feedback set, used to diagnose and mutate, and a Pareto/validation set, used to select candidates. Final reporting uses a separate test set.[^1]

1. Evaluate the initial program on the Pareto set.
2. Choose a parent using the instance-wise selection rule below, and choose a module to edit, cycling across modules.
3. Execute that parent on a small feedback minibatch. Collect the module's trace and numeric plus textual feedback, such as an unmet formatting constraint or missing document.
4. Ask the reflection model to revise that module's prompt; keep the rest of the program unchanged.
5. Re-evaluate the candidate on the same minibatch. A minibatch improvement allows entry into the candidate pool and a full Pareto-set evaluation.
6. Repeat until the rollout budget is exhausted. Return the candidate with the highest aggregate Pareto-set score.[^1]

For parent selection, find every candidate tied for best on each instance, take their union, and prune dominated candidates. Sample a remaining candidate with weight proportional to the number of instances on which it leads. This is more specific than retaining every mathematically non-dominated point: a candidate must enter through an instance-best set. It is also different from a beam that simply retains the highest average scores.

## An intuitive example and the merge operator

Consider three development questions. Candidate A scores [1, 1, 0], while B scores [0, 0, 1]. A has a higher mean, but B uniquely solves the third question. A greedy parent selector repeatedly develops A; GEPA can also develop B because it contributes a different success pattern. This numerical example is explanatory, not an experiment reported by the authors.

The optional merge operator combines modules from branches with a common ancestor. If only one branch changed a module, that version can be inherited; if both changed it differently, the pseudocode chooses the better-scoring branch's version. The accompanying prose describes complementary/disjoint prompt changes, while Algorithms 3–4 actually admit a pair with at least one complementary module and include conflict handling for others. Likewise, the code rejects an ancestor strictly better than either child, allowing equality even though the prose says both children improve. These details matter when implementing an exact reproduction.[^2]

Merge is invoked at most five times in the reported optimization runs. It creates a new candidate requiring evaluation; combining good parts is not proof that their interaction will be good.

## Experimental setup

The six tasks are HotpotQA, IFBench, HoVer, PUPA privacy-conscious delegation, AIME-2025, and LiveBench-Math. They cover multi-hop retrieval, constrained outputs, privacy/utility tradeoffs, and mathematics. Executors are Qwen3-8B and GPT-4.1-Mini dated 2025-04-14, with a 16,384-token context limit. The Qwen experiments use temperature 0.6; GPT-4.1-Mini uses 1.0.[^3]

| Task | Train / validation / test | Important protocol detail |
|---|---|---|
| HotpotQA | 150 / 300 / 300 | Retrieval feedback names missing relevant documents |
| IFBench | 150 / 300 / 294 | Test constraints are out of distribution relative to training |
| HoVer | 150 / 300 / 300 | Multi-hop retrieval measures relevant-document recovery |
| PUPA | 111 / 111 / 221 | Feedback separates response quality from privacy leakage |
| AIME | 45 / 45 / 30 questions × 5 runs | Train/validation use 2022–2024; test uses 2025 |
| LiveBench-Math | 368 questions split approximately into thirds | Snapshot retrieved 2025-07-30, shuffle seed 0 |

Controls include MIPROv2, TextGrad, Trace/OptoPrime, GRPO, and an unchanged baseline. GEPA uses minibatches of three. Prompt-optimizer rollout budgets are matched to MIPROv2's expenditure with reported discrepancies up to 10.15%. GRPO's compound-system configuration uses LoRA and 24,000 rollouts. Thus sample efficiency is measured in executions, not an exact equality of dollars, GPU hours, or reflection tokens.[^3]

## Results and component tests

| Six-task aggregate | Baseline | GRPO | MIPROv2 | GEPA | GEPA + merge |
|---|---:|---:|---:|---:|---:|
| Qwen3-8B | 45.23 | 48.91 | 47.84 | 54.85 | 52.40 |
| GPT-4.1-Mini | 53.03 | — | 58.67 | 65.22 | 66.36 |

These are the paper's aggregates of different task metrics, not a universal accuracy scale. On Qwen, GEPA exceeds GRPO by 5.94 aggregate points, but GRPO is better on AIME: 38.00 versus 32.00. The headline sample-efficiency example is IFBench: GEPA reaches 38.61 after 678 rollouts, compared with GRPO's 35.88 after 24,000. The table's total GEPA IFBench budget is larger, 3,593; 678 is the point where that best prompt was found.[^4]

Holding the evolution harness fixed across four Qwen tasks, greedy parent selection achieves 54.89, beam search 53.95, and GEPA selection 61.28, against a 48.84 baseline. This is more direct evidence for the selection mechanism than the full-system comparison. Merge helps the GPT aggregate but hurts the Qwen aggregate, including a Qwen IFBench decline from 38.61 to 28.23. Prompts evolved using Qwen transfer to GPT-4.1-Mini with a 62.03 aggregate, versus its 53.03 baseline.[^4]

The paper also explores inference-time kernel search and adversarial robustness. For NPU kernels, GEPA with GPT-4o reaches mean vector utilization 30.52 versus 4.25 for a ten-step sequential refinement baseline. For 35 CUDA tasks, the fraction beating PyTorch eager exceeds 20%. These experiments deliberately optimize the tasks being solved, so they measure search-time solution discovery, not held-out task generalization. An evolved distracting instruction reduces GPT-5-Mini's AIME-2025 pass@1 from 76% to 10%; inspection attributes much of the failure to literal placeholder formatting, which is narrower than proving mathematical reasoning disappeared.[^5]

## Research connections and limitations

TextGrad and Trace share textual credit assignment; MIPROv2 searches instructions and demonstrations; GRPO changes weights. MAP-Elites motivates retaining behaviorally different winners, although GEPA uses task-instance score vectors rather than a predefined behavior grid. WikiSkill subsequently adds an explicitly curated knowledge layer, while GEPA accumulates much of its learning in evolved prompts, traces, and ancestry.[^1]

The method depends on meaningful diagnostic feedback, a representative development set, and an executor capable of following evolved instructions. Per-instance winners can specialize to noisy examples. Small minibatches can admit changes that fail more broadly, and repeated validation selection can overfit. A reflective explanation proposes a reason for failure but does not identify causality by itself. Additional reflection calls and longer prompts also have costs beyond the reported rollout count.

## Everdict changes and a discriminating experiment

Everdict can make parent selection an interchangeable driver policy over immutable candidate records. Compare greedy best, top-k beam, and GEPA-style instance winners under identical candidate-evaluation and reflection budgets. Retain per-case results, candidate ancestry, exact editable module identity, and evaluator feedback with its permitted disclosure tier. Use development feedback for mutations and a separate final confirmation for any adoption claim.

Measure confirmed task utility, diversity of solved-case sets, repeated unsuccessful mutations, and total search cost. Introduce merge only as a separately ablated operator with explicit parent versions and conflict rules. A gain from selection would support a development archive; it would not justify making the archive's highest development score an adoption verdict. This is an Everdict proposal derived from the paper's mechanisms.
