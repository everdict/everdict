# R22 — Terminal-Bench: final-state evaluation, task audits, and failure evidence

Terminal-Bench defines interactive computer tasks by a container, instruction, time limit, reference solution, and tests of the final state. Terminal-Bench 2.0 supplies 89 difficult tasks and a substantial task-audit process. Its research contribution is evaluation infrastructure and empirical diagnosis, not a method that evolves agents. For Everdict, the central lesson is that useful evolution depends on a trustworthy, versioned outcome check and interpretable failure evidence. This note follows arXiv 2601.11868v1; the reported model ranking is historical.[^1]

## What the benchmark measures

A terminal agent can install software, edit code, recover files, run experiments, and inspect intermediate results. Its outputs are changes to a computer environment. Terminal-Bench tests whether the final container satisfies the instruction, rather than scoring the command sequence or accepting a confident final message as proof of completion.[^2]

This permits multiple valid solution paths. A COBOL-to-Python migration is checked for equivalent input-output behavior; an asynchronous job runner must handle interruption and cleanup; a scientific sampler must satisfy distributional and interface requirements. Other tasks cover system configuration, machine learning, file recovery, games, security, and media. Software engineering is the largest category, but not a majority of the dataset.

Compared with HumanEval and code-only benchmarks, these tasks require environment interaction and longer dependencies between actions. Compared with SWE-bench, the scope extends beyond repository issue repair. Compared with web/desktop benchmarks, the terminal is the main flexible interface. However, the framework does not require every agent to use only shell commands: product agents may have dedicated tools that manipulate the same container.

Outcome-based evaluation does not mean that method constraints disappear. If an instruction requires a particular source of truth or preservation property, the checker must account for it through observable evidence. A final file with plausible contents can still be wrong if its data were guessed rather than recovered from the specified source.

## Dataset construction and the three validity criteria

Ninety-three contributors submit 229 tasks, from which the authors select 89 using difficulty and quality review. Each accepted task receives three experienced human reviews, totaling about three reviewer-hours per task on average, in addition to authoring effort.[^2]

Specificity means the instructions describe the acceptable final states and the tests accept those states. Solvability means a reference workflow can pass the tests. Integrity means an agent cannot exploit a benchmark-only shortcut, such as reading future commits from a repository history. These are evaluation targets, not properties guaranteed merely by storing files in Docker.

The reference solution is a human-written sequence that derives the result, not a script that simply prints a hidden answer. Running it demonstrates at least one successful path. A no-op agent must fail. Neither check alone establishes that every valid alternative passes or that every invalid shortcut fails; that is why the process also uses human and adversarial review.

Task authors estimate expert and junior-engineer completion times. The table's counts sum to 74 rather than 89: experts are estimated below one hour for 36 tasks, between one hour and a day for 35, and between a day and a week for three. These are author estimates on the displayed population, not a timed human performance study or a complete 89-task cost measurement.

## Quality-control pipeline and its limits

Deterministic checks run the reference and dummy agents, inspect required fields, and prevent tests or oracle solutions from being copied into the agent's starting image. Contributors also check instruction/test coverage in both directions, explicit filenames and schemas, dependencies, and potential shortcuts. LLM-assisted tools examine ambiguous requirements and failures before human review.[^3]

A debugging tool compares failed trajectories with the instruction. If tests require an undocumented function name, exact schema, or supposedly optional example, the task may be underspecified. Repeated failures on the same check can motivate an audit, but are not conclusive evidence of a bad task: a real capability deficit can also be systematic. Human inspection remains necessary to resolve that ambiguity.

An adversarial agent attempts to pass by exploiting likely test weaknesses without seeing the tests or oracle. Discovered examples include altering the test environment, guessing results, or outputting many possibilities when a checker verifies the presence of a correct answer but ignores wrong extras. Authors inspect its trajectories whether or not the attempt passes. This tests the integrity of the evaluator, a different role from optimizing ordinary task performance.

Dependency pinning has an explicit exception: the checks require Python dependencies to be pinned but discourage pinning apt package versions that may disappear from repositories. Thus the paper's general reproducibility language should not be interpreted as every transitive package being fixed forever. Prebuilt image identity, runtime resources, and any network downloads remain part of the effective environment.

The Agentic Benchmark Checklist assessment averages 0.896, with 0.857 outcome validity, 1.000 task validity, and 0.830 reporting. The accompanying discussion acknowledges missing objective test-coverage metrics, residual nondeterminism, no private held-out set, and no quantitative estimate of how remaining task flaws affect scores. This is a structured assessment with developer involvement, not an independent proof of perfect tests.

## Harbor, Terminus 2, and agent identity

Harbor provides the task schema, registry, sandbox integrations, and execution harness. The experiments use Daytona with 32–100 containers in parallel. Terminus 2 is a deliberately simple comparison agent: a model emits keystrokes into a tmux shell and receives terminal output. It can use interactive programs and additional shells, and it summarizes context with model calls when the context window fills.[^4]

“Minimal” therefore does not mean behavior-free. Shell persistence, output capture, waiting, summarization, and stopping decisions all influence success. Claude Code, Codex CLI, Gemini CLI, OpenHands, and Mini-SWE-Agent expose different interfaces and may be tuned for particular models. A model name alone is not a complete candidate identity.

The paper reports at least five benchmark repetitions for supported pairs and 32,155 task attempts overall. It says sixteen frontier models in the setup, but Appendix A's table actually lists 21 distinct model names across 55 agent/model combinations. This mismatch should be preserved as a reporting inconsistency rather than silently treating sixteen as the full table's size. Provider defaults are used for configurable reasoning effort, with first-party APIs for proprietary models and Together.AI for open-weight models.

## Main resolution results and harness interactions

The principal statistic is the average fraction of resolved tasks across attempts, with 95% confidence intervals. It is not a best-of-five success rate. The following are selected rows from the detailed table.[^5]

| Model and agent | Resolution rate |
|---|---:|
| GPT-5.2 / Codex CLI | 62.9% ± 3.0% |
| Claude Opus 4.5 / Terminus 2 | 57.8% ± 2.5% |
| Gemini 3 Pro / Terminus 2 | 56.9% ± 2.5% |
| GPT-5.2 / Terminus 2 | 54.0% ± 2.9% |
| Claude Opus 4.5 / Claude Code | 52.1% ± 2.5% |
| Gemini 3 Flash / Terminus 2 | 51.7% ± 3.1% |
| Kimi K2 Thinking / Terminus 2 | 35.7% ± 2.8% |
| Qwen 3 Coder 480B / Terminus 2 | 23.9% ± 2.8% |
| GPT-OSS-20B / Terminus 2 | 3.1% ± 1.5% |

The main figure chooses each model's best tested scaffold. It describes the strongest observed pairing, not an isolated causal model comparison. GPT-5.2 gains 8.9 points with Codex CLI versus Terminus 2, while Opus 4.5 does better with Terminus 2 than Claude Code. The model/harness interaction is visible and a universal best scaffold is not established.

The paper compares GPT-5.2/Codex 62.9 with GPT-5-Nano/Codex 11.5, and Gemini 2.5 Pro/Terminus 32.6 with the same model/OpenHands 15.7. These are approximately 51.4 and 16.9 percentage-point gaps. Reading the prose's rounded “52%” and “17%” as relative percentage improvements would be incorrect. The observation that the tested model change is larger does not prove that model choice always matters more than harness engineering.

Task-level matrices show persistent unsolved tasks, timeouts, and token usage, as well as tasks that become solvable with stronger models. This is useful for selecting diagnostic task families, but repeatedly optimizing against those public failures turns the benchmark into training/selection data for that optimizer.

## Cost, time, and longitudinal analyses

The paper plots a cost/performance frontier and reports benchmark runs costing roughly one to one hundred dollars under its model prices and accounting. Most attempts finish within twenty minutes and fewer than 25 model calls; extreme attempts last about two hours, make hundreds of calls, and approach 100 million total tokens.[^6]

Appendix A's token table explicitly says its counts cover 74 tasks, despite the main benchmark containing 89. Do not use those counts to reconstruct a precise full-89-task price without resolving the run configuration. Input-token totals also depend on repeated context and caching conventions. A low marginal API price does not include evaluator infrastructure, failed setup, or future maintenance by default.

Across models, average turn count has correlation −0.028 with success (p=0.916), and output-token count −0.170 (p=0.515). These observational comparisons show that verbose models are not necessarily successful. They do not show that increasing a fixed model's allowed compute cannot help: that requires a budget intervention within the same model/harness. The appendix discusses some older model names not present in the final result table, another reason to avoid merging all panels into one fully aligned dataset.

A release-date plot shows strong progress over approximately eight months, nearly doubling the best score from Gemini 2.5 Pro to GPT-5.2. Release date, model capability, harness, and provider configuration move together. The prediction that the benchmark may saturate is a forecast from the paper, not evidence of current saturation or a fixed future trajectory.

## Human-estimated versus empirical difficulty

Empirical difficulty is defined using Terminus 2 outcomes across the chosen frontier models: easy at least 66.7%, medium between 33.3% and 66.7%, and hard below 33.3%. It is relative to the evaluated model population, not an intrinsic permanent task property.[^7]

The correlation with author difficulty is 0.436 (p<0.001). Of tasks labeled hard by humans, 93.3% are empirically hard. Of human-medium tasks, 54.5% are empirically hard, 29.1% medium, and 16.4% easy. Tasks involving creative strategies or unfamiliar operational details can be harder for agents than their human labels suggest.

For evolution, this motivates retaining both domain labels and empirical response profiles. A candidate may improve common procedural tasks while leaving scientific or adversarial reasoning untouched. Reassigning difficulty after each generation without preserving the original definition would make trend comparisons misleading.

## Trajectory-level failure analysis

The authors sample two failed Terminus 2 attempts per task/model where available and adapt the MAST taxonomy into execution, coherence, and verification categories. Docent helps summarize/search traces; two human annotators refine labels. On twenty calibration trials, reported Cohen's kappa is 0.93. A GPT-5 high-reasoning judge agrees with 120 human-labeled traces at 90%, with 92% precision and 90% recall.[^8]

The detailed labels cover disobeying explicit specifications, repeating ineffective steps, continuing past a justified stopping point, mismatch between stated claims and actions, losing context, drifting from the task, stopping prematurely, skipping substantive verification, and relying on weak verification. These labels can overlap: guessing data and checking only that the output file exists can violate both the source requirement and the verification requirement.

The paper finds execution failures prominent for the examined strong proprietary models, with a more balanced mixture for Qwen Coder. Percentages are conditioned on sampled failures and the judge's taxonomy, not the probability that every future run will fail for that reason. Judge agreement gives useful validation, but does not turn its root-cause explanations into causal facts.

A recovered-data example illustrates the distinction: inability to fetch an authoritative source is followed by writing a guessed answer and confirming that the file contains it. The final `cat` checks persistence, not truth. Another example distinguishes a plan to preserve simulation behavior from actual edits and observed checks. Everdict can use these categories to organize evidence while retaining links to the concrete trace that supports each label.

## Command-level failure analysis

A separate study judges individual terminal input/output pairs. GPT-5 medium detects whether an output shows a command failure, reaching 92.4% agreement against majority labels from three annotators on 66 pairs. GPT-5 high then assigns failure categories, with 82.0% agreement on fifty author annotations. These are different judges/tasks and validation sets from the trajectory analysis.[^9]

Observed command-error rates range from 9.2% for Grok 4 to 26.7% for GPT-OSS-120B. Across 3,800 uniformly sampled failures, missing executables or PATH resolution account for 24.1%, followed by application execution failures at 9.6%. These percentages describe command failures, not shares of all unsuccessful benchmark tasks.

The taxonomy covers invocation/CLI syntax, filesystem permissions, environment configuration, builds and toolchains, package repositories, network access, runtime/resources, interpreter errors, services/platform assumptions, data formats, and testing. It distinguishes, for example, a missing binary from a missing input file, an unavailable package from an authentication error, and an assertion failure from test-collection failure. That granularity can guide a concrete repair.

However, a failed diagnostic command may be expected and useful. A deliberate negative test or a probe for an optional program should not automatically count as bad reasoning. The next action and final task outcome determine whether the failure was recovered productively. Minimizing all nonzero commands can discourage useful exploration.

## Adapters and semantic preservation

The framework reports 26 adapters covering repository repair, programming, scientific reproduction, interactive environments, code performance, ML engineering, and security. An adapter supplies a natural-language task, container, programmatic evaluator, and optionally a reference solution. Its development protocol calls for parity experiments: run the same agents/models in native and adapted forms over repeated trials.[^10]

This is more than a file-format conversion. Mounts, available tools, timeouts, reset behavior, and what the verifier observes can change the task. The paper describes a parity requirement, but does not provide a complete numerical parity table for every adapter in this section. A successful general framework does not eliminate the need to validate each imported benchmark's semantics.

## Everdict evolution proposal

Everdict already has a Terminal-Bench importer; the research implication is to preserve and test its semantic boundary when using imported tasks for evolution. Record task/source version, image digest, resource limits, model settings, harness bytes, verifier bytes, and disclosure policy. An adapter change that alters observation or grading should create a new evaluation identity, not silently reuse old evidence.

For the documented first evolution loop, use train traces for diagnosis, separate selection tasks for comparing immutable candidates, and held-out confirmation under a fixed family budget. Public Terminal-Bench tasks repeatedly inspected during optimization cannot themselves supply untouched confirmation. The platform owns authoritative completion and evidence identity; the driver may curate failure reports and propose prompt/tool/helper changes.

A concrete first experiment could compare a seed with a helper that checks environment prerequisites and a helper that checks the actual final artifact. Include a matched extra-retry baseline and preserve all budgets. Report task success, regression by family, timeout rate, useful versus wasteful failed commands, and complete cost. Audit whether a newly successful candidate solves the stated task or exploits the checker. This is a proposal, not a claim that those candidate changes have been implemented.

## Limits and reading route

Network access, public oracle material, provider drift, hardware variability, and imperfect tests limit reproducibility. A canary string assists cooperative decontamination but cannot prevent intentional training or benchmark lookup. The study reports not observing oracle lookup in its trajectories; that is different from making lookup impossible.

Read the task definition and audit pipeline before the rankings, then the detailed table and both error taxonomies. The unresolved 16-versus-21 model count and 74-versus-89 cost scope should remain visible in any numerical reuse.
