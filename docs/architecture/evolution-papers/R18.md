# R18 — How Well Do Agentic Skills Work in the Wild?

This study separates three problems often collapsed into “skills help agents”: finding relevant skills, deciding to read them, and benefiting from their content. It then tests whether rewriting retrieved skills before execution repairs the gap between curated benchmark skills and public repositories. The answer is conditional: retrieval helps, distracting choices hurt, and task-specific refinement can help substantially, but increased skill loading is not sufficient for increased task success. This note follows arXiv 2604.04323v1.[^1]

## Research question and surrounding work

A curated-skills benchmark places an unusually helpful package beside the task. Production agents instead face a large, heterogeneous catalog, ambiguous descriptions, overlapping instructions, and skills that assume unavailable dependencies. Performance with the right package forcibly loaded is therefore a different estimand from performance with autonomous discovery and selection.

The paper relates reusable agent skills to executable libraries such as Voyager, retrieval and memory systems, and skill generation/evolution methods. Its distinct emphasis is the deployment pipeline connecting these components. A skill optimizer may produce excellent content without solving retrieval; a retriever may rank a package highly without establishing that it applies to the current environment. Query-specific refinement also resembles test-time adaptation: it spends additional reasoning on the actual target task before solving it, rather than demonstrating a universally improved library.[^2]

## Corpus, representations, and search

The authors collect 34,198 public skill folders from skillhub.club and skills.sh, retrieving their original GitHub content. They retain MIT/Apache-2.0 material, remove entries without names/descriptions, and deduplicate content. The resulting pool is a selected public corpus, not a census of all skills or an independently audited set of correct procedures.[^3]

Each skill has a name/description representation and a full SKILL.md representation. Sparse retrieval uses SQLite FTS5/BM25: field weights are 10 for name and 5 for description, with full-content weight 5 when included. Dense retrieval uses Qwen3-Embedding-4B and cosine similarity. Hybrid retrieval combines ranks with reciprocal rank fusion: each method contributes its weight divided by 60 plus the item's rank. This avoids directly comparing BM25 and embedding score scales.

For content-aware dense retrieval, metadata similarity receives weight 0.95 and content similarity 0.05. These settings are selected using synthetic queries derived from task instructions and Recall@5 against curated skills. Consequently, the search configuration is informed by the benchmark's target skills; it is not an entirely untouched retrieval test.

The agentic retriever receives a finding-skills procedure and search/detail endpoints. It decomposes the task, issues or revises keyword/semantic/hybrid queries, inspects descriptions or full content, and selects ten skills; downstream evaluations use the top five. The workflow also allows GitHub stars to break relevance ties. Popularity is a selection heuristic, not evidence of execution quality.

## Retrieval experiment: finding a reference is only the first stage

The retrieval experiment uses Claude Opus 4.6 in Claude Code, includes curated reference skills in the searchable pool, and measures average recall of those references.[^4]

| Retrieval method | Recall@3 | Recall@5 | Recall@10 |
|---|---:|---:|---:|
| Direct semantic | 38.1% | 47.0% | 52.3% |
| Agentic keyword | 24.1% | 26.6% | 27.5% |
| Agentic semantic | 56.8% | 63.1% | 66.5% |
| Agentic hybrid, metadata | 57.7% | 63.5% | 66.7% |
| Agentic hybrid, with content | 57.3% | 65.5% | 68.3% |

Agentic query formulation helps semantic retrieval, while keyword-only interaction performs poorly. Including content improves recall at five and ten, but slightly reduces it at three. The data therefore support a modest configuration-dependent gain, not a universal advantage for indexing more text. Recall also assumes the reference package is desirable: missing it does not prove every returned alternative is useless, and finding it does not prove the solver will read it.

## Execution protocol and the curated-to-public gap

The execution study uses 84 SkillsBench tasks, excluding three specified tasks, and all 89 Terminal-Bench 2 tasks, with three runs per condition. The executors are Claude Opus 4.6/Claude Code v2.1.19, Kimi K2.5/Terminus 2, and Qwen3.5-397B-A17B-FP8/Qwen Code v0.12.3. The open models run through local SGLang; Kimi's maximum input length is 253,952. Harbor supplies Docker environments. SkillsBench timeouts are multiplied by 1.5 for every model; Terminal-Bench uses 2× for Kimi/Qwen and 1× for Claude. Cross-model outcomes thus include different harness and timeout conditions.[^5]

The paper progressively changes access: force all curated skills to load; allow autonomous loading of curated skills; add distractors to make five candidates; retrieve five from a pool containing the curated skills; retrieve from a pool without them; and remove skills entirely. This helps localize deployment losses.

For Claude, success falls from 55.4% with forced curated loading to 51.2% with autonomous curated loading, 43.5% with distractors, 40.1% with retrieval including curated skills, and 38.4% without curated skills. The no-skill baseline is 35.4%. The stages are not uniformly monotone for every model: Qwen changes from 41.2% forced to 31.6% autonomous and then 33.7% with distractors; Kimi scores 38.5% forced versus 38.9% autonomous. “Forced loading” is therefore an informative reference condition, not a mathematical upper bound.

Claude loads every curated skill in 49% of autonomous-curated runs, falling to 31% with distractors. Its rate of loading any skill falls from about 62% with curated access to 44% with retrieval and 16% when curated skills are absent. Kimi loads skills more frequently but does not achieve Claude's success rate. Discovery, loading, and effective application need separate measurements.

## Two refinement algorithms and their information boundaries

Query-agnostic refinement edits one retrieved skill at a time without the target query or the other retrieved skills. In an Ubuntu 24.04 environment, the refiner uses a skill-creation procedure, generates synthetic test queries, compares attempts with and without the skill, judges the outcomes, and revises metadata/content. Although the main text describes iterative improvement, Appendix C specifies one refinement iteration in the experiments. For cost reasons, only skills actually retrieved are refined, not the entire 34,198-item collection.[^6]

Query-specific refinement receives the real task, its environment/data/tools, and all retrieved skills. It explores a possible solution, identifies useful instructions, merges or repairs them, and emits task-tailored skills. Evaluation feedback is self-judged rather than obtained from the ground-truth task verifier. This avoids direct verifier-answer access, but still spends additional target-specific exploration. It should be compared with an equally funded exploratory attempt without skill rewriting; the study does not isolate rewriting from every benefit of that extra computation.

The query-agnostic cost could in principle be amortized across future tasks. The query-specific cost recurs with each query, and its output is not automatically a reusable cross-task improvement. Environment-state isolation, preparation tokens, and final solver tokens should be recorded separately in a reproduction rather than assuming all preparation is free or that every artifact is reset.

## Refinement results and the counterexamples

The following entries are pass rates; loading rates are a separate diagnostic.[^7]

| Benchmark/skill pool | Condition | Claude | Kimi | Qwen |
|---|---|---:|---:|---:|
| SkillsBench | No skills | 35.4% | 21.8% | 20.5% |
| SkillsBench, curated included | Retrieved | 40.1% | 33.5% | 26.7% |
| Same | Query-specific | 48.2% | 26.7% | 30.8% |
| Same | Query-agnostic | 42.0% | — | 26.2% |
| SkillsBench, curated absent | Retrieved | 38.4% | 19.8% | 19.7% |
| Same | Query-specific | 37.9% | 23.1% | 21.5% |
| Same | Query-agnostic | 37.4% | — | 24.6% |
| Terminal-Bench 2 | No skills | 57.7% | 46.6% | 44.7% |
| Same | Retrieved | 61.4% | 50.6% | 44.2% |
| Same | Query-specific | 65.5% | 56.2% | 49.1% |
| Same | Query-agnostic | 63.3% | — | 44.9% |

Query-specific refinement improves seven of nine model/pool cells. The two exceptions matter: Claude without curated skills declines slightly, and Kimi with curated skills falls 6.8 points even as loading rises from 69.7% to 95.2%. More explicit, more frequently consumed instructions can still mislead an executor. Query-agnostic refinement is mixed and is omitted for Kimi because the implementation requires subagents unavailable in its harness; the missing cells are not zero gains.

On Terminal-Bench, query-specific refinement improves all three executors over both retrieved-only and no-skill conditions. These are promising end-to-end results under the given preparation protocol. Three repeats do not by themselves establish the statistical significance of every small difference or robustness to a different corpus snapshot.

## Coverage analysis and a worked mechanism

GPT-5.4 judges how well the retrieved package covers each task on a five-point scale, reading SKILL.md and helper files with large truncation limits. Mean coverage with curated skills is approximately 3.83–4.01 across models, compared with 3.31–3.49 without them; Terminal-Bench is 3.96–4.08. Higher coverage accompanies larger refinement gains. This is correlational, judge-dependent evidence: coverage can covary with task difficulty, and generated judgments are not a proof that the library contains every missing concept.[^8]

A tensor-parallel example combines guidance on weight sharding and custom autograd functions into instructions for differentiable distributed collectives. The distinction matters because a single-process implementation can appear correct while gradients fail when world size exceeds one. Refinement helps when the necessary pieces exist but need integration. The case illustrates a mechanism; it does not establish that rewriting can always recover missing technical knowledge or that all generated integrations are correct.

## Everdict evolution implications and proposed experiment

Everdict should measure retrieval relevance, actual loading, and verified task outcomes separately. A mutable wiki can improve navigation while a candidate skill improves execution; those are different interventions. Preserve the original source bytes, retrieval query/ranking, selected package hashes, preparation trace, and final skill hash so a gain can be attributed to the actual supplied material.

A useful experiment has four arms: retrieved skills unchanged; query-agnostic refinement frozen before evaluation; query-specific refinement; and a preparation-budget-matched exploratory attempt that writes no skill. Keep executor, task environment, total budget, and final verifier fixed. Include curated-present and curated-absent task groups to distinguish integration from missing coverage. Report pass rate, load rate, regression cases, preparation cost, and amortized cost over repeated use.

These are proposals for Everdict's documented first evolution loop, not claims of shipped functionality. Train tasks may supply refinement feedback; selection compares immutable candidates; confirmation uses held-out tasks under a fixed family budget. Target-specific preparation during confirmation must be a declared part of the candidate procedure, with its cost charged, rather than an unrecorded opportunity to change the candidate after seeing results. Self-judged coverage or successful loading can guide the driver, but neither can authorize adoption.

## Evidence limits and reading route

This is a controlled study of selected public skills and three particular executor/harness pairs, not a guarantee about every skill ecosystem. Corpus licensing/filtering, synthetic retrieval tuning, model-specific infrastructure, self-judged refinement, and extra preparation budget all affect interpretation. The most reusable result is the decomposition of the pipeline and its failure cases.
