# R19 — AutoHarness: synthesizing action checks and executable policies

AutoHarness turns a model's ability to write code into a way to improve its actions. A frozen LLM proposes and refines Python harnesses using execution feedback; the resulting code checks actions, generates candidates, or replaces the runtime LLM with a policy. The experiments show that eliminating invalid actions can make a smaller model competitive with a larger one, and that some single-player strategies can be compiled into inexpensive code. They do not show that legality guarantees strategic quality or that generated checks are universally correct. This note follows arXiv 2603.03329v1.[^1]

## Problem, prerequisites, and related research

An action can fail at two distinct levels. It may violate a rule, such as moving a chess piece through another piece, or be legal but strategically poor. Natural-language knowledge of a rule does not ensure that a model applies it to the current board. A harness can address the first failure with executable state-dependent checks, while leaving strategic ranking to the model.

This is the action-applicability problem from planning. Compared with prompting or tree-of-thought reasoning over an internal world model, AutoHarness moves some reasoning into a program checked against the environment. It is related to Code as Policies, Voyager's reusable programs, Eureka's reward-code search, Reflexion's failure feedback, and AlphaEvolve's program evolution. Its particular combination is multiple code hypotheses, environment critiques, and Thompson-sampling-guided refinement of an online, multi-turn agent interface.[^2]

The learning occurs in external code, not foundation-model weights. A “critic” here summarizes execution errors; it is not the ultimate authority on game legality. The game environment provides that authority during training and evaluation. This separation is essential: a generated checker agreeing with its own generated action is not sufficient evidence of correctness.

## Three harness forms

The method exposes two Python functions: `propose_action(board)` and `is_legal_action(board, action)`. The board is a textual observation, so parsing is part of the learned program. A malformed parser can invalidate otherwise correct chess or puzzle logic.[^3]

An action filter proposes legal candidates in code and lets the LLM rank them. An action verifier lets the LLM propose first, then checks the proposal and requests another answer with an illegal-action warning if necessary. This acts like rejection sampling: the output distribution is restricted by the learned acceptance predicate, although a wrong predicate can either admit bad actions or reject good ones.

A harness-as-policy makes the choice itself. In the reported policy experiment, it uses Python and ordinary libraries such as NumPy without runtime LLM calls. The change is substantial: optimizing legality alone seeks any allowable action; optimizing a policy must also learn which legal actions produce reward. The study primarily evaluates action verification and treats complete policy generation as an additional experiment, not as evidence that every agent task can be compiled away.

## Search loop and feedback

The optimizer keeps code hypotheses in a tree. Thompson sampling chooses a node to refine, balancing uncertain alternatives against promising candidates. The paper follows an earlier code-search method and reports a heuristic weight of 1.0; its short method section does not provide a complete standalone posterior-update specification. Reproduction should use the actual search implementation rather than inventing an ordinary Beta-Bernoulli bandit from the name alone.[^3]

Each refinement uses ten parallel environments, rolling out up to 1,000 steps with automatic resetting. A rollout stops on an illegal action or code-execution failure. Up to five failed steps are sampled for the critic to consolidate, then the refiner receives the original code, observations, and error feedback. If the checker accepts an action that the environment rejects, both functions need repair; if the checker already rejects that invalid action, the proposer needs repair.

Gemini 2.5 Flash performs code generation. For legality training, search stops when the observed legal-action rate reaches 1.0 or a timeout occurs. The reported average is 14.5 iterations, with 19 of the 32 selected end-to-end evaluation games below ten iterations. This latter denominator matters: the paper also trains harnesses for 145 games, and Appendix A lists some other variants requiring many more steps, including Breakthrough-small at 136.

The refinement prompt asks for errors to be fixed across observed boards, concise code, and avoidance of loops. These are synthesis instructions, not formal guarantees. A regression archive of previously failing states would be a natural additional safeguard, but the paper's description should not be silently expanded into an unreported exhaustive regression system.

## Benchmark construction and legality evaluation

The authors select all one-player and two-player TextArena games, excluding nine with free-form text/dialogue action spaces. The resulting 145 include familiar games and numerous variants. Some observation strings are manually stripped of their available-move hints. In the chess example, the board and UCI action syntax remain, but the explicit valid-move list is removed. This prevents simply copying an enumerated answer and tests the learned applicability logic.[^4]

Held-out rollouts use ten random seeds per game and length 1,000. Appendix A reports a 100% legal-action rate for all 145 learned harnesses. That is an empirical result on sampled trajectories, not a proof over every reachable state or every possible action string. The rollout distribution is partly determined by the generated proposer; rare castling, history-dependent rules, malformed inputs, and valid moves that a checker mistakenly rejects need separate coverage if the check is to become an authority boundary.

The distinction between false acceptance and false rejection is particularly important. A conservative policy that proposes only a small safe subset can achieve excellent observed legality while excluding the best strategy. A full checker audit would independently sample both legal and illegal actions and compare the predicate with the environment, rather than only measuring the actions the current policy happens to attempt.

## End-to-end game results

For efficiency, downstream play uses 16 one-player and 16 two-player games. All agents receive the same optimized prompting protocol. Single-player evaluation runs 20 matches per game and measures reward. Two-player evaluation runs 40 matches with random seeds, split evenly between moving first and second, and reports wins/draws/losses.[^5]

Against Gemini 2.5 Pro, Flash plus the learned verifier wins the comparison on nine of sixteen two-player games. Its aggregate match win rate is 56.3%, compared with Pro's 38.2%; the remaining outcomes are draws. Against unmodified Flash, it wins twelve of sixteen game comparisons and has an aggregate win rate of 64.8%. The number of game types won and the fraction of matches won are different statistics even when the first rounded proportion happens to coincide with a reported match percentage.

On single-player tasks, the verifier system exceeds Pro on eight games, ties on five, and trails on three. Mean reward is 0.745 versus 0.707 for Pro and 0.673 for Flash. Thus a legality intervention produces a real downstream gain, but it does not dominate every game or demonstrate optimal play. The public plots supply per-game outcomes; no broad claim of uniform improvement is justified by the aggregate.

## Complete policy generation experiment

The policy experiment changes the search heuristic to zero if an illegal action occurs, otherwise `0.5 + 0.5 × terminal reward`, with reward normalized to [0,1]. This gives every fully legal trajectory at least 0.5 while reserving the remaining range for task quality. It is a deliberately strong preference for legality; it is not the same objective as maximizing reward without constraints.[^6]

Search uses Gemini 2.5 Flash for at most 256 iterations and takes 89.4 iterations on average, reaching mean heuristic 0.939. The policy is then evaluated on the sixteen single-player games. All ordinary conditions have twenty repetitions, but GPT-5.2 has ten and GPT-5.2-High five because of cost. Unequal repetition counts mean different uncertainty, particularly on stochastic games.

| Agent on the sixteen single-player games | Mean reward |
|---|---:|
| Gemini 2.5 Flash | 0.673 |
| Gemini 2.5 Pro | 0.707 |
| Flash plus action verifier | 0.745 |
| GPT-5.2, no thinking | 0.635 |
| GPT-5.2-High | 0.844 |
| Generated Python policy | 0.870 |

The policy wins three game comparisons against GPT-5.2-High, loses five, and ties eight, despite having the higher mean reward. Different reward margins explain why average reward and per-game win counts disagree. The generated policy requires no inference-time LLM calls; the GPT-5.2 experiments reportedly cost about $640. This does not mean the full method is free: code-search model calls, training rollouts, CPU execution, and maintenance must be amortized over subsequent use. The paper does not supply a universally applicable break-even deployment count.

Two-player code policies are not evaluated here. The authors explain that opponent modeling and lookahead may require a more demanding world model. The single-player result should not be generalized to adversarial planning without another experiment.

## What the generated code reveals

The Minesweeper example first parses the board, applies local mine/safe-cell deductions, compares subset constraints, and finally uses risk heuristics when deduction stalls. If one neighborhood contains another and their remaining mine counts are equal, the extra cells are safe; if the difference in mine counts equals the number of extra cells, all are mines. This illustrates how reusable symbolic reasoning can replace repeated natural-language deliberation.[^7]

Its fallback risk estimate assumes a standard board with ten mines, and averages local clue-derived probabilities. Those choices are useful heuristics, not exact probabilistic inference or guaranteed transfer to other board specifications. The chess snippets implement coordinate conversion, king lookup, and attacked-square checks for different piece movements. Only excerpts are shown, so they cannot establish that every history-sensitive chess rule is implemented correctly.

These examples make the evolution target concrete: a parser, local predicate, or reusable decision routine. They also expose why provenance must include the environment variant. A program that is correct under a ten-mine assumption can become wrong after an apparently minor benchmark configuration change.

## Limitations, missing controls, and interpretation

The paper gives broad sampled legality coverage and narrower end-to-end reward coverage. It does not report a matched search-method ablation proving Thompson sampling better than random or greedy refinement, an exhaustive checker soundness/completeness audit, or a general transfer test to unseen game rules. Removing valid-move hints makes the task harder but is itself an environment modification that must be versioned.

The strongest supported claim is that automatically synthesized external programs can reduce a specific, measurable failure mode and sometimes carry a complete policy. The evidence is weaker for treating a generated verifier as a trusted platform component. Zero observed failures is compatible with unobserved edge cases; legality is compatible with losing; low marginal inference cost is compatible with expensive search.

## Everdict evolution proposal

A useful Everdict candidate could add a narrow runtime preflight check or deterministic helper while retaining the platform's frozen evaluator. For example, it might validate required output paths before submission or parse an artifact before asking the executor to repair it. The driver can evolve that helper using train failures, but the helper must remain a candidate behavior: it cannot replace the authoritative completion check merely because it passed its own examples.

Compare a seed, a budget-matched retry prompt, a generated checker with retries, and a generated executable helper. Measure final success, invalid-action rate, false rejections, retries, wall time, search cost, and regression on unrelated tasks. Include adversarially selected edge cases and inputs outside the proposer-generated distribution. Separate parser mistakes from rule mistakes and strategic mistakes so the next mutation targets the right layer.

For the documented first evolution loop, preserve exact helper bytes, declared edits, source/build provenance, task/environment identity, and evaluator identity. Train feedback can guide the search tree; selection ranks immutable candidates; held-out confirmation and its budget remain outside the driver's authority. These are proposed applications, not completed Everdict implementation. The paper's results have not been independently reproduced here.
