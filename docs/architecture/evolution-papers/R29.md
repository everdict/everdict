# R29 — Qwen3.6-27B: coding gains and preserving reasoning across turns

Qwen3.6-27B is an April 2026 model release emphasizing agentic coding and optional preservation of reasoning from earlier conversation turns. The cited resource is a release announcement; this detailed note uses the official model card and configuration at revision `6a9e13bd6fc8f0983b9b99948120bc37f49c13e9`. It contains substantial benchmark evidence, but no complete paper-level training recipe or controlled study attributing gains to each innovation. For Everdict, the distinctive research question is whether retaining prior reasoning reduces repeated work without preserving mistakes.[^1]

## The problem and its relation to external memory

A coding agent repeatedly reads files, proposes changes, runs commands, and reacts to failures. When the next turn discards earlier reasoning, it may reconstruct a plan or repeat an investigation. Retaining reasoning can provide continuity, but it also consumes input context and can keep an abandoned assumption influential.

Qwen3.6 adds training and an option for using earlier reasoning traces. This is conversation-context management inside the executor workflow. It differs from a wiki curator that turns many past attempts into reusable knowledge, and from an optimizer that selects immutable candidate artifacts. A retained trace is not automatically a validated skill or authoritative evidence.

The release's agentic-coding focus also differs from isolated code generation: repository tasks require navigation, edits, tools, and state tracking. Consequently, evaluation must identify the harness and its resource limits. A score cannot be explained by parameter count alone.

## Architecture and disclosed training information

The 27B model is dense and combines a vision encoder with a causal language model. The language stack has 64 layers, hidden width 5,120, and feed-forward intermediate width 17,408. Sixteen groups each contain three Gated DeltaNet layers and one gated full-attention layer. Thus the model mixes forty-eight linear-attention layers with sixteen full-attention layers.[^2]

Full attention uses 24 query heads and four KV heads with dimension 256. The linear-attention configuration has sixteen key heads and forty-eight value heads with dimension 128. The vocabulary is padded to 248,320, output embeddings are untied, and the configuration includes one multi-token-prediction layer. The vision encoder has 27 layers, hidden width 1,152, and patch size sixteen.

The default context is 262,144 tokens, with a documented YaRN extension to 1,010,000. As in Qwen3.5, native capacity and extrapolated capacity are distinct execution conditions. The configuration retains the `qwen3_5_text` model type, reflecting architectural compatibility; that does not imply identical learned weights or behavior.

The card identifies pretraining and post-training and says additional training supports historical reasoning preservation. It does not provide the full datasets, objectives, reward decomposition, training compute, or a matched ablation isolating that training. Community feedback and improved coding utility are release motivations, not a reproducible training algorithm by themselves.

## Coding and agent benchmark results

The main table compares Qwen3.6-27B with Qwen3.5-27B, Qwen3.5-397B-A17B, Qwen3.6-35B-A3B, Gemma4-31B, and Claude 4.5 Opus. The dense 27B model is different from the 35B-A3B MoE variant; total and active parameter counts must not be conflated.[^3]

| Benchmark | Qwen3.5-27B | Qwen3.6-27B | Change |
|---|---:|---:|---:|
| SWE-bench Verified | 75.0 | 77.2 | +2.2 points |
| SWE-bench Pro, refined set | 51.2 | 53.5 | +2.3 points |
| SWE-bench Multilingual | 69.3 | 71.3 | +2.0 points |
| Terminal-Bench 2.0 | 41.6 | 59.3 | +17.7 points |
| SkillsBench, 78-task subset | 27.2 | 48.2 | +21.0 points |
| NL2Repo | 27.3 | 36.2 | +8.9 points |
| Claw-Eval Avg | 64.3 | 72.4 | +8.1 points |
| Claw-Eval Pass^3 | 46.2 | 60.6 | +14.4 points |
| QwenClawBench | 52.2 | 53.4 | +1.2 points |

The largest listed improvements occur in Terminal-Bench and the selected SkillsBench condition, rather than uniformly across every agent benchmark. On Terminal-Bench the 27B model ties Claude 4.5 Opus at 59.3 in this table; on SWE-bench Verified Claude scores 80.9 versus 77.2. Neither observation establishes universal equality or superiority across coding work.

QwenWebBench rises from 1,068 to 1,487, while Claude scores 1,536. These are Bradley–Terry/Elo-style ratings from an internal visual frontend benchmark, not percentages. The benchmark covers seven English/Chinese frontend categories, including web design, applications, games, SVG, data visualization, animation, and 3D. Rendering and a multimodal judge evaluate code and visual correctness. Rating differences cannot be mixed with success-rate percentage-point gains.

The card labels one metric Pass^3 but does not fully define its aggregation in the listed footnotes. It should remain labeled as reported rather than be silently converted into pass-at-three, where any attempt succeeds. Likewise, SkillsBench's Avg5 refers to averaging five runs, not testing five tasks.

## The experimental conditions behind the numbers

The SWE-bench series uses an internal agent scaffold with Bash and file-edit tools, temperature 1.0, top-p 0.95, and a 200K context window. The authors correct problematic tasks in the public SWE-bench Pro set and evaluate baselines on the refined set. Within-table comparisons benefit from that shared correction, but these scores are not automatically comparable to an unmodified public benchmark without the exact correction manifest.[^3]

Terminal-Bench 2.0 uses Harbor/Terminus-2, a three-hour timeout, 32 CPUs, 48 GB RAM, temperature 1.0, top-p 0.95, top-k twenty, an 80K output limit, and 256K context, averaged over five runs. The hardware figures describe the task execution allocation in the protocol; they do not establish the GPU memory or inference cost required to serve the model.

SkillsBench uses OpenCode on 78 self-contained tasks, excluding API-dependent tasks, with five runs. This differs from the full 87-task SkillsBench v4 collection described in R15. The card does not provide the same detailed per-task skill-condition analysis as that paper, so 48.2 cannot be substituted for its full benchmark score or interpreted as an isolated benefit from supplied skills.

For NL2Repo, the card says other models use Claude Code with temperature 1.0, top-p 0.95, and up to 900 turns. That wording does not establish a completely identical native harness for every model. QwenClawBench uses a stated real-user-distribution benchmark, temperature 0.6, and 256K context, but the card does not supply the full sampling and auditing details needed to verify representativeness.

Five-run averages reduce some sampling variability, but the table supplies no uncertainty intervals or paired significance tests. It also does not report the complete end-to-end search/training costs or the exact contribution of reasoning preservation to these rows.

## Knowledge, reasoning, and visual results include regressions

Knowledge changes are much smaller than the coding gains: MMLU-Pro moves from 86.1 to 86.2, MMLU-Redux from 93.2 to 93.5, and SuperGPQA from 65.6 to 66.0. GPQA Diamond improves from 85.5 to 87.8 and LiveCodeBench v6 from 80.7 to 83.9. HLE falls slightly from 24.3 to 24.0. HMMT February 2026 remains 84.3. The full AIME 2026 I-and-II score is 94.1 versus 92.6; the card warns this coverage differs from some earlier Qwen3.5 notes.[^3]

The visual table covers STEM, general QA, documents, spatial understanding, video, and interaction. AndroidWorld improves from 64.2 to 70.3; RefSpatialBench from 67.7 to 70.0; VideoMMMU from 82.3 to 84.4. Other results regress: MathVista mini 87.8 to 87.4, DynaMath 87.7 to 85.6, CharXiv reasoning 79.5 to 78.4, and MMBench 92.6 to 92.3. OCRBench remains 89.4.

These negative and unchanged cells are useful for evolution design. A candidate optimized for coding may preserve broad knowledge reasonably well yet worsen a document or reasoning subskill. Without repeated runs and uncertainty, small differences should be treated as reported changes rather than established causal effects.

## What reasoning preservation actually changes

By default, the card says thinking blocks associated with the latest user message are retained, following an interleaved-thinking pattern. Enabling `preserve_thinking` allows historical-message reasoning to remain available. The model is trained to use it. This changes the serialized context supplied on later turns, even if the task, weights, and external files are otherwise identical.[^4]

The card argues that retaining reasoning can improve consistency, reduce repeated reasoning, and improve KV-cache reuse. These are plausible mechanisms and provider claims. No isolated on/off table here quantifies when they offset the extra history tokens or when stale reasoning is harmful. A shorter newly generated response can coexist with a larger input and total memory footprint.

Self-hosted examples set `chat_template_kwargs.preserve_thinking` to true. An adjacent Alibaba Cloud note contains an inconsistent false value in the expression it says to replace, while the preceding enabling example uses true. Treat this as a documentation inconsistency and verify the rendered prompt in the chosen integration, rather than copying that sentence as an unambiguous configuration.

Thinking is otherwise on by default, and the old textual `/think` or `/nothink` switches are not officially supported. General thinking recommends temperature 1.0 and presence penalty zero, whereas precise coding uses temperature 0.6. This differs from Qwen3.5's general-thinking presence-penalty recommendation of 1.5. A nominal model upgrade can silently change sampling as well as weights and history policy.

## Serving and long-context guidance

The release documents SGLang, vLLM, KTransformers, and Transformers serving, reasoning/tool parsers, and optional multi-token speculative decoding. Its inspected guidance names SGLang 0.5.10 or newer and vLLM 0.19.0 or newer. These are historical source recommendations, not an installation performed in this task.[^4]

The card recommends at least 128K context to preserve complex-task reasoning when reducing the default context for memory reasons. It also recommends 32,768 output tokens for ordinary tasks and 81,920 for difficult competition problems. These are operating recommendations, not controlled evidence for an optimal budget. Static YaRN may affect short contexts, and video preprocessing/frame sampling determines which visual evidence is available.

Open weights and an Apache-2.0 artifact license support local experiments, but a model's advertised size does not determine actual accepted-task cost. Serving precision, batch size, context history, speculative acceptance, cache hits, and failed attempts all matter.

## A concrete Everdict evolution experiment

Compare three history policies on a fixed Qwen3.6-27B revision: default historical-thinking removal, full preservation, and a curated decision summary that retains verified findings plus unresolved questions. Give every arm the same tools, task-family splits, maximum budget, and starting files. This is a proposed Everdict study, not an experiment in the release card.

Measure final correctness, repeated file reads and commands, recovery after an intentionally invalidated assumption, total input/output tokens, cache-adjusted cost, wall time, and peak memory. Add tasks where an early plan becomes wrong after new evidence. This tests whether continuity helps the agent update its beliefs, rather than merely repeat them consistently.

Record the exact serialized-context policy and template digest with the candidate. A curator may replace a derived summary, but preserve raw tool observations and previous decision records in the ledger. Prior reasoning must not acquire the authority of a confirmed environmental fact. Keep model upgrades separate from history-policy changes during attribution, and confirm any coding gain against document and reasoning regressions before adopting the candidate.
